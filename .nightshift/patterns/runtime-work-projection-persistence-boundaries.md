# Runtime work, projection, and persistence boundaries

Use this pattern wherever state changes trigger work that may outlive one model turn or presentation process. It prevents the runtime, domain, and UI layers from becoming competing writers and keeps internal knowledge away from player-facing surfaces.

## Ownership

| Concern | Owner |
|---|---|
| Save detection, digest production, baseline correctness | State-extraction core |
| Diff consumption, durable state-event handoff, process and worker lifecycle | Execution runtime |
| Work selection, priority, visibility, and domain record transitions | Domain feature |
| Spoiler projection and player-safe result content | Domain disclosure service |
| Rendering, navigation, and user commands | Presentation client |

Every mutation has one owner. A presentation client may request that a result be consumed, but the domain service performs and persists the transition. A domain scheduler may request execution, but the runtime owns the attempt, retry, and cancellation machinery.

The shared opaque-token profile applies to every runtime, adapter, binding-epoch, play-session, session, store-incarnation, durable operation, session-close, and event identity: NFC UTF-8, no C0 or C1 controls, 1 to 128 Unicode scalars, and at most 512 UTF-8 bytes. Identity comparisons are exact and malformed identities fail closed. Durable non-reuse applies only to identity kinds named by `RetentionPolicyV1`; every other identity remains governed by its documented binding, journal, deduplication, or tombstone lifetime.

`EventIdV1` is the runtime-owned profile for `eventId`: it uses the shared opaque-token grammar, is unique within the current adapter, signed-in principal, and runtime journal instance, and is fresh when a runtime rebinds an event. Malformed or colliding values fail closed; historical event IDs remain compact evidence for duplicate and late-result decisions.

Runtime ingress creates internal `InteractionContextV1` with immutable interaction ID, receipt timestamp, monotonic ingress order, and the current authoritative `playSessionId` (or null when no sitting is active). Before the Focus matrix, the runtime admits this context; missing or malformed context fails closed before Focus sees the request. A context older than the admitted watermark, or carrying a valid play-session ID different from the current session, is mutation-free stale before malformed or identity handling, pending-reset, expiry, fingerprinting, deduplication, keepalive, or selection. Only admitted contexts enter the Focus matrix, which is exhaustive within that scope. Chat and every derived focus command share an admitted context; command JSON cannot supply or fingerprint these fields. An admitted chat may perform one keepalive or expiry reset, then derived malformed bytes return `invalidCommand` with no invocation, fingerprint, deduplication, command keepalive, or second refresh. Retries preserve context order. `requestId` remains separate command dedup identity.

## Work visibility classes

- **Response notice:** player-visible information caused by a known state change. It appears before ordinary guidance and is not an inbox task.
- **Hidden enrichment:** automatic research or recomputation. It never appears in the inbox, including while queued, retrying, or blocked offline.
- **User-visible deferred task:** work the user explicitly asked to receive later. It may appear as queued, researching, ready, and consumed.

Visibility is assigned by the domain when work is created and is never inferred from duration, worker type, retry count, or result size.

## Durable state-event lifecycle

Creation:

- The domain creates a durable outbox record in the same domain-store transaction as the state transition that requires delivery. The record carries a strict opaque `logicalOutboxId` outside ProjectionV1 and player output, the domain-defined identity and version fields needed to validate that transition, immutable origin evidence, creation time, safe typed payload, and complete post-transition projection when the domain has one. One logical outbox ID represents one transition; multiple transitions from one request receive distinct IDs. Consumed-diff records include adapter and playthrough identity, source and target state generations, schema, and adapter versions. The domain transaction never makes a cross-store journal write.
- For consumed diffs, the core commits the state-event outbox record and then advances the baseline under one `consume.lock` critical section using atomic temp-then-rename writes. The record is the commit point, and the next locked outbox operation rolls an unapplied baseline forward from it, so "consumed" and "eligible for replay" are one durable fact in the domain store, while journal delivery remains a separate runtime-owned step. This applies while the runtime holds consumer ownership; the core half, including the ownership marker that keeps the bridge and the runtime from consuming the same root, is specified in [state extraction section 7.6](../features/state-extraction.md#76-durable-consumption-consumer-ownership-state-event-outbox-and-settlement).

Domain outbox and runtime journal protocol:

- The runtime journal owner drains outbox records under one `journal.lock` critical section. It validates identity, versions, origin evidence, safe payload, `logicalOutboxId`, and projection integrity before appending a journal event, then records the outbox ID in a journal-owned delivery ledger. `eventId` is runtime-owned and must satisfy the runtime event-ID validation profile; it is unique within the current adapter, signed-in principal, and runtime journal instance. A malformed event ID or an event-ID collision fails closed, quarantines the malformed or colliding event, and leaves the outbox pending for repair or retry. Matching `(adapter, principal, logicalOutboxId)` duplicates are no-ops; conflicting bytes are quarantined fail-closed. Minting algorithms are left to the owning runtime design. The append and delivery-ledger marker are journal-owner mutations; the domain remains the only writer of domain state and outbox records.
- A crash before the domain transaction commits leaves neither state nor outbox record. A crash after commit and before drain leaves the outbox pending, with no lost event. A crash after journal append and before the delivery marker is recovered by outbox-ID deduplication as an idempotent duplicate no-op. A journal append failure leaves the outbox and journal unchanged for retry. A delivery-marker failure leaves the journal event and outbox pending, so the next drain deduplicates the event and records delivery. After durable append and delivery settlement, runtime sends stable `outboxSettlement` carrying the logical outbox identity, source binding, outcome, version, and integrity evidence. Focus validates it and atomically marks its domain outbox settled, then compacts or writes a bounded domain tombstone; runtime never deletes domain rows. Pre-append, append-before-ledger, ledger-before-settlement, domain-commit-before-response, validation/domain/persistence failure, post-settlement runtime failure, foreign/stale/missing settlement, duplicate settlement, restart, and retention remain explicit branches: pending rows retry, matching settled records replay as no-ops, conflicts fail closed, and only the owning domain may settle or compact its row.
- Outbox replay order is source-receipt order. A later save creates a later outbox record and never overwrites an unacknowledged predecessor. The runtime drains pending records before admitting newer dependent commands when the domain contract requires that ordering.
- After a runtime restart, pending domain records are rebound before command admission. The domain preserves logical operation identity, immutable origin evidence, and its authoritative projection revision, while the runtime mints current-runtime event ID, journal sequence, timestamps, and integrity metadata and derives the current complete projection. Old runtime event identity and old projection bytes are never replay authority.
- The execution runtime owns a typed `runtime.handoff` signal carrying a durable `handoffIdentity`, new `runtimeInstanceId`, source and target adapter and binding identities, and ordered phase ledger before that instance's first projection. A same-identity duplicate with matching bindings is a no-op; a conflict fails closed. Consumers clear the prior instance, revision, and projection baseline on handoff; prior-instance projections remain stale, and an invalid first projection leaves handoff-pending active. Loss, withdrawal, downgrade, or verification failure of an admitted capability enters `capability-pending`; a valid replacement enters `projection-pending` until idempotent acquisition accepts the first structurally valid projection for the admitted identity. Adapter switching carries adapter identity and a fresh opaque binding epoch through the handoff, capability, projection, commands, and events; prior-epoch traffic is stale, and target-adapter projection is admitted only after the target capability, healthy catalog, and first projection are valid. Focus stores the runtime identity as immutable origin evidence and mints a distinct focus-owned `adapterHandoff` reset `operationId`; the identities are associated durably and never reused interchangeably.
- The runtime owns idempotent acquisition of the authoritative current ProjectionV1 on attach or reconnect, capability replacement, and runtime or adapter handoff. Acquisition fabricates no event and does not advance the domain projection revision when state is unchanged. An overdue acquisition first follows the normal expiry-reset path. Commands remain blocked until the admitted identity and binding epoch have a structurally valid projection and a healthy catalog; a structurally valid fallback projection does not release target commands.
- ProjectionV1.revision is domain-owned. Runtime rebinding derives and preserves that authoritative revision; the runtime owns event identity, journal sequence, timestamps, integrity metadata, delivery state, and acknowledgement only.
- Single-writer reconciliation: the domain owns transition and outbox creation; the runtime journal owner is the sole writer of journal append, delivery markers, acknowledgement, replay, compaction, quarantine, and repair. A presentation client may acknowledge a projection through the runtime but never writes either store directly.

Journal repair is a coordinated runtime/domain handshake. Runtime owns quarantine and the journal-repair idempotency identity `(adapter, principal, journal identity, target sequence, operationId)`, validates immutable target evidence, and never fabricates a focus projection or revision. Focus CAS-validates current state and commits one Balanced `journalRepair` reset/outbox or an authorized no-state-change outcome when already Balanced. Runtime appends only the domain-authorized or rebound event. Same identity replay returns the stored outcome; a different target conflicts; stale, foreign, or retired targets are terminal no-ops; write failure leaves the original journal and cursor unchanged for retry. Restart partial states resume under the same identity, and command admission remains gated until repair reaches terminal completion. Journal repair is distinct from catalog repair and from focus-owned reset or promotion namespaces.

For ordinary command transitions, outbox identity derives from the full deduplication scope `(adapter, principal, runtimeInstanceId, requestId)` or a domain-minted equivalent containing it, never from `requestId` alone. Chat keepalive uses runtime-scoped interaction identity. Multiple transitions from one request receive distinct ordered logical outbox identities; operation-driven reset and promotion retain their operation identities. Logical outbox IDs remain stable across rebind while runtime event metadata is fresh.

Refresh:

- Later save changes create later ordered outbox records and journal events. They do not overwrite an unacknowledged predecessor.
- Walk-back enrichment may annotate the event used for a landing brief, but it does not change which diff was consumed.

For the coordinator MVP's core-state family, the runtime feature's State acceptance and context safety contract additionally gates first exposure on durable positive exact-byte core acceptance, including the selected state independently of event delivery. Retirement without acceptance recovers through disclosed resync. Later rejection invalidates potentially exposed provider history, withholds further output and requires a clean session plus acknowledged correction/current state. Positive evidence, write-ahead observation intent, original settlement bindings, retirement suppression and outstanding correction survive repair, restart, consumer release/re-hand-over and retention; opaque retirement establishes conservative uncertainty before it can hide rejection, and expired acceptance cannot introduce uncertain bytes into a clean generation; neither compaction nor ordinary resume proves old context forgotten. Client exit remains a process exit, and recovery never treats missing safety history as clean. This specialization does not replace the domain projection/rebind or terminal-stale protocol below.

Acknowledgement and replay:

- Delivery is acknowledged only after a spoiler-projected notice or brief is durably retained by the active session or confirmed presented by the client.
- Startup first rebinds pending domain outbox records to the current runtime and drains them in order, then replays unacknowledged journal events before treating newer ordinary guidance as current. Rebinding preserves logical operation identity, immutable origin evidence, and the authoritative domain projection revision, but mints current-runtime event identity, journal sequence, timestamps, and integrity metadata while deriving the current projection; old projection bytes are never replayed.
- After authoritative Balanced startup state is established and before command admission, the runtime validates every pre-restart non-promotion focus outbox against that state. A typed post-state that no longer holds becomes a terminal stale or superseded, deliveryless outbox-settlement outcome: runtime records compact identity and audit evidence, emits no event or client delivery, and sends the stable source binding and `terminalStale` outcome through `outboxSettlement`; Focus validates and accepts that settlement, then settles or tombstones its domain row with no focus transition or event. Runtime advances or compacts its stale ledger only after Focus acceptance. A failed settlement remains pending and retryable. Reset and fault-clear records proceed only when still valid; promotion and durable `pendingReset` paths remain separate.
- Each consumer persists a cursor with journal identity, last contiguous acknowledged sequence, and last accepted projection or domain revision. Delivery or acknowledgement failure leaves both event and cursor unchanged for idempotent retry.
- A sequence gap triggers one durable-journal reread. If the predecessor is still absent, a stable repair operation moves the gapped event and dependent suffix to quarantine, records compact identity and integrity evidence without duplicating player-originated payload text, and appends the domain's complete safe recovery event at the next sequence after the last good event. Replay resumes from the unchanged last-good cursor. If a quarantined or stale outbox record is encountered, the runtime records its stable identity and repair evidence, leaves domain state unchanged, and retries or surfaces the domain-defined safe fault rather than acknowledging it as delivered.
- Malformed or unsupported-version events use the same suffix-quarantine recovery. Events from a retired journal instance and events below a consumer's accepted revision retire as terminal no-ops with compact audit evidence. Events at equal revision generally retire too, except a pending `focus.promoted` rebind with current identity triple, stable promotion and logical outbox IDs, undelivered status, and exact authoritative projection bytes; that delivery-only exception is accepted without revision or domain mutation. Delivery-only duplicates are no-ops and conflicts are invalid. They never overwrite current domain state or block the current cursor.
- Repair and retirement are idempotent by operation ID. A journal-repair operation ID is unique within adapter, principal, journal identity, and repair target sequence. It matches the missing event and dependent suffix by immutable event and outbox identities, records compact repair evidence, quarantines the suffix before appending one complete safe recovery event, and replays the same outcome on duplicate delivery. A repair-write failure leaves the original journal and cursor untouched, surfaces a recoverable fault, and retries later. Consumers stay on their domain-defined safe projection until a valid contiguous event resumes delivery.

Safety ordering precedes exact replay. Pending reset and overdue expiry reconcile before deduplication replay. Deduplication projection bytes are historical, not replay authority: if the stored projection remains current-safe, exact replay returns it byte-for-byte; if it is stale and no safety transition is required now, preserve historical `accepted` and `code`, derive the authoritative current projection, return `stateChanged: false`, and perform no mutation. After a committed safety transition or recovery, preserve the historical acceptance and code but return the current safe projection with `stateChanged: true`; do not reapply selection or create activation or outbox side effects. Failed pending-reset recovery returns the safe persistence-fault path.

The runtime persists a terminal-stale delivery ledger keyed by outbox identity and source binding for pre-restart outboxes whose typed post-state no longer holds. Terminal retirement is represented by the deliveryless `outboxSettlement` outcome, counts as settled for predecessor ordering, survives restart, and deduplicates repeats. Focus acceptance is the domain acknowledgement: it settles or tombstones the domain row without a focus transition or event. Runtime retention and compaction advance only after that acceptance; a failed settlement leaves both settlement and stale-ledger work pending and retryable. Reactivation is explicit and never reuses an identity. Generic stale retry wording applies only before this terminal branch is reached.

Invalidation and retention:

- Schema or adapter-version incompatibility prevents projection and reports a recoverable stale state; it never converts the event to acknowledged.
- A reload rewind creates an explicit later event. It does not rewrite history to make earlier forward progress appear current.
- Acknowledged runtime delivery records may be compacted according to a retention policy, while preserving enough identity and audit metadata to avoid duplicate delivery; the authoritative journal event remains governed by its journal retention and settlement lifecycle.
- Runtime may physically compact only its journal, delivery, reaction, or terminal-stale records after the owning domain has accepted the matching settlement and required acknowledgements are terminal. Pending or failed domain outbox rows remain for retry. Compaction is idempotent, never removes the journal event, and retains compact identity, outcome, version, and integrity evidence for duplicate detection. A domain outbox row is settled or replaced by a bounded tombstone only by its owning domain after validated `outboxSettlement`; the runtime never rewrites or retires that domain state.

For core state events, the coordinator's [payload integrity and lossless transport](../features/companion-execution-runtime.md#payload-integrity-and-lossless-transport) binds the exact retained projection to its accepted source hash across reload, recovery and delivery; compact bindings are historical evidence and transient codec artifacts supply no recovery authority. Its [synthetic-cursor discharge and retention specialization](../features/companion-execution-runtime.md#journal-retention-and-operational-status) distinguishes actual acknowledgement from history discharged through acknowledged recovery or explicit abandon. The generic terminal-acknowledgement conditions below use that defined terminal obligation for this family; they do not relabel a skipped event as delivered. Other domain settlement, Focus promotion and `terminalStale` rules are unchanged.

Scope and consumers:

- Journals are isolated by adapter and playthrough.
- The runtime is the sole writer. Domain projectors read events and attach derived records; presentation clients receive projected records only.

## Domain work lifecycle

Creation records the triggering state generation, visibility class, domain purpose, priority, evidence status, and idempotency identity. Refresh supersedes or recomputes derived results when their inputs change. Cancellation stops future attempts without claiming the work succeeded. Retry preserves the original work identity and records each attempt. Completion stores the internal result before projection. User-visible consumption is a domain transition invoked by a client.

Stale and provisional results remain explicitly marked. A failed probe or worker run maps to the most cautionary available status, never to clean, complete, or safe-to-disclose.

`RetentionPolicyV1` is normative for every durable record. Each durable family is either listed in the retention matrix with an explicit owner, trigger, age bound, count bound, compact evidence, and replay or late-result behavior, or is a named fixed-cardinality or special-lifecycle record with its own lifecycle. No durable family is unclassified. `pendingReset` has at most one marker per focus store and remains until its reset operation reaches terminal recovery. A pre-store external-fault record has at most one current record per unavailable `(adapter, principal)` store scope, remains authoritative while the main store is unavailable, and is removed only after successful replacement and recovery reconciliation. Neither record is age- or count-compacted while its lifecycle is active; failed writes and recovery remain retryable.

Version 1 fences exactly Focus `entryId` and `activationId`, Focus `creationOrdinal` high-water, and runtime `sessionCloseId` in their owning `(adapter, principal, identityKind)` namespaces. `playSessionId`, `gameProcessInstanceIdentity`, `logicalOutboxId`, settlement, event, request, operation, handoff, and repair identities have only their specified binding, journal, deduplication, or tombstone lifetime; this policy makes no permanent non-reuse claim for them. Fenced records are outside age and count retention. A genuinely new namespace initializes its fence at zero and first mint advances it to one. Minting and dependent state commit atomically. Restart reloads the unchanged fence. Valid repair preserves or imports it without decreasing it. Missing, corrupt, colliding, exhausted, or unavailable fences fail closed. Pruning and compaction never decrement or remove a fence. The creation-ordinal high-water is advanced atomically with each new entry, and repair cannot decrease, reuse, or synthesize an already-consumed ordinal.

The version-1 retention matrix below is per `(adapter, principal)`. Focus owns terminal activation, audit, comparison, promotion, domain-outbox, settlement-tombstone, pending-reset, and pre-store fault records; runtime owns journal, delivery, reaction, terminal-stale, and handoff ledgers; the runtime handoff identity phase ledger and session-close tombstone are fixed-cardinality special-lifecycle records; the session lifecycle owns its fixed active or ended-awaiting marker. Its age origin is the later of `terminalAt` and the last required replay or delivery acknowledgement; when no acknowledgement is required, acknowledgement time equals `terminalAt`. For the core-state synthetic-skip specialization, the durable discharge.at supplies the discharged obligation's resolution time in this calculation while the skipped event's actual acknowledgement remains absent unless independently established. A record is age-eligible when `now` is greater than or equal to age origin plus its family period. A missing required acknowledgement, pending or retryable dependency, foreign record, conflict, invalid compact evidence, or live dependent makes the record ineligible.

Retention runs under the owning family lock after every successful write that can change family cardinality or terminal eligibility, and once during startup after durable load, validation, repair, and runtime rebind reconciliation but before command admission. Each pass first compacts every eligible age-expired record, then compacts count-over-bound records in ascending `(ageOrigin, stable family identity)` order until the family is within bound. Startup and retry use the same ordering. Compaction retains the named evidence. A failed compaction leaves the source record and all prior durable state unchanged and retries later. Duplicate replay returns the compact outcome. A late result whose dependency was compacted is a terminal stale no-op. If a family remains over bound with no eligible record, admission fails closed with `runtimeCapacityExceeded`.

| Durable family | Compaction trigger and finite bound | Compact evidence retained |
|---|---|---|
| Terminal activation and selection audit | Terminal dependencies settled; 180 days and at most 4,096 records | Activation or selection identity, outcome, schema version, source binding, terminal time, and integrity digest |
| Terminal comparison evidence, jobs, attempts, and leases | Job and every referenced pair terminal; 180 days and at most 4,096 records | Job, attempt, pair and entry identities, captured versions, terminal outcome, terminal time, and integrity digest |
| Request deduplication results | Request terminal and every derived outbox settled; 30 days and at most 8,192 records | Full dedup key, request fingerprint, accepted/code outcome, resulting revision, terminal time, and integrity digest; replay derives the current-safe projection as specified below |
| Promotion operation ledger and handoff | Promotion terminal and every required reaction and delivery settled; 365 days and at most 1,024 records | Operation, candidate and resulting focus identities, terminal outcome, latest revision, acknowledgement time, and integrity digest |
| Domain outbox and settlement tombstone | Owning transition terminal and runtime settlement accepted; 180 days and at most 8,192 records | Logical outbox and settlement identities, source binding, outcome, version, revision, settlement time, and integrity digest |
| Runtime journal, delivery, reaction, and terminal-stale ledger | Accepted domain settlement is durable and required delivery, reactions, and acknowledgements are terminal; 180 days and at most 8,192 records per ledger kind | Journal ID, historical event ID and sequence, logical outbox or session-close identity, consumer or source binding, status/outcome, schema and projection/domain revision, terminal and acknowledgement times, and integrity digest |
| Other terminal operation tombstones | Operation terminal with no live dependent state; 365 days and at most 4,096 records | Operation kind and identity, source binding, terminal outcome, version, terminal time, and integrity digest |
| Core state-event outbox tombstones (per companion root) | Record settled by the runtime or abandoned by an explicit release; 180 days and at most 512 records | Logical outbox identity and sequence, kind, outcome, record digest, journal and event identity, repair operation identity, and settlement time |

The state-extraction core owns the last row and the records around it, which state extraction section 7.6 specifies: the consumer-ownership marker and the outbox ledger header are fixed-cardinality records; a pending state-event outbox record is a special-lifecycle record that remains until its settlement, an explicit abandon, or a repair's quarantine of an invalid record, and ordinary publishes are refused at 16 pending records, while a resync publish is exempt because a stream repair must commit its resync before it can drain what fills the outbox (an unchanged retry replays a live resync above the complete rejected-candidate ceiling, whether the candidates are pending or changed-retired; fencing the latter need not reduce pending count, so preventive allocation reservation under the 1,024-child ordinary ceiling and separately bounded control recovery up to 1,032 children supplies the physical bound); and the outbox quarantine admits at most 64 diagnostic entries, pruning before a move and retaining the fenced source when admission or cleanup fails. The coordinator MVP's fixed-cardinality authority records and bounded journal quarantine are classified in the runtime feature's storage section. Its [repair prerequisites and attempts](../features/companion-execution-runtime.md#repair-prerequisites-and-attempts) retain one root operation with bounded subordinate attempts/episodes and one plan-bound journal recovery-event slot. Historical completion does not release an effectively unfinished repair or its protected evidence. The coordinator's [independent recovery witness](../features/companion-execution-runtime.md#independent-recovery-witness) survives operation-file loss until acknowledged disclosure or explicit abandon, separately from context correction. Its [recovery capacity admission](../features/companion-execution-runtime.md#recovery-capacity-admission) reserves bounded control progress before consumption and reports irreducible refusal without pruning protected history; explicit abandon remains a separately budgeted user decision. These specializations leave the matrix constants unchanged. A synthetic repair/release cursor advance is not acknowledgement: skipped history becomes terminal through its recorded acknowledged recovery disclosure or explicit abandon, with that distinct provenance retained for compaction. This state-event recovery rule does not introduce deliveryless `terminalStale` for core state events or change the domain-projection replay contract.

For a compacted request-dedup record, matching replay returns the stored acceptance and code and derives the authoritative current-safe projection under the current lock. With no required safety transition it returns `stateChanged: false` and performs no mutation, outbox, activation, or selection side effect. If a safety transition is required and commits, it returns the current safe projection with `stateChanged: true` and performs exactly that transition. Failed derivation or safety persistence leaves the compact record unchanged and returns the existing typed retryable fault. A different fingerprint conflicts. Stale, foreign, malformed, or corrupt compact evidence fails closed.

Every compacted runtime journal, delivery, reaction, or terminal-stale record retains every historical journal binding needed for duplicate and late-result decisions. Rebinding may mint fresh current-runtime event metadata, but it never discards the historical journal ID, event ID, or sequence recorded by the compact evidence. Guidance-resolution results are runtime-owned scheduling evidence: they bind the guidance pass, active focus identity, candidate identities and order, comparator and disclosure versions, and current store or evidence generation, rather than activation or entry fields when no activation is involved. The runtime owns execution and delivery; Focus owns any later semantic state transition that consumes the result.

The domain may replace its outbox row with a bounded settlement tombstone after runtime has durably recorded either the delivered event and settled delivery ledger, or the deliveryless `terminalStale` outcome, and the owning domain has accepted the matching `outboxSettlement` under the source binding. Runtime may compact its related journal, delivery, reaction, or stale ledger only after that accepted domain settlement is durable and every required consumer reaction or acknowledgement is terminal. Optional consumers do not block. Required consumers remain retained while pending or retryable. Ledger-before-settlement retries the same settlement identity; domain-settlement-before-response replays the stored outcome. Validation, domain persistence, settlement, or acknowledgement failure performs no compaction and leaves retryable state intact. Runtime failure after settlement re-reads the durable tombstone or settled marker before retrying. Foreign, stale, missing, or conflicting settlement fails closed and cannot resurrect the domain row. Runtime never deletes or rewrites a domain row.

`runtimeCapacityExceeded` is runtime-owned operational fault state, not a ProjectionV1 fault and not a domain mutation. On capacity exhaustion or an over-bound family with no eligible record, runtime does not compact, acknowledge, advance a cursor, settle an outbox, mint an identity, or enqueue hidden work. The affected record and ledger remain unchanged and retryable after eligibility, capacity, or dependency state changes. Failure to persist the capacity fault also leaves pre-call state unchanged and fails closed. Duplicate capacity reports replay their stored outcome. The fault clears only after a successful retention pass brings the family within bound. For the coordinator's core-state family, its Recovery capacity admission specialization also requires admitted document budgets and control workspace; its fault is derived rather than a separate persisted record, and explicitly planned bounded repair/release control remains available only when that transition passes its own admission. Ordinary over-capacity work remains refused. When compact evidence is unavailable or corrupt, replay and late results fail closed rather than reusing an identity or recreating prior work. A future capability version may change these bounds only with an explicit migration and compatibility contract.

## Play-session lifecycle

A play session is one period of companion-engaged play: the boundary the [session focus](../features/session-focus.md) dial auto-reverts on, the [psychologist persona](../features/psychologist-persona.md) emits its end-of-session report on, and the runtime's process lifecycle brackets. The runtime owns the session boundary, validates an OS-backed `gameProcessInstanceIdentity` that is stable for one process lifetime and distinct across PID reuse, mints one collision-resistant stable `playSessionId` at session start, and emits one durable session-end event that every domain consumer reacts to; no feature or client owns session identity or end detection.

Start:

- A session starts at the first game activity after an end: the adapter's game process appears, or the first player interaction after a sign-off. The next interaction after a sign-off starts a fresh session with a balanced focus dial and a new `playSessionId`. The ID is unique within the adapter, principal, and runtime session ledger, and is persisted atomically with `gameProcessInstanceIdentity` and session status. An exact restart identity match preserves the active sitting; a mismatch closes the prior sitting once and starts a new one. No process closes an active sitting and opens none; an ambiguous, unreadable, or failed probe fails closed. A stale process exit is a no-op. The singleton state is either `active(playSessionId, processIdentity)` or `endedAwaitingNextInteraction(endedPlaySessionId, processIdentity-or-absence, sessionCloseId)`.

End (composite signal, one event):

- Game process exit (automatic primary): the runtime watches the adapter's game process (the adapter declares its process name in an adapter-owned runtime manifest, not in `adapter.json`) and treats exit as the end of the session. This is the ground truth for "stopped playing."
- User sign-off (manual): a player-facing "end session" command ends the session even while the game is still running. It is a deliberate close, so every session-end reaction fires.

The session-end event is a lifecycle event, distinct from consumed-diff events, and does not depend on the durable-consumption protocol. It records adapter identity, playthrough identity, authoritative `playSessionId`, the cause (process-exit or sign-off), and start and end times. Runtime owns a strict opaque `sessionCloseId`, atomically bound to the ended session, cause, timestamps, status, and end outbox in the `(adapter, principal, sessionClose)` namespace. `sessionCloseId` is the canonical session-end identity carried through replay and Focus reset handling; Focus does not mint a second close identity. Same binding replays; a different binding conflicts; malformed, colliding, or persistence-failed close leaves no partial state. The ID is carried through session-end replay and focus-selection or reset work; a TUI restart never ends a session. A new game-process sitting gets a new ID, while duplicate close signals for an already-ended ID are no-ops. Missing or malformed IDs fail closed and never become an apparently clean session boundary. The close tombstone remains through required reactions and delivery, then compacts to bounded identity, outcome, version, and integrity evidence.

Save-activity quiescence is deliberately NOT a session-end signal. The runtime derives session ends only from the game process and explicit sign-off. A failure or absence of process monitoring does not degrade to a heuristic session end; it is treated as a fault to surface and fix, not as a boundary to guess. A failed or absent process check maps to the most cautionary status ("no session-end derived"), never to clean or complete.

Consumers react, never emit: the focus dial reverts to balanced on any-cause end; the persona queues its report on any-cause end. Startup replays unacknowledged session-end events in order, per the durable state-event lifecycle above. A runtime restart may recover the same `playSessionId` only from the persisted active-session record plus matching process identity; it never restores an ID from a client, domain projection, or unverified text.

Session-end restart replay preserves a stable logical close identity plus the ended `playSessionId`, not the old runtime event ID. A new runtime rebinds it with fresh event ID, sequence, runtime identity, projection binding, and integrity metadata; old event bytes retire, and deduplication uses the logical close identity. Replay is gated only against commands for the ended `playSessionId`. Once a newer play session is established, its commands may proceed; delayed replay of the older end is retired by the play-session guard with no reset, revision, event, or focus mutation. A rebound end for an older play session is delivered to the current domain, where the play-session guard retires it as stale without resetting a newer session.

## Playthrough identity (settled)

Playthrough identity is the signed-in Windows principal, resolved by the runtime from `[Security.Principal.WindowsIdentity]::GetCurrent()` (principal ID and SID) at startup. It is never user input: the TUI exposes no profile or account control, and no other presentation surface does either.

The binding follows automatically from the adapter layout: the adapter's `saveDirectory` lives inside the current user's profile (`%USERPROFILE%\AppData\LocalLow\...`), so the running principal and the single save set owned by that principal coincide. One user, one save set, one timeline per adapter.

Consequences:

- The isolation key for journals, state-event and session-event records, domain persistence, agent sessions, and user preferences is (adapter, principal identity).
- The instance is single-principal: the runtime runs as whoever owns the saves it reads, and there is no identity-switching surface anywhere in the stack.
- Identity resolution is fail-closed: if `WindowsIdentity::GetCurrent()` yields no principal or an unexpected context, the runtime denies identity-keyed work (no journal event, no session start) and reports the fault. A failed identity check is never a clean identity.
- Multiple playthroughs within one user are out of scope. Distinguishing a fresh run from a loaded old save remains deliberately un-attempted (state-extraction section 12 anti-goal); a later multi-playthrough data question is a domain question, not an identity question.

Adapter identity and binding epoch are transport and session identity, not automatically semantic evidence provenance. Valid unequal runtime, adapter, or binding epoch identities are rejected before expiry as mutation-free stale requests; malformed identities are invalid commands. Only the current identity triple reaches expiry, deduplication, keepalive, or selection. Existing evidence remains valid across an epoch change only when adapter identity, semantic adapter version, comparator and threshold and disclosure versions, store incarnation and generation, entry content and versions, and eligibility remain valid. Semantic drift is retryable stale or superseded. An adapter switch completes old session-end, discards the runtime-wide active selection through the typed handoff reset, retires old-epoch work and delivery, binds the target store and epoch, emits target session-start, then admits the target Balanced/current projection and releases commands. Switching back never restores the prior selection.

## Process recovery (settled)

The runtime owns process and worker lifecycle, so recovery policy is runtime-owned. Failures fall into three classes, each with a defined response:

1. **Core command exits mid-operation.** Already crash-safe by construction: state files and the domain outbox use atomic temp-then-rename writes, the consume transaction commits the outbox record before the baseline and the next locked operation rolls an unapplied baseline forward, and file locks release when the holding process dies. Recovery is bounded retry of the non-consume command, outbox drain retry by the runtime journal owner, work-file reaping of orphaned dump/digest `tmp` entries, and classifying a consume-lock timeout as transient `busy` rather than a fault. No reconstruction is ever needed.
2. **Agent session subprocess exits mid-turn.** The runtime reattaches the same session id in a fresh subprocess, replays any unacknowledged state events from the journal, and surfaces a "session reconnected" notice. State events carried by an interrupted turn are redelivered on later player-submitted turns until acknowledged; the runtime never resubmits the player's message itself. The once-per-source-receipt ordering in the durable state-event journal remains the acknowledgement boundary.
3. **Presentation client exits.** Detach is not a session end. A runtime that outlives its client keeps running headless, retains unacknowledged events, and replays them in order for the next client attach over the same host seam. Until a slice adds such a background process, the runtime and its client share one process, so a client exit is a runtime exit: it still ends no session and loses no event, and the next start recovers through the durable journal, agent-session resume, and the startup sequence (decided 2026-10-05 for the coordinator MVP).

Required session-end reactions are recorded in a runtime-owned ledger keyed by `(adapter, principal, sessionCloseId, consumerId)`. Close state, end event, and each required-consumer snapshot commit atomically or under an explicit close marker. Each reaction is `pending`, `applied`, `terminal-no-op`, or `retryable`; duplicates replay, optional consumers do not block, unavailable required consumers remain recoverable pending, and explicit retirement has a terminal branch. Compaction waits for all required terminal outcomes plus runtime acknowledgement.

Startup reconciliation of an overlay runtime restart:

- At session start the runtime records the validated `gameProcessInstanceIdentity` and process id. On startup it checks the process name, pid, and identity:
  - Same validated identity running: the player kept playing through the downtime; the session continues and unacknowledged events replay.
  - Different validated identity running: the previous sitting ended while the runtime was down and a new one started; synthesize the old session-end event with cause process-exit, then open a fresh session for the new identity.
  - No process running: synthesize session-end on the previous session, no phantom-open session; the next game-process appearance starts a new session.
- An ended-awaiting-next-interaction state never resumes its ended ID. The next interaction or later process appearance mints one fresh `playSessionId`; exit while awaiting emits no second close, and duplicate sign-off replays the existing close.
- A missing process watch (no process name declared, or the check fails) is fail-closed per the play-session lifecycle rule: neither an ended nor an ongoing session is invented; the fault surfaces and no session-end or session-start is derived from a failed check.

## Projection boundary

Internal knowledge, raw source material, unseen graph relationships, and unprojected task results never cross into prompt assembly, notifications, inbox views, objective boards, or logs visible to the player. Every player-facing consumer accepts projected records rather than filtering raw records itself.

Broader spoiler modes change the projector policy. They do not grant direct UI access to the internal store.
