# Scratch cleanup exit handler never fires

Tracked from Nightshift run a69edaac-e54c-47ec-ba9c-3e2c5bb3418d (2026-11-13), which fixed the runtime fixture host side of the same cause ([Fixture cleanup contract](fixture-cleanup-contract.md)).

## Recorded evidence

`Register-ScratchCleanup` in `core/tests/TestSupport.psm1` registers a `PowerShell.Exiting` engine event to remove every scratch root a harness creates through `New-ScratchCompanionRoot`. A probe in the run registered the same event in a script started as `pwsh -NoProfile -File` on pwsh 7.6.10 and found it never fired: at the end of the script, after an explicit `exit 0`, after reading stdin, and with or without `-SupportEvent` (8 of 8 cases). The PowerShell test harnesses that create roots this way all run as `pwsh -File`, the core ones under `core/tests` and two runtime ones, `runtime/test/Test-PathAdmission.ps1` and `runtime/test/Test-FilePublication.ps1`. Those that do not remove their own roots (for example `Test-Acquisition.ps1`, `Test-Watcher.ps1` and both runtime harnesses) leave them under `.tmp` until a later harness's `Clear-StaleScratchRoots` sweep reaps them once their creator process has exited; others already remove their roots in `finally` blocks with their own `Remove-Item` calls (for example `Test-EntryFence.ps1` and the section 11 live-probe harnesses), and `Test-StatePredicates.ps1` does so with `-ErrorAction SilentlyContinue`, which hides any residue. Nothing has been seen to fail because of it; the cost is accumulated scratch and cleanup that only happens as a side effect of later runs.

Two related points from the run's final fixture review belong to the same fix: `runtime/test/fixtures/companion-root.ps1` creates its root and can then fail while staging it (for example when switching the consumer owner fails), and that exit removes nothing; and the header comments of `Clear-StaleScratchRoots` and `Remove-ScratchCompanionRoot` in `TestSupport.psm1` still describe the exit handler as removing roots at an orderly exit.

## Follow-up

Replace the exit-handler cleanup with explicit removal: a helper that removes every scratch root the process registered (built on `Remove-ScratchCompanionRoot`), called from each harness's own `try`/`finally` and from the fixture host's staging failure path, reporting residue rather than hiding it, and replacing the harnesses' existing ad-hoc removals. Keep `Clear-StaleScratchRoots` as the backstop for crash-killed processes, decide whether residue should fail a harness, and correct the two comments.

## Resolution

Fix: `Register-ScratchCleanup` and its `PowerShell.Exiting` handler are gone from `core/tests/TestSupport.psm1`. Three helpers replace them. `Remove-OwnedScratchRoots` removes the named scratch roots this process created, or all of them, through `Remove-ScratchCompanionRoot`; it attempts every root, keeps a survivor owned, and writes each survivor as one `scratchResidue` JSON line on stderr instead of throwing, since it runs in `finally` blocks. `Complete-ScratchHarness` removes every root still owned and exits 1 when any survives, which overrides an exit 0 the body was leaving with. `Exit-HarnessFailure` writes a body failure as the host would and exits 1, so that failure stays visible beside a residue report. Every harness that creates roots through `New-ScratchCompanionRoot` or a staging helper built on it, the core harnesses under `core/tests` plus `runtime/test/Test-PathAdmission.ps1` and `runtime/test/Test-FilePublication.ps1`, now ends in that `try`/`catch`/`finally` template. The flat harnesses keep their bodies unindented inside the `try`, so their here-string fixtures keep their bytes. `Test-EntryFence.ps1`'s end-of-run removal loop gave way to the template's `Complete-ScratchHarness`, and the per-test removals in the two section 11 live-probe harnesses and `Test-StatePredicates.ps1` became `Remove-OwnedScratchRoots` calls, which report residue instead of hiding it. `runtime/test/fixtures/companion-root.ps1` removes its registered roots when staging fails and then rethrows. `Clear-StaleScratchRoots` stays as the backstop for crash-killed harnesses and for roots that survive a harness's own removal, and the comments on it and on `Remove-ScratchCompanionRoot` no longer describe an exit handler. User decision: a surviving root fails its harness even when its tests passed.

Verification: the `HarnessCleanup` section of `core/tests/Test-ScratchCleanup.ps1` covers a named removal that keeps going past a held file, reports and keeps only the survivor, and refuses a root this process did not create before removing anything. It also runs child harnesses built on the template as `pwsh -File`: a clean run exits 0 with nothing left; a held root exits 1 with its residue report, even when the body passed, after an early `exit 0`, and with a body failure that stays on stderr. And it runs the fixture host with its `-StagingFault` switch, which exits nonzero and leaves no root. Every harness the change touched was run individually as a recorded check, except the section 11 live probes. They ran one probe at a time, and in that run five probe selectors whose removal the change edited had no recorded run. Probe 02 needs a hand-placed example save that was not present under `.tmp`. Probe 06 failed with `New-CompanionWarningSink` unresolved, as it also did at the run's base commit. Probes 56, 56-59 and 59, whose shared session-observation helper gained the same `Remove-OwnedScratchRoots` call, need a running game and cloud-sync confirmation, and a default run skips them. No automated check reproduced the original defect before the fix, because the fix replaces the implicit exit-time cleanup with an explicit call rather than repairing it; the probe recorded above (8 of 8 cases) stands in.
