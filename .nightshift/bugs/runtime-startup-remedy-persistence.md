# Startup remedy persistence

Tracked after Nightshift run fcfa6785-114e-4b4b-8b99-da04c43bc219, which delivered the startup safety recovery status fix.

The evidence below is the original finding. Time-dependent wording refers to its review snapshot and must be checked against current files before a fix.

## Recorded evidence

A fresh code review of that run (finding `startup-remedy-status-persistence`, confirmed by its skeptic) found that the host names the remedy for a safety-refused provider start only in one `providerSafetyRefused` notice, emitted before attachment and replayed only to the first attached client (`startupNotices` in `runtime/src/session-host.ts`). `formatStatus` in `runtime/src/text-client.ts` carries remedies for capacity refusals, reaper-limit operational warnings and the journal fault `repairFailed`, but none for a provider safety refusal, so `/status` and later status lines never repeat it. The closing docs review of that run found three readouts it leaves without a remedy. After an initial safety refusal the provider stays `starting`, because `ProviderLifecycle.start` returns false without changing state, and submissions answer `notReady`. After an invalidation during start the provider keeps the label it had: `starting`, `reconnecting` after an earlier exit, or `ready` when the invalidation lands after binding but before `SessionHost.start` completes (so `ProviderLifecycle.start` already returned true), as [Suppressed provider readiness readout](runtime-suppressed-provider-ready.md) records; submissions answer `notReady` and the host still emits `restartRequired`. After a plain initial safety refusal, `/new` rechecks through `ProviderLifecycle.replace`; when that refuses, its catch sets the provider to `failed`, submissions answer `providerUnavailable` and the client prints only `New session: providerUnavailable.`. After an invalidation during start or a final attachment refusal, `startNewAgentSession` refuses `/new` outright before `replace` runs, so the earlier readout stays (`starting` with `notReady` after an invalidation) and the client prints the same line. After a final attachment refusal, `blockAfterFinalSafety` sets the provider to `failed` from the start while submissions answer `notReady` through the final-safety block. Chat still fails closed; the gap is a player who missed the notice not being told what to do.

## Proposed follow-up

Keep the last safety-refusal remedy on the live status surface, for example a refusal field on the provider part of `HostStatus`, set wherever the host emits `providerSafetyRefused` (`SessionHost.start` and `blockAfterFinalSafety`), surviving a failed replacement and cleared only when the host itself becomes ready through a start or replacement, never merely because `ProviderLifecycle.start` returned true, so the attach status line, `/status` and status changes repeat it, and the client can repeat it after `notReady`, `providerUnavailable` or a refused `/new`. The new remedy sits beside the existing capacity, operational and `repairFailed` remedy text on the status line and stays distinct from the capacity state-safety restore text. The provider state `failed` already occurs in two of these readouts but cannot carry the remedy, because start and attachment use it to decide whether to exit or attach. This changes the status-surface contract in `.nightshift/features/companion-execution-runtime.md`, so it needs its own spec amendment and client tests that `/status` shows the remedy after the initial refusal, after a refused `/new` on both its recheck and its outright-refusal paths (including an invalidated initial start followed by `/new`) and after a final attachment refusal. [Suppressed provider readiness readout](runtime-suppressed-provider-ready.md) changes the same provider readout after an invalidated initial start, so whichever fix lands first sets a label and refusal-field contract the other must adopt.

## Status

The user chose to track this item on 2026-10-24 in that run's closing triage. No fix or publication was authorized by that choice.

Fixed on 2026-10-25 in Nightshift run f5a12322. `HostStatus` gained `provider.safetyRefusal` (`retryable`, `restartRequired` or null), set wherever the host emits `providerSafetyRefused` and cleared only when the host itself becomes ready through a start, replacement, resume or reconnect, so a refused `/new`, a failed replacement and a provider that reads `ready` while the host stays unready all keep it. `formatStatus` renders it after the other remedies with the notice's text, so the attach status line, every status change and `/status` repeat it; the field is separate from the `failed` provider state that start and attachment read. The status-surface contract in [companion execution runtime](../features/companion-execution-runtime.md) states this, and client tests cover the initial refusal, a refused `/new` on its recheck and outright-refusal paths (an invalidated initial start included), a final attachment refusal, the lifecycle-ready but host-unready case, and delivery through the attach snapshot and status changes. One status line can still show the provider ready beside the remedy during a successful session change; that is tracked as the quick win "Safety refusal ready flicker".
