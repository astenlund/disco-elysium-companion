# Cold inventory of the event ceiling may exceed the runtime budget

Tracked on 2026-11-16, first as a failing timing test, then restated as the runtime risk below after the measurements showed the failure was not a helper source regression.

## Recorded evidence

On LUMINOS on 2026-11-16, the first native Inventory read of 8,193 newly written compact events at production depth, one past the 8,192 retained-handoff bound the timing test models as the event ceiling, took 38 to 59 seconds (about 4.7 to 7.2 ms per event), over the runtime's 30-second inventory budget, while a repeated read of the same files took 2.2 to 3.2 seconds (about 0.27 to 0.40 ms per event). A CPU profile of the test put 96% of its run in system calls and about 50 of the 54 seconds it attributes to the Inventory read in the read-access `CreateFileW` of `nativefs.OpenRead`, one per event file, while the attribute-only opens of the same files took under 2 seconds in total.

The [Go native helper MVP report](../runs/reports/2026-10-24-go-native-helper-mvp.md) recorded about 0.13 ms per event, a measurement the user reports came from LUMINOS too. `bc18d83`, the commit that added the timing test named below, measured 59.3 seconds on 2026-11-16 as well, and the Inventory read path has changed since only on error paths, in a once-per-request input check and in comments, so a helper source regression is ruled out. The build toolchain is not the cause either: at `bc18d83` the pin in `runtime/native/compiled-images.json` already named `go1.26.0`, and `runtime/src/native-image.ts` refused any other Go on PATH then as it does now, while `go1.26.0` is also the Go on PATH today; only a `go test` run under a different toolchain than the build, such as through a `GOTOOLCHAIN` override, is not ruled out, and the time is spent inside system calls rather than Go code. The `bc18d83` test timed a single read straight after writing, so if the report's figure came from that test, first reads of newly written files were fast on LUMINOS in October; the report does not name the test, so that is an inference. Windows updates installed on 2026-10-29, 2026-11-11 and 2026-11-12 and Defender's real-time scanning of each first read-access open are the leading hypothesis, unconfirmed.

`TestInventoryOfTheEventCeilingAtProductionDepthFitsTheBudget` in `runtime/native/helper/internal/inventory/timing_test.go` now gates only the repeated read on its 15-second budget and logs the first read's time, so it no longer protects the first-read case.

## Production write shape

Production does not write events the way the test fixture does: on every completed create, rewrite or reconstruct, the helper's codec (`ExecuteCodec` in `runtime/native/helper/internal/events/runtime_codec.go`) reads the published event file back through `nativefs.ReadBounded`, and the runtime's codec in `runtime/src/codec.ts` then reads it again in Node, both before any Inventory reads it, while the fixture writes its files without reading them. A scratch probe on LUMINOS on 2026-11-16 approximated that shape, writing each of the 8,193 events in place and reading it back through `nativefs.ReadBounded` immediately afterwards: the read-backs took 56.3 seconds in total (about 6.9 ms per event), and the two Inventory reads that followed took 2.19 and 2.08 seconds (about 0.27 and 0.25 ms per event). In that probe the first-open cost landed on the read-back, a few milliseconds per event at write time, which suggests that an Inventory in ordinary play reads files the host has already seen.

The probe's read-back matched the helper's own first read, the same `nativefs.ReadBounded` in the writing process, but it differs from production in at least two ways: the helper publishes each event by writing a temporary sibling and moving or replacing it into place (`nativefs.PublishValidated`) before the codec reads the final path back, not by writing the final path; and the helper creates that temporary exclusively and flushes it before closing (`writeNew`), while the probe wrote through `os.WriteFile` without a flush.

## Publication and reboot probe

A second scratch probe on LUMINOS on 2026-11-16 published each of the 8,193 events through `nativefs.PublishValidated` as a create-only publication, which moves the temporary into place, into a data root under the repository's `.tmp` folder, then read each back through `nativefs.ReadBounded`: the publications took 64.7 seconds in total (about 7.9 ms per event), the read-backs 1.6 seconds (about 0.19 ms per event), and an Inventory that followed 1.16 seconds (about 0.14 ms per event). After the user rebooted LUMINOS, the first Inventory of that untouched data root took 3.72 seconds (about 0.45 ms per event) and a second 1.48 seconds (about 0.18 ms per event). Through that create-only move, the first read-access open after publication was thus already warm, while publication itself cost about 7.9 ms per event, which the probe did not split between scanning, the flush, the move and the admission checks, and one reboot of LUMINOS left the files far inside the budget. The Inventory figures over published files, 0.14 ms per event before the reboot and 0.18 ms for the second read after it, are nearer the MVP report's 0.13 ms than the 0.25 to 0.40 ms warm reads above, whose files the timing test and the first probe both wrote through `os.WriteFile` without a flush or move under a Go test temporary folder (`t.TempDir()`) rather than the repository's `.tmp` folder. The gap is unexplained and may lie outside those differences: if the MVP report's figure came from the `bc18d83` test, as inferred above, that test wrote its files the same way.

## Replace publication probe

The journal's rewrites, compaction included (`rewriteCurrent` in `runtime/src/journal.ts`), publish over an existing event file, which takes the replace branch of `nativefs.PublishValidated` (`replaceFile`, through `ReplaceFileW`) rather than the create-only move. A third scratch probe on LUMINOS on 2026-11-16, after a review following the closure found that branch unmeasured, published the 8,193 events create-only into a new data root under the repository's `.tmp` folder (7.7 ms per event, read-backs 0.21 ms per event, then an Inventory of 1.18 seconds), then republished each over itself through the replace branch with the same bytes and read it back: the replacements took 98.7 seconds in total (about 12.0 ms per event) and the read-backs 2.0 seconds (about 0.25 ms per event), and the two Inventory reads that followed took 3.51 and 2.96 seconds (about 0.43 and 0.36 ms per event). Replaced files were thus also warm for the next Inventory, far inside the budget, though somewhat slower to read than files that were only moved into place; the probe did not reboot after the replacements.

## Open questions

- Whether a scanner signature update makes the host rescan files it has already seen, so that the first Inventory afterwards reads a ceiling-sized data root fully cold; the reboot did not.
- What a missed budget does to the player's turn. The runtime refuses any inspector native request budgeted over 30 seconds, its resource observation budgets Inventory at 30 seconds or the operation's remaining deadline if that is shorter, and it turns a failed Inventory into an unavailable capacity refusal.

Packing settled history into fewer files, recorded as a candidate in [Long-lived runtime history](../features/runtime-long-lived-history-preservation.md), would likely shrink a cold read if its cost is per open rather than per byte scanned, which is unmeasured.
