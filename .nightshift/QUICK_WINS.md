# Quick wins

Refactors ready to land when time allows; not blocking any feature, but would improve the codebase meaningfully.

This file is **one of four repo-local indexes** agents consult on demand when relevant (alongside `FEATURES.md`, `BUGS.md`, `PATTERNS.md`). Active entries are kept inline, organized under thematic `##` sections you invent as work emerges. When a quick win lands, append a shipped-note entry to [`QUICK_WINS_HISTORY.md`](QUICK_WINS_HISTORY.md); do not move it within this file. Negative-knowledge findings (approaches attempted and reverted) are first-class promotion candidates from the history into the relevant `.nightshift/patterns/<slug>.md` Cautionary tales sections.

Capture shorthand: name the refactor, describe the current smell in a sentence or two, sketch the preferred shape. A reader should be able to start work from the entry alone. Anchor entries on identifiers that survive refactors -- symbol names, entry titles, commit hashes, config keys -- never on line numbers, plan-phase ordinals, bullet positions, or temporal qualifiers ("new", "recent"): a precise locator that rots misleads harder than a coarse one that holds.

**After adding a new entry, run `/nightshift:ready`** from the repo root to confirm it parses as a quick-wins work item against the real grammar in `skills/ready/ready.js`. Quick wins carry no `**Requires:**` line; the failure mode to catch is an entry that doesn't parse as a `- ` bullet or `###` heading (ready reports it as a prose-only-section notice) while you can still fix it in the same session.

Implemented quick wins are archived in [`QUICK_WINS_HISTORY.md`](QUICK_WINS_HISTORY.md), read only when consulted (not at session start) so the active backlog above stays scannable. When a quick win lands, append its entry there rather than to this file.

Backlog prose is one paragraph or one bullet per physical line, never hard-wrapped at a column: a search hit then shows the whole entry, the parsers anchor on whole lines, and an edit shows as one changed line instead of a reflowed block. `/nightshift:ready` reports a hard-wrapped file as a notice and `/nightshift:init-backlog` unwraps it.

## Validator exception rule follow-ups

These user-tracked cleanups came from Nightshift run c042bda1-bd4e-43a4-9f69-4e01213b1b79. None was fixed by this tracking edit.

- **Turn-context reader exception rule.** The exception hierarchy paragraph in state-extraction section 7.1 says a validator that wraps a lower-level rejection keeps it as `InnerException` (turn-context validators wrap nested parse or document rejection in `TurnContextProtocolException`), that unexpected exceptions, injected validator faults included, propagate unchanged, and that callers catch only the exact expected domain type, never the base type; the "Validator exception boundaries" bullet in section 11 asks tests to assert the first two. The code contradicts each clause. `TurnContextProtocolException` in `core/DigestDiff.psm1` has only a message constructor, and `Read-WalkResultDocument` in `core/private/WalkProtocol.ps1` rethrows without a cause. The protocol validators end in a catch-all that rethrows any other exception as their domain rejection, among them `Read-TurnContextEnvelope`, `Read-TurnContextDiagnostic`, `Assert-TurnContextAttemptResult`, `Get-TurnContextIdentity` and `Assert-TurnContextWarnings` in `core/private/TurnContext.ps1`, `Read-StateEventDiagnostic` and `Assert-StateEventNonFailureResult` in `core/private/StateEvents.ps1` and `Read-WalkResultDocument`, so a core-side programmer fault surfaces as a protocol or document rejection (for the envelope reader, `envelope-invalid` or `envelope-serialize-failed`). Injected adapter validator faults do not propagate unchanged either. `Assert-AdapterDigestDocument` in `core/private/AdapterConfig.ps1` wraps an unexpected validator exception, a validator-thrown `AdapterConfigurationException` included, in `AdapterValidatorInfrastructureException` (pinned in `core/tests/Test-AdapterConfig.ps1` and `core/tests/Test-Consumption.ps1`), turns a validator that writes output into an unwrapped `AdapterConfigurationException`, and passes any other `CompanionContentException` subtype through unchanged. Each boundary then maps these outcomes to its own reason, `adapter-validator-infrastructure-failed` at some (as `core/tests/Test-TurnContext.ps1` pins) and other reasons elsewhere; take the per-boundary classification from the code and from the boundary rules the spec search below finds, not from this entry. The same 7.1 paragraph's closed list of six `CompanionContentException` subtypes also omits four that `core/DigestDiff.psm1` declares: `AdapterConfigurationException`, `SaveSourceException`, `SaveCandidateLimitException` and `SaveDigestStageException`. Some callers catch more than the exact type: the envelope callers' catch-alls the section 7.5 `Read-TurnContextEnvelope` paragraph describes, and `Read-CompanionConsumerMarker` and `Read-StateEventLedger` in `core/private/StateEvents.ps1`, which catch the base `CompanionContentException` as content-invalid. Nothing misbehaves with the shipped adapter, and for most clauses the spec simply misdescribes the code. One clause is a design question: the general adapter validator contract in state-extraction section 6.1, mirrored in `core/digest-schema.md` (the schema mirror check in `core/tests/Test-DocumentValidation.ps1` requires the two to change together), says any validator exception other than `AdapterDigestValidationException` is validator infrastructure failure, the cautionary reading, while the code takes the content-rejection reading for the passed-through subtypes; decide which side changes before rewording it. The adapter side is governed too: `Assert-AdapterDigestSemantics` in `adapters/disco_elysium/Validate-Digest.psm1` catches the base type and attempts a cause-keeping `AdapterDigestValidationException` wrap through a two-argument constructor the core type does not declare, a branch nothing reaches today. Search the catch clauses in `core/` and in each adapter release's `Validate-Digest.psm1` for rethrows as a domain type and catches of the base type instead of relying on this list, search `.nightshift/features/state-extraction.md` and `core/digest-schema.md` by key term for every statement of these rules, then reword them by category: which wraps keep a cause, which validators fail closed with a catch-all, how adapter validator faults are classified, and which callers catch the base type.

## Test runtime follow-ups

These user-tracked ideas came from the retrospective discussion after Nightshift run 65584d32-c500-4a15-8def-fcabe561940a. None was implemented by this tracking edit.

- **Parallel core test groups.** A full `core/tests/Test-StateEvents.ps1` run takes about 33 minutes (observed 2026-11-11), which dominates repair loops that rerun it. `core/tests/Invoke-StateExtractionTests.ps1` starts each test file of a runner `-Group` in its own `pwsh` process and waits for it before starting the next (`Invoke-TestScript`), and each file runs its sections (the values of its own `-Only` parameter, distinct from the runner's `-Group`) one after another in that process. Scratch roots carry the creating process id (`New-ScratchCompanionRoot` in `core/tests/TestSupport.psm1`), and since the concurrent scratch cleanup fix (`.nightshift/bugs/parallel-scratch-cleanup.md`) concurrent sweeps no longer race each other. Preferred shape: run a file's sections as separate processes, a bounded number at a time, reporting each one's output and exit code. `-Only` does not mean the same thing in every file: in some a value runs that section alone and `All` runs them all, while in others a value stops the file after that point or runs a block that `All` skips, and some files have no `-Only` at all. Only the first kind can be split as it stands, so read each file's `-Only` handling before splitting it, turn the others into a partition first or run them whole, and confirm that the split sections together run exactly what the serial `All` run does. Also search the test files for other shared state (fixed paths, named synchronization objects, machine-wide state) and keep any section that uses it serial. Before making it the default, compare wall-clock time and machine load with the serial run, and watch for timing-sensitive failures under parallel load: the bounded child-process helpers in `TestSupport.psm1` default to a 30-second timeout, and the scratch sweep stress groups are timing-dependent.
