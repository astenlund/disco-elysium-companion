# Candidate: source-bound bootstrap image pins for CLI chat

Status: user-approved governing design for private implementation on 2026-10-18, since folded into [integrated startup execution](../features/runtime-startup-execution-30.md); where the two differ, that spec governs and later amendments live there. The production selector remains off until the full acceptance gates pass. The [private transfer spike](runtime-image-pin-transfer-spike-20261018.md) showed that one PowerShell helper can duplicate read-share handles for the Go broker, native observer and their ancestors into Node, then exit while same-user write opens and ancestor rename remain denied. A copied-root supervised `metadata` call took 2.987 seconds after a separate 1.612-second supervisor setup. A later in-memory bootstrap probe took 2.507 seconds without transfer and 2.564 seconds with transfer in two separate single runs; this is feasibility evidence, not an established saving, repeatability result or product startup measurement.

Only the direct `node runtime/src/cli.ts chat` entry point may select this fast path for players in this slice; the private copied-root fixture main defined in the governing spec may also select it and carries the same obligations. The exported `runCli`, programmatic `createChatRuntime`, status, consumer, repair, bridge and non-chat callers continue to use PowerShell. The direct-main branch holds a module-private selection token that these callers cannot supply. The bootstrap helper physically admits both exact artifact slots and their parents under its admitted installation root. It returns an exact absent classification only when both executable slots and the release manifest are positively absent; chat then continues with the PowerShell broker and job query instead of the compiled images, still on the combined fast backend path, with a visible reason and separately reported timing. An unreadable, redirected, unexpected-kind or present-but-invalid slot, or one absent slot beside a present slot, never counts as absent and fails closed. Prepared artifacts belong to one admitted installation root inside this repository and one fixed source-to-binary generation. A private copied-root fixture may name a separate admitted installation worktree under the same repository, as the approved design permits. Artifact preparation and trusted build provenance for both executables remain separate gates. Any mismatch after fast selection fails closed without a permissive retry.

For selected fast chat, Node reads bounded bytes of the exact bootstrap script, native source, image-pin source, image-pin script `BootstrapImagePins.ps1` and one reviewed package wrapper, requires fixed release hashes and ordinary installation paths, then sends one complete top-level expression with their captured Base64 bytes through the existing supervised `metadata` role. This selected method invokes installed `pwsh -NoProfile -NoLogo -NonInteractive -Command -` with one bounded stdin expression terminated by a newline; the ordinary `PathInspector.metadata` method retains its `-File` transport. The package decodes the verified bytes, runs the bootstrap as one in-memory scriptblock, and compiles C# from the captured text. The selected bootstrap receives its source text explicitly and reports under the fixed name `Get-BootstrapScope`, because `$PSScriptRoot` and `$PSCommandPath` do not identify an in-memory script. It never executes a repository script or native source by pathname on this fast route. The helper's input stays within the existing 1,048,576-byte finite-control bound. Private `memory-bootstrap-e` returned exact scope and pin output with empty stderr and positive metadata-job stop in 2.715 seconds after supervisor setup; both write opens and ancestor rename were denied while Node lived, both binaries launched, and those operations succeeded after Node exited. A truncated expression produced no pins but exited 0, so exit code alone never establishes absence or success. The one-run probe does not establish final release hashes, repeatability, product startup timing or complete write footprint.

The combined helper preserves the existing `sid` and two path-admission fields and semantics. Its selected reply adds exactly one `imagePins` field; the ordinary reply remains exactly `{sid,paths}`. The selected field is either exactly `{status:"absent"}` after the two-executable-and-manifest physical absence proof or a ready record with `status:"ready"` and the bindings below. A missing, extra or other status is invalid. The selected request binds a fresh 32-lowercase-hex nonce, current Node PID and native creation identity, admitted companion and installation roots, fixed artifact generation and exact broker/observer paths and hashes. The helper independently verifies the target process identity, root and path ancestry, ordinary kinds, single-link binaries, expected hashes from held file handles, and the current scope admission. It opens each unique ancestor from volume root through both binary parents with `FILE_READ_ATTRIBUTES` and `FILE_SHARE_READ`, and both binaries with `GENERIC_READ` and `FILE_SHARE_READ`, rejecting reparse points and changed volume or file identity. The selected helper must open ancestors outside the repository read-only and keep binary targets and all app-controlled writes inside the repository; complete write containment remains an acceptance gate. Dedupe uses native volume and file identity, not culture-sensitive or case-folded spelling.

While every source handle remains open, the helper duplicates them into the exact Node process with `DUPLICATE_SAME_ACCESS` and noninheritable target handles. After closing its local copies, it temporarily duplicates every target handle back, checks its kind, canonical path, volume and file ID, and rehashes each binary from the returned handle at offset zero. The ready `imagePins` record has status `ready`, version 1, request nonce, target PID and creation identity, installation-root and candidate-scope-path hashes, fixed generation, broker and observer hashes, and an ordered nonempty `handles` array of at most 64 entries. Each entry binds kind (`directory`, `broker` or `observer`), canonical path, 16-lowercase-hex volume, 32-lowercase-hex file ID, and a nonzero target HANDLE value rendered as exactly 16 lowercase hexadecimal digits. Ancestors occur from volume root to each binary parent in first-seen order with identity deduplication; the final two entries are broker and observer. The array length is the duplicate count, with exactly one broker and one observer and no duplicate handle value or object identity. No handle value enters player output, status or ordinary logs. Node validates every field against its held request and source evidence, then requires the `metadata` job positively absent before marking one process-scoped pin set ready. The helper is the native handle-identity authority; Node cannot inspect a Windows HANDLE merely from its receipt value. A malformed, missing, extra or partial receipt grants no compiled launch authority.

Transfer and startup exits carry the pin obligation explicitly. Before duplication, only helper-local handles exist. After any subset, a caught failure closes the exact target handles in reverse order with `DUPLICATE_CLOSE_SOURCE` and reports failure; a rollback error, abrupt helper death, missing or invalid reply, partial stdout, timeout, or job-stop uncertainty leaves ownership unknown even when the helper exits 0. The direct-main fast CLI in that state launches no compiled binary, does not attach a client, attempts bounded helper stop and positive absence, reports the uncertainty, and calls `process.exit(1)` after its diagnostics and stop attempts so the OS releases any partial target handles. A validated reply before helper-job absence is likewise no authority. After ready, failure to claim the instance guard, a not-owner result, invalid scope/marker/source, provider refusal, status-only attachment, normal `/quit`, shutdown or any failed-open path retains the pin set while that CLI process lives; it never tries to close selected handles while a compiled helper could launch. The existing guarded shutdown and all-role stop proofs run first, then the direct-main branch calls `process.exit` with the final code, releasing the noninheritable handles even if unrelated event-loop handles remain. If stop is uncertain, no clean marker or healthy attachment is claimed and the CLI remains unavailable until process termination; the next start still performs complete predecessor and durable-state admission. A second fast startup in the same Node process is refused. Programmatic hosts cannot select this path until a separate exact-handle close lifecycle is designed and approved.

This candidate changes `Get-BootstrapScope.ps1`, its native dependency, `scope.ts`, `read-only-inspection.ts`, `backend/index.ts`, the private artifact adapters, CLI selection and source hash lists. It adds no retained worker or process role: the existing supervised `metadata` bootstrap job stops before instance-guard acquisition and marker work. The Node handles preserve pathname identity during every later Go broker and native observer launch, including turns after startup. Existing per-launch source and binary hash checks still run; the instance guard, worker source proof, ownership reconciliation, state-event settlement, journal, safety, watcher, provider binding, final worker stop and verified client attachment retain their current gates. No pending or failed pin state becomes an authority cache or substitutes for those checks.

Before the selector can be enabled, establish the exact source-to-binary installation contract for both executables, the release-hash trust root, target PID plus creation matching, handle identity and count, caught and abrupt partial-transfer faults, and source drift after capture. The selected transport must redirect every helper-controlled profile, temporary and compiler path to admitted repository-local scratch before launch; source audit and a complete process-tree write observation with no lost events must cover the direct CLI pre-guard interval as well as bootstrap. This write proof is open, and observed redirection in the private probe is not enough. Test absent, unreadable, redirected, stale, duplicated, unexpected-kind and foreign-root artifacts; late helper reply and job uncertainty; guard-claim and every post-transfer failure; all compiled roles stopped on shutdown and restart; and read-share interference with other work during a full chat. The decisive performance gate is repeated product-process-to-healthy-attachment timing on copied new-save and acknowledged-restart roots with transfer inside bootstrap, then user-coordinated real-provider new-save, acknowledged restart and recovery runs only after private negative paths and fresh independent GPT-6 Sol or Opus 5.5 code and documentation reviews. Both routine starts must repeatedly be healthy within 30 seconds, recovery within 180 seconds. A miss leaves the goal open.
