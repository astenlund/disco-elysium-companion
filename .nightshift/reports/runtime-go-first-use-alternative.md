# Private Go first-use transport alternative

This is an investigation note, not an accepted startup design. The compiled selector remains off. The goal remains a healthy attached chat client within 30 seconds of process launch on routine new-save and acknowledged-restart starts, and within 180 seconds for eligible recovery. A copied-save synthetic-provider result does not satisfy the real-provider goal.

As of 2026-10-18, before the source-bound compiled-image path replaced it, the private fast path used a framework-dependent C# broker apphost, managed assembly, dependency document and runtime configuration document, plus a Go job observer. The broker's behavior is implemented in `runtime/scripts/ProcessBroker.cs` and `runtime/scripts/NativeJobs.cs`; `runtime/native/process-broker/Program.cs` is a small entry point. A separate restricted-token C# fixture produced a Windows application error with status `0xC0000142` before its read and write controls ran. That fixture result does not establish that the ordinary broker fails or that Go would succeed. It also exposed a Windows System event outside the repository, so no further restricted-token launch is authorized by this note.

One alternative is an explicit, one-time preparation command that builds a Go broker and observer from pinned local source into a versioned repository directory, validates the complete artifact set, then publishes a complete marker last. Chat would select an already complete version before launch and would not compile, repair or replace it during startup. The first preparation duration and the combined wait until first healthy chat would be reported separately. No automatic first-run compilation would be hidden inside the 30-second chat measurement. A later build would stage a new version beside the old one; incomplete staging would remain inert, and rollback would select only a separately admitted complete version.

A Go broker might reduce the launch trust surface to one direct executable for the broker and one for the observer, avoiding the C# broker's apphost, managed assembly, hostfxr, framework, `.runtimeconfig.json` and `.deps.json` proof obligations. This is a source-level inference, not a measured startup saving or a claim that Go is write-free. The Go port must preserve the exact control-frame grammar, explicit child environment, parent and child PID plus creation identity, scoped job membership, output forwarding, deadlines, error framing and complete-tree stop used by the current supervisor. A simpler binary layout is useful only if those behaviors remain equivalent.

Before any selector is enabled, preparation needs reproducible source-to-binary evidence and positive repository-only write containment for the compiler and its descendants, including failure paths and telemetry. Launch needs physical path and exact executed-image proof, a check that the selected bytes cannot be changed between admission and mapping, and positive process-tree write containment. A locally matching manifest, Node read handle, before/after hash or clean synthetic run is insufficient. The Windows-managed diagnostic boundary observed in the restricted-token fixture remains unresolved. If any proof is missing or ambiguous, selection stays off and the current PowerShell route remains authoritative.

A private spike can implement the Go control parser and job behavior without touching the real companion root or original saves. It should compare copied-root new-save, acknowledged restart and eligible recovery with a source-frozen control, including healthy attachment, journal and safety state, eight-role stop proof and exact selected save identity. Real SDK measurements require the user's coordination after the execution and write boundaries are established. The existing 120-second post-publish settlement gate is unchanged.
