# Private Go broker startup spike, 2026-10-18

This report records local, ignored evidence from a private Go first-use prototype branch whose changes this branch now carries. The compiled selector remains off in the CLI and no change was published. The goal remains a healthy attached real-provider client within 30 seconds for routine new-save and acknowledged-restart starts and within 180 seconds for eligible recovery. None of the results below meets that full goal.

The Go broker prototype parses the version-2 control frame, claims a scoped kill-on-close Windows job, retains parent and child creation identities, forwards the three streams, and reports the current six-field owned-process header. Focused Go tests passed, and the binary built under repository-local cache, profile and temp paths. An independent clean build with the same Go 1.26.0 toolchain, source hashes and flags reproduced the 3,493,888-byte executable with SHA-256 `8c155a47b1f9ed796e8b91b1436506baa60b59e522993cb114f8c67185728255`. The build record is under `.tmp/go-repro-build-20261018/run/result.json`. Reproduction is not a trusted release provenance or executed-image proof.

A direct private protocol fixture passed: the broker sent the expected header before child output, forwarded `hello`, returned the child's exit code 0, and the exact child identity and named job were absent afterward. A second fixture used a Go child that closed its operating-system stdin handle while remaining alive. The broker exited 125, killed the child and left the named job absent; its retained result is under `.tmp/go-native-early-close-go-20261018/run/result.json`. The earlier PowerShell-child fixture timed out after `Console.In.Close`, did not persist its random job name and could not prove that the underlying handle closed. It is retained separately as inconclusive evidence under `.tmp/go-native-early-close-20261018/`. A focused `ProcessSupervisor` fixture passed core command output, provider-style echo, live identity and quiescence in `.tmp/go-supervisor-20261018/run/tap.log`. These process fixtures did not use game saves or the real consumer.

The first release-backed copied-root owner preparation passed but its measured child failed before startup because the isolated worktree lacked the pinned SDK package. That root, `.tmp/acceptance-go-20261018/run-7bce2c0279831e89`, is preserved with positive stop proof and no attachment result. A byte-checked copy of the installed SDK 0.3.289 package then supplied the static import. The next new root, `run-c14eecdab314bdc7`, passed owner preparation in 278.145 seconds, separately from chat timing, and staged exactly one verified in-repository save copy in 5.815 seconds. Its parent reports are `.tmp/acceptance-go-20261018/parent-prepare-release-c14eecdab314bdc7.json` and `parent-stage-save-c14eecdab314bdc7.json`.

On that source-frozen copied root, a fake-provider new-save start reached parent-observed healthy attachment 27,237.393 milliseconds after the product child was spawned. It then completed one accepted turn, durably acknowledged the event, shut down cleanly and proved harness, bootstrap and product jobs absent. An acknowledged restart on the same root reached healthy attachment in 19,554.486 milliseconds, resumed the fake session with the same acknowledged turn and again proved all jobs absent. The parent reports are `.tmp/acceptance-go-20261018/parent-new-save-c14eecdab314bdc7.json` and `parent-restart-c14eecdab314bdc7.json`. These clocks include product-child import and copied-root runtime startup, but use a synthetic provider rather than the real SDK and are not measurements of the CLI against the actual companion root.

A separate supervised child then opened the copied backend and exited after writing only a dirty runtime marker. The marker interruption report at `.tmp/go-marker-recovery-20261018/marker-interrupt-3ffb901a3f5f0967.json` records a changed runtime instance ID, unchanged inventory and identity of every other durable file under the copied root's runtime-data and state trees, unchanged source snapshot and absent named jobs. Recovery from that marker reached parent-observed healthy attachment in 20,636.792 milliseconds, resumed the same fake provider session, returned to a clean marker with ready safety and retained the acknowledged event. Its parent report is `.tmp/go-marker-recovery-20261018/marker-recovery-11dd20afc07ec138.json`; harness, product and bootstrap jobs were positively absent. The fixed 120-second post-publish settlement gate was not altered.

These are single observations on one copied save and one synthetic provider. The Go binary is not selected by production CLI code. The package copy, per-launch hashes and before/after source inventories do not prove the exact bytes mapped by Windows, the trusted source-to-binary release relation, or the full process-tree write footprint. Windows-managed Event Log and Error Reporting entries are exempt from the repository-only write rule by the user's 2026-10-18 clarification; app-controlled outside-repository writes remain prohibited. Repeated real SDK attachment measurements, failure and recovery breadth, production selector design and independent final review remain open. A reviewer's minor observation that the recovery parent accepts the two child frames in reversed order was deferred under the user's standing minor-only disposition; the current child emits them in the expected order.

A separate private restricted-token diagnostic, on a diagnostic branch whose probe commits were not retained, narrowed its earlier `0xC0000142` failures. Its minimal native child exited zero under the original token but failed under a write-restricted token until the random restricting SID was added to that token's default DACL. With the corrected DACL, a Go child and a Go grandchild ran under the restricted token, passed repo-local allowed and denied write controls, and reported job membership. The launcher verified the first child in the exact named job before resume and both scoped jobs absent afterward. A read-only Windows access check on Public Documents reported add-file access for the original token and denial for the restricted token; no external write was attempted. The C# apphost still failed before its controls ran. The latest two-process result is in the sibling worktree's `.tmp/proof-6d82/restricted-run-go-grandchild-20261018-f`, manifest SHA-256 `d9183af53f4b73f348fbc036d90f12970566b96f473dfe84a1d86cd7c7124e8e`. It does not prove that the production Go broker can be launched under this token while preserving the supervisor's broker-PID and stream contract, that all outside paths deny writes, or that the production process tree meets the write boundary. The CLI selector remains off.

The next private diagnostic on that branch used the restricted Go child to start the installed PowerShell 7 executable and a repo-local control script. The PowerShell child exited `0xC0000142` before script output in both `restricted-run-pwsh-grandchild-20261018-b` and `restricted-run-pwsh-home-grant-20261018-a`. The latter granted the random SID write access to the six redirected repo-local profile and temp directories before launch, so missing grants on those directories were not the sole cause. The installed PowerShell executable's SHA-256 matched before and after, the restricted Go parent exited with a recorded failure, and both scoped jobs were independently observed absent. No core helper or real companion root was used. This token policy is not yet a usable containment route for existing PowerShell helpers, and the exact loader dependency remains unknown; simple repetition is not a substitute for a deciding diagnostic. The default Go-grandchild path still passed after these changes in `restricted-run-go-after-pwsh-20261018-a`.

A same-source private pair on that branch narrowed the loader hypothesis without changing any production code. A basic native executable imported only `KERNEL32.dll` and exited zero under the corrected restricted-token configuration. The variant additionally importing `USER32.dll` for `GetDesktopWindow` exited `0xC0000142` under the same configuration, while an ordinary-token direct run of that exact variant recorded exit zero in `.tmp/proof-6d82/direct-user32-control-20261018-a.json`. Both manifests recorded identical ordered source, controller and Go artifact hashes; only the selected native output hash differed. Its explicit exits are 0 and 2, so failure before entry is inferred rather than traced. The runner checks both named jobs absent before accepting or refusing a result, but the independent read-only checks after these two runs were not separately retained. This supports a USER32-related initialization boundary; it does not prove which Windows object was denied or that the C# and PowerShell failures have no other cause. The optional ETW trace candidate was rejected by fresh review and never executed.

A separate fresh copied root, `run-5b18b09718f76a1b`, completed owner preparation and staged one verified save. A private attempt to attach the actual Claude SDK through the Go broker returned `providerUnavailable` after repeated start attempts, with no healthy attachment frame. The product child recorded its last provider start at 59.886 seconds, and the parent report `.tmp/acceptance-go-20261018/parent-real-provider-5b18b09718f76a1b.json` records complete stop proof, source snapshot equality and 69.007 seconds to a failed result. The fixture redirected USERPROFILE and APPDATA into repository-local directories; the redirected profile had no `.claude` directory. Missing authentication is a hypothesis, not a diagnosed SDK error, because the provider start path collapsed the underlying failure. No credential was copied. This probe was premature under the approved startup design, which requires private write proof and independent reviews before any real-SDK measurement. Its complete write footprint was not established, so it is not an acceptance attempt and must not be repeated before those gates. It supplies no real-provider healthy-start timing and does not advance the 30-second acceptance gate.
