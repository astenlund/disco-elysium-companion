# Private executable image guard spike, 2026-10-18

The compiled Go broker and native job observer remain private selectors. A fresh code review and independent skeptic confirmed that hashing their Node read handles before launching by pathname does not bind the bytes Windows maps for execution. The ordinary CLI still uses PowerShell. The existing [image-gap report](runtime-artifact-image-gap-20261018.md) records that blocker and the failed leaf-only seal approach.

A repository-local `Probe-Pins.go` control opened read-only handles with `FILE_SHARE_READ` on the copied broker and every ancestor from the volume root through the broker's parent. Opening the file for writing and renaming its parent were denied while those handles were held, and the broker still launched and exited 125 on empty control input. A first attempt using only `FILE_READ_ATTRIBUTES` on the file did not deny a write open. The corrected generic-read file pin denied it. Its immediate post-close parent rename control was inconclusive, but a separate later `postclose-rename.json` recorded that the same parent could be renamed and restored after the probe process exited. The probe paths, Go source, wrapper and results are under `.tmp/go-production-20261018/.tmp/artifact-ancestor-pin-20261018/`; the copied broker matched SHA-256 `aa52d71f8a2243bdcb83bc394a12fe8193e413eb70b3543130f69df5a99c5d13` before and after the probe.

A second private control used installed PowerShell 7 with an in-process P/Invoke helper to hold those handles across a Node-launched broker. `.tmp/go-production-20261018/.tmp/pwsh-image-guard-20261018/run-b/result.json` records guard readiness at 840.885 milliseconds and total control wall time 966.635 milliseconds. It observed a denied same-user write open and parent rename while the guard was active, a broker exit of 125, a clean guard exit, unchanged broker digest, and successful parent rename after stop. Its earlier `run-a` result did not retain a complete wall-time field and is excluded from timing conclusions. These controls show the tested file-sharing behavior, not a production guard lifecycle or complete adversarial proof. Windows file-sharing semantics are described in [CreateFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).

A single orchestrator retained the guard and parent lifecycles around a copied-root acknowledged restart using the existing synthetic provider. `.tmp/go-production-20261018/.tmp/pwsh-image-guard-20261018/guarded-restart-0e073f3cb728c77f/result.json` records guardian readiness at 825.641 milliseconds, healthy attachment 20.341 seconds after the product child spawned, and 22.958 seconds from guardian launch to attachment. The broader clock includes harness-parent preflight before the product child spawned and is not a product startup measurement. The parent report under `.tmp/go-first-use-20261018/.tmp/acceptance-go-20261018/parent-restart-0e073f3cb728c77f.json` records one retained acknowledged turn, ready safety, fresh state, running watcher, healthy journal and positive absence of harness, bootstrap and product jobs. Both parent and guardian exited zero, with guardian stop recorded after the parent completed. A preceding manual guard-and-restart observation on another copied root reached healthy attachment in 20.323 seconds but retained no cross-process guard log; it is not used as guard-overlap proof.

A fresh copied root was prepared and staged with positive owner and job-stop proof, then run through a single guard-and-parent orchestrator. `.tmp/go-production-20261018/.tmp/pwsh-image-guard-20261018/guarded-new-save-0e073f3cb728c77f/result.json` reports a passing synthetic new-save with guardian readiness at 849.209 milliseconds, healthy attachment 28.666 seconds after the product child spawned, and 31.298 seconds from guardian launch to attachment. The broader clock includes harness-parent preflight before the product child spawn and is not a product startup measurement. The parent report under `.tmp/go-first-use-20261018/.tmp/acceptance-go-20261018/parent-new-save-0e073f3cb728c77f.json` records a committed and accepted state event, one acknowledged turn, fresh state, ready safety, healthy journal, running watcher and positive absence of named jobs. The guardian and parent both exited zero; the broker digest matched before and after. These are single private observations, not repeated real-provider results.

This guard currently pins only the Go broker, not the native observer executable. It has no runtime role, source-attested hello, durable failure recovery, positive scoped-job proof or production shutdown integration. The PowerShell helper's own complete write footprint, the observer's source-to-binary provenance, all descendant writes and the real SDK's default-profile footprint remain unproved. Holding volume-root and ancestor handles for a full session also needs an interference assessment. A production candidate must give both binaries one admitted guard lifetime with predecessor, source, scope, nonce, stop and crash behavior, keep every ownership and state gate unchanged, and show repeated healthy new-save and acknowledged-restart attachment within 30 seconds including guard startup. No compiled selector is enabled by this spike and the goal remains open.
