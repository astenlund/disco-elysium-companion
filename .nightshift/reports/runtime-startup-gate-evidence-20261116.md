# Startup gate evidence, 2026-11-16

These private results re-measure the routine startup timing of [Coordinator startup latency](../features/runtime-startup-latency.md) on current main and exercise the private gates its feature record listed as open: enabled-watcher recovery, entry-point exits, provider-start refusal, a real warm core-reply worker failure before its first reply, and the separately timed 120-second interaction gate. The live real-provider gate is not part of this report; its procedure is in [the live-run procedure](runtime-startup-live-run-procedure-20261116.md).

## Method

The committed harness `runtime/test/acceptance/startup-gates/run-gates.ts` copies `core` and the Disco Elysium adapter into a fresh companion root under the repository's `.tmp`, points the copy's adapter at a save folder inside that root, enables the watcher, hands consumption to the runtime, and stages the newest of the supplied save copies with its write time. It runs `gate-main.ts` once per run as its own Node process with the synthetic provider and no provider prestart, a gate taking one or more runs (its settling run, the fault run and any restarts); the CLI gates call the product `runCli` on the copied root. Each run has a deadline after which its process tree is killed, and `watch-log.mjs` follows the output. The supplied saves were the private bench copies of real saves already used by earlier fixtures; the harness refuses the adapter's live save folder, and it checks at the end that the three newest supplied copies, the only ones it can stage, and the staged copies are unchanged.

Times run from the harness spawning a gate process to receiving its `attached` frame, so each is an upper bound that includes Node startup. A run counts as healthy only when the attachment shows the runtime as consumer, fresh state, ready safety, a healthy journal, a running watcher and a ready provider. The counted healthy attachment of the [startup execution objective](../features/runtime-startup-execution-30.md) also requires a bound provider and verified startup-worker stop; the harness does not read those separately, and relies on the design's rule that attachment is withheld when either fails. Recovery runs wait up to 180 seconds from process start for that status. A settling run, whose acknowledged turn is meant to end with ready safety, precedes each worker fault, the interaction gate's success and failure pair, and each watcher comparison sequence, so that no fault case inherits an earlier run's correction; every settling run in the recorded runs did, and from `4db659a` the harness records the run directly after a settling run as missed when it does not. The not-owner and provider-refusal cases follow ordinary healthy starts instead.

The records show only timing: each commit named below that carries measured harness or runtime code (`b0cfbcc` and the harness commits) was made a few seconds to a quarter of an hour after its run started, except `9f90839`, committed just before its run; that each commit matched the working tree its run measured is the author's account, not something the records show. The reference run, whose gate results are tabled below, measured the working tree then committed as `eaed5d3`, whose runtime source is that of `b0cfbcc`; the supplied and staged saves were unchanged afterwards. Review then corrected the harness at `b58af35`: each run now records a verdict against its own gate check, an acknowledgement counts only when the backend returned a binding, and a failed event action or a signal-killed run can no longer end or hang the driver with a gate process left running. A full run of the corrected harness at `b58af35` gave the same outcomes, with every run meeting its check except the restarts after the worker kill during acquisition and after the gate-failed turn, the two recovery paths that need an acknowledged turn, described after the gate table. A further review found that a verdict did not yet check the time bound, so `4db659a` makes each healthy verdict require healthy status within 30 seconds for a routine start and 180 seconds for a recovery run, on the same clock as the times below. A full run at `4db659a` gave the same verdicts, and its supplied and staged saves were unchanged. A fresh review then found that a run killed at attachment could exit on its own during the shutdown that followed attachment and still count as killed, so `1cfb2fc` holds those runs attached until the kill arrives and requires that the kill ended the run; it also stages only `.ntwtf.zip` files. A full run at `1cfb2fc` gave the same verdicts, both runs killed at attachment ended by the kill, and its supplied and staged saves were unchanged. A last fresh review led `9f90839` to require the transport refusal's exact message for the kill on sight, to require that the gate-failed turn took at least 120 s, and to end a still-suspended settlement by finding it again by script and root instead of by a pid the runtime may already have released. A full run at `9f90839` gave the same verdicts with its supplied and staged saves unchanged; when its gate-failed turn ended, the lookup found no settlement process left; a suspended process cannot exit by itself, so the runtime had evidently ended it already.

The settled run before the reference run gave the same outcomes, with the enabled-watcher recovery also healthy in 6.6 s and the gate failure's turn ending at 129.7 s.

Two recovery paths leave a `contextUncertain` correction that only an acknowledged turn clears, so neither reaches healthy recovery within 180 seconds on its own. After the worker is killed during acquisition, the restart attaches degraded with a ready provider; in the recorded runs it took no turn and stayed degraded, and the next start's acknowledged turn cleared the correction. After a gate-failed turn, the first restart attaches status-only, and a second restart and a turn are needed. The user chose to record them together as one open question for the recovery target rather than open a backlog entry. During that status-only session the provider read `starting` throughout without any provider start being attempted (the phases go from provider selection straight to startup-worker closure). [Suppressed provider readiness readout](../bugs/runtime-suppressed-provider-ready.md) records the same label after an invalidated initial start, a different path, so its fix may not cover this one.

## Defect found and fixed

The first conclusive worker kill on sight, in the second gate harness run and again in the third, failed the start with `Owned process termination could not be requested.`, not the transport refusal. When an owned process exits before Node delivers its broker's `close` event, `ChildProcess.kill()` returns false, and `ProcessSupervisor.stop` treated that as a final refusal and threw `termination-unverified` without awaiting the termination proof. Commit `b0cfbcc` makes a refused signal fall through to the same bounded termination wait and quiescence proof, so a process that truly survives still fails closed; `process.test.ts` reproduces the race deterministically and failed with that message before the fix. The same race could have blocked the transport's fallback after a worker died mid-request, since that fallback requires a verified stop.

Commit `c07929d` adds regressions for the gates that had none: `startup-worker-failure.test.ts` runs real startup workers that exit before their hello or stay silent past the handshake deadline, and requires the transport refusal, a verified stop and a launchable role; `client/start-chat-provider.test.ts` pins `providerUnavailable` with one worker closure and no attachment safety; and `client/cli.test.ts` pins the `notOwner` exit with no provider phase.

## Superseded runs

Three harness defects invalidated parts of earlier runs that day, and their figures are not used above. The helper that suspends the settlement script matched its own command line, suspended itself and hung the first run for about 3 hours 20 minutes; the same flaw made its first worker kill on sight inconclusive. The early harness waited only for `turn.completed`, so the gate-failed turn appeared to hang for 300 seconds although it had failed at the gate. And until settling runs were added, later runs inherited a `contextUncertain` correction, so that run's recovery and watcher comparisons measured degraded starts rather than recovery from a healthy predecessor.

## Limits

The provider is synthetic and no real client attached, so these runs say nothing about the real SDK's initialization, its write footprint or live readiness. Timings come from one machine, whose new-save attempts ranged from 12.8 to 19.5 seconds apart from one at 26.3 seconds. The worker kill on sight lands after the broker reports the worker's identity, so the transport's fallback for a worker that exits before its identity is not exercised here. The client does not print the watcher state ([Watcher state missing from the chat client readout](../BUGS.md)), which matters for the live run but not for these runs, since the harness reads backend status directly.
