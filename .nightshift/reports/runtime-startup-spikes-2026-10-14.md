## Implications for a design

The initial spikes selected batching the two pre-marker admissions at each site, startup role checks with explicit per-role evidence, and reuse of the valid release reservation through storage initialization. The largest measured recovery cost was repeated launch of mutating runtime-file publication, but its warm native spike did not establish the full writer and crash contract. Extending the startup worker to inventories, reply validation or codec operations required a separate agreed design for source identity, bounded requests, per-request freshness and quiescence, failure handling, deadlines and each mode's side effects. The approved Inventory/Marker design and implementation evidence are recorded below; reply and codec warming remain undecided. The existing marker inventory and other pre-worker checks cannot be credited as savings from a worker that starts later. No safety, ownership, settlement, retention or provider-send gate may be removed based on these timings. First-answer latency remains unmeasured.

## Remaining architecture checks

The private event-metadata fixture under `.tmp/e/` staged valid, invalid and absent event inputs and obtained a native one-shot `Get-EventMetadata.ps1 -Batch` result with the expected status set and request hash. Its once-loaded scratch worker reached readiness but did not return the framed stdin request in bounded attempts. The worker was stopped. No byte-for-byte parity or warm timing was obtained, and the fixture does not support a production event-metadata worker. This is a scratch transport failure of undetermined cause, not evidence of a runtime defect or of a saving.

A proposed persistent startup core host was stopped before a timing run. Current `CoreClient.invoke` uses a supervised one-shot `core` process per command and then separately validates its bounded reply. `Kernel.checked` verifies that the `core` process job has stopped before clearing each pending safety check. Publish commits a core outbox record, the runtime durably appends and binds it in its journal, and only then can Settlement run; a synthetic or skipped journal append would invalidate the comparison. Existing PowerShell entry scripts also call `exit` and release entry-fence, configuration and lock leases per invocation. Retaining one process across Publish and Settlement therefore requires a different correlated per-request idle proof, fresh authority and source admission, and lossless crash/unknown-consumption behavior. A single-use prewarmed process that still stops per checked command is a distinct unmeasured idea, not the attempted persistent-host spike. No core-host timing or implementation was produced.

The locally installed `@anthropic-ai/claude-agent-sdk` 0.3.289 declarations describe alpha `prewarm()` and `SpareProcess.claim()`. Prewarming parks a process before a session exists; claiming binds it and sends the first prompt together. The current runtime instead calls provider safety, starts or resumes the provider session and writes its durable binding before client attachment. A parked process cannot satisfy the agreed bound-provider healthy-readiness target at startup, and claiming during acquisition would send input before state is admitted. Deferring binding until the first turn would be a different product contract. This API was inspected locally, not exercised in a live probe, and no provider-overlap saving is claimed.

At the end of those architecture checks, the best private fresh-save combination was 47.588 seconds to a fake-provider-bound and verified-stop boundary, with no client attachment or real provider. The two completed warm-helper micro-spikes did not establish a whole-start saving; the event-metadata and persistent-core attempts established none. Before production changes, any proposed architecture, including a single-use prewarm variant, needs a separately agreed safety proof and credible full-start timing path; otherwise the player-facing target or deferred presentation requirement must be revisited. The current 30-second healthy target remains in force until the user changes it.
