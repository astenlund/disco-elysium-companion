# Startup delay spikes, 2026-10-14

The prior user-reported live launch reached the chat prompt in 90.738 seconds; its phase boundaries and status are recorded in [runtime timing verification](runtime-timing-verification.md#startup-stage-investigation-from-the-user-reported-live-launch). The initial sequential private spikes below used the same runtime sources and changed no production source, real consumer marker, provider credential or SaveGames file. Later sections record applied batching and warm inventory changes against their own source snapshots. All probes used private repository roots or synthetic process names. Small timings are single-machine observations, not additive predictions for a player launch. The clean fixture intentionally had no save, so its safety was ready and journal healthy but freshness was failed. The recovery fixture used a private bridge release and handover; its status ended with recovering safety.

## Input and watcher boundary

The CLI currently opens readline after backend startup, provider binding and metadata-worker shutdown. A private presentation-only prototype made a draft editable at 22.898 ms process age during a simulated 120 ms startup. Enter before readiness retained an unsent draft, and readiness triggered zero host submissions; a second explicit Enter after readiness sent once. Bounded draft, quit and startup-failure cases also passed. This shows the proposed interaction state machine, not real terminal behavior or a faster answer. The governing runtime contract attaches the client after provider start and forbids automatic queuing or resending of denied input, so an early draft shell needs an agreed client design.

Two source-matched, watcher-enabled versus disabled private controls reached fake-client attachment in 82.444 and 77.217 seconds respectively. The enabled watcher start itself took 5.820 seconds and completed its identity publication before attachment. A later serial control that included real instruction assembly and FileToolAdapter preparation measured watcher start at 5.722 seconds, preparation at 0.641 seconds, fake provider callback at 0.114 ms, and durable `SessionStore.bind` at 6.620 seconds. The same private source digest was recorded before and after each paired control. The prepared overlap candidate can move only that 0.641-second preparation beside watcher start while keeping current backend serialization; full provider start awaits backend authority. Because this bound is below the requested one-second threshold, that candidate was not timed. The initial watcher fixture failed before measurement with an owned-process transport error; its 278-character scope path is a hypothesis for that failure, not a proven cause. A shorter private root was used for the passing controls, and the failed root was retained after read-only process and job-absence checks.

## Implications for a design

The initial spikes selected batching the two pre-marker admissions at each site, startup role checks with explicit per-role evidence, and reuse of the valid release reservation through storage initialization. The largest measured recovery cost was repeated launch of mutating runtime-file publication, but its warm native spike did not establish the full writer and crash contract. Extending the startup worker to inventories, reply validation or codec operations required a separate agreed design for source identity, bounded requests, per-request freshness and quiescence, failure handling, deadlines and each mode's side effects. The approved Inventory/Marker design and implementation evidence are recorded below; reply and codec warming remain undecided. The existing marker inventory and other pre-worker checks cannot be credited as savings from a worker that starts later. No safety, ownership, settlement, retention or provider-send gate may be removed based on these timings. First-answer latency remains unmeasured.

## Applied batching control

The bounded batching change now uses one fresh admission batch for scope discovery and one for an existing scope's directory and binding, checks all startup process roles through one read-only native job query with complete ordered response validation, gathers the metadata worker's temp and source evidence in one supervised helper while retaining the worker's independent source handshake, and carries one valid release reservation through storage initialization. Later individual job checks and the fixed state and provider gates remain in place.

The source-checked no-save private control at `.tmp/startup-spikes/backend/batched-clean-result.json` reached fake-provider binding and verified worker stop in 65.242 seconds, against 83.035 seconds in the earlier `.tmp/startup-spikes/backend/clean-result.json` control. These are separate runs with the same fixture shape and named sources unchanged within each run, not a controlled live player comparison. Phase spans changed from 6.383 to 4.342 seconds for scope admission, 4.752 to 2.658 for existing-scope admission, 30.718 to 19.000 for marker and worker bootstrap, and 5.291 to 3.206 for storage recovery. The corresponding one-shot path admission counts changed from two to one, two to one, and nine to four for those first three phases; storage recovery changed from two native resource inventories to one. The combined observed difference was 17.794 seconds. The later outbox, acquisition, retention and watcher/provider tail spans did not show a comparable reduction. The control still missed the 60-second private clean target by 5.242 seconds, and its missing save left freshness failed despite ready safety, a healthy journal, zero unacknowledged events and a running watcher. At that batching-only snapshot, a representative fresh-state or live player startup remained unmeasured.

Focused validation passed: the scope batch private case, three startup-job cases, all 11 owned-process transport cases, five metadata-worker opening cases, four private backend metadata-worker cases, all 48 in-memory capacity cases, the native process-job fixture, the selected existing-scope ownership integration case and runtime TypeScript typecheck. A pre-existing in-memory capacity fixture lacked the current inspector's `closeStartupSession` method; the mock gained that no-op so its shutdown test could run. No full runtime suite or real-root consumer command was run. These checks cover the bounded batching behavior, not the separately proposed warm read-only worker extension.

## Warm read-only Inventory and Marker control

The approved worker extension routes only exact, no-input `Inventory` and `Marker` requests through the startup-scoped worker after its scope-bound hello. `Event` and `Quarantine` remain one-shot, as does the pre-worker marker reservation. The worker makes a fresh native resource observation per request and still stops with verified quiescence before fake-provider binding. A focused private case observed ordinary `codec.json` residue appearing and disappearing through `Inventory`, while `Marker` consistently ignored it; a multiply linked scope binding caused a typed refusal, and a later fresh request succeeded. A separate stopped-worker case refused the next inventory and then used the one-shot helper after verified stop. Exact reply-shape and four-mode routing unit cases passed. These cases do not exercise a live companion root.

The source-checked watcher-enabled no-save private control at `.tmp/startup-spikes/backend/warm-clean-result.json` reached fake-provider binding and verified worker stop in 49.611 seconds, compared with 65.242 seconds for the matching batching-only control in a separate run, an observed difference of 15.630 seconds. The control still had failed freshness because it contained no save, despite ready safety, a healthy journal, zero unacknowledged events and an enabled watcher. The result meets the private 60-second no-save control target in one run; it does not establish a representative fresh-state or player-facing prompt time.

The private bridge handover and recovery control at `.tmp/startup-spikes/backend/warm-recovery-result.json` reached the same fake-provider boundary in 114.434 seconds after setup, versus 156.601 seconds for the separate batching-only recovery run, an observed difference of 42.168 seconds.
