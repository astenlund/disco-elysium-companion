# Selected-image fixture evidence, 2026-10-19

These private results exercise the source-bound compiled-image path end to end through `runtime/test/support/selected-chat-main.ts`, the private fixture main that the governing [startup design](../features/runtime-startup-execution-30.md) admitted on 2026-10-19. Each run spawns the fixture main as its own Node process against a copied companion root, with the worktree as the admitted installation and image root, a synthetic provider backed by a real supervised `provider` child, and the in-memory verified client attachment. The product CLI selector stays off. The harness lives in `.tmp/cc-eefa8669/harness/` and copies saves only from the verified bench copies under `.tmp/p6a17/.tmp/ownedrefresh17/bench/real-saves`; the original SaveGames folder was not read. Every run proved all process roles stopped for the copied root and its data scope, compared the staged save and the bench copies before and after, and checked the durable journal, cursor, binding, marker and safety records for its mode.

The five rows from `928ab4b` through the first `49dd79b` row show a slowdown of the machine, not of the code. Later the same evening, `928ab4b` attached new saves in 31.0 to 39.0 seconds, missing the 30-second target. About half of its added time sat in startup acquisition, which no change since `021b959` touched, most other phases slowed somewhat, and the absent-image fallback slowed by a similar amount. An A/B rerun of `021b959` right afterwards reproduced the slowdown. Spot checks between those runs, whose output was not kept, showed processor load at 4 percent, no trace session running and ample free memory; the cause was not found. The slowdown was present again early on 2026-10-20, when `3cd197c`, a second `021b959` control and then `49dd79b` attached new saves in 34.7 to 37.4 seconds; startup acquisition took 16.0 to 17.6 seconds in those four runs against 11.7 to 13.4 seconds in the eleven retained new saves before the slowdown. The 30-second margin of the earlier rows therefore depends on machine state. Around midday another job ran on the machine, and run times then swung with no consistent difference by commit: the absent-image fallback below was both slow and fast on each side of the broker change. The last row therefore measures that load, not the code.

The first two rows were measured before the independent review's repairs changed code on this path; the `dca5a4d` row re-measured the repaired code, and the `021b959` row re-measured after a later review round, which also rebuilt both compiled images. ## Pins and shutdown

Every image-backed run returned a ready pin set. After `host.shutdown()` stopped every role, write opens of both pinned executables failed with `EBUSY` while the fixture process lived, and the harness then opened both for write after the process exited. No run left an executable write lock behind. Release of the ancestor-directory rename restriction after exit, which the governing spec also requires, was not checked.

## Negative cases

Each case builds a damaged copy of the image root (inside the installation, except that the foreign-root copy sits under the repository's `.tmp`, outside it), runs the fixture main in the product configuration against an already-run copied root, and requires the refusal reason, and in every refusal case except the foreign-root one a pattern in its bounded detail, to match the intended check. The hard-link pattern also accepts the generic incomplete-release detail, and the foreign-root case checks only its `invalidInputs` reason, which several input checks share; the recorded details name the intended cause in every case that records one. Refusals after the transfer mark keep the pin obligation unknown, so the fixture exits hard. In every refusal case the copied data scope was byte-identical before and after, all roles were stopped, and no executable in the damaged image root stayed locked. The table records the pass on `21fd5be`, with broker `3159986b...` and the contained PowerShell broker for the absent case; each of its eleven reports records that commit, and the earlier passes on `1cd254f`, `021b959`, `928ab4b`, `d422b84`, `3cd197c` and `49dd79b` gave the same pin states, reasons and details. ## Write containment

One no-prestart new-save ran under an elevated NT Kernel Logger session (`PROC_THREAD`, `LOADER`, `FILE_IO`, `FILE_IO_INIT`, `FILENAME`) started and stopped through `gsudo` with the user's approval; the run itself was unelevated. The merged trace covers 2 minutes 57 seconds with 0 lost buffers and 0 lost events. The fixture main's process tree held 1,039 processes: 2 `node.exe`, 425 `conhost.exe`, 196 `pwsh.exe`, 228 `job-observer.exe`, 187 `go-broker.exe` and 1 `dedump.exe`. Write-class operations are writes, deletes, renames, security and extended-attribute changes, set-information classes that alter a file, and creates whose disposition can create or overwrite. They are attributed to the tree when a tree process issues them, or when the System lazy writer flushes a file object a tree process currently holds open.

Apart from file-system journaling, tree processes issued no write-class operation outside the repository. 7,794,677 operations landed inside it, and 173 more, also attributed to tree processes, were NTFS `$LogFile` and `$Mft` journaling that the file system performs itself. Three single System lazy-writer flushes outside the repository were attributed through reused kernel file-object addresses to files owned by other software running at the time: a Hermes Nightshift status file, a Claude Code hook marker and an unrelated temporary folder. No tree process created or wrote them directly. The analyzer and its report are `.tmp/cc-eefa8669/harness/analyze-trace.mjs` and `.tmp/cc-eefa8669/w/writes-r-75f7b7c3-v2.json`. This covers the whole run, including the pre-guard interval and bootstrap; it covers one new-save run with a synthetic provider, not a restart, a failure path or the real SDK's provider-owned footprint. Because it traced the fixture main rather than the direct CLI entry, it does not by itself discharge the governing spec's direct-CLI pre-guard write proof. It also ran on the images released before the later rebuilds, so no rebuilt image has been traced. No absent-image run was traced either. Before `890bb76`, the absent path ran the provider's PowerShell broker with the real user profile, so those absent-fallback runs most likely wrote PowerShell profile data under the user's `%LOCALAPPDATA%\Microsoft\PowerShell`, outside the repository.

## Other observations

The three no-prestart new-save runs on `658b086` recorded their one acknowledged turn at 122.5, 123.3 and 125.0 seconds, the last of them under kernel tracing, the two on `dca5a4d` at 120.1 and 127.0 seconds, and the two on `021b959` at 133.8 and 127.3 seconds, with a provider that answers immediately; during the later slowdown, turns took 135.3, 142.7 and 137.7 seconds on `928ab4b` and 136.1 seconds on the `021b959` control, then 136.1 and 136.9 seconds on `3cd197c`, 133.9 seconds on the second control and 133.6 seconds on `49dd79b`; under the midday load they took 138.5 and 167.8 seconds on `21fd5be` and 159.8 seconds on the `49dd79b` control. That fits, though it does not yet confirm, the post-acquisition journal drain in `runtime/src/backend/delivery.ts` running until its 120-second settlement budget expires; this belongs to [Coordinator whole-turn latency](../features/runtime-interaction-latency.md). The helper `pwsh` processes issued about 7.8 million write operations to PowerShell's `StartupProfileData-NonInteractive` JIT profile in the per-start helper profile during the traced run, and because every chat start creates a new `runtime-startup-*` profile, no start can reuse a warm profile and the folders accumulate under the installation's `.tmp`. Earlier private probes ran the `dotnet` CLI under a fresh `DOTNET_CLI_HOME` each time; the SDK treated each as a first run and appended that home's tools folder to the persistent user PATH. The repository's `.tmp` holds 71 such `toolpath` first-run markers, dated 2026-10-14 to 2026-10-18, as many as the tools-folder entries under that `.tmp` that a later session on 2026-10-19 found in the user PATH, when the inherited PATH had grown past the 8,191 characters cmd accepts. Every runtime helper, broker and test environment that redirects the .NET home now also sets `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=false` and `DOTNET_GENERATE_ASPNET_CERTIFICATE=false`.

## Injected faults

The user chose to cover the fault cases without adding fault hooks to the hash-pinned helper. `runtime/test/Test-NativeImagePins.ps1` drives the native pin primitives against real processes and passed three consecutive runs whose logs were not kept; later sets of three consecutive passes, on the tree of `021b959` and on 2026-10-20 at the pre-rewrite `c2eef80`, whose native pin sources match `6625ea6`, kept their logs under `.tmp/cc-eefa8669/native-pins-r5/` and `.tmp/cc-eefa8669/native-pins-r13/`. It covers the following:

- A target whose creation identity differs by one tick is refused before any duplication.
- A partial transfer into a live target rolls back, and both files are writable again.
- A target killed mid-transfer makes the next duplication and the rollback close both fail, yet the operating system released the pin it already held.
- A helper that transfers a pin and exits without a receipt leaves the pin denying writes inside the target until the target exits hard, which releases it.
- Replacing a file with identical bytes keeps its path and hash but changes the file identity that the helper's held-versus-admitted comparison checks.

`runtime/test/source-bound-bootstrap.test.ts` adds a late reply, job-stop uncertainty, no receipt and a truncated receipt, each refused after the transfer mark so the direct main's obligation stays unknown. The harness's `guard-loss.mjs`, run on the images released before the later rebuilds, held the copied scope's instance guard while the fixture main started: the pins were verified ready, the guard claim then failed with `Another runtime owns this scope.`, the fixture exited 1 under the hard-exit obligation, the data scope was byte-identical, every role was stopped and both executables were writable afterwards. Its retained report records the exit code and the fixture's final frame, with ready pins, no attachment and that message, but not the byte-identity, role-stop or writability results; `guard-loss.mjs` writes `passed` only after asserting each of those. The composite rollback flow inside `BootstrapImagePins.ps1` is exercised through its primitives rather than end to end, and same-hash replacement inside `OpenHeld`'s own admission-to-open window is covered by the property it relies on, not by winning that race.

## Still open

These gates remain open, each defined in the governing spec:

- The direct-CLI pre-guard write proof. The trace above covered one fixture-main new save, not the direct CLI, a restart or a failure path.
- Independent verification of source-to-binary provenance and the release-hash trust root.
- Go broker parity with the PowerShell broker it replaces.
- Launch from a non-canonical spelling of the installation path.
- The fast backend path's own acceptance matrix, which selection also enables.
- Release of the ancestor rename restriction after exit.
- Copied-save runs with ready pins of the remaining post-transfer states the spec lists: not-owner, provider refusal, status-only attachment, normal `/quit` and failed open. Healthy shutdown and, on the earlier images, guard loss have run.
- Clean fresh code and documentation reviews.
- Before any live run, the real SDK's default-profile footprint, with no model input and no tool call during initialization.
- User-coordinated real-provider new-save, acknowledged-restart and recovery runs.
- The decision to enable the selector.

The 30-second goal is not met until those real-provider runs repeatedly attach healthy within it.
