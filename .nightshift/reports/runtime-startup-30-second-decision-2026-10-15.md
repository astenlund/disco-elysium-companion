# Healthy 30-second startup: decision record

The agreed target remains healthy client attachment within 30 seconds from process start for both a newly detected save and an acknowledged-binding restart, with healthy recovery within 180 seconds. Ownership, fresh admitted state, journal and safety authority, watcher observation, bound provider readiness, verified child stop and the fixed 120-second interaction settlement gate remain requirements. A status-only or input-only client does not satisfy this target. The current three-worker execution slice is locally implemented and reviewed but has not passed the private or live target.

## Measured position

A [source-locked copied-save control](../../.tmp/startup-30/real-full-d5474d66f0eb2d47-fresh.json) attached a healthy in-memory fake client in 53.450 seconds from immediately before backend opening. The clock excludes process launch, real provider startup and actual client transport. Its selected source hash is `97c17ec5afd657708b2be06f3c9132213c56e97eb2614615274eebae18255fed`; worker stops, selected source files and copied saves verified after cleanup. It exceeds the private 30-second boundary by 23.450 seconds before excluded costs.

A separate [full-turn copied-save result](../../.tmp/startup-30/real-full-6467fd5ed8bc6060-result.json) attached a healthy fake client in 58.499 seconds, completed a fake-provider turn and durable acknowledgement, then attached the same provider session on an acknowledged restart in 43.565 seconds. It used a different instrumented source hash, so these durations are not speed comparisons with the 53.450-second control. The source and copied saves verified afterward. Repeated source-frozen private starts and real-provider and real-client timings remain unmeasured.

A [synthetic early-metadata batch comparison](../../.tmp/startup-30/early-metadata-spike/comparison-result.json) recorded 14.458 seconds for six one-shot admission batches and 7.704 seconds for a source-checked worker including attestation, launch and verified stop. A separate source-matched [whole-start control](../../.tmp/startup-30/early-metadata-spike/real-full-28ffab9a6a0f3698-fresh.json) and [candidate](../../.tmp/startup-30/early-metadata-spike/real-full-d7567bcace5c34f0-fresh.json) recorded healthy fake-client attachment at 57.600 and 48.200 seconds, an observed one-pair difference of 9.399 seconds. Only the later three of six pre-marker path admissions used the worker; the candidate also warmed marker inventory, moved predecessor admission before prior-marker and watcher checks, and skipped the later check. An independent source trace confirmed the recorded interval and these authority differences. The result is an optimistic test-only bound, not a safe production change or a demonstrated causal saving.

The [prepared-save prototype](../../.tmp/startup-30/save-preparation-spike/RESULTS.md) passed one private match case with equal normalized committed and settled state. Its constructed synthetic totals were 30.675 and 29.682 seconds, a 0.993-second arithmetic difference assembled from sequential intervals around an 18-second synthetic wait. No real backend overlap or client attachment was measured, fallback cases were not run, and the prepared artifact lacks the leased work group required by the current core contract. This route is not being promoted for the present objective.

Source tracing found no current-contract seam for full core Publish to overlap guarded marker, recovery and journal setup. In the 53.450-second control, the Publish child occupied 10.075 seconds; removing that entire interval would still leave 43.375 seconds before excluded costs. Post-marker core refresh has at most a 2.606-second observed overlap window before Publish starts and would need a distinct supervised role and phase-table revision. A [warm-service source trace](../../.tmp/startup-30/warm-service-spike/NO-GO.md) found no refreshed healthy reconnect API: current attach returns retained status and `/quit` shuts the backend down. A persistent service is a possible new product architecture, but cannot be counted as a cold-start speedup without revising its lifecycle and measuring it.

A later source-matched [all-six control](../../.tmp/startup-30/early-metadata-spike/real-full-2997dbe773f2cdef-fresh.json) and [all-six candidate](../../.tmp/startup-30/early-metadata-spike/real-full-fd83bd0d3af3f941-fresh.json) reached healthy fake-client attachment at 55.324 and 46.231 seconds from the same timed boundary, an observed one-pair difference of 9.093 seconds. The candidate clock includes 4.743 seconds of early predecessor admission, source proof, launch and hello; all six early PathInspector batches used fresh native worker admissions, whereas control used six one-shot calls. Both had the same selected source hash `4352c22e9e470133fa075d56e37122851207d56543aa38117a85ee3b297644d6` and verified private copy and worker-stop checks. An independent source trace found that the candidate used a fixture-known scope before ordinary guard acquisition, bypassed the normal inspector queue for these six calls, moved predecessor admission before the guard and skipped its later check, and required a clean prior marker with no watcher. These differences prevent a production safety or causal saving claim. Even this optimistic fake-provider candidate remained 16.231 seconds above 30 before process launch and real-provider cost.

A separate source-matched [early read-worker shutdown control and candidate](../../.tmp/startup-30/early-shutdown-spike/) tested stopping metadata and core-reply workers during fake-provider startup. Healthy fake-client attachment regressed from 57.553 to 118.314 seconds. The candidate detached the read workers before provider binding, after which the independent trace counted 30 serial one-shot metadata subprocesses occupying 60.282 seconds inside a 61.639-second binding interval; control binding occupied 1.184 seconds. Both private source, save and stop checks passed. Keeping the metadata worker available through provider binding is necessary in the current path; early read-worker shutdown is not a useful startup optimization.

## Design boundary

The measured evidence does not establish a path to the original cold healthy 30-second target. It also does not prove the target impossible. The existing contract orders marker completion, recovery, consumer reconciliation, outbox drain, authoritative Publish, journal append, Settlement, safety and provider binding; crossing those boundaries requires a governing design decision, not a skipped check or an early status label.

One route keeps the original cold target and funds a new, separately agreed authority design. It would investigate a source-attested read-only bootstrap transport before the current worker seam and a revised core phase arrangement, with complete guard, prior-marker, predecessor, source, crash, cleanup and verified-stop behavior. The next private proof should use paired source-frozen whole starts and stop any candidate that cannot bring the healthy fake-client boundary near 25 seconds, leaving margin for process launch and a real provider. The 25-second figure is an investigation budget, not a demonstrated saving or a revised acceptance target. A later user-coordinated live test still decides success.

The other route changes the user-facing target to healthy attachment to an already running coordinator. That service would retain the backend, guard, watcher and provider across client detachment and add authenticated local IPC, a refreshed-health gate, ordered event replay and explicit stop/recovery. It could avoid repeating cold initialization at each `chat` launch, but a service-down cold start remains a separate measured case and current APIs cannot assert healthy reconnect. A manual service kept within the repository can be investigated first; OS autostart or registration would write outside the repository and needs separate explicit authorization. Choosing this route changes what a 30-second success means.

No choice between these routes has been recorded. No production change follows from the private spikes. The original SaveGames directory and the real companion consumer root were not mutated by these investigations; all measurements and experimental mutations used repository-local copies and private roots.
