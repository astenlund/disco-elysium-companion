# TUI companion app

A terminal app that wraps the companion in a refined interactive experience, hiding the plumbing (watcher terminal, state refresh, Get-Diff consumption, stderr classes) and keeping a Claude session alive behind the scenes for the whole play session.

## Ownership boundary

The TUI is a presentation client of the [companion execution runtime](companion-execution-runtime.md). It renders chat, freshness, errors, dialogs, notices, objectives, plans, and deferred results. It invokes runtime and domain commands but does not consume diffs, supervise workers, write domain transitions, or filter raw internal knowledge itself.

The runtime owns agent and process lifecycle. Adaptive guidance owns research records, spoiler projection, and deferred-work transitions. The shared contract is [Runtime work, projection, and persistence boundaries](../patterns/runtime-work-projection-persistence-boundaries.md).

## Candidate slices

These are provisional design seams while the feature remains Exploring. They are not the formal `**Slices:**` block consumed by `/nightshift:ready`.

### Terminal shell

Provide streaming chat, live freshness and classified error status, a current state header, a landing brief, and basic native single-select dialogs. Begin with one adapter and a neutral theme. Consume runtime-projected state and interaction events rather than invoking state-core writers directly.

This is the likely TUI MVP once the runtime coordinator contract is firm.

### Advanced dialogs and session-plan pane

Add batch flows, richer per-option notes, persistent plan presentation, and the remaining native interaction affordances beyond the basic dialog surface.

### Deferred research inbox

Render projected user-requested tasks, readiness indicators, navigation, and consume commands. The adaptive domain service remains the writer for queued, researching, ready, and consumed transitions.

### Per-adapter theming

Apply adapter-owned palette and artwork data with graceful terminal color degradation. This follows adapter catalog and theme-contract design rather than blocking a neutral single-adapter shell.

Terminal bitmap images extend this slice beyond ASCII/Unicode motifs (idea captured 2026-08-15). Target terminal graphics generally with protocol detection: sixel (Windows Terminal 1.22+), kitty graphics protocol, iTerm2 inline images, degrading to the existing ASCII/Unicode motif fallback when no protocol is available. Assets are user-provided or agent-fetched online; SteamGridDB is the natural fetch target and its category set (grid, hero, logo, icon at standard sizes) is the model for a per-adapter asset convention, so a user dropping in files and the agent fetching them land in the same slots. Placement is deliberately open: both branding surfaces (landing screen, header, empty states) and contextual art (portraits, location or item imagery tied to game state) are in the design space; contextual art must respect the spoiler projection boundary if it keys off game state.

### Per-question model effort control

Expose a temporary stronger-reasoning action that reverts after one question. Keep model configuration in the runtime and the keybinding and feedback in the TUI.

### Session focus control

The TUI is projection-driven and has no internal `playSessionId` invariant. It renders the first valid current projection on attach or reattach and treats selection-event replay as optional. Adapter handoff clears the old view and awaits the target capability, healthy catalog, and first valid projection; no-session is safe Balanced, while stale or invalid projection remains Balanced with a delivery fault. A delayed old-session end never clears a newer selection, and `playSessionId` remains outside ProjectionV1, UI state, and logs.

Own the consumer side of the paired [Session focus: TUI integration contract](session-focus.md#tui-integration-contract) slices. Render a status-bar chip and canonical selection options in the received projection order without client-side sorting, expose Balanced through the separate `focus.balance {}` action, show the selected transient ad hoc row as display-only with a visible Provisional marker, make an automatic reset to Balanced visually clear without a toast or chat notice, and briefly highlight a promoted focus as saved. The focus state itself is adaptive-guidance domain state carried by the runtime; the TUI presents the projection and invokes commands without writing domain state or retaining or validating `playSessionId`. It renders the first valid projection on attach or reattach; selection-event replay is optional. Ordinary chat keepalive is carried as the typed `focus.keepalive` event with `source: chat` and a complete post-keepalive projection through the same event stream as command keepalive; the TUI does not synthesize or locally refresh expiry. On capability loss the TUI enters capability-pending and shows Balanced with the delivery fault; after a valid declaration it remains projection-pending until the first valid projection. A typed adapter handoff carrying a fresh binding epoch clears the prior adapter focus UI and waits for the target adapter's capability, healthy catalog, and first projection before enabling controls; no-session is safe Balanced, stale or invalid projection remains Balanced with a delivery fault, and prior-epoch events and projections are stale.

This slice may land before or after its provider counterpart. Before the provider exists, it stays capability-gated and is tested against the shared contract fixtures. The provider-neutral declaration carries current runtime identity, adapter identity, opaque adapter-binding epoch, session-focus capability version `1`, and promotion mode `compatibility` or `active`. An absent, malformed, unsupported, or downgraded declaration disables focus commands and live promotion, clears stale focus UI to a visible Balanced capability-unavailable state, and never permits local inference or emulation. The TUI acquires the authoritative current ProjectionV1 on attach or reconnect, capability replacement, and runtime or adapter handoff; acquisition does not invent events or revisions when state is unchanged, and target commands remain blocked until the admitted identity and binding epoch have a healthy catalog and structurally valid projection. When the second slice lands, that change adds the end-to-end integration test and activates the control.

On adapter handoff the TUI discards the old focus selection and displays the target's safe Balanced state until capability and first projection admission complete. A promotion rebound uses the current catalog label and current projection, never an origin label from stale event bytes. Equal-revision current-runtime promotion signals are accepted only when projection bytes match the authoritative projection and the logical operation is undelivered; conflicting same-revision signals are invalid and duplicate identities are no-ops.

The preferred cheaper order is to land the provider contract first, then this TUI control. The provider establishes the executable capability, command, projection, event contract, and shared fixtures, leaving end-to-end integration for the second landing. The reverse order remains supported through capability gating and fixtures when delivery constraints require it.

Promotion rendering and end-to-end promotion behavior remain inert until the Session focus Promotion domain and active-selection conversion and Promotion delivery and restart rebind slices are available. Earlier provider or TUI work may validate compatibility-only promotion event schemas, fixtures, and a non-emitting renderer branch. The TUI never treats a compatibility fixture as a live promotion.

### Deferred seeded focus management continuation

Add capability-gated rename and removal controls for seeded canonical focus entries while preserving picker order and the provider's Balanced reset behavior when the active entry is removed. This is a downstream presentation continuation: it consumes the headless seeded management contract and never becomes a dependency of the headless focus domain. Without the advertised provider capability, the TUI hides or disables these controls and does not emulate management locally. It remains deferred and non-parser-visible while this parent is Exploring.

### Deferred promoted focus management continuation

Add the corresponding capability-gated rename and removal controls for promoted canonical entries after the Promotion domain and active-selection conversion and seeded management continuations graduate. Without the advertised provider capability, the TUI hides or disables these controls and does not emulate management locally. It remains deferred and non-parser-visible while this parent is Exploring.

Maintenance invariant: any change to the shared focus command, projection, capability, or event contract must inspect and update the linked slice in the other feature in the same change.

## Architecture sketch (from the 2026-08-08 discussion)

- **Session-host seam (authoritative host API).** The runtime-owned [SessionHostV1 contract](companion-execution-runtime.md#sessionhostv1-contract-runtime-owned) is the provider-neutral host API that the TUI consumes; the TUI never imports a provider library directly. Its four faces map to the four presentation needs, with provider capabilities asserted per provider rather than assumed:
  - **Conversation stream**: a uniform event stream of turn deltas, full turns, and context compaction boundaries, so the TUI renders the same shapes for every provider. The Claude Agent SDK streaming-input mode yields this natively; a llama.cpp gateway or alternate endpoint must be adapted to the same framing.
  - **Host dialog callbacks**: tool-call events that the host renders as its own UI instead of text. The Agent SDK's `canUseTool` intercepts AskUserQuestion and lets the TUI render the selectable dialog; a host may answer by returning the selection. A provider that cannot host dialogs (llama.cpp gateway, alternate Codex) asserts `noDialog` and the TUI shows a degraded prompt-by-text mode rather than faking a dialog.
  - **Session control**: open by id, resume across restarts and days, auto-compaction handling, and hard interrupt of a stuck turn. Session ids come from the Agent SDK; other providers must supply their own or the TUI treats the session as ephemeral.
  - **Model override**: the per-question stronger-reasoning action that bumps to a stronger model for one question then autoreverts (Opus at high effort for the Claude host). Providers assert whether per-question override is supported; a provider without it exposes no "think harder" keybinding. Provider capabilities are declared by the runtime when a provider starts and never inferred from behavior; a missing capability degrades presentation visibly, never silently. The primary provider is the Claude Agent SDK (TypeScript, streaming mode, Claude Code's own engine), which reuses the existing `claude /login` OAuth, ships the native binary as a platform dependency, and resolves session ids across projects (the login route and its probe are recorded in the runtime feature's [Claude Agent SDK provider](companion-execution-runtime.md#claude-agent-sdk-provider) section). Declared alternate providers are Codex CLI and Claude Code via an alternate endpoint (OpenRouter), both expected to assert a subset of the same capabilities, and a local llama.cpp gateway expected to assert only the active stream plus text dialogs. The retired fallback of shelling out to `claude -p --resume` is removed because it cannot intercept dialog tool calls in flight, which the host dialog contract requires.
- **Plumbing becomes runtime internals.** The runtime supervises the watcher loop, state hydration, refresh, and the consuming state-event acquisition (`Publish-StateEvent.ps1`, state extraction section 7.6). The TUI opens immediately while those operations happen asynchronously. State-dependent questions wait for a valid snapshot and answer as soon as it arrives; state-independent conversation remains available during hydration. Save events refresh the snapshot in the background, and the UI shows its freshness state rather than implying stale data is current. The stderr classes ([stale-current], [reset-write], ...) render as status-bar states instead of raw lines.
- **Adapter enumeration.** The runtime hosts `core/` and consumes the provider-neutral immutable adapter-release seed resource and active release binding; the TUI renders the validated adapter catalog as its game menu. The canonical Disco Elysium identity is `disco_elysium`; hyphenated aliases are not admitted. The core/adapter seam as implemented is already shaped for the "single companion app with a growing list of game-specific adapters" direction.
- **Pre-warmed first response.** The work the first question currently pays for moves to runtime startup and idle time: spawn the session, refresh state, and create a durable pending event for the consuming diff before the user types. The event survives a runtime, session, or TUI restart until its projected brief is acknowledged. First-response latency then approaches plain chat latency without relying on model context as the only copy of a consumed diff. Natural landing screen: the projected situation brief pre-rendered before the user types, so summoning the app greets the player with the lay of the land.
- **Idle-aware recap: walk back to the last eventful save.** Idling the game stacks autosaves with no changes between them, and pre-warm consumption advances the baseline through each of them, so "since last read" can be truthfully empty while the last real progress sits several saves back. This is now a specified core capability, not presentation logic: the runtime invokes `core/Find-LastEventfulSpan.ps1` (spec section 7.4) and consumes its JSON contract (found/boundHit/span/diff, with the UNEVENTFUL predicate, ambient-path tolerance, and bounds all owned by the script), framing the landing brief around the returned span. Runtime knobs reduce to the script's `-MaxSaves`/`-MaxAgeHours` parameters; the TUI decides how to present dry results. The game's autosave rotation limits how far back the disk can answer.
- **Deferred research inbox.** The companion's [adaptive guidance knowledge](adaptive-guidance-knowledge.md) feature may create durable result records for research the user explicitly asks to receive later. The TUI presents only those user-initiated records, marks ready results, and provides a keybinding to jump to and consume the next one. Silent warm-start and save-triggered enrichment stays out of the inbox.
- **Native dialogs.** In an SDK host, tool calls surface to the host app, so AskUserQuestion becomes a dialog the TUI renders itself: own keybindings, per-option notes UI, a persistent session-plan pane built from selections. Probed 2026-08-08: the stock CLI's single-select preview dialogs render generously (32+ lines, 100+ columns, working per-selection notes), which the sequential guidance flow now uses; the native-dialog payoff is therefore batch/multiSelect flows with notes, richer layout than the flattened-markdown preview pane, and persistent panes, not basic notes support (the annotations field exists in the tool result schema for a host to populate). Also enables a live header (day/time/location, vitals, money from current.json) and a spoiler-safe objective board.
- **Stack lean: TypeScript + Ink + Agent SDK** (Ink is what Claude Code's own TUI uses; one language for UI and session control). Alternative: Go with Bubble Tea to match the dedump toolchain, talking to the session via the headless CLI or a small TS sidecar. The PowerShell core stays the state layer the app invokes and is not reimplemented; the runtime MVP extends it with the consumer-ownership marker and state-event outbox of state extraction section 7.6.
- **Per-game theming.** The active adapter styles the app: an adapter-owned release metadata theme block or sibling theme resource supplies a color palette and optionally basic artwork (an ASCII/Unicode motif or logo for headers and empty states), so the companion looks native to the game it is following rather than generic. Theming is data the adapter ships, like the dump and digest commands, so each new game brings its own look; the app carries a neutral fallback theme for adapters that ship none. Terminal constraints apply (palette degrades gracefully from truecolor to 256/16 colors). Bitmap artwork via terminal graphics protocols layers on top of this; see the Per-adapter theming candidate slice for the captured design notes (protocol detection, asset sourcing, placement).

## Why a TUI and not an Electron-style app

The decisive interaction pattern: a TUI is summonable as a fullscreen drop-down console via Windows Terminal quake mode, one keystroke over the running game and one keystroke away again, exactly like the classic quake console. An Electron app competes with the game for screen space and alt-tab attention; the quake overlay makes the companion feel like part of the game's own surface. Secondary benefits: negligible resource footprint next to a running game, and terminal rendering is the native habitat of the underlying session anyway.

## Known costs and open questions

- The current setup gets the full interactive Claude Code environment free (skills, memory, conversation continuity). An SDK host recreates only what it configures: system prompt, allowed tools, and the companion CLAUDE.md need explicit wiring. Straightforward, but that is where the effort goes.
- The user intends to split dev and exec workflows (developing the companion vs. using it during play) either when building the TUI or before it; the app is naturally the exec side of that split. The app defaults to Sonnet at medium effort (the machinery does the heavy lifting; latency is the felt experience; spoiler discipline rules out the smallest tier) and offers a "think harder" mode, a keybinding that bumps to Opus at high effort for open judgment calls like build walkthroughs. Decided 2026-08-08: the bump is per-question and auto-reverts; a sticky bump would silently tax every subsequent quick question. Dev sessions stay on the strong tier.
- Auth is settled: the primary Agent SDK provider reuses the existing `claude /login` OAuth, with no second auth surface; alternate providers bring their own endpoint and key resolution. The route was confirmed on 2026-10-05 with two qualifications recorded in the runtime feature's [Claude Agent SDK provider](companion-execution-runtime.md#claude-agent-sdk-provider) section: a real-request probe is the implementation plan's first step, with a long-lived token as the fallback, and the SDK documentation's statement about claude.ai login in third-party products was weighed by the owner for this personal tool.
- Open, and owned by this draft: whether the TUI needs a runtime process that outlives it. The coordinator MVP runs the runtime in its client's process, so closing the client ends the runtime, and the pattern's process-recovery rule allows that until some slice adds a background process and a client transport (decided 2026-10-05). If the TUI wants state kept fresh, sessions watched, or notices queued while it is closed, that slice has to be named and added to the runtime feature before the terminal shell graduates.
- Still open: whether the watcher-derived save-event stream should proactively surface notable changes in the UI between questions (that is a runtime notice-delivery decision, not a TUI one).
