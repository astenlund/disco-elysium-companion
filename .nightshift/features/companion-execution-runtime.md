# Companion execution runtime

Build the host layer between the existing state-extraction core, domain features such as adaptive guidance, and presentation clients such as the TUI. The runtime owns the persistent agent session, the single consuming diff reader, durable state event delivery, background worker execution, and orderly process lifecycle. It does not decide what game guidance means or how that guidance is displayed.

## Ownership boundary

- `core/` owns save discovery, stability checks, state extraction, digest and diff computation, baseline correctness, and historical walk-back.
- The runtime supervises those core entry points, owns the single consuming reader, journals state events durably, hosts the agent session, executes background work, and coordinates cancellation and shutdown.
- Domain features decide what work should run, its priority and visibility, and the state transitions of their own records.
- Presentation clients render projected records and invoke runtime or domain commands. They do not write baselines or domain state directly.

The shared lifecycle and projection rules live in [Runtime work, projection, and persistence boundaries](../patterns/runtime-work-projection-persistence-boundaries.md).

## Slices

The MVP and continuations below form the formal `**Slices:**` contract in `FEATURES.md`. The single-session state coordinator is designed to decision-complete depth in [Coordinator MVP design](#coordinator-mvp-design). The durable-consumption protocol, play-session lifecycle, playthrough identity, session-host seam, and process recovery have their interfaces and failure behavior settled in the pattern and in [Settled design decisions](#settled-design-decisions); the two slices that implement the rest of that settled material, Play-session lifecycle and Domain command and projection host, are named here and still need their own concrete design before they ship. The remaining slices are provisional seams whose interfaces still gain gates.

### Single-session state coordinator (MVP)

Host one configured agent session and one adapter. Supervise the core commands, expose streaming chat, freshness and classified error state, and a host-facing interaction event surface. Own the only consuming diff reader while the runtime holds consumer ownership, and retain each pending state event durably before its underlying change can be considered delivered. Replay unacknowledged events after app or session restart and support clean shutdown without abandoning consumption or presentation state.

This is the runtime MVP. The durable handoff protocol is settled: each state or domain transition commits its domain-owned state and durable outbox as one durable fact (for a consumed diff, the outbox record is the commit point and the baseline is rolled forward from it), while the runtime separately journals, delivers, acknowledges, and compacts that handoff. See [durable state-event protocol](../patterns/runtime-work-projection-persistence-boundaries.md#durable-state-event-lifecycle). The slice changes the core: it adds the consumer-ownership marker, the state-event outbox, and settlement specified in [state extraction section 7.6](state-extraction.md#76-durable-consumption-consumer-ownership-state-event-outbox-and-settlement). At dark shipment the bridge remained the absent-marker default consumer; see [Cutover and bridge retirement](#cutover-and-bridge-retirement) for the later explicit hand-over.

Implementation status: the section 7.6 core and coordinator runtime were delivered as a dark MVP. The original Nightshift delivery passed its named runtime checks on their recorded inputs, including private bridge, first-owner recovery, live SDK provider, and fixed one-new-record gate checks. Later publication repairs to journal fault retention, recovery carry placement, read-only status batching, and watcher identity comparison passed focused runtime and native tests plus TypeScript checking; the named private integration checks were not rerun on that repaired snapshot. On 2026-10-13 the user explicitly handed real-root consumer ownership to the runtime and exercised live chat plus a graceful restart. That smoke test does not establish the three save-change, crash-redelivery and bridge-release live cutover claims below, or the provisional native file-tool and whole-profile write claims. An absent marker still defaults to the bridge, and explicit release can restore bridge ownership. Revision-specific evidence and limits are in the [runtime timing report](../reports/runtime-timing-verification.md) and [provider verification report](../reports/runtime-provider-verification.md).

### SessionHostV1 contract (runtime-owned)

`SessionHostV1` is the runtime-owned, provider-neutral, versioned contract consumed by every presentation client. It exposes four faces: a conversation stream of turn deltas, completed turns, and context-compaction boundaries; host dialog callbacks for typed user questions and answers; session control for start, resume-by-id, graceful close, and interruption; and a per-question model override whose scope ends with that question. The runtime carries the current runtime, adapter, binding-epoch, principal, and play-session identities through the contract without exposing them as player-authored content.

Each provider declares the capabilities it can satisfy. A missing or withdrawn capability produces a typed degraded state and disables only the affected operation; the contract never emulates an unavailable dialog, stream, resume, interrupt, or override. Restart and handoff rebind the same logical session only when its identity and current bindings validate; otherwise the runtime fails closed, retains pending work for retry, and keeps commands gated until a valid host and projection are admitted. Provider-specific SDK behavior, authentication, and session transport remain adapter-owned behind this contract.

### Play-session lifecycle

Watch the adapter's game process and own the play-session boundary: validate an OS-backed `gameProcessInstanceIdentity`, mint and persist one `playSessionId` per sitting, accept the player sign-off command, emit one durable session-end event bound to a runtime-owned `sessionCloseId`, keep the close tombstone, and reconcile the recorded process identity at startup. From this slice on, each new sitting starts a fresh agent session and `InteractionContextV1` carries the current `playSessionId`, so every part of the slice can be verified live by starting and quitting the game. The required-consumer reaction ledger for session-end events is not here: it ships with the Domain host slice, where its first consumer arrives (decided 2026-10-05). The interfaces and failure behavior are settled in the pattern's [play-session lifecycle](../patterns/runtime-work-projection-persistence-boundaries.md#play-session-lifecycle) and [process recovery](../patterns/runtime-work-projection-persistence-boundaries.md#process-recovery-settled) sections. The runtime itself consumes nothing from this slice; it exists because Session focus and the psychologist persona react to its events.

One decision is already made for it. The adapter declares its game process name in an adapter-owned runtime manifest beside `adapter.json`, never in `adapter.json` itself: that file's member vocabulary is closed and any edit changes the configuration receipt an in-flight publisher holds (state extraction section 8). For Disco Elysium the process name is `disco` (probed 2026-10-05: the Steam install's executable is `disco.exe`, and the section 11 live-probe suite already calls `Get-Process -Name disco`).

### Domain command and projection host

Host domain features behind the runtime: admit each `InteractionContextV1` in monotonic order before any domain sees it; route strict-JSON domain commands and return their results; schedule domain-supplied deadlines and report timer failure; signal runtime start; drain registered domain outboxes into the journal and return `outboxSettlement`; rebind projection-bearing and session-close events after a restart; keep the required-consumer reaction ledger for session-end events; acquire the authoritative projection on attach and reconnect; publish volatile projection updates; run the journal-repair handshake with the owning domain; gate commands behind `capability-pending`, `projection-pending`, and pending-reset recovery; and expose the same-principal maintenance channel. The MVP's state-event drain is the first, projection-free instance of the outbox protocol, and this slice generalizes it to registered domains. Session focus's preset MVP is its first consumer and the source of most of its requirements. It requires Play-session lifecycle, because an admitted interaction carries the current `playSessionId`.

### Background work broker

Execute domain-supplied work with bounded concurrency, priority, cancellation, retry, offline handling, rate limiting, and coordinated shutdown. The broker knows how to run and persist work attempts, but not whether research is useful, player-visible, or spoiler-safe. Those are domain decisions.

After startup and pending-reset or handoff gates, the broker rehydrates persisted nonterminal comparison jobs under their original job identities. Queued and retryable jobs resume; interrupted in-flight attempts become retryable rather than complete; terminal jobs remain terminal. Attempt and result identities prevent duplicate application, and restart creates no new comparison job.

### Adapter catalog and session isolation

Enumerate installed adapters and isolate agent sessions, state-event journals, domain persistence, and user preferences by adapter and playthrough. A single-adapter runtime can ship before this generalization.

### Proactive notice delivery

Deliver domain-produced, spoiler-projected notices between questions without turning hidden enrichment into inbox entries. Preserve ordering with pending state events and ordinary responses, and retain notices until acknowledged by a presentation client.

## Coordinator MVP design

This section is the decision-complete design of the [Single-session state coordinator (MVP)](#single-session-state-coordinator-mvp). Its core half (the consumer-ownership marker, the state-event outbox, and settlement) is specified in [state extraction section 7.6](state-extraction.md#76-durable-consumption-consumer-ownership-state-event-outbox-and-settlement) and is not repeated here. Where this section makes a settled decision or pattern rule concrete it says so; where it defers one it names the owner.

One rule shapes every recovery path below. An operation that clears or moves a marker carrying an obligation (the cursor, a journal event, consumer ownership) first writes a durable operation record of what it intends, backed by the independent recovery witness where repair can hide owed history. Mutating commands reconcile the applicable incomplete operations and their independent authority before choosing a dependent branch. A marker is never the only evidence that work is still owed.

### Process, code, and configuration

- **Code.** A new top-level `runtime/` directory holds one TypeScript ES-module package. Node.js runs the sources directly through its built-in type stripping, so there is no build step and no emitted JavaScript (probed 2026-10-05 on the installed Node v22.23.2: both `node --test` and a plain `node <file>.ts` ran TypeScript with no flags). The package therefore uses only erasable TypeScript syntax, pins `engines.node` to `>=22.23`, type-checks with `tsc --noEmit`, and tests with `node --test`. Its only runtime dependency is the provider package named under [Claude Agent SDK provider](#claude-agent-sdk-provider). The PowerShell core stays the state layer and is reached only through its entry scripts.
- **Process model.** One process hosts the runtime and at most one in-process presentation client. `SessionHostV1` messages are plain serializable data, so a later transport can carry the same contract unchanged, but the MVP ships no background process and no inter-process transport. Client exit ends the process. That is a runtime exit, which the durable journal, agent-session resume, and startup recovery below already cover; it loses no event.
- **Single instance.** The pattern's `journal.lock` is realized as a process-lifetime single-instance guard plus one in-process serialized journal queue. The guard is a named pipe `\\.\pipe\game-companion-runtime-<first 32 hex of SHA-256 over the lowercased canonical candidate data-root path admitted below (resolved repository root plus safe components, including any not-yet-created suffix)>`. A second runtime for the same data root fails with `runtimeAlreadyRunning`, and the operating system releases the name when the owner dies, so a crash leaves no stale lock. A pipe is used because Node offers no portable exclusive file share mode (probed with the real-process `runtime/test/guard.test.ts` case `releases kernel ownership after its owning fixture process dies`: a second owner is refused through the `EADDRINUSE` mapping and the name is reacquired after owner death; dated probe and scope are in the provider verification record).
- **Entry point.** `node runtime/src/cli.ts <command>` has exactly four commands: `chat` (the runtime with the text client; the default), `status` (a read-only report), `consumer <runtime|bridge> [--abandon-undelivered]` (switch consumer ownership), and `repair` (run the stream repair). [Startup, shutdown, and recovery](#startup-shutdown-and-recovery) states what each one runs.
- **Configuration.** `runtime/companion.config.json` is checked in and has exactly `configVersion: 1`; string `adapter` (the adapter directory name, passed to the core as `-Adapter`); string `game` (the adapter identity, which every receipt and record must repeat ordinally); object `provider` with string-or-null `model`, string-or-null `effort`, and object-or-null `questionOverride` (`{ "model": <string>, "effort": <string> }`); and object `watcher` with Boolean `enabled`. An effort value is one of `low`, `medium`, `high`, `xhigh`, or `max`. A missing file, an unknown member, or an invalid value fails with `configurationInvalid`. A null `model` or `effort` means the provider's own default, and `questionOverride: null` means the provider declares no question override. The checked-in file carries the model decision of 2026-08-08 recorded in the TUI draft: a Sonnet-tier default at medium effort and an Opus-tier override at high effort for one question. Exact model identifiers live only in that file.

### Identities

Every identity below follows the shared opaque-token profile and is compared exactly.

- **Principal.** Resolved once per command from the current Windows SID. Chat may obtain it through the combined read-only `runtime/scripts/Get-BootstrapScope.ps1`, which returns exact `{sid,paths:[rootAdmission,scopeAdmission]}` from one supervised observation; other commands use `runtime/scripts/Get-Principal.ps1`, which returns exact `{ "sid": <string> }`. Both read `[Security.Principal.WindowsIdentity]::GetCurrent().User.Value`; the SID is the principal token and exact isolation key, `-Principal` value of every publish and value every drained record must carry. Chat independently reconstructs and validates both path admissions, then re-admits under its guard. A failed, empty, malformed or mismatched result fails with `identityUnavailable` or `dataRootUnavailable` according to its failed field, and no journal access, bound session or core command follows. The complete chat-only bootstrap contract is in [integrated startup execution](runtime-startup-execution-30.md#batched-source-proof-and-wire-contracts).
- **Adapter.** The adapter identity is the configured `game`. The configured `adapter` only selects the directory, which the core resolves case-insensitively; the two need not be equal. A receipt or record whose `game` differs from the configured one is never accepted.
- **`runtimeInstanceId`, `runtimeSessionId`, and `adapterBindingEpoch`.** Each is 32 lowercase hex from 16 fresh random bytes, minted once per process start before any recovery. `runtimeInstanceId` must differ from the previous start's recorded value and from `runtimeSessionId`; a collision is regenerated up to three times and then fails startup. None is restored after a restart. The MVP has one adapter and never switches, so one epoch lives as long as the process. Acquisition-domain comparison uses the core's [current save-selector recipe](state-extraction.md#acquisition-domain-identity); the intended adapter-directory-aware recipe and its [pending policy decision](state-extraction.md#acquisition-domain-recipe-decision-pending) are separate from this runtime identity epoch and game/principal storage isolation.
- **`journalId`** is minted with the journal. **`eventId`** (`EventIdV1`) is 32 lowercase hex from 16 fresh random bytes and is unique within the journal: a collision with any retained event, compact evidence or retained handoff aborts that append with nothing written, and the retry mints a fresh one. **`interactionId`** is minted the same way, once per player submission and never by a retry or a redraw. An **operation identifier** is `jr-` (repair), `rl-` (release) or `ho-` (hand-over) followed by 32 lowercase hex from 16 fresh random bytes.

### Storage

The identity-scoped runtime data root is `runtime-data\<gameKey>\<principalKey>\` under the admitted companion root, using the exact identity mapping and scope binding below, and `runtime-data/` joins `.gitignore`. It is inside the repository because the standing hard limit forbids the companion from modifying anything outside it, and it is separate from the core's `state\` so that each root has exactly one owning layer.

```
runtime-data/<gameKey>/<principalKey>/
  scope.json                      immutable exact game/principal binding
  runtime.json                    last start: runtimeInstanceId, startedAt, cleanShutdown, watcher process
  agent-session.json              provider session binding
  state-safety.json               acceptance-check intent, context generation and recovery witness
  agent-session-index.json        the sessions a named resume may bind (at most 32)
  prepared-context.txt            one transient, non-authoritative provider context block
  operations/<operationId>.json   repair and release records
  quarantine/                     files set aside by a repair
  journal/
    journal.json                  journalVersion, journalId, createdAt, highWaterSequence, historyVerified
    events/<sequence>.json        one event per file; <sequence> is 16 zero-padded decimal digits
    cursor-agent-session.json     the one MVP consumer cursor
    recovery-event.json           one plan-bound protected journal copy during recovery
```

**Storage admission.** Raw identities are never path components. Validate the configured game and resolved principal against the shared opaque-token profile first, without trimming, case folding or Unicode normalization; invalid input is `configurationInvalid` or `identityUnavailable` respectively. Derive `gameKey` as `g-` followed by the full lowercase hexadecimal SHA-256 of the game's exact UTF-8 bytes, and `principalKey` as `p-` followed by the same encoding of the principal's exact UTF-8 bytes. These fixed 66-character ASCII components preserve case-distinct identities and avoid Windows separators, dot segments, reserved device names and trailing-dot/space aliases without narrowing the logical identity grammar. Hash equality is not identity equality: the scope binding below must compare both original tokens ordinally and fail closed on a collision.

Every command first admits the physical companion root and the candidate `runtime-data/<gameKey>/<principalKey>/` before any candidate-directory creation, runtime metadata read, watcher termination or other runtime-owned write. Normalized physical paths are bounded to 32,760 characters and 64 components by the native admission helper; exceeding either bound is `dataRootUnavailable`. Existing ancestors from the admitted repository root through the candidate and every existing owned target must be ordinary directories/files in their prescribed role, with no symbolic link, junction, other reparse redirection or multiply-linked file. Resolve existing paths and verify their component boundaries remain under the admitted runtime-data subtree and exact candidate scope, never core state or another scope. Missing trailing directories are allowed only after their existing ancestors pass, and are created one component at a time under the instance guard, with each created component rechecked. Invalid, conflicting or unverifiable admission is `dataRootUnavailable` and touches no candidate content. Publication rechecks its parent and every existing target before staging or replacing; sibling temps/backups, operation records, journal/cursor/events, safety records and quarantine all use this same boundary. Reads for standalone status obey it without creating or repairing anything; an absent or empty unbound candidate is reported as not initialized, without reading other scope metadata. The supported concurrency model remains the single runtime writer with read-only status clients; path indirection is never an ownership transfer.

Each scope has an immutable, create-only `scope.json` with exactly integer `runtimeScopeVersion: 1`, string `game` and string `principal`, carrying those exact validated tokens and no unknown or duplicate members, within the `config` budget. Admission may read this file after path checks and before other scope metadata. A valid file must match the configured/resolved identities ordinally. Absent scope binding in an empty candidate directory permits initialization under the guard, with `scope.json` atomically published before runtime.json or any other owned file; concurrent create collision is reread and admitted only if identical in meaning. A crash after directory creation but before publication leaves empty directories that the same initialization can reuse. A missing binding beside any content, including an interrupted binding-publication sibling, is unverified ownership and fails closed without adopting, deleting or relabeling that content. Invalid, unreadable, mismatched or aliased binding does the same; it is never inferred from a directory hash, an event or a provider session. The operator must restore a verified binding or resolve the candidate separately before that command can proceed. No consumption has started in the initial temp-only crash state. Ordinary startup residue cleanup runs only after scope admission and cannot adopt that unbound scope.

`scope.json` is fixed-cardinality authority for the lifetime of that identity scope. Startup, every command, publication, retention, repair and read-only status preserve and verify it; release, hand-over, header/cursor repair, context invalidation, operation loss and provider replacement never recreate or retarget it. Runtime-created descendants cannot grant broader ownership than this binding. A valid binding beside absent journal data follows ordinary journal initialization and lost-history recovery, not a new scope. Hash keys and scope-file version are deterministic persisted format, not configuration knobs; changing them requires a separately specified migration. Raw identity-named directories are not silently migrated or treated as the new scope. The MVP creates this format on its first dark installation; it makes no claim that existing arbitrary runtime-data content is safe to import.


Every file is written whole through the discipline of state extraction 7.1: a unique sibling temp `<target>.<32-lowercase-hex>.tmp`, complete bytes, flush, close, then atomic publication on the same volume. A runtime-owned PowerShell 7 helper under `runtime/scripts/` performs publication with `.NET File.Move(temp, target, false)` for an absent or create-only target and `.NET File.Replace(temp, target, backup, true)` for an existing target. Create-only publication never falls back to replacement. The replacement backup is a separate, unique sibling `<target>.<32-lowercase-hex>.bak`; it is never a pre-existing file chosen by the caller. Only the creator cleans up a temp or backup during normal execution, and cleanup failure never changes a completed publication into a failed one. Startup removes owned publication siblings only under the single-instance guard, in the narrow pre-marker `runtime.json` pass and the later full phase-D pass described below. The runtime remains the sole writer; its separate, read-only `status` process is an expressly supported concurrent reader. The helper's existing-target primitive must preserve complete old bytes for an already-open supported reader and expose complete new bytes to a new reader. Plain Node rename does not meet this contract on the installed Windows build: it returned `EPERM` with an open Node read handle, whereas a runtime-owned PowerShell invocation of `File.Replace` succeeded with a separate Node reader held open (probed 2026-10-06 on Node v22.23.2). Unlink-then-rename is prohibited because it introduces a missing-target interval.

Publication and lossless-codec requests are serialized by one process-local publication queue, created empty at runtime start and drained before shutdown releases the guard. Each helper has explicit path arguments, no shell interpolation, bounded stdout/stderr, a 30-second deadline, and verified termination before the next request or cleanup can proceed; an unverified live helper retains ownership and blocks dependent publication. The core command queue remains separate, so a journal write never waits recursively on the core call that caused it. After the helper terminates, the caller verifies the target against the exact bytes it staged; matching bytes establish completion even if the helper's final response was lost, and a readable absent or different target is a failed publication. An unreadable target leaves publication uncertain: the caller invalidates its cached authoritative view and takes the existing I/O-failure path without performing subsequent dependent writes or acknowledgements from that cache. Before retry or later use, journal/header/cursor/event callers reload the journal, operation callers reread their operation records, safety callers reread the fixed record and protected operation obligations, session-binding/index callers reread that pair, scope callers repeat storage admission, and runtime-metadata callers reread their metadata; absent or invalid records take their already-defined recovery paths, while unreadable records continue to fail closed. No invalidated view becomes valid merely because a turn succeeds or a timer fires. Temp-only, published-with-backup, and published-without-a-collected-response are expected crash states: the pre-marker pass discards only admitted `runtime.json` siblings and phase D discards other admitted owned siblings after marker admission, then recovery reads complete targets through the existing journal, operation and binding protocols. A backup is diagnostic residue, never independent replay authority. Genuine publication failures keep the documented drain, repair, cursor and startup consequences; a supported status reader alone is not a reason to accept those failures.

**Pre-marker runtime metadata residue.** For `chat`, either `consumer` direction and `repair`, after phase B has admitted the physical root, taken the single-instance guard and verified or created the exact immutable `scope.json`, but before the phase-C runtimeMarker inventory and reservation, verify the prior publication job is quiescent. If termination is unverified, retain the guard while the process lives and perform no cleanup or marker write. Under the existing 120-second cleanup deadline and 65,536-entry discovery ceiling, completely enumerate only the admitted identity-scoped runtime-data root, never a parent, core state, SaveGames or another scope. Select only top-level ordinary-file siblings whose complete case-sensitive basename is `runtime.json.<32 lowercase hex>.tmp` or `runtime.json.<32 lowercase hex>.bak`; the suffix alone, a near match, a directory, a reparse point or a multiply linked file grants no delete authority. Admit the `runtime.json` target as absent or an ordinary file and validate the scope binding hash, guard and publication quiescence before the scan and again before each deletion. Record each selected sibling's and existing target's admitted physical identity and bounded exact-byte digest, then recheck path, object kind, volume, identity, link count and bytes immediately before removing only the sibling. A missing, unreadable, changed or contradictory selected object or target, changed binding, lost guard, failed quiescence, incomplete discovery or failed unlink stops without another deletion and without marker admission; it is phase-C `dataRootUnavailable` or the existing termination-unverified failure, not a clean capacity result. A foreign or unexpected name is never deleted. Other recognized owned residue families remain for phase-D full cleanup after Marker admission. Marker still admits every immediate root entry before filtering: a malformed, reparse or otherwise foreign root object can fail admission even when it is not a `runtime.json` prefix. A foreign or near-match prefix never gains deletion authority from this narrow pass; any resulting uncertain or failed Marker inventory stays closed without broadening the cleanup rule. No `.bak` is replay authority, and this pass never reads its contents as state, rewrites `runtime.json`, adopts an unbound scope or releases consumption. Crash before enumeration or after a complete scan with no deletion repeats a fresh guarded scan; crash after any number of successful unlinks leaves the complete target and remaining exact siblings for the same idempotent scan on restart; crash after cleanup but before marker reservation simply rechecks Marker; a crash during marker staging or after complete marker publication can leave a new tmp/bak, which the next pre-marker pass removes before rereading the complete target. Phase D still performs its full bounded owned-residue cleanup and safety/journal recovery. Standalone `status` takes no guard and never deletes a sibling or infers marker admission from its absence; it reports only separately admitted target metadata as observed. Failure on any mutating command stops before core consumption, provider start or repair movement. An empty root with no matching sibling performs no deletion and proceeds to the unchanged marker inventory.

The runtime never writes under `state\`. The provider executable keeps its own state in two locations under the user profile, outside the repository, as every Claude Code process on the default profile does (see the provider section): the configuration file `.claude.json` at the profile root with its temp, lock, and backup siblings, and the Claude configuration directory `.claude\` under the user profile. The runtime neither reads nor writes them and no session tool can reach them; they are host-owned, exactly as for today's Claude Code companion sessions. Within those locations the observed members are `.claude.json`, its rotating backups under `.claude\backups\`, and the transcripts under `.claude\projects\`, and the stored login's credential store is expected there as well; that list is provisional (probed 2026-10-06 on 0.3.289 with Claude Code 2.1.289, against an empty redirected profile with one turn that used no tool; the default profile with the stored login, a turn that uses a tool, a resume, and a compaction are not yet probed). A write by the executable anywhere else outside the repository is outside the exception: it fails the isolation claim, blocks cutover, and goes to the user, and it is never absorbed by extending this list. The user accepted this design on 2026-10-05 with the exception named as the transcript store; the configuration-file and backup writes were observed on 2026-10-06, they are inseparable from the user-decided stored login on the default profile, and avoiding them would take a token and a redirected configuration directory, which is the user's choice.

An operation record holds its identifier, kind, cause, and start time; the plan it committed to (for a repair: the last good sequence, the affected events with their readable identities and file hashes, any cursor position it will write, the versions its step-3 receipt reported, the retained handoffs and acceptance/presentation dispositions defined under State acceptance and context safety, its correction identity or null, the outbox identities its step 4 recorded as retired, and any step-4 rewind in progress; for a release: its mode, the sequences it abandons, and the skipped ranges that its synthetic cursor advancement will discharge; for a hand-over: its runtime-owner plan; both consumer-operation kinds also carry the protected safety intent described below); and a completion time and outcome that stay null until its first terminal outcome, then remain historical facts. Each repair record additionally has the required top-level `recovery` object below; release and hand-over records omit it. Repair liveness uses effective incompleteness, including an active recovery episode beside a historical terminal outcome. The outcome is exactly `completed`, `recordRejected` (a repair, below), `abandonedByRelease` (a repair that a release ended, under [Cutover and bridge retirement](#cutover-and-bridge-retirement)), or `refused` (a release that ended with nothing switched, under the same section). A `refused` record is terminal like any other: phase E resumes incomplete core operations and separately reconciles protected safety obligations even on terminal records, release step 1 counts effectively unfinished repairs and release step 4 terminates their active recovery episodes, `status` derives no stream fault from its refused outcome, but still reports any unresolved safety obligation, and retention treats it as any terminal operation record. It records no payload text. An operation record that cannot be parsed may be the only evidence of owed work, so it is never deleted: release step 1 counts it like an incomplete repair, and at a `chat` or `repair` start the stream repair with cause `operationLost` moves it to `quarantine\` as its recorded discharge and discloses with a `resync`. A quarantined file is named `<original file name>.<32-lowercase-hex>.quarantined`.

Each durable family is classified as the pattern's retention policy requires. `scope.json` is fixed-cardinality immutable scope authority; `runtime.json`, `agent-session.json`, `state-safety.json`, `journal.json`, and the cursor are fixed-cardinality records replaced in place; `agent-session-index.json` is one bounded record of at most 32 entries, replaced in place. Events follow the journal row of the retention matrix and the explicit synthetic-cursor discharge rule below. Lossless-codec input/control staging and prepared-context.txt are bounded, operation-lifetime, non-authoritative artifacts with creation, use, failure and cleanup governed by Payload integrity and lossless transport; they never become a new replay store. `journal/recovery-event.json` is one fixed-cardinality protected journal copy, bounded to one complete event, with no independent delivery identity or retention timer. Operation records follow the row for other terminal operation tombstones, except that a repair record carrying a protected handoff or outstanding correction is never pruned, including a historical completed repair with an active episode, a protected recovery slot or skip-discharge reference, or an outbox file that is still present, as the core never prunes a tombstone whose file remains. The safety section defines all protection references and capacity handling. `quarantine\` is diagnostic evidence, never replay input. At each bounded retention pass, admitted quarantine files are sorted by last-write UTC time and ordinal filename; only unprotected oldest files are deleted toward the 256-file limit. Destinations still named by pending prerequisite actions are protected. A completed mass quarantine can lose excess unprotected diagnostics at a later pass, while a repair action may temporarily exceed 256 beforehand. If protected files keep the remaining count above 256, maintenance reports exhausted `quarantineFiles` and retains them with the unfinished action; unavailable inventory fails closed without claiming the cap is met.

### Core supervision

The runtime runs core entry scripts as child processes through one queue that runs at most one script at a time (the watcher excepted). Each child gets an explicit argument vector with no shell, the companion root as working directory, bounded stream capture, and a deadline after which its process tree is terminated (probed with the real-process deadline and parent-exit cases in `runtime/test/process.test.ts`; the provider verification record states their exact job/child scope, and a deadline on the real provider executable remains provisional).

| Child | Deadline | After termination |
|---|---|---|
| `Publish-StateEvent.ps1` | 3,600 seconds, the outer liveness cap of state extraction 7.5 | Always drain, whatever the exit. |
| `Set-StateEventSettlement.ps1` | 120 seconds | Apply the settlement results below. |
| `Set-CompanionConsumer.ps1` | 120 seconds | Continue the release or hand-over. |
| `Get-Principal.ps1` or chat-only `Get-BootstrapScope.ps1` | 30 seconds | Admit the exact result or fail before dependent work. |
| `Watch-Saves.ps1` | None; long-lived | Restart policy below. |

Every queued child's stdout and stderr are each capped at 65,536 bytes. Capture overflow, a deadline, an abnormal exit code, or an unparseable result is classified diagnostically as `supervisor` with reason `capture-overflow`, `deadline`, `abnormal-exit`, or `result-invalid`; that class alone grants no provider input or settlement authority. Terminating a core child mid-operation is the hard-crash path the core already tolerates: atomic state writes, lock release when the holder dies, and reconciliation or the startup reaper for leftovers.

**Watcher.** When `watcher.enabled` is true the runtime keeps one `Watch-Saves.ps1` child alive so `current.json` stays fresh between questions. An exit restarts it after 1, 5, and 30 seconds and then every 60 seconds; a run that survives 10 minutes resets that ladder. Its streams are drained and discarded. The runtime records the child's process id and start time in `runtime.json`; at the next start, a process that still matches both is a watcher orphaned by a crash and is terminated before a new one starts (the real-process `runtime/test/platform/platform-native.test.ts` orphan-job fixture verifies identity matching and termination of its owner and descendant; a real `Watch-Saves.ps1` orphan through a full chat startup remains a separate provisional live claim). When that `runtime.json` write fails after a spawn, the runtime terminates the just-spawned child's tree and counts a failed start on the ladder, so an unrecorded watcher never outlives a running runtime. A crash between a spawn and its `runtime.json` write is an accepted residual: it leaves one unrecorded watcher, which only competes for the cycle lock and is ended by hand or at reboot, at most one per crash in that window. The watcher is a precomputation optimization and never a correctness gate: with it stopped or disabled, every acquisition still refreshes stale state itself. Shutdown terminates its process tree.

**Acquisition.** Normal acquisition is scheduled once during `chat` startup and once per admitted chat interaction when journal and safety admission permit it, before that turn goes to the provider; a journal fault skips that acquisition rather than running a child. A save event alone triggers nothing in the MVP. The first normal attempt uses `-RequireRecord` when no uncompacted state-bearing event exists; an `unchanged` target mismatch permits exactly one further `-RequireRecord` transaction for that startup or interaction. Planned repair/resync publication and replay are additional checked core calls under their own recovery operation, not extra normal acquisition moments. Every completed call, including the conditional follow-up and repair/resync, still updates operational warnings and follows the same checked-intent/result rules below. A chat interaction waits for its acquisition to terminate, then passes the bounded acceptance gate under State acceptance and context safety before any state reaches the provider. All publish and settlement observations use that section's durable check intent. An acquisition failure permits a disclosure-only turn only when no checked intent remains unresolved and all other safety and provider authority validates. A complete validated exit-1 diagnostic can clear its uninterrupted check and carry its classified failure in the block, provided it did not establish a rejection or another safety obligation; a failure before any check is armed can likewise carry a `supervisor` classification after safe readback. A child deadline, capture overflow, abnormal exit, unparseable or shape-invalid reply, or failed dependent publication after a check is armed leaves that intent unresolved, so no provider input, including disclosure-only input, is admitted until reconciliation. Resolve an uncertain arm publication from durable bytes before selecting either branch. The same distinction applies to the extra `-RequireRecord` transaction and startup acquisition. Four rules govern it:

- The runtime must always hold the state the core last consumed. It passes `-RequireRecord` on the first attempt when its journal holds no uncompacted state-bearing event. When a receipt says `unchanged` but its `target` identity differs from the state of the newest state-bearing event, the runtime's copy is stale (the bridge may have consumed in between), so it runs one more transaction with `-RequireRecord` before the turn proceeds.
- A receipt whose `game` differs from the configured one sets the journal fault `adapterMismatch`.
- A version change is a reset point. When a receipt's `schemaVersion` or `adapterVersion` differs from that of any unacknowledged event, the runtime runs the stream repair with cause `versionChange`. When a publish or a settlement ends `outbox` / `outbox-record-invalid`, or any settlement ends `settlement` / `settlement-quarantined` outside a running repair, it runs the stream repair with cause `coreRejected`.
- While a journal fault is set the runtime runs no acquisition at all: nothing further is consumed, so nothing can be lost behind the fault.

This failure distinction applies to runtime-hosted startup and interaction publication, its checked intent, the resulting context and live status, and the corresponding Child processes, Operational warnings, State acceptance and Verification clauses of this design. State extraction 7.6 still defines the core and bridge diagnostic grammar; a runtime error class does not change that grammar or grant another consuming command permission to send state.

### Journal

One journal event is one file with exactly these fields:

```jsonc
{
  "eventVersion": 1,
  "journalId": "...",
  "sequence": 7,
  "eventId": "...",
  "type": "state.consumed",          // state.consumed | state.snapshot | state.resync
  "occurredAt": "...",               // append time, RFC 3339 UTC with Z
  "runtimeInstanceId": "...",
  "adapter": "disco_elysium",        // the game identity
  "adapterBindingEpoch": "...",
  "principal": "...",
  "logicalOutboxId": "...",
  "recordSha256": "...",
  "payloadBindingSha256": "...",    // immutable binding of source hash to exact retained payload text
  "coreRepairOperationId": null,     // null for ordinary records; exact opaque core token for resync
  "attemptRef": null,                // null or { operationId, attemptOrdinal }; verified runtime association
  "schemaVersion": 2,                // copied from the record's nested documents
  "adapterVersion": 2,               // copied from the record
  "settlement": "pending",           // pending | accepted | unknown; latest outcome
  "acceptance": null,                // null | { journalId, eventId, generation }; positive exact-byte evidence
  "acknowledgedAt": null,            // set when the event is acknowledged
  "compacted": false,
  "payload": { /* the record's baseline, sourceFloor, refresh, warnings, baselineReset, diff, and state */ }
}
```

The field names it shares with the Session focus event envelope are the same names, so the Domain host slice extends this envelope with `projectionRevision` and `projection` instead of replacing it. The event file is also the delivery-ledger entry for its outbox record: appending the event and recording the outbox identity are one atomic write, so the pattern's "appended but not yet marked" crash state cannot occur for this family.

#### Payload integrity and lossless transport

Every full journal event requires payloadBindingSha256, exactly 64 lowercase hexadecimal characters with no whitespace or normalization. Compact events retain the same non-null value. It is SHA-256 of the exact concatenation UTF8("companion-core-payload-v1"), one byte 0A, the 64 ASCII bytes of recordSha256, one byte 0A, and P. P is the payload object's exact persisted UTF-8 token text. This detects independent corruption within the existing single-writer and trusted-producer boundary; it does not authenticate coordinated rewriting or rollback of mutually consistent evidence and introduces no secret key or second source-payload archive.

Construct P from the same frozen, completely read source bytes used for recordSha256, after their ordinary validation. Emit exactly baseline, sourceFloor, refresh, warnings, baselineReset, diff and state in that order, with fixed ASCII names and compact outer punctuation. Copy each source value's JsonElement.GetRawText() without changing its nested member order, numeric lexemes, escapes, strings or internal whitespace. Null stays the literal null. P has no BOM or surrounding whitespace. On reload, hash the actual payload object's raw token text; ordinary parse-and-reserialize is not equivalent. Metadata-only rewrites preserve P and its binding unchanged, including acceptance renewal, generation change, acknowledgement and a new destination journal. A different source gets its own new binding. Missing integrity evidence is never repaired by merely hashing a questionable payload anew.

The runtime-owned PowerShell helper supplies this lossless codec as well as the existing publication boundary. On the installed PowerShell 7.6.6/System.Text.Json 10.0.0.0, the private probe verified JsonElement.GetRawText(), strict UTF8Encoding(false, true), SHA256.HashData and Utf8JsonWriter.WriteRawValue(System.String, Boolean) with false. It preserved a number above JavaScript's safe integer range, a long decimal, negative zero, exponent spelling, escaped text and a seven-fractional-digit timestamp. This establishes that helper surface, not runtime integration. The helper constructs and verifies P, preserves it in event rewrites, and writes selected raw diff/state values into the final context. TypeScript orchestrates identities, gates and lifecycle using bounded control metadata and opaque prepared text; it must not JSON.parse/JSON.stringify these payload values. Required codec capability is checked before consumption; an unavailable capability fails closed rather than choosing an unverified serializer.

Use admitted file-backed staging for frozen source/control input and prepared output, never multi-megabyte payloads in argv or the 65,536-byte control streams. Each serialized codec request owns at most one input and one control sibling temp under its admitted scope, using the existing target/token/tmp grammar, strict corresponding document profiles and publication/termination rules. There is no accumulated request directory or source archive. Charge these temps, their target publications and the protected recovery copy in peak workspace. Remove owned staging after verified helper termination; uncertain termination retains ownership and blocks dependent work. Guarded startup removes only admitted residue after preceding helper ownership is resolved; unreadable or failed cleanup never grants a new staging allocation or authority from residue. Batched verification remains bounded by child deadlines and the existing interaction gate budget, which it cannot reset.

The fixed prepared-context.txt is one transient, non-authoritative artifact per admitted scope. It holds the exact complete tagged context block to be sent, capped at 4,194,304 UTF-8 bytes including tags. It is absent on clean initialization, created only for the current interaction after payload verification, and published under the storage protocol. Bind its exact bytes/hash and the selected event/state identities, generation and interaction in the immutable in-memory send snapshot. Recheck those fences immediately before send; a changed or unreadable dependency discards permission to use it. Read and send those exact bytes as opaque text, then remove the artifact after the send has taken its own immutable copy, or on cancellation/failure after no active helper or send owns it. Failed cleanup prevents a second artifact. A guarded restart discards it before a new interaction and never uses it for replay, acceptance, recovery, acknowledgement or status state. Codec/preparation failures use the existing supervisor and I/O failure rules and supply no provider input from stale text. No ordinary retention period applies to this operation-lifetime artifact.

Publish and verify the pending event, P and payloadBindingSha256 atomically before any settlement can retire its source. Event-before-high-water recovery verifies the full event before raising high water. After a positive settlement, correlate the original identity/hash/binding, revalidate retained payload integrity, then publish acceptance. Settlement-before-acceptance recovery uses that already-durable binding and original request; already-settled alone does not recreate missing integrity evidence. A lost helper response follows exact-target postcondition verification; an unreadable target invalidates cached authority and blocks dependent settlement, acceptance and delivery. A successful metadata rewrite leaves a complete old or new event with the same P/binding. Re-establishment requires independently verified matching source bytes or an already-bound valid copy under a durable repair plan, never a checksum refreshed from the damaged copy.

One verifier governs full-payload admission to immutable in-memory snapshots, post-publication readback and reload. Invalidate a snapshot on replacement or uncertain publication. Apply it to drain/deduplication/cleanup, startup, replay, newest-state selection, repair planning and carry restoration, history/finalization, provider start/resume/reconnect/send, acknowledgement and correction discharge, release/hand-over, retention and read-only status. Writers that preserve it are initial append, settlement/acceptance updates, acknowledgement stamping, repair reconstruction, carry publication/restoration, handoff propagation and compaction. Actual send and acknowledgement use the verified snapshot plus the existing identity/generation fences. Check the chosen acknowledged state independently of the unacknowledged prefix; unchanged generatedAt/source is freshness evidence only and never replaces payload integrity.

Before an event exists, absent binding supplies no delivery authority. In an existing full event, absent/null/malformed/duplicate binding, absent payload, unsupported event format or binding mismatch is damaged authority. Use the existing single reread for unexpected readable damage, distinguishing expected manifest partial states. Infrastructure unreadability stops dependent action without declaring corruption, deleting evidence or creating clean authority. Matching integrity with expired acceptance still requires current-generation positive renewal under the original binding; unknown/conflict does not renew it. Contradictory event/handoff/carry bindings fail closed. A fresh matching source can support planned reconstruction; without a trustworthy payload source, preserve known original identities, acceptance and missing-history obligations and use disclosed recovery. An older digest is never a substitute.

Detected persisted-payload damage invokes contextUncertain, not a fabricated core rejection. Preserve or arm the independent witness/repair obligation before removing evidence, retain a stronger existing coreRejected reason, and invalidate possibly exposed provider history before reuse. Suppress affected in-flight output and acknowledgement through the existing invalidation protocol. This rule also applies below the cursor: a full state-bearing record required as current state or potentially retained in provider history is not covered by the merely logged compact-history gap exception. Recover a trustworthy exact copy when available; otherwise use bounded resync/replacement and missing-history disclosure. A fresh accepted, non-degraded correction/current-state turn in a clean eligible session still discharges correction; release, hand-over and repair completion do not.

A protected carry must satisfy both its whole-file plan hash and payload binding before copying; hashing an already-damaged copy does not validate its origin. Verify the destination before deleting the last trustworthy source/carry. Every retained handoff adds required payloadBindingSha256: the same exact 64-hex value when a trustworthy projection exists, or null only for an explicitly cleanup-only handoff without one. Null never grants replay or selected-state authority. Such an unbound handoff can remain cleanup-only or gain a binding only through independently verified exact source/copy reconstruction; positive cleanup alone cannot restore retired presentation. Existing replayable handoffs without a trustworthy binding cannot replay. Compact events omit P legitimately and retain the binding as historical evidence, not selectable state; compaction verifies the full event before removal and preserves the ordinary eligibility/discharge rules. Quarantine remains diagnostic.

Charge the added binding and every codec staging/prepared-context byte in the existing read/write profiles and complete-transition reservations, including later acceptance/acknowledgement expansion and publication siblings. A document already at its cap does not gain an exception: refuse before source settlement or destructive movement, retaining the pending core record or existing obligation. All retention counts and document caps stay unchanged. The single protected recovery-event slot remains the only durable duplicate payload; transient codec files carry no recovery authority.

The 2026-10-07 private stub probe settled and deleted an original record, replayed its binding as already-settled, and received settlement-conflict for a different source hash. Changing only a retained unspentPoints digit from 2 to 3 still passed structural validators and matched an unchanged acquisition target; the source-bound payload digest distinguished it. This is core/serialization evidence over a constructed event envelope, not an executed runtime or provider path. Runtime fixtures must cover the mutation before and after acknowledgement, unchanged acquisition, every provider reuse path, missing/malformed/mismatched binding, unreadability, expired acceptance, surviving/deleted sources, handoff/carry/compact forms, capacity edges and each publication interruption. Assert preserved obligations and truthful disclosure, not only checksum inequality.

**Drain.** The drain runs on the journal queue after every publish terminates, at startup, and before every settlement retry; while a stream repair's operation record is incomplete, a drain outside that repair's own step 4 runs step 5 alone (see [Stream repair](#journal)):

1. List `state\outbox\` for record file names in ascending sequence, under the runtime read contract of state extraction 7.6.
2. Read each record's bytes once and compute their SHA-256. Parse strictly: UTF-8 without a byte order mark, no duplicate property name at any depth, depth at most 64, and size within the `state-event` budget. Validate the exact root field set and types of 7.6, the `logicalOutboxId` composition, the kind invariants, and the pairwise checks that need no nested validator: `baselineReset` against `baseline` and `diff.baselineGeneratedAt`, `diff.currentSource` and `diff.currentGeneratedAt` against `state`, and version equality between the nested documents. The nested diff and digest are otherwise producer-validated by the core and carried through the lossless codec as opaque JSON. The frozen source supplies P and payloadBindingSha256 before append; a duplicate full journal copy must pass the same integrity check.
3. Classify. A record that fails step 2 is `invalid`. A valid record whose `principal` or `game` is not this runtime's is `foreign`. A `logicalOutboxId` the journal already holds with the same `recordSha256` is a duplicate: append nothing, and send its settlement again under its original binding whatever the event's settlement state, because a surviving file can require cleanup or have become pending after a core ledger rebuild. Consult retained repair handoffs before appending as specified under State acceptance and context safety. The same identifier with a different hash is a `conflict`.
4. Append every other record in order. The next sequence is `highWaterSequence + 1`. Write the event file, which must not already exist, and then raise `highWaterSequence` in `journal.json`. A crash or a failed write between those two writes leaves one event above the recorded high water, which every drain, and startup, first verifies, including payload binding, before raising the high water. A journal read or write failure here (the event file, the high-water raise, or exhausted `eventId` retries) is not a classification: the drain stops appending at that record, which stays in the outbox because it was never settled, and the next drain takes it.
5. Send settlements for pending events, duplicates and surviving retired handoffs in ascending core sequence, using each record's retained original settlement binding. Stop at the first retryable result or required recovery. Positive evidence, unknown/conflict handling and presentation retirement follow State acceptance and context safety. An interaction's drain and settlement work shares its one gate budget; budget exhaustion leaves the rest for a later drain, never an unbounded batch before chat.

A `foreign`, `invalid`, or `conflict` record is never appended and stays in the outbox, and the drain stops appending at it so that order is preserved; step 5 still settles the events appended before it. `invalid` starts the stream repair below with cause `outboxInvalid`. `foreign` and `conflict` confer no automatic disposal authority: they raise the journal faults `foreignRecord` and `outboxConflict`, whose supported recovery is the operator's `consumer bridge --abandon-undelivered` followed by a fresh hand-over. Explicit abandon also covers a changed retired file through the core's reset-before-new-fence protocol; ordinary hash cleanup remains refused. Real I/O or capacity failures preserve the release intent until retry can finish.

**History verification.** `journal.json` also carries Boolean `historyVerified`. Every journal is created with it false, by phase D or by the `header` repair, because a new journal cannot tell whether an earlier journal of this data root held events that were never delivered, and no core result can tell it either: the core retires records by delivery, abandonment, quarantine, and pruning, and only delivery is ordered. The flag becomes true in exactly three ways, only after their grounding evidence is durable: a hand-over whose core result reports `previousOwner: bridge`, because only a supported release writes a valid bridge marker and every release either confirmed a verified, fully acknowledged journal or removed the baseline so the bridge disclosed a reset; repair finalization with a durable accepted-recovery checkpoint, whose `resync` discloses missing history; that checkpoint precedes the flag, and the active episode completes afterward; or a completed abandon release step 4, which has discharged every earlier obligation into a disclosed baseline reset. A hand-over from any other marker outcome (`absent`, `runtime`, or `invalid`) leaves the flag as it is: an absent marker may have been deleted by hand (state extraction 7.6), so the first hand-over of an install pays one cautionary `resync`. While the flag is false, the journal's first append runs the stream repair with cause `lostJournal`, so a journal that cannot vouch for earlier deliveries always follows the first records it appends with the disclosure that changes may be missing: the repair's `resync` lands in the same drain, right after them. The flag never returns to false for the same journal. Release step 1 treats an unverified journal like an incomplete repair.

**Settlement results.** The outcome matrix and positive acceptance evidence are defined under State acceptance and context safety. Settlement must establish admission before first delivery of any event or chosen state, and is no longer asynchronous permission to use merely appended records. Exact rejection invalidates context whether the event is never injected, injected but unacknowledged, or acknowledged. Inside repair step 4 it also invokes the recorded rewind; elsewhere it starts `coreRejected`. An `outbox-record-invalid` result starts `coreRejected` and conservatively invalidates potentially affected context. No result retroactively erases historical acknowledgement.

**Cursor and acknowledgement.** The MVP has one consumer, `agent-session`, whose cursor file is exactly `{ "cursorVersion": 1, "journalId": <string>, "consumerId": "agent-session", "lastAckedSequence": <integer>, "lastSentSequence": <integer>, "lastAcceptedRevision": null, "updatedAt": <string> }`; state events carry no domain projection, so the revision is always null. A state event is *delivered* when its diff, with the current state, is placed in a turn's context block. It is *acknowledged* when the provider reports that turn complete and successful and the runtime's acceptance, context-generation and identity fences still hold. That is the MVP's rendering of the pattern's "durably retained by the active session": the turn, context block included, is then part of the provider's persisted transcript. The model-facing projection is the identity projection: the same spoiler-safe digest and diff the bridge injects today.

**Cursor validity and bounded recovery.** Parse only the exact cursorVersion 1 field set, `consumerId: "agent-session"`, an admitted opaque `journalId`, canonical UTC `updatedAt`, null `lastAcceptedRevision`, and nonnegative safe-integer `lastAckedSequence` and `lastSentSequence`. With a valid header, the cursor journalId must equal the header journalId and both positions ordinarily lie at or below `highWaterSequence`. There is deliberately no `lastAckedSequence <= lastSentSequence` rule: a best-effort sent-mark write can fail, the turn can still be sent and successfully acknowledged, and the cursor can then have acknowledged position above its persisted sent mark. A cursor with `lastSentSequence > highWaterSequence` is not an ordinary valid pair. It may be read solely as an expected intermediate state when a readable, identity-bound recovery witness and active prerequisite manifest prove that an already-started step-2 high-water reduction owns the exact old/new header, cursor, target and next action; resume that same recorded action before generic `cursor` cause selection, new consumption, provider input, confirmed release, or synthetic skip inference. A missing, unreadable, stale or contradictory witness/manifest never licenses the exception: fail closed as unavailable authority or the existing cursor repair condition once readable evidence resolves it, without manufacturing acknowledgement. After the manifest completes, the ordinary cross-record predicate applies again. A cursor position above high water without that exact owner is a `cursor` fault, while a valid `lastAckedSequence > lastSentSequence` at or below high water remains ordinary history.

The mandatory safety/binding publications under State acceptance and context safety precede provider input; their failure blocks that input. The following delivery bookkeeping then brackets a turn in a fixed order. Before the turn is sent, the runtime raises `lastSentSequence` to the highest sequence the turn carries; an event above `lastAckedSequence` and at or below the previous `lastSentSequence` has been sent before and is marked `redelivery: true`, and the client receives the notice `stateRedelivered`. If that optional sent-mark write fails after this turn was admitted, retain the raised process-local mark and use the existing best-effort all-redelivery fallback. Only when the failure is a typed capacity preflight refusal does it additionally record the unavailable or exhausted diagnosis in live capacity status; an unrelated I/O failure creates no capacity refusal. The already-prepared turn may be sent exactly once only if the single-writer guard, current safety generation, provider identity, durable binding/index and exact prepared context are reverified at the send gate; loss of any of those required authorities forbids send. The exception grants no new core consumption, event append, replacement provider binding or waiver of a required publication. Only a diagnosed unresolved capacity slot blocks later new submissions until a safe capacity recheck or restart; an unrelated sent-mark failure follows its existing later-turn redelivery behavior and independent publisher/guard gates without a new blanket process block. A completed current turn can acknowledge only through its ordinary independent fences and publication preflights. After restart the failed mark remains absent and redelivery follows the existing duplicate-show rule. Only an actual provider send emits `stateRedelivered` for a redelivery candidate; a refused unsent turn neither emits that notice nor acknowledges an event. The runtime keeps the raised mark in memory for the rest of this process, so a later turn in that process still labels those events as redeliveries. The persisted mark is the only evidence that survives a restart: events sent under a failed write ride a turn after a restart unmarked, which is part of the accepted duplicate-show side. After a successful, non-invalidated turn whose safety generation still matches, the runtime acknowledges the longest prefix of the events the turn carried, taken in sequence order from the cursor, whose sequence still names the same `eventId` in the journal: it writes the cursor forward to the end of that prefix, keeping the cursor's current `lastSentSequence` (a repair's step 2 may have lowered it during the turn), then stamps `acknowledgedAt` into each acknowledged event file, then updates `agent-session.json`. When the first carried event no longer names the same `eventId`, because a repair replaced it while the turn was in flight, the cursor is unchanged, nothing is stamped, and the replacement events, the `resync` among them, ride the next turn under their own identities. A turn that fails, is interrupted, or dies with the provider subprocess acknowledges nothing, and neither does a failed cursor write; those events ride the next turn again, marked as redeliveries wherever a sent mark covers them, which is the accepted duplicate-show side of never-loss. A missing `acknowledgedAt` stamp may be filled from the cursor's `updatedAt` only for an actual acknowledgement advance. Before doing so, consult retained skipped ranges from repair and release records; synthetic recovery/release cursor positions are not acknowledgement evidence, and those ranges never gain a stamp from that inference. Unavailable or contradictory provenance fails closed. Independently established historical stamps remain unchanged.

**Replay.** After any restart, every event above the cursor is still unacknowledged and rides the first turn whose acceptance and context-safety gates permit it (an incomplete repair holds back the events above its last good sequence) in sequence order under its original `eventId` and sequence. State events carry no projection, so the pattern's restart rebind (fresh event identity and a re-derived projection) does not apply to them; rebind arrives with the first projection-bearing event, in the Domain host slice.

**Stream repair.** The journal is contiguous when `journal.json` is valid and every sequence from `lastAckedSequence + 1` through `highWaterSequence` has a valid event file of a supported `eventVersion`. A gap at or below the cursor affecting only compact historical evidence is logged, not repaired. Damaged full payloads that supply chosen state or may remain in provider history instead follow Payload integrity and lossless transport, regardless of cursor position. The runtime checks contiguity at startup and before every delivery; a violation triggers one reread before it counts. A file that cannot be read because of an infrastructure failure (as opposed to absent or content-invalid) is no violation, as in state extraction 7.1: no `gap`, `header`, or `cursor` repair starts on it, and the interaction's freshness is `failed` with `journalUnavailable` until a read succeeds. The stream repair is the single recovery for every way the event stream can be damaged, and its causes are closed:

**Phase-E capacity cause selection.** After consumer/safety reconciliation, resume any effectively unfinished repair and its prerequisites before considering a new cause. Read the structural journal, cursor and operation authority afresh under the single-instance guard. Missing or invalid `header`, `cursor`, `operationLost` or `gap` takes that existing priority; unreadable or contradictory authority is unavailable and cannot be treated as a capacity repair candidate. Only under an explicit `repair` command, with structurally healthy authority and no higher-priority cause, perform one bounded pass of already-authorized eligible retention and exact-authority cleanup before choosing a new capacity cause. The pass uses its own complete maintenance admission and may compact only evidence the existing retention proof permits; a failed, incomplete or unavailable pass leaves obligations in place and starts no new `capacity` root. Within that `repair` command, re-read the complete authority and assess the prospective ordinary transition, including the next append and reserved recovery/release workspace, from fresh inventory under the guard. If admitted, clear that transition's capacity refusal and start no capacity repair. If unavailable, report `capacityUnavailable` and withhold dependent work without a new repair root. If complete and exhausted, report the measured dimensions and owed summary. `chat` runs no extra phase-E capacity assessment or retention pass: its existing F/G admission and phase-H retention classify and withhold new consumption when required, then direct the operator to `repair`; it never opens a capacity root on the player's behalf. In `repair`, the new-cause order is `header`, `cursor`, `operationLost`, `gap`, then any historical root whose recorded replay still owes cleanup, then `capacity`; an active or newly selected higher-priority root wins and there is at most one new root per start. Before selecting `capacity`, preflight its entire repair, recovery publication and finalization plan under Recovery capacity admission. If that plan or its control workspace does not fit, or its authority is unavailable, refuse before witness, operation record, core call, cursor change or event move. A measured ordinary failure alone never promises a repair can fit, including an irreducible protected 8,193-event backlog. With an admitted plan, the operator has already received the command's pre-action capacity-rewind caution below. Step 1 records the same bounded witness and root before step 2 moves anything. The command's eventual result reports a bounded exact count and inclusive range for affected events and verified retained handoff/core-record status only from that durable validated plan, marking unreadable or absent evidence unknown. If the process or final output fails after plan publication, no committed action is undone; the next `repair` start resumes the same plan and can report its verified extent. No plan-aware prompt, pre-step-2 callback or unverified extent claim is required. A crash before any durable intent repeats the fresh phase-E classification on the next `repair` start; a surviving witness or root resumes that exact obligation and plan before new cause selection, even if a later capacity reading differs. A failed partial plan publication remains an owed recovery under the independent witness, not permission to allocate a competing capacity root.

Every cause runs the same five steps when its complete next transition passes Recovery capacity admission below; otherwise it takes that section's explicit refusal branch. Each step tolerates being already done and first honors the independent witness and any active prerequisite manifest:

1. Reserve the bounded transition, arm the independent recovery witness, then write the operation record with the cause, its complete retained handoffs and plan, any correction identity, and the initial recovery attempt and episode defined below. Verify both publications and activate the witness before moving evidence, changing a cursor, or launching a checked child. Preparation with no operation yet is an owed recovery, never an empty history.
2. Carry out the cause's action from the table. When that action lowers the high water below the cursor's `lastSentSequence`, it also lowers `lastSentSequence` (and the in-memory sent mark of a failed sent-mark write) to the new high water, a cursor position the plan records, because the sequences above it will name new events that were never sent.
3. Run `Publish-StateEvent.ps1 -Resync -RepairOperationId <active attempt token>`, where the token is derived from the owning root operation and current attempt ordinal as specified below. The core collects admission-rejected candidates from both untombstoned pending records and changed-retired files, including version or source-domain rejection. It establishes a durable resync strictly above the complete candidate ceiling before writing their exact-byte fences, or replays a live resync that already satisfies that condition. `outbox-quarantine-deferred` means that disclosure is durable but candidate fencing is unfinished: untombstoned candidates remain pending, while changed-retired candidates retain their old dispositions as retirement conflicts. The step remains incomplete; its resumed call replays the above-candidate resync and retries fencing. This grants no delivery permission before the acceptance gate.
4. Drain. A record that is still in the outbox is taken again as a new event with its preserved acceptance and original settlement binding when its handoff is replayable and its acceptance can be established in the current generation, even if its earlier event was quarantined in step 2; a presentation-retired handoff is cleanup-only and never appended; the `resync` event follows it. Before appending anything, the step records in the operation record the outbox identity (`logicalOutboxId` and `recordSha256`) of every record still in the outbox whose `schemaVersion` or `adapterVersion` differs from the step-3 receipt's: a successful step 3, whose receipt carries no `outbox-quarantine-deferred`, proves that its repair-mode reconciliation retired every such record and that only its file move can have failed, so it is not pending; with none, the list is empty. Every drain, this one included, suppresses presentation of a record whose exact identity a repair recorded this way, while performing its ordered cleanup settlement under the recorded handoff. This avoids stranding a predecessor that a core ledger rebuild revived; an unresolved cleanup stops later settlements but never re-exposes the retired payload. A record no repair recorded, including a genuinely pending old-version record, is appended as before and keeps triggering `versionChange`. Step 3 can also have retired a surviving record the runtime cannot recognize from its bytes, such as one whose nested content the core rejects at equal versions, or the record of an unacknowledged event that a repair whose step 2 leaves such events in place (`gap` below its first bad event, `outboxInvalid`, `operationLost`) did not move; the settlement this drain sends for it then answers `settlement-quarantined`, and the step invalidates context and rewinds. It first writes into the operation record that record's identity among the retired ones together with the rewind's plan: the sequence before the event as the last good sequence, every event from it through the high water with its identity and file hash, and any lowered sent mark. Only then does it move those events to `quarantine\`, lower the high water to that last good sequence and the sent mark with it as step 2 does, clear the rewind from the operation record, and drain again, which skips the record. When the rewound record was genuinely pending until step 3, later core records could not settle before it, and this drain stopped at its quarantine answer; those surviving records are therefore taken again with retained handoffs. A changed-retired candidate does not support that inference: retain each suffix event's actual acceptance and original binding rather than deriving unsettled status from sequence alone. Previously accepted records keep that evidence, and an absent record does not manufacture a replacement payload; the existing resync discloses history that cannot be recovered after the repair. The durable states are the rewind recorded with nothing moved, part of its events moved, and the high water lowered with the rewind not yet cleared, and a resumed step 4 completes a recorded rewind, whose moves tolerate being already done, before it drains. Each rewind records one more retired identity of a finite outbox, so the step ends. The recovery event therefore lands after the last good event and after every surviving record the core still holds. It is the domain's complete safe recovery event: it tells the session that changes may be missing and supplies the full current state.
5. Finalize the active recovery episode only with a usable journal and durably available, positively accepted current-generation recovery event. Record the accepted-recovery checkpoint, complete any deferred carry-release action under its separate gate below, publish `historyVerified` for that journal, then complete the episode and fill the root's historical completion fields only if this is its first terminal outcome. Failed finalization resumes those writes without another resync publication. A pending context correction stays in `state-safety.json` until successful recovery delivery.

Only one repair may be effectively unfinished at a time. Its own journal prerequisites are validated and recovered within that root before resuming; no competing top-level repair cause is started. References to an incomplete or unfinished repair in this design use the effective-incompleteness rule below, including active recovery beside historical completion. Other operation kinds retain their completion and separately protected safety obligations. While a repair's record is incomplete, outside its own step 4 no drain appends a record, because its step 3 may not yet have set aside a record the core rejects, so without an active prerequisite a drain only sends settlements of already journaled events; with an active prerequisite it additionally withholds any settlement that could delete the last needed payload or alter a planned target; and any turn needing state while the repair remains incomplete takes the acceptance gate's disclosure-only branch, because its step 4 may have appended records whose settlement is not yet answered. Replayable records and events remain owed until delivery; presentation-retired records are discharged only through the required missing-history resync, never silently acknowledged. `lostJournal` cannot recur for the same journal, because its repair's accepted-recovery finalization sets `historyVerified`. `operationLost` has these complementary branches: a damaged completed record costs one extra `resync`; a damaged release record whose core switch had run makes the `resync` refused as `notOwner`, which leaves the repair incomplete until the next hand-over, as for a `header` repair after a release; an abandon release cannot mark an unparseable record `abandonedByRelease`, so it stays for the next `chat` or `repair` start and costs one more disclosure after the re-hand-over; `consumer` runs no repair; and `status` reports an unparseable record among the faults derivable from operation records. In the `cursor` and `capacity` cases the `resync` tells the session that changes may be missing, which is the cautious reading of a position that cannot be trusted; replaying every retained event instead was rejected because it could flood a session with months of old diffs.

While a repair step is executing, the journal state is `repairing` and a chat submission is rejected with `notReady`. If a step fails, the operation record stays incomplete with whatever durable state that step left (a step-4 drain may have appended some records), which the step tolerates when it resumes, the journal state becomes `fault` with code `repairFailed`, and the repair resumes at the next `chat` or `repair` start. A repair has one terminal failure: if the record that caused `outboxInvalid` is still in the outbox after step 3, the core considers it valid and the runtime does not. The active episode records `recordRejected` and the named file/hash; the root's completion fields record that outcome only if this is its first terminal result, the journal fault `recordRejected` is derived from it for as long as that file remains, and no further repair is started for the same file. The file can also remain because the core tombstoned it as quarantined and only its move failed (state extraction 7.6 permits that and retries the move), so the outcome is not final: at every `chat` or `repair` start while that file remains, before the phase F drain, the runtime first durably activates or resumes that root's recovery episode, then runs one `Publish-StateEvent.ps1 -Resync -RepairOperationId` with its current attempt token. The same episode-governed replay runs for any historically completed repair whose record names a file that is still present, a step-4 retired identity included, so the core keeps retrying a failed move even under `repair`, which runs no acquisition; in `chat` every ordinary publish's reconciliation retries it as well. A skipped retired record is neither a fault nor a status field, because the core considers it retired and nothing is owed; the runtime logs it. The remaining recovery cases are: a core ledger rebuild while such a file survives revives it as pending in the core, and the next start's replay retires it again; a record whose delete keeps failing uses its retained handoff, so a terminal unknown/conflict preserves earlier positive acceptance but never creates it, while an unverified or rejected handoff is cleanup-only; and an acknowledged event later answered `settlement-quarantined` retains its historical acknowledgement but invokes context invalidation and an outstanding correction, not logging alone. The startup replay is an episode of its existing root, not a new root repair, but every rejecting observation invokes the safety protocol and any required repair intent; the core's repair-mode reconciliation retries the move, and the publish returns `replayed` for the pending resync, which the drain then takes once the file is gone. It commits a fresh one instead when the earlier resync was itself quarantined or does not lie strictly above every rejected candidate, including changed-retired candidates. The core fences either candidate class only after that above-candidate `resync` is durable; the phase F drain then takes that `resync`, which discloses that changes may be missing. A replay that ends without a receipt leaves its durable check unresolved and invokes conservative context recovery; one carrying `outbox-quarantine-deferred` leaves the repair work pending and gives no new delivery permission. A candidate it could not fence keeps its original classification: a changed-retired candidate remains a retirement conflict under its old tombstone, and Normal refuses it as `outbox-setup-failed`; an untombstoned candidate remains pending.

Normal-mode handling of ordinary pending records remains subject to every recovery restriction: a structurally invalid record stops ordinary operations at `outbox-record-invalid`, which starts `coreRejected`; a record of another version can be appended when appending is permitted and triggers `versionChange` at the next receipt; and a record of another game or principal is `foreign`. A same-version record that would be rejected only by producer-mode admission, such as one whose source domain the held configuration no longer has, can be appended, positively accepted through structural settlement and delivered in ordinary flow with no `-Resync` and no other incomplete recovery. This remains a residual for ordinary pending records only, not retirement conflicts; a source-domain change is not a runtime reset point.

While fencing remains deferred, outside drains cannot append new records and state delivery remains withheld. On an unchanged retry, a never-journaled candidate that remains producer-rejected stays blocked if fencing fails and is quarantined if fencing succeeds. An already-journaled, still-replayable candidate whose valid payload survives may instead settle structurally before fencing when no blocking prerequisite prevents it, and may be delivered ahead of the `resync` after recovery completes and all delivery gates pass, including verified payload integrity and positive current-generation acceptance under its original binding. A configuration change that makes a rejected record producer-admissible is a different input transition, not an unchanged retry. When the core still considers the record valid, the file stays and the fault persists, and its resolution is the same operator release as `foreignRecord`.

#### Repair prerequisites and attempts

These rules govern initial repair, retry, rewind, and completed-repair replay. O denotes the owning root repair operation's unchanged `operationId`; no separate operation file is created for an attempt or episode. The new fields use the same strict JSON grammar, duplicate/unknown-member rejection and whole-file publication as the existing operation plan. Array ordinals are zero-based nonnegative safe integers within the referenced array; no wrap, renumbering, case folding, or token normalization is allowed. Null is the explicit empty reference; empty strings and dangling indices are invalid. All fields named as exact shapes below are required.

**Identity and persisted shape.**

Keep the existing operation identifier O, original cause, plan, correction identity, completion time and outcome. Once the original operation first reaches a terminal outcome, its completion time/outcome become historical facts and are never cleared or relabeled by later replay. The required top-level `recovery` object has exactly `attempts`, `episodes`, and `activeEpisode`:

- attempts: a nonempty append-only array. Each entry has exactly publication, selectedRecord and journalEvent. publication is due, deferred or observed. selectedRecord is null or { logicalOutboxId, recordSha256 }, with recordSha256 null until exact bytes have been read. journalEvent is null or { journalId, eventId, sequence }. All identities and hashes use their existing grammars; sequence uses the journal's supported integer range. Initially there is one entry: due, null, null. An attempt's array index is its immutable ordinal.
- episodes: a nonempty append-only array. Each entry has exactly activationId, trigger, phase, attemptAtStart, replacementAttempt, prerequisite, acceptedRecovery, successorEpisode, releaseOperationId, startedAt and endedAt. activationId is the fresh 32-lowercase-hex token first durably armed in the recovery witness for this episode, copied unchanged; collision with a retained activation retries at most three times and then refuses. trigger is initial, completedReplay, header, cursor, gap, rewind or recoveryMissing. phase is preparing, reconstructing, publishing, draining, verifyingHistory, completed, transferred, recordRejected or abandonedByRelease. attemptAtStart is an existing attempt ordinal; replacementAttempt is null or the single replacement allocated by this episode. prerequisite is null or the journal plan described below. acceptedRecovery is null or { journalId, eventId, sequence, generation, acceptedAt }, identifying durable positive evidence, not merely a receipt. successorEpisode is a strictly greater valid episode ordinal only for transferred; releaseOperationId is non-null only for abandonedByRelease. Times use the existing UTC timestamp grammar; endedAt stays null until the episode terminates or transfers. Episode indices are immutable ordinals.
- activeEpisode: null or an episode ordinal. At most one episode is active. New repair creation atomically installs attempt 0 and episode 0: trigger `initial`, phase `preparing`, attemptAtStart 0, null replacement/prerequisite/acceptedRecovery/successor/release references, startedAt equal to the root start, and endedAt null. `activeEpisode` starts at 0. Later episodes start in `preparing` with their stated trigger, the current attempt ordinal and new UTC start time; other references begin null until their specified durable transition. A recordRejected episode remains active while its named disagreement, safety or recovery obligation remains unresolved; endedAt stays null in that case. On a later chat/repair start it reuses the same episode and current attempt for its permitted cleanup replay, first durably setting publication due. It allocates neither another episode nor another replacement merely because the same file remains. The historical root fault remains visible.

Arrays are never reordered or individually pruned, so ordinal references cannot change meaning. The root record's existing state-event byte/token/text budget bounds their growth; the existing protected-handoff and operation limits also apply. A prospective over-budget update refuses before mutation and preserves the old obligation. These arrays are removed only with the root operation after every subordinate obligation and protection reference has ended, under the existing terminal-operation retention policy. This avoids adding a separately pruned attempt ledger or another identity high-water record.

For attempt ordinal 0, pass O as the core RepairOperationId. For ordinal n greater than zero, pass O followed by '-r' and n in canonical unsigned decimal without leading zeros. This ASCII token is derived, never normalized or reminted on retry, and fits the core's existing opaque-token grammar. The current attempt is the last attempts entry. Every startup retry, deferred fence and completed-repair replay uses that attempt's token, not automatically O. A single core attempt can legitimately return several successive resync records under the core's existing quarantine/above-candidate rules; persist each displaced record's handoff before changing selectedRecord.

Every journal event, compact event, protected recovery copy, and retained handoff carries required `coreRepairOperationId` and `attemptRef` fields. `coreRepairOperationId` is null for ordinary records and the exact validated opaque core token for a resync. `attemptRef` is null or exactly `{ operationId, attemptOrdinal }`; operationId uses the `jr-` plus 32-lowercase-hex root grammar, and attemptOrdinal is a nonnegative safe integer referring to that named root's attempts array, never the containing repair's array. Ordinary records require null association. A resync may be unassociated when no runtime owner has been established. Omitted members, partial objects, empty tokens, wrong kinds, duplicate/unknown members and contradictory associations are invalid. All comparisons are exact, without normalization.

Initialization copies the core token from validated exact record bytes. Establish a non-null attemptRef only from durable root/attempt evidence tying its recorded publish request and correlated selected identity/hash to those bytes, or from an already verified retained association. Token resemblance and a receipt alone are insufficient. Persist selected-record/hash and association evidence before settlement or another destructive action can remove their last source, then publish the destination event before recording its journalEvent reference. Interrupted writes reconcile the same durable evidence; displaced selected records retain their original handoffs before a successor is selected.

Copy both fields unchanged across roots, episode transfer, rewind, header/cursor/gap reconstruction, protected-slot preservation and compaction. A repair retaining another root's resync neither adopts nor renumbers its attempt. Original journalId/eventId settlement bindings, exact record hash, acceptance history and presentation prohibition remain distinct from replacement destination metadata. Association may be enriched from null only by newly established evidence, durably before dependent use. A verified historical reference remains retainable after its owner is absent or unreadable, but does not supply current recovery authority; a readable contradictory owner fails closed instead of being silently treated as unknown.

Unassociated history may still be kept, deduplicated and settled through its exact identity/hash and demonstrable original binding under the existing safety rules. Unknown ownership alone grants no acceptance and does not reject otherwise usable history. Missing original byte/binding evidence takes conservative recovery, never a binding synthesized from current event metadata. Only a root's own readable current attempt, exact selected record, destination event, required position and current-generation acceptance can establish its acceptedRecovery checkpoint or discharge its correction. Another root's or an unassociated resync cannot do so. Lost/content-invalid authority uses operationLost/contextUncertain where applicable; infrastructure unreadability stops authority-dependent action.

The association rule governs drain/classification/deduplication, selected-record displacement, settlement/cleanup, prerequisite and carry handling, startup and completed replay, history/finalization, delivery/acknowledgement gates, release, retention, and read-only status. Status distinguishes unknown historical association from verified active recovery without mutation. Protect needed owner records and handoffs under the existing budgets; never force an association to make pruning possible. Historical self-contained metadata is not a claim that its owner is still live.

**Effective incompleteness and replay.**

A repair is effectively unfinished whenever activeEpisode is non-null, its original operation has not terminated, or a required recovery obligation cannot be established from readable authority. Unresolved carryRelease is such an obligation even when all structural actions are confirmed; its recorded removal postimage and progress, not historical completion or an empty executable suffix, discharge it. A correction naming a historical repair requires current recovery evidence; historical completion alone does not satisfy it. Do not reopen every historical repair merely because some unrelated operation changed the safety generation.

Before a completed-repair resync replay, arm or transfer the independent witness to the intended completedReplay activation, then atomically open that episode with the existing current attempt and set that attempt's publication to due. Verify and activate the witness before the checked-operation safety writes and child launch. The old completion remains visible, but all admission and release consumers now see effective incompleteness. Failed replay, lost reply and outbox-quarantine-deferred keep this SAME episode active. A subsequent start resumes it rather than opening another episode and resetting its replacement allowance. If another repair already owns active recovery, do not concurrently activate this root or steal the correction pointer; finish the existing recovery first. Existing single-writer queues enforce that ordering.

The safety correction continues to point to root O, never an attempt or episode. Existing correction-identity lookup still reconciles crashes between the operation's correction binding and the safety pointer. Missing, contradictory or multiple matches fail closed. Preserve an existing coreRejected reason; replacement, replay and generation refresh never downgrade it or clear correction.

**Prerequisite plan and crash recognition.**

The `carryRelease` rule below permits removal of a protected predecessor payload after its designated replacement has durable current-generation acceptance and a verified destination/high water, before delivery acknowledgement. It does not declare the predecessor delivered, discharge missing-history provenance, or clear correction.

A prerequisite plan has exactly kind, actions, nextAction, carry, carryRelease and skippedRanges. kind is header, cursor, gap or rewind. actions is an ordered, bounded write-ahead manifest; nextAction is its first unconfirmed action index. carry is null or exactly `{ path, sha256 }`, with path equal to `journal/recovery-event.json` and sha256 the lowercase SHA-256 of its exact planned bytes. carryRelease is null or exactly `{ attemptRef }`, where attemptRef is exactly `{ operationId, attemptOrdinal }`, bound to the designated replacement recovery attempt under Deferred carry release below. Its operationId and ordinal use the same exact grammar, scope admission, non-normalization and required-member rules as event attemptRef; null is the only empty carryRelease form, and null attemptRef, omitted/unknown/duplicate members, dangling indices and contradictory bindings are invalid. It occurs only at prerequisite level, never on an action, event or handoff. skippedRanges uses the provenance grammar below; an empty list is `[]`. A null prerequisite means no structural or carry-release action is owed. An empty actions list has nextAction 0 and is structurally reconciled; otherwise nextAction is in 0..actions.length, with equality meaning all recorded actions confirmed, not discharge of a pending carryRelease. Ordinary plans initialize carryRelease to null. This dark-MVP format supplies no implicit missing-field migration: an omitted field is invalid authority, not a null default.

The action vocabulary is closed to preserving a recovery event, quarantining a named old journal member, publishing a header, publishing a cursor, appending a recovery event, raising high water and removing the protected carry. Each action binds every affected admitted relative path and its expected preimage and postimage, each either absence or a lowercase SHA-256 of exact bytes. A quarantine move binds both source and selected destination. The action kind determines its required paths and metadata; missing, duplicate, contradictory or out-of-scope paths are invalid. Header and cursor actions contain their complete small metadata postimage. Event actions contain destination metadata and a reference to validated journal/outbox bytes, never payload in the operation. Quarantine destination names are selected once in the plan. Every readable affected event's handoff is retained before its action is authorized.

On resume, compare each target with its recorded preimage/postimage before executing. A matching postimage advances nextAction even if the progress write was lost; a matching preimage executes the same action. A planned missing source, the planned new header before its cursor, and an event above the old high water are expected intermediate states, not fresh damage. An already-authorized quarantine move does not require recovering payload from its diagnostic destination; an absent source does not create another repair. A conflicting destination is never overwritten.

An unreadable target stops without reconstruction or new identity allocation. An unexpected readable absence/content-invalid value gets the existing single reread. Only persistent observations outside the manifest's permitted intermediate states constitute new damage. First arm the witness transfer to the successor activation, then record the successor episode and transfer the outstanding plan, handoffs, carry ownership and unresolved obligations to it in ONE root-record publication. Verify that publication and switch the witness before further destructive action. The old episode becomes transferred, not completed. Do not discard an unexecuted obligation when rebasing its actions against the newly observed state. Permit at most one new damage episode per command start; further damage stops for a later start. Repeated observation of the same planned partial state allocates nothing.

Retain the existing structural policy: header reconstructs a fresh journal and cursor 0; cursor reconstructs at high water; gap/rewind quarantines the specified suffix and lowers high water/sent marks. The preservation exception below is the necessary narrow clarification to the header's 'all contents' wording, not authority to import arbitrary old history.

**Protected recovery payload.**

The fixed-cardinality `journal/recovery-event.json` slot exists only while a recorded preserve action or retained carry cleanup owns it. It is absent on an empty new root and is never created by status or ordinary delivery. It contains one ordinary, complete, uncompacted journal event envelope, not a new payload format. It is a protected journal copy, never directly selected for delivery, acknowledgement or newest-state lookup. It uses the state-event budget and normal storage admission/publication protocol. Its temporary duplicate is bounded to one event per scope and creates no additional logical event or retention timer.

Before moving the last available recovery event, or launching a core call that could delete its surviving outbox file, record a preserve action and the exact carry-file hash in the active prerequisite plan. Then publish and verify the slot from a valid journal event or a completely read, validated matching outbox record. Preserve or reserve its stable original settlement handoff before any settlement. No core call capable of removing the source occurs until preservation is durable. A crash before slot publication retries from the original source; a crash after publication recognizes the recorded exact slot bytes. If both source and valid slot are absent/content-invalid, take the missing-payload branch. Infrastructure failure or an uncertain slot publication instead stops; it is not evidence of payload loss.

Header reconstruction quarantines the old journal contents except this EXACT plan-bound slot. A filename alone grants no exception. Suffix reconstruction likewise preserves it until its destination is durable. A slot may be refreshed or replaced only by its owning plan after the earlier payload's destination is durable and its cleanup is confirmed. No new episode, startup cleanup or unrelated operation adopts an unbound slot. The slot's original acceptance remains historical until the ordinary current-generation gate admits it. Recovery into a new journal uses fresh destination event metadata, null acknowledgedAt, and the retained original settlement binding. A carrier may restore the selected recovery only when it can occupy the required post-policy recovery position without displacing newer surviving records or violating source order. In particular, cursor reconstruction must not merely reuse a resync now below its synthetic cursor; it needs a new recovery event above that position. If the preserved record cannot satisfy placement, ordering or current recovery requirements, retain its handoff and use the replacement attempt rather than forcing it into the stream.

### State acceptance and context safety

State delivery requires positive core acceptance of the exact record bytes and verified integrity of their retained payload projection. Retirement and acceptance are separate facts. Each journal event adds exactly `acceptance: null | { journalId, eventId, generation }`, where `journalId` and `eventId` are the original settlement request's identities under the shared opaque-token grammar and `generation` is the exact current 32-lowercase-hex safety token when the positive result is durably accepted; the owning event's `logicalOutboxId` and `recordSha256` bind the evidence to the record. Compaction preserves it. Before a repair moves an event, its operation plan preserves this evidence, payload binding and original settlement binding alongside its immutable record identity; a replacement of the same exact record inherits that evidence and binding. Absence, invalidity or unreadability confers no acceptance. Neither acknowledgement, an outbox filename, disappearance, an `unchanged` or `replayed` receipt, nor a terminal `unknown` creates it. This is the existing core structural settlement assurance, not a new source-domain check; the separately stated equal-version source-domain residual remains.

The complete settlement matrix is: a positive result durably establishes acceptance in the current generation and marks settlement `accepted`; `settlement-unknown` or `settlement-conflict` marks settlement `unknown` but preserves any prior acceptance of those exact bytes, but confers delivery permission only while its generation is current; without such evidence it invokes `settlementUnverified` recovery and confers no delivery permission. A demonstrable earlier settlement binding is retried before declaring evidence unavailable. Exact `settlement-quarantined` revokes eligibility even after positive acceptance or acknowledgement and invokes the context invalidation below. `settlement-hash-mismatch` remains `outboxConflict`, with no new acceptance. Every other failure, including out-of-order, leaves the event retryable and supplies no new acceptance. A cleanup attempt never revives a record already retired from presentation. An acceptance-write failure leaves the check unresolved and supplies no permission from a merely in-memory result.

**One delivery gate.** After the interaction's separately bounded acquisition child terminates and before its post-publish drain starts, one 120-second settlement budget covers queue waits caused by settlement, predecessors, retries, acceptance publications and all reselections. It never restarts after a repair or new result. Do not schedule a whole unbounded settlement batch ahead of this gate. If a check or protected operation intent is durably armed, expiry while queued, during its child, during result validation, or before its completion publication leaves that intent unresolved, even when the surviving process observed no child launch. No complete validated result exists to discharge it, and process-local knowledge of no launch cannot erase a durable obligation after a crash. A child terminated at the remaining-time limit supplies no validated semantic result even after its process tree is verified quiescent. The pending intent blocks provider input, including disclosure-only input, until reconciliation; an admitted-turn interruption requires a later `chat` or `repair` startup to mint a new safety generation and `contextUncertain` correction, plan resync recovery, and reject the old provider session. A startup-acquisition interruption instead enters the conditional second safety reconciliation in that same startup before provider admission. If either reconciliation fails, keep provider input unavailable and retain the obligation for a later start. Once accepted current state is available, the replacement clean session discloses that earlier state-based guidance may be unreliable and does not automatically resend the interrupted question. An earlier pending obligation retains its own recovery rule when this gate expires.

`carryRelease` is a read-only, identity-scoped summary derived from the validated safety record, operation inventory and exact carry evidence, not a field in the fixed safety record. It initializes to `unavailable` before the first observation, refreshes on each safety observation, and returns to `unavailable` if authority is missing, stale, unreadable or contradictory. `none` means no qualifying deferred-carry entry is retained in current authority; `waitingReplacement` means a bound live episode has no authorized removal action yet; `pendingCleanup` means its removal action is planned but not confirmed; `resolved` means retained deferred-carry evidence exists but no live deferred obligation remains; `unavailable` means the summary cannot be established. Clients use only the current whole status or attach snapshot and treat an absent or stale readout as `unavailable`. This summary grants no cleanup, history, provider or release authority and uses the existing operation and carry bounds under Deferred carry release. Standalone status exposes the same readout inside its expanded `stateSafety` document, without mutation.

### Agent session delivery

**Context block.** The lossless codec prepares the final tagged block from verified payload bytes, with raw diff/state values preserved through the provider boundary. TypeScript and the provider adapter pass that block as opaque text. Every turn the runtime sends carries one runtime-authored context block as the first content block of the player's message, and the player's text verbatim as the second. The block is the tag `<companion-turn-context>`, one compact JSON object, and the closing tag. The object has exactly:

```jsonc
{
  "companionTurnContextVersion": 1,
  "interactionId": "...",
  "requestReceivedAt": "...",
  "sessionOpening": false,           // true on the first turn of an agent session
  "freshness": { "state": "fresh", "class": null, "reason": null, "lastGoodGeneratedAt": "..." },
  "operational": { "state": "current", "warnings": [] }, // unknown | current; independent of events
  "correction": null,                // null | { correctionId, reason }; pending context correction
  "degraded": null,                  // null | "eventTooLarge" | "stateTooLarge"
  "events": [ { "eventId": "...", "sequence": 7, "type": "state.consumed", "redelivery": false, "baselineReset": false, "warnings": [], "diff": { /* 7.2 diff, or null */ } } ],
  "state": { /* 6.1 digest */ }      // or null
}
```

`sessionOpening` is true exactly while the bound session's `turnsCompleted` is 0, and `turnsCompleted` rises only when a turn succeeds and its cursor write, when it has one, succeeds, so a failed first turn leaves the next one opening. `freshness.state` is `fresh` only when the acceptance/context-safety gate permits state-dependent guidance and this interaction's acquisition ended `committed` or `unchanged` and the drain that followed left the receipt's target identity equal to the integrity-verified state of the newest uncompacted state-bearing event, and `failed` otherwise, with the validated class and reason. `replayed` belongs only to a repair's `-Resync` publication; an interaction acquisition carrying that outcome is an invalid checked result, diagnosed as class `supervisor` and reason `result-invalid`; its armed intent remains unresolved, so no context block reaches the provider until safety reconciliation. Under a journal fault it is `failed` with class `journal` and the fault code as its reason; and when the acquisition succeeded but the journal could not take its record (a read or write failure in the drain, outside a repair), it is `failed` with class `journal` and reason `journalUnavailable`, with `lastGoodGeneratedAt` from the newest journaled state. `journalUnavailable` is an interaction-level reason, not a fault: it is neither stored nor derived, the journal state stays as it is, acquisitions continue (the core's 16-record pending bound is the backstop), and it clears with the first drain that appends the record. `state` is the digest of the newest uncompacted state-bearing event admitted by the acceptance gate, never an older fallback when the newest is unresolved, and is wanted exactly when `events` is non-empty, `sessionOpening` is true, the session's `needsState` flag is set, or a context correction is pending. `needsState` is set when an agent session starts, whenever the provider reports a context-compaction boundary, and when a turn whose block dropped a wanted state (`degraded: "stateTooLarge"`) succeeds; it is cleared when a turn that carried `state` is acknowledged, unless a boundary was reported during that same turn. For a turn that dropped a wanted state, `agent-session.json` is written with `needsState` true before the cursor write, and when that write fails the turn's success acknowledges nothing, exactly as a failed cursor write does, so the event rides again and the state stays wanted. A provider without the compaction capability leaves it permanently set. The paths that already keep the flag right are unchanged: a provider without compaction boundaries (permanently set), an opening turn (set at session start), a named resume (bound with it set), a startup resume and a reconnect (each binds it true, because the runtime cannot know whether the provider compacted the transcript before a crash lost the binding write, at the cost of one state block per resume), and a `header` or `cursor` repair (its `resync` is a new event, so the state is wanted through `events`). An opening turn leaves `turnsCompleted` at 0 until state-dependent guidance is permitted and its block carries state: freshness must be fresh, positive acceptance and the safety-generation fence must hold, operational status must be current without a reaper-limit warning, and degradation must be null. A successful disclosure-only turn does not consume the opening brief. After a permitted opening turn and its required writes succeed, later turns follow the ordinary completed-turn counter rule.

The block is capped at 4,194,304 UTF-8 bytes. Once acceptance and context safety permit delivery, the following ladder makes progress under that cap; unresolved data instead follows the disclosure-only gate:

1. All unacknowledged events in ascending sequence, with the state when it is wanted, if that fits.
2. Otherwise as many events, in order, as fit with the state; the rest ride later turns, still unacknowledged.
3. If the first event alone does not fit with the state, that one event is sent with `diff: null` and `degraded: "eventTooLarge"`, with the state when wanted.
4. Otherwise, when level 3 does not fit, the block carries `state: null`, with the first unacknowledged event, if there is one, sent with `diff: null`, and with no event otherwise; `degraded` is `"stateTooLarge"` when a wanted state was dropped and stays `"eventTooLarge"` when no state was wanted. If that block still does not fit, the event's `warnings` is replaced by an empty list; a block with one header-only event and no state always fits the cap.

`degraded` therefore has a bound meaning: `stateTooLarge` says a wanted state was dropped, and `eventTooLarge` says the first event's diff, and at the floor its warnings, were dropped.

A degraded turn still acknowledges its carried event when it succeeds and all required durable acknowledgement writes succeed: the instructions require disclosure that some change details or wanted state were omitted. The disclosure discharges only that event, never omitted state or correction, and never establishes which component exhausted a provider window. With no event, it acknowledges nothing. A wanted state omitted by the deterministic byte cap leaves `needsState` set; recomputing the cap on each submission keeps disclosing the omission while the same wanted state still cannot fit. A new agent session does not change this local cap. A digest admitted by the core under its 8,388,608-byte budget can exceed the 4,194,304-byte block budget and remain undeliverable until the admitted content changes enough to fit, an accepted residual with no client-side remedy. Provider-window recovery below is separate: neither a provider rejection nor success without state proves whether that state can fit.

**Provider-window recovery.** Recompute the deterministic byte ladder from current admitted data on every submission. The player text remains verbatim outside the block cap; no additional input-size limit, automatic resend, splitting, summarization, transcript editing or failed-message deletion is introduced. A current provider result of `prompt_too_long` fails that turn with `contextExhausted`, acknowledges nothing and establishes only that its combined input did not fit. Neither that failure nor a successful state-omitting request identifies the limiting component or proves that omitted state cannot fit. Failed-message persistence and provider history remain opaque.

Recovery is bounded volatile advisory metadata for the currently bound logical session. Retain at most two variants, ordinary and the configured one-question override. Each holds the current verbatim-text fingerprint, effective provider-configuration fingerprint, next descending shape, shared failure count from zero through four (reported as `descendingFailures`), at most four failed candidate fingerprints from ordinary or disclosure attempts, one failed revalidation-candidate fingerprint or null, the last failed ordinary ladder block's byte count or null and its compaction observation, the exhausted disposition, and one state-bearing revalidation allowance plus its last observed relevant-change fingerprint or null. Use SHA-256 with unambiguous length framing for fingerprints, preserving exact player-text bytes and effective provider/model/effort/options; retain no extra transcript or historical questions. Equal ordinary and override configurations share progress. Changing text or effective configuration starts that variant at shape 1 with zero failures, no failed candidates, null failed-byte/revalidation/relevant-change fields, the current compaction observation, an unexhausted disposition and one unused allowance. A matching ordinary ladder failure updates its byte count, compaction observation and relevant-change fingerprint observed at that send; a failed revalidation records only its separate candidate fingerprint and leaves those ordinary ladder fields unchanged and consumes no additional counted failure. These fields share the episode's existing reset and invalidation lifecycle. Selecting the override preserves the ordinary variant; reverting restores it. A new event, changed source hash, acknowledgement, successful delivery, routine save or freshly minted interaction never resets an unchanged text/configuration episode.

The four descending shapes are: (1) the current byte-cap selection; (2) the largest ordered event prefix fitting half the last failed block bytes, retaining the wanted state and at least the first event where feasible; (3) the first event with its diff omitted and the wanted state, or the wanted state alone when no event remains; (4) no state and at most the first event header, dropping its warnings only when necessary to meet the byte cap. All shapes retain complete `operational` and `correction` values. The existing degradation meanings and byte-cap fallback apply. Skip an infeasible shape, a shape equivalent to a failed candidate, or a shape that does not reduce the failed candidate; skipping does not send a request or consume a failure. If no smaller candidate exists, the descending path is exhausted. After each matching ordinary ladder `prompt_too_long`, record the failed candidate, increment the shared failure count once and advance the shape monotonically. Ordinary and disclosure failures together never exceed four in that episode. Success leaves the next shape and count unchanged; another failure reason leaves them unchanged too. An exhausted unchanged episode is refused unsent with `contextExhausted` unless its one revalidation is eligible. Acquisition and safety admission still precede that selection, so a pending obligation is retained even when no provider input follows.

A settlement-pending disclosure is classified explicitly for its attempt from the admitted snapshot, and reclassified from the actual send-time fallback when that replaces a prepared block. It is outside the four shapes: in an unexhausted episode with fewer than four counted failures, admit its one non-state candidate without the ordinary next-shape or failed-byte comparison, provided its fingerprint has not already failed. An equivalent failed disclosure is refused unsent without exhausting otherwise available ordinary progress; an already exhausted episode also refuses it unsent. A real `prompt_too_long` on it records its fingerprint and increments the shared failure count, exhausting at four, but leaves the ordinary next shape, failed bytes, relevant-change baseline and compaction baseline unchanged. Success or another failure changes none of those fields and never consumes the state-bearing revalidation allowance. The classification belongs only to that immutable attempt: preparation and send-time replacement supply it, retryability inspection uses the same rule, cancellation or terminal completion drops it, and stale instance results cannot use it. Absent classification takes the ordinary rule; inconsistent classification, including a state-bearing disclosure, fails closed. It grants no acceptance, acknowledgement, opening-counter or correction authority.

Candidate comparison is codec-owned and semantic, without rewriting transmitted or validated bytes. Ignore runtime interaction IDs and request times, redelivery bookkeeping, source/event identity and timestamp churn that changes no substantive content. Preserve distinctions in game-state values, event type/order/content, baseline-reset notices, warnings, freshness classification, correction, instructions and effective provider options. Fingerprinting must not coerce raw state numbers or strings through a lossy TypeScript JSON round-trip. A changed digest hash or event ID alone is never evidence of reduced content or a refund. Required operational or correction fields are never removed to create a smaller candidate. With no event, equivalent state-only shapes are skipped; with no wanted state, equivalent header-only shapes are skipped. Once a header-only candidate has failed, do not repeatedly send its equivalent.

After a prior window failure, an observed compaction boundary or materially changed admitted state/content can make the unused revalidation eligible on the next player submission. Use it only when a wanted state-bearing candidate fits the local byte cap and differs materially from the last failed candidate, or compaction changed the history observation. It selects the best current state-bearing byte-cap candidate once, before returning to ordinary descending selection. Consume the allowance at actual provider send, regardless of outcome; absent state, byte-cap exclusion, safety refusal or failure before send does not consume it. A failed revalidation returns to the prior reduced or exhausted disposition without a new descent, a new allowance or a component-level diagnosis. A successful revalidation uses the normal delivery and acknowledgement rules, then returns to the saved descending disposition without replenishing it. Thus the episode permits at most four counted ordinary or disclosure failures plus one revalidation failure, and every attempt requires a player submission. Repeated saves or compactions never replenish the allowance.

Capture variant, episode and provider-instance identity with each send; only its matching current terminal result updates recovery. Ignore late results from ended instances. Override setup/revert and acknowledgement ordering remain as specified in the provider mapping: an unsent setup failure consumes no window attempt, and a failed revert cannot undo a completed acknowledgement. Compaction invalidates previous fit observations and sets `needsState`; it proves neither an empty transcript nor removal of a failed message. Preserve both variants across a subprocess reconnect to the same logical session, including `overrideReset`, while rebinding `needsState` true. Explicit replacement initializes fresh variants without acknowledging events. A switch to a different indexed logical session discards the old volatile variants and initializes unknown fit evidence for the selected session; resuming the already bound session preserves them. Runtime restart may re-pay the bounded ladder from shape 1 even when resuming history, without claiming that history is empty. Shutdown discards advisory metadata only; durable obligations remain.

Absent metadata permits only an initial bounded attempt after ordinary admission. Stale fit observations give no success guarantee and do not refund attempts. Inconsistent internal metadata fails visibly as an unsent `providerError` and marks recovery unavailable until logical-session replacement or runtime restart; never silently initialize over it. Recovery metadata cannot grant acceptance, choose older state, clear `needsState`, consume the opening brief, advance the cursor or discharge correction. Cursor, binding, safety and correction writes retain their existing success/failure ordering. Settlement-pending disclosure supplies no fit evidence and no reset; a `prompt_too_long` on that disclosure still counts against the matching episode and can exhaust it, with all obligations retained.

All consumers use this same episode: `submitChat` chooses text/configuration identity, post-acquisition preparation chooses admitted candidates, send/result handling updates only the matching attempt, and compaction, override, session binding, acknowledgement, failure and status/attach/text-client paths preserve these rules. `turn.failed` reports whether another attempt is currently permitted, not a prediction that it will fit. On exhaustion explain that the attempted combined input exceeded capacity; changing the question, an available model choice or an explicitly requested new session may help, but none is guaranteed. Replacement cannot fix text already too large for an empty session or the local block-cap residual. The runtime never replaces a session merely for window exhaustion.

**Agent-session binding.** `agent-session.json` is exactly `{ "agentSessionVersion": 1, "providerId": <string>, "providerSessionId": <string>, "createdAt": <string>, "turnsCompleted": <integer>, "needsState": <bool>, "instructionsSha256": <string>, "stateGeneration": <token> }`. `stateGeneration` is the context-safety generation token, with the exact grammar and lifecycle above; it is copied unchanged into every index entry. `instructionsSha256` covers exactly the bytes the runtime appends to the system prompt, in appended order (see Instructions below). Beside the binding, `agent-session-index.json` is exactly `{ "agentSessionIndexVersion": 1, "sessions": [ <entry> ] }`, each entry carrying the binding's fields with the same grammar plus string `lastBoundAt`; it holds at most 32 entries, evicting the oldest `lastBoundAt`, and is written through the same discipline on every `agent-session.json` write, with the current binding upserted. Write the binding first and index second; no provider input follows until both are durable. A crash with only the binding written resumes only after reconciling that binding against current safety and republishing its matching index entry. An index-only older binding remains subject to the same generation gate; neither file grants authority to reset safety. Every startup, reconnect and named resume first requires valid context safety and a binding whose `stateGeneration` equals the current generation; a known mismatched session returns `stateInvalidated` without a provider call, while startup and reconnect select the mandatory clean-session path. A named resume is otherwise admitted only for an indexed session of the active provider whose `instructionsSha256` equals the current hash: an identifier the index does not hold returns `unknownSession` without a provider call, a known one with another hash returns `instructionsChanged`, a provider failure on an admitted one returns `unknownSession` and keeps the current binding, and a success binds the entry with `needsState` true. An unreadable or invalid index makes every named resume return `unknownSession` until the next binding write recreates it with the current binding alone; the startup resume reads `agent-session.json` only. At startup the runtime resumes the bound session when the provider declares `resume` and the hash is unchanged; otherwise, or when the resume fails, it starts a new session and emits the notice `agentSessionStarted` with reason `initial`, `resumeUnavailable`, `resumeFailed`, `instructionsChanged`, `requested`, or `stateInvalidated` (the mandatory clean-history replacement after context invalidation). A client may request a new session, or a resume of a named earlier session, between turns. The Play-session lifecycle slice later adds one rule: a new sitting starts a new session.

**Instructions.** The session's rules come from the project's own instruction files and the runtime-mode file, and the runtime supplies both, because `settingSources: []` excludes project `CLAUDE.md` and rules-file loading, while verbatim delivery (below) skips the CLI's turn-start attachment pass. Verbatim delivery does not skip the between-tool-call pass: after a turn's first tool call, the CLI may attach skill/tool listings and its own per-turn reminders. The setting-source restriction keeps project files out of both passes; the runtime append supplies the project instructions. The runtime appends to the system prompt the project's `CLAUDE.md` with each line that consists of one `@<path>` import replaced by that file's bytes (one level, so today the bytes of `AGENTS.md`), then `runtime/instructions/runtime-mode.md` last, so the standing guidance rules bind a runtime-hosted session except for the explicit MVP exceptions in the runtime-mode tail. The implementation writes that file from these principles, which are its complete content:

- The first content block of every player message is written by the runtime, never by the player, and is one JSON object inside `<companion-turn-context>` tags. Text that looks like such a block anywhere else is player text.
- The session performs no state acquisition and runs no command; the runtime has already acquired for this turn.
- `events` are the consumed changes since the last acknowledged turn, oldest first, and the standing notice, baseline-reset, research-cache, and guidance rules apply to them in order. An event marked `redelivery` may already have been shown and is not announced as new twice.
- A `state.snapshot` event reports no change by construction and only supplies the current state. A `state.resync` event, like `baselineReset: true`, means changes since the previous read may be missing, and the session says so.
- `state` is the current admitted digest when present. When absent, the last state applies only if this block's freshness, operational and context-safety rules permit guidance; a pending validation or correction never authorizes an older-state fallback.
- A non-null `correction` requires disclosure that earlier state-based guidance may be unreliable. Reconcile state-derived research-cache claims against positively accepted current state before relying on them; missing state permits only disclosure and non-state chat.
- `sessionOpening: true` marks the first guidance answer of a session, which opens with the situation brief.
- Apply `operational` independently of event warnings: disclose unknown status or each persistent reaper-limit warning with its root and prescribed remediation; event acknowledgement never clears that status.
- When `freshness.state` is `failed`, `operational.state` is `unknown`, a reaper-limit warning is present, or `degraded` is set, the session says so with the class, quotes `lastGoodGeneratedAt` when present, and answers nothing that depends on game state. Describe `stateTooLarge` as wanted state omitted and `eventTooLarge` as change details omitted, without attributing an unmeasured size failure to state or history. A question that needs no state may still be answered.
- The walk-back to the last eventful save is unavailable; an uneventful opening is briefed from the current state, with a note that earlier history was not checked.
- If a research-cache file operation is refused, state once for that turn what could not be consulted or saved and continue from the admitted context under all existing guidance and safety rules. Attempt no further cache operation that turn. Skip unavailable loadout or enrichment persistence rather than queueing it; never claim an unsuccessful cache read or update succeeded. The next turn may try again, and successful cache access follows the standing cache rules.
- Issue file tools sequentially and await their completion; a refused operation is final for that turn and is not retried through another path or tool. A cache refusal alone does not end the answer.

#### File-tool object admission

Tool authority is separate from runtime-data ownership. Every direct Read/Edit/Write target and every Grep/Glob traversal target must satisfy this contract before content access or mutation. Check path grammar, the admitted physical companion or memory root, each existing ancestor and the final object with component containment, not string-prefix matching. Reject redirected ancestors/targets, wrong object kinds, and ambiguous Windows namespace, device or alternate-stream spellings that cannot be admitted reliably. Existing file targets must be ordinary regular files with a trustworthy link count of exactly one. Apply that rule across every permitted read directory, not merely memory or a particular extension. The existing runtime-data checks do not implicitly cover memory tools.

The private Windows Node v22.23.2 probe establishes that realpath leaves a hard-link alias under its allowed pathname, while fs.stat(path, { bigint: true }) exposes nlink/dev/ino for the demonstrated files; both forbidden-source aliases had link count 2 and admitted path predicates. It does not establish complete reparse detection or SDK tool behavior. Admission requires supported non-following platform metadata for redirection and object-kind checks, and reliable identity/link metadata for existing files. Unsupported, unreadable, inconsistent or unavailable metadata denies the operation. Admission never follows, copies, unlinks or replaces an unsafe target to make it admissible.

Absence is distinct from invalidity. Missing Read/Edit targets and missing search roots are refused without creation. An absent Write leaf may proceed only below a freshly admitted ordinary parent, with an unambiguous safe leaf and a pinned-provider creation path verified to preserve the boundary. Missing intermediate directories require checked component-by-component creation and revalidation; if the native operation cannot provide that, refuse it. A target appearing or changing before use requires new admission; an earlier absent result is not permission for the new object. FileWriteInput alone supplies no exclusive-create guarantee.

A single-file Grep uses direct file admission. Directory Grep and Glob require admission of the root and every potentially traversed descendant before the native call, including hidden entries and nested aliases, not merely returned matches. A path-selecting Glob pattern and Grep file filters must stay within that root; Grep's content regex is not a path. A conservative preflight inspects the entire selected subtree and refuses the call if any entry is unsafe or unverifiable, so it need not rely on undocumented ignore/traversal behavior. Glob is an enumeration operation, not a claim of file-content reading, but its traversal and returned targets remain confined. Post-filtering results cannot repair a forbidden read.

Each admission scan is bounded to 8,192 inspected entries, 64 descendant-directory levels and 5,000 milliseconds of monotonic elapsed time. The retained paths and required kind, identity, link and redirection metadata must also fit the config byte/token/decoded-text profile in their bounded serialized representation; arbitrary filesystem-error text is not retained as metadata. Charge an entry before retaining or descending into it. An incomplete scan, exceeded limit or failed metadata operation denies the whole call without partial results. A timed-out preflight loses permission permanently; a late continuation cannot allow it or mutate files. If its metadata work has not actually stopped, retain the guard until that work ends rather than accumulating new scans.

The supported tool namespace has one cooperating runtime owner per physical companion root, with no uncoordinated host namespace replacement during an admitted operation. chat takes a separate process-lifetime named-pipe ownership guard before enabling file tools: its name is `\\.\pipe\game-companion-file-tools-<digest>`, where digest is the first 32 lowercase hexadecimal characters of SHA-256 over the strict UTF-8 bytes of the lowercased admitted canonical companion-root path. There is no empty-root form; failed root admission denies file tools before guard creation. It carries no client transport. Only one such owner exists per companion root, even when different identity-scoped runtime-data directories exist. An unavailable or contended guard denies file tools; other tool decisions and state delivery retain their existing rules. Acquisition of the pipe alone is not proof that an earlier provider's admitted work ended.

Within that ownership, one volatile file-operation guard coordinates all provider instances and all five file tools from preflight through actual completion. Its states are unavailable, idle, preflight, permitted and uncertain; preflight/permitted/uncertain bind the exact provider instance and SDK tool_use_id without normalization or reminting. Initialize unavailable at runtime start and enter idle only after namespace ownership and predecessor-provider quiescence are established. Atomically claim preflight before its first asynchronous check. Overlapping requests, including parallel requests in one model turn, receive the fixed denial without modifying the current owner. A preflight refusal clears only its own guard after its work has stopped, because no native operation was authorized. Before returning permission, change that guard to permitted; the canonical validated input and admission evidence belong only to that operation.

A correlated successful or failed completion retires the guard only when the operation and its required footprint/cleanup are known finished. Cancellation, timeout, missing completion evidence or lost communication makes it uncertain; those events, a successful chat turn and a new provider instance never silently release it. Verified termination of the owning provider and its operation descendants may discharge it. Reconnect/replacement keeps file tools denied until predecessor work is known quiescent, then admits each new request afresh. Runtime shutdown retains ownership while work remains and cannot claim clean shutdown on uncertain completion. After a crash, missing in-memory guard state or a newly free pipe is not quiescence evidence: file tools remain unavailable until the provider-process lifecycle establishes that earlier work ended. If that proof cannot be obtained, preserve refusal rather than inventing a clean owner. The metadata snapshots are never persisted or reused as lasting approvals.

These preflight/guard rules address pre-existing aliases and cooperating runtime operations. They do not claim protection against coordinated privileged-host path replacement during an operation. Detected replacement, changed identity/link metadata or lost ordering invalidates the current admission. Supporting an adversarial concurrent host namespace would require a separately verified mechanism and product decision; the file-tool guard is not an OS sandbox. Runtime-data publication retains its own independent ownership and admission rules.

Admit the full operation footprint before enabling it: content reads, existing-target writes, creation, replacement, operation-owned temporary/backup artifacts and cleanup. File-operation staging stays in the permitted write area with checked ownership and object metadata. Re-admit an artifact before removal; absence is harmless, while unreadable, changed or unowned artifacts stay untouched and are reported. Interrupted operations grant no broad residue-cleanup authority. Provider-owned transcript/configuration persistence retains exactly the existing location-bound profile exception; that exception never makes those paths session-tool targets and is not silently expanded by a tool request. Verify and classify the pinned provider's actual auxiliary writes against those existing boundaries rather than inferring their location or ownership from a tool name.

SDK 0.3.289 supplies the mandatory PreToolUse hook with permissionDecision, permissionDecisionReason and updatedInput, and Options supplies hooks and a fixed tools list. Use that pre-tool boundary to deny or pass a validated canonical input; canUseTool is not its substitute. Correlated PostToolUse/PostToolUseFailure can supply lifecycle observations. PostToolUse.updatedToolOutput exists for all tools, but replacement of output after execution cannot prevent the original read or undo a write. The declared interfaces supply neither an admitted file handle nor a callback for each descendant open. Therefore the relevant operation remains refused unless the pinned SDK's hook ordering, error/timeout behavior, traversal/creation and complete mutation footprint have been verified to uphold this contract. A failed verification supplies no permission. Do not restore functionality by silently adding MCP tools, aliases, redirected profiles or a custom filesystem provider.

The runtime-mode instructions tell the session to issue file tools sequentially and await completion. A refusal stays final for the turn. Admission/reconnect/cleanup failures use the existing fixed denial, without a permission prompt or a new capability claim.

A dialog answer names, per question, the chosen labels or the player's own text. A provider declares exactly six Boolean capabilities when it starts, and the runtime never infers one from behavior: `streamingText`, `dialogs`, `resume`, `interrupt`, `questionOverride`, and `compactionBoundaries`. A missing capability disables only its own operation, visibly: without `streamingText` a client gets only `turn.completed`; without `dialogs` the question tool is denied; without `resume` every start is a new session; without `interrupt` or `questionOverride` the operation returns `capabilityUnavailable`; and without `compactionBoundaries` the runtime sends the state in every turn, because it cannot know the state survived. The contract never emulates a missing capability.

### Claude Agent SDK provider

The first provider wraps the package `@anthropic-ai/claude-agent-sdk`, pinned to exactly 0.3.289. Every API citation in this subsection was checked on 2026-10-05 against that version installed in a scratch directory: its type declarations (`sdk.d.ts`, `sdk-tools.d.ts`) and its package manifest. How the running executable behaves is a separate matter, covered by the live-claim lines under [Verification](#verification). Facts that shape the design: the package requires Node 18 or later; the Claude Code executable arrives as an optional platform dependency (about 250 MB unpacked for Windows x64); and the earlier "V2" session functions were removed, so `query()` with a streamed prompt is the one session interface.

The runtime programs against a small internal provider interface, never against the package. It has exactly six operations: start a session, new or resumed by id, which declares the six capabilities and yields the provider's session id; send one turn (context block, player text, and an optional model override), which yields text fragments, dialog requests, compaction boundaries, current provider source-metadata observations, and exactly one terminal completion or failure; interrupt the running turn; close the session; verify that an owned session remains live with exact process identity and is neither closing nor ended; and notify the runtime when the provider's process exits. The declared alternates implement the same six operations with their own capability declarations. For this provider the mapping is:

**Failure-signal policy.** For a correlated failed result after the interruption and `prompt_too_long` checks, classify the latest top-level assistant error under the pinned SDK 0.3.289 `SDKAssistantMessageError` union. `authentication_failed`, `oauth_org_not_allowed` and `cloud_credential_error` yield `authenticationFailed`; `rate_limit` and `overloaded` yield `rateLimited`; `account_on_hold`, `verification_required`, `billing_error`, `invalid_request`, `model_not_found`, `server_error`, `unknown` and `max_output_tokens`, as well as an absent or newly unknown error value, yield `providerError`. The ordinary failed-result path is retryable for a fresh player submission when normal admission returns, never an automatic resend; the incompatible current initialization path retains its separately stated non-retryable `providerError`. A `rate_limit_event`, including `rate_limit_info.status: rejected`, is metadata, not by itself a terminal failure or a replacement for a correlated assistant error. `api_error_status` alone, including 401 or 429, does not override the observed assistant-error mapping; a failed result with only that status is conservatively `providerError`. `blocking_limit` is a context-window blocking reason and `rapid_refill_breaker` is compaction thrashing in the pinned CLI; neither is evidence of subscription quota, and a failed result with either reason but no mapped assistant error remains `providerError`. An interrupted result stays `interrupted` before any of these classifications, emits no second terminal if the host already ended the turn and never acknowledges. This policy matches the current `ClaudeProvider` classification and the installed SDK/CLI source; the dated probes observed `prompt_too_long`, `blocking_limit` and `aborted_streaming`, not live authentication or subscription-limit failures. The linked provider evidence now records a passing synthetic fake-stream classification sweep for the pinned SDK error set. That sweep does not establish live authentication or subscription-limit emissions, and the remaining end-to-end failure and acknowledgement checks stay open.

The provider leaves session persistence at its default, which stores transcripts in the Claude configuration directory under the user profile. It keeps the default profile, so isolation is achieved by the switches above and not by a separate configuration directory, which would also hide the stored login; the consequence is that the executable maintains its own state in the two profile locations the storage section bounds.

**Provider exit classification.** The internal exit reasons are exactly `subprocessExited`, `overrideReset`, and `providerUnavailable`. `ClaudeProvider` emits the last for a current incompatible or uncorrelated initialization, immediately cancels tool/dialog admission and closes its process. `ProviderLifecycle` initializes its incompatibility latch false per runtime lifetime, sets it only for that current-instance reason, clears the source readout, prevents binding proof and all start/resume/replacement/reconnect attempts, and retains it until a new runtime lifecycle is constructed. Shutdown still verifies process/tool termination. A stale instance's exit cannot set it. `SessionHost` receives reconnect callbacks only for the first two reasons; its existing failed-provider checks reject chat and session control for the last. The public turn-failure vocabulary remains unchanged: the affected turn uses non-retryable `providerError`, and no acknowledgement or extra terminal event follows. Public `sessionReconnected` notices keep only the two recoverable reasons; the text client and attach/status consumers observe the existing `failed` state.

**Reconnect.** Context invalidation takes precedence: it never resumes an old-generation session and instead follows the clean-session path above. A validated pending-check process block also forbids reconnect. If its current provider subprocess exits after the block is established, verify predecessor termination and safety authority, permit transient `reconnecting` status while those checks run, then set provider status `failed` without starting the 1/5/30-second retry ladder or another provider process. Preserve the block, durable obligations and window episode; emit no second turn terminal or `sessionReconnected` notice and resend nothing. A later otherwise-valid `submitChat` still returns `notReady` ahead of the provider's failed state until another process start reconciles safety. When neither invalidation nor this block applies, a subprocess exit ends the in-flight turn, if any, as `turn.failed` with `subprocessExited`, and begins a same-session reconnect ladder. Reconnect makes exactly three attempts, each after its 1-, 5-, or 30-second delay, with no immediate attempt. A successful attempt starts a fresh subprocess resuming the same session, binds `needsState` true, and emits `sessionReconnected` with reason `subprocessExited`, or `overrideReset` when the provider ended the process itself after a rejected question-override call (see the provider mapping). After all three attempts fail, the provider state is `failed` and chat is rejected with `providerUnavailable` until the next start. A fresh provider start instead attempts immediately before those three delayed retries. Same-logical-session reconnect preserves ordinary and override window-recovery episodes; a mandatory clean-session replacement initializes them. The runtime never resubmits a player's message on its own. The unacknowledged state events ride whatever turn comes next.

**Authentication.** Decided 2026-10-05: the chosen route is the existing Claude Code subscription login on the default profile, with a successful real request under that setup required before implementation relies on it. Authentication stays provider-owned, and the runtime never reads, stores, copies, or forwards a credential: the provider starts the executable with the runtime's environment and default profile and uses whatever credential the executable resolves.

- Evidence for the route. Non-interactive Claude Code processes on this machine have inherited the stored login with no setup, on 2026-09-17 and 2026-09-26 in the Nightshift project's records (that the stored login was the credential used is inferred there from the code injecting none). The probe below establishes a working SDK request under the same default-profile setup; identification of the precise non-API-key method remains an inference.
- The probe. One SDK session sends a one-word real request and records the credential source the `init` message reports. A logged-in status check is not accepted as proof; in Nightshift's testing it passed while a real request failed. Probed 2026-10-05 before implementation: a 0.3.289 session started with the default profile and no injected credential reported `apiKeySource: "none"`, which means no API key was reported, and completed the request. That value is consistent with the chosen subscription login but does not distinguish it from a bearer token or third-party authentication; the result proves a working request on the default profile, not a unique credential-kind classification. The production-provider probe repeated that successful default-profile request on 2026-10-08 and again observed `none`; the same classification limit applies.
- If the probe fails, the route becomes a long-lived token created once with `claude setup-token` and supplied as `CLAUDE_CODE_OAUTH_TOKEN`, which authenticated an empty profile on this machine on 2026-09-29. No design change is needed, because the provider only passes the environment through. The credential file is never copied: copies expire or race refresh-token rotation.
- The open point. The Agent SDK overview states that, unless previously approved, Anthropic does not allow third-party developers to offer claude.ai login or rate limits for their products, including agents built on the SDK, and points them to API-key authentication. This runtime is a single-user personal tool that offers nothing to a third party; the owner has chosen the login route knowing that statement. An API key in the environment remains a working alternative with no design change.
- A correlated assistant error `rate_limit` or `overloaded` maps a failed turn to `turn.failed` with `rateLimited`; a standalone SDK rate-limit event or result API status is not enough to assert that classification. The precise signal of a live subscription-limit request remains provisional until observed. Status shows the SDK-reported API-key source; `none` leaves the non-API-key method unspecified. This is a truthful source readout, not a credential-kind classifier, and changes neither the chosen login/token route nor the prohibition on credential access.

`provider.credentialSource` retains its existing field name and is a string or null containing only current SDK-reported API-key-source metadata, never an inferred authentication kind or a `tokenSource` fallback. Before the current provider has supplied that metadata, and when it is replaced or reconnecting, it is null and the client renders `unavailable`. A current initialization reply's `account.apiKeySource`, when supplied, initializes it; a subsequent current `system/init.apiKeySource` supersedes it. Ignore metadata from an ended provider instance. Render `none` as no API key reported, with the non-API-key method unspecified; render the SDK's other current or legacy strings verbatim as source labels, without inventing stronger meanings. Provider fixtures cover unavailable metadata, `none`, synthetic other labels and replacement/rebind; other declared current and legacy source labels and source clearing across a real reconnect remain unasserted. The runtime never reads environment credential values or credential stores to fill the gap.

**Guarded startup candidate.** Chat alone may invoke the same `ClaudeProvider.start` or resume call after guarded phases A through C and before D through H complete, with an optional startup cancellation signal; ordinary callers without the signal keep the existing behavior. This candidate is not yet bound to `ProviderLifecycle` or the runtime. It receives no state, question, tool permission or client and cannot become current or make provider status ready. The controller creates the cancellation token before the call, observes rejection immediately, owns the pending promise and either transfers its exact settled session after all phase-I checks or cancels it. Cancellation is checked after awaited prerequisites and before SDK query or process spawn, abort observation is registered once a session exists, and a cancelled call cannot spawn later or resolve into a transferable session. On any startup refusal, owner change, changed instructions or generation, or guard loss, mark cancellation before awaiting, allow at most 60 seconds for settlement, close a late session and positively prove its scoped provider job absent. Unknown settlement or stop keeps the guard while the process lives and blocks status-only attachment and clean marker. A crash leaves predecessor admission to find a survivor. The complete selector, failure and timing contract is in [integrated startup execution](runtime-startup-execution-30.md#guarded-unbound-provider-initialization).

**Final provider proof.** The initial and final instruction reads admit ordinary singly linked source files, read bounded bytes, re-admit exact identity and re-read identical bytes. Before `backend.startup` enters its serial queue, chat may directly call `sessions.readBinding()` and `backend.safety()`, which read `agent-session.json` and `state-safety.json` without queue entry or mutation. Positive absent binding with valid safety and no pending check, correction or witness selects fresh initialization; a valid binding under the same safety may select exact resume only when provider, instruction hash, capability and generation match. Known binding mismatch selects fresh; invalid, unreadable or uncertain binding or safety, and valid safety with a pending check, correction or witness, select no prestart. The final phase I still calls the full `providerSafety`, including recovery and authority reconciliation, and may discard the candidate. After D through H, final instructions and `providerSafety` decide the lifecycle. A candidate with mismatched instruction hash or resume id is closed and proved absent before normal start. An exact candidate is usable only after one request-local `ProviderSession.verifyLive` observation of matching PID and creation identity in the scoped job, neither closing nor ended; observe exit before use and recheck after durable binding and immediately before client readiness or send. Closing, exit, guard, scope, owner or generation change, expiry and ambiguous native query invalidate that fact. The final phase-I checks still control all provider input, binding, session notices, namespace ownership and tool use. An unbound candidate never discharges state, settlement, journal, safety or recovery obligations. The real SDK's default-profile write footprint and absence of model input/tools during initialization must be independently verified before shipping this path.

### Status surface

The status surface is one value, sent whole on every change:

```jsonc
{
  "consumer": "owner",               // owner | notOwner | unknown (before the first acquisition)
  "freshness": { "state": "fresh", "class": null, "reason": null, "lastGoodGeneratedAt": "...", "checkedAt": "..." },  // unknown | acquiring | fresh | failed
  "operational": { "state": "current", "warnings": [] }, // same object and lifecycle as the turn context
  "stateSafety": { "state": "ready", "correction": null, "carryRelease": "none" }, // carryRelease: none | waitingReplacement | pendingCleanup | resolved | unavailable
  "journal": { "state": "healthy", "fault": null, "unacknowledgedEvents": 0 },  // healthy | repairing | fault
  "capacity": {
    "runtimeMarker": { "state": "admitted", "reason": null, "dimensions": [] },
    "release": { "state": "admitted", "reason": null, "dimensions": [] },
    "repair": { "state": "unchecked", "reason": null, "dimensions": [] },
    "maintenance": { "state": "admitted", "reason": null, "dimensions": [] },
    "ordinary": { "state": "admitted", "reason": null, "dimensions": [] },
    "owed": { "unacknowledgedEvents": 0, "pendingOutboxRecords": 0, "unfinishedOperations": 0, "protectedHandoffs": 0, "safetyObligation": false, "historyDisclosure": false }
  },
  "watcher": "running",              // disabled | running | restarting | stopped
  "provider": { "state": "ready", "credentialSource": "..." },  // starting | ready | reconnecting | failed
  "windowRecovery": null,            // null before a submission; live bounded summary below
  "previousShutdownClean": true
}
```

`windowRecovery` is null before a current-session submission; otherwise it is exactly `{ variant: "ordinary" | "override", state: "ready" | "exhausted" | "unavailable", descendingFailures: <integer 0..4>, revalidationAvailable: <Boolean> }` for the last selected variant. Ready means descending selection is not exhausted, not that a request is known to fit; exhausted can still have an unused allowance whose eligibility needs fresh acquisition. Unavailable means inconsistent advisory metadata and permits no send. The live status and attach snapshot read the same in-memory summary and emit changes after selection/results, compaction and binding transitions. They never expose text/fingerprints or mutate recovery. Standalone status does not expose a live `windowRecovery` value: it renders recovery information unavailable and never reconstructs it from persisted transcripts or counters. The text client uses the same conservative failure explanation and never represents an allowance as an automatic retry.

`capacity` is a volatile fixed-cardinality object with exactly the five transition keys shown plus `owed`, in that order. Each transition value has exactly `state`, `reason`, and `dimensions`. It is not persisted authority, a new journal fault, or permission to bypass the next preflight. `state` is `unchecked`, `admitted`, `unavailable`, or `exhausted`. `reason` is null except when unavailable; then it is one of `inventory`, `documentInventory`, `additions`, `recoveryAuthority`, `stateSafety`, `reservation`, `publicationScope`, `scopeAuthority`, `eventFinalization`, `unreservedAddition`, `workspace`, `codecScope`, or `otherAuthority`. The last code is the fail-closed rendering of an unrecognized or unclassified dependency, never a claim of exhaustion. `dimensions` is an empty array except when exhausted; then it is a nonempty, deduplicated array in the fixed order `uncompactedEvents`, `retainedHandoffs`, `fullTerminalOperations`, `quarantineFiles`, `freeSpace`, `documentBytes`, `documentTokens`, `documentText`, `operationFinalizationBytes`, `operationFinalizationTokensOrText`, `operationFinalizationDocument`, `otherResource`. Map per-document `:bytes`, `:tokens`, and `:text` to their corresponding bounded categories; a previously unknown exhausted dimension maps to `otherResource`, not an arbitrary filename, path, or text. If exact internal evidence has more entries, normalize and deduplicate every entry before rendering; never silently truncate the set or render a partial list as complete. This is classification for presentation; the internal admission decision retains exact document-specific evidence. There are at most twelve public dimensions per slot and no free-text or unbounded collection in this field.

**Capacity assessment ownership.** The five slots bind to concrete transition sources, not to a target filename or whichever reservation happens to be latest when an asynchronous failure returns. `runtimeMarker` owns all three `runtime.json` publication sites: the pre-kernel phase-C bootstrap, the watcher persistence callback, and shutdown, each with its own captured marker reservation; the earlier bootstrap scope binding remains phase-B data-root admission and does not fabricate a live capacity slot. `release` owns startup release-control reservation and both `consumer runtime` hand-over and `consumer bridge` release, including their intent, core-result, safety, cursor and completion publications; `repair` owns new and resumed repair plans, prerequisites, resync, recovery acceptance and finalization; `maintenance` owns the bounded retention, compaction and authorized cleanup pass; and `ordinary` owns ordinary acquisition, outbox drain and settlement, context preparation, sent mark, acceptance, acknowledgement and ordinary safety/session-binding/index publications. A write shared by these paths belongs to the transition that requested it: repair/release safety, acceptance, cursor or binding writes keep their repair/release owner, while other operation-owned metadata uses its requesting transition. The watcher persistence callback first serializes its marker reserve, preflight and publication with competing capacity work under the held guard and existing publication ordering; it never borrows a mutable latest reservation. If that ordering or its captured marker owner cannot be established, leave the previous runtime record intact, report unavailable `otherAuthority` across the five slots and fail the watcher persistence rather than claim success. Shutdown has no assumed active owner: under the still-held guard, after provider/tool/core quiescence and before its `cleanShutdown` publication, take a fresh `runtimeMarker` reservation and pass that immutable owner through the runtime.json preflight. Verify the resulting metadata and publication helpers quiescent before releasing the guard. A refusal updates that slot, leaves `cleanShutdown` false, and follows the existing failed-shutdown guard/forced-exit rules; it never borrows an earlier release or ordinary owner merely because one was latest. At each reservation or preflight call, capture the immutable transition kind and its source-bound operation/reservation identity before awaiting a publisher, codec or workspace helper; pass that owner through every nested preflight and classify the eventual result against that captured source. Each in-flight helper carries its own captured owner across the existing supervisor, metadata and publication queues; overlap stays within those queues and their existing deadlines, without a new global single-owner assumption. Completion releases that helper's owner and invalidation marks it stale, but an earlier asynchronous catch still uses its own captured source, never a later process-global latest owner. A stale or unprovable owner takes the existing all-five-slot `otherAuthority` unavailable branch. Attribution is never persisted, inferred from a path, or treated as capacity permission after restart. Mandatory acceptance, acknowledgement, safety and binding writes remain required admission boundaries regardless of which slot reports them. The optional sent-mark publication is attributed to `ordinary` for diagnosis, but only its separately specified best-effort fallback can still send the already-admitted turn when the other gates remain valid; later new submissions see the unresolved ordinary refusal.

`capacity.owed` is one shared, non-authoritative, bounded observation with exactly six fields as in the sketch. The four counts are nonnegative safe integers or null: `unacknowledgedEvents` counts the valid uncompacted journal suffix above the valid cursor; `pendingOutboxRecords` counts the complete admitted core outbox inventory; `unfinishedOperations` counts effectively unfinished valid operation records; and `protectedHandoffs` counts distinct handoff identities still protected by the reconciled obligation graph. `safetyObligation` and `historyDisclosure` are Boolean or null, where true means a validated pending duty, false means complete validated evidence of absence, and null means unreadable, absent, contradictory, stale, unscanned, or otherwise unverified authority. A null count likewise means unknown, never zero. Initialize all six fields to null at process start. Refresh each field only from a complete, stable, scope-bound read of its own journal, outbox, operation, safety, or witness/provenance authority under the single writer; a complete resource vector may prove exhaustion even while an owed component remains unknown. On an unavailable capacity assessment, keep only components whose authority was independently revalidated during that attempt and set the rest to null. Any mutation, failed publication, guard loss, or invalidation of an authority sets its corresponding components to null before another status emission; a success in a different transition does not refresh them implicitly. Restart starts unknown and reconstructs only through fresh authority reads. Live status, attach, text-client and operator output render each known nonzero count or true duty and explicitly label every null component unknown; they do not equate all zero/false in a stale or partial snapshot with no work owed. The existing `journal.unacknowledgedEvents` field remains unchanged and is not substituted for this obligation summary when its authority is stale. Standalone read-only status keeps capacity unavailable and reports only its separately validated durable fields, without reconstructing this volatile summary.

After the bootstrap `runtimeMarker` assessment succeeds, initialize its slot to admitted and all other slots to `{ "state": "unchecked", "reason": null, "dimensions": [] }` when the kernel is created. A marker refusal before the kernel exists has no live status: the CLI classifies its typed error, exits nonzero, and a later start assesses the marker again. Each complete assessment updates only its own slot. A success replaces that slot with admitted and clears only its earlier refusal; an unavailable or exhausted result replaces that slot with the corresponding diagnosis before the error reaches the host. A later unavailable result supersedes a previous exhausted result in that slot without discharging its admission obligation. Other slots, and independent journal/safety faults, remain unchanged. Any slot still unavailable or exhausted blocks `submitChat` and new player-input send, except the already-admitted turn's optional sent-mark publication case below, regardless of a success in another slot; the host returns `notReady` before minting an interaction when idle. An unchecked slot alone is not a refusal: its transition still needs a fresh complete preflight before the dependent core call, write, or provider input. This includes ordinary acquisition after a newly admitted interaction. If a prior refusal cannot be safely rechecked in that process, the host keeps chat blocked and directs a safe `chat` or `repair` restart; it does not queue a question. Attach, read-only status, interrupt, shutdown, and safe repair/release commands remain available under their own authority. `/new` and named resume retain their existing provider-safety, session-binding, and publication gates; a capacity refusal alone adds no unconditional rejection or new result for those controls. A successful session change neither rechecks nor clears any capacity slot, and the next chat submission remains blocked until admission is restored. The client never offers `/new` as a capacity remedy.

Publication uncertainty, guard loss, stale reservation, or invalidated resource authority downgrades each prior admitted slot affected by that authority to unchecked; it retains every unavailable or exhausted slot as a refusal until a fresh same-kind assessment replaces it. A capacity error with a known transition updates that slot to its classified unavailable or exhausted result even if its previous value was admitted. If a capacity error cannot be attributed to a transition because its reservation or caller identity is lost, set all five slots to unavailable with `otherAuthority`, visibly blocking every dependent path until a restart reconstructs and rechecks its needed transitions; do not drop the error or attribute it optimistically to the latest operation. A process restart discards all volatile slots, reconstructs marker admission from the new bootstrap, and rechecks each transition the startup or resumed durable operation actually needs; no old refusal is silently treated as cleared work because every dependent path still preflights before action. A transition not needed on that start stays unchecked. No timer, provider reconnect, successful unrelated write, or standalone `status` read upgrades any slot. The fixed slot map is the entire in-memory capacity refusal set: no hidden refusal list or implicit latest-result precedence exists.

The live status and attach snapshot expose the same capacity object and emit `status.changed` when any slot or owed component changes. The text client renders every refused slot in the fixed key order: `capacity unavailable (<transition>: <reason>)` with dependency-specific restore-and-recheck guidance, or `capacity exhausted (<transition>: <dimensions>)` with actual-capacity-change guidance, a safe restart/repair route, and the separate explicit abandon choice. An unchecked slot is rendered as not yet assessed only when pertinent to the requested operation; an admitted slot is not a promise that the next preflight or publication will succeed. `scopeAuthority`, `publicationScope`, `reservation` and other unavailable codes do not imply a transient space shortage. When journal/safety authority cannot establish what remains owed, the client and operator output say its extent is unknown; they never infer zero from the existing initial or last-observed `journal.unacknowledgedEvents` counter. This repair leaves that counter's type unchanged and never uses it as proof that an unavailable capacity inventory owes nothing. The client never describes unavailable inventory as a full journal or claims that abandon is guaranteed, and never suggests `/new` as a capacity remedy. A required-capacity refusal during an admitted interaction emits one terminal failure `capacityBlocked` with `retryable: false`; a typed capacity refusal at the optional sent mark records its capacity slot but does not alone end that turn, while unrelated I/O failure retains the fallback without a capacity diagnosis; the current status gives its unavailable/exhausted classification. A validated pending durable state check instead keeps the stronger `stateInvalidated` terminal and its existing restart guidance while status still shows the capacity diagnosis. Before send, no provider input occurred unless only the optional sent-mark write failed and the existing independent safety, binding, provider and prepared-context send checks all still passed; after send, the provider may have received the input and no acknowledgement is inferred from the failed publication. The terminal text does not claim which branch occurred when it lacks that evidence. Neither failure resubmits player text. The standalone `status` command performs no full guarded capacity admission and reports `capacity: "unavailable"` as a volatile-only observation; its durable journal summary does not infer `runtimeCapacityExceeded` from count alone. Its notice names capacity alongside the other live-only fields. `repair` and `consumer` report all current refused slots with bounded reasons/dimensions, but their exit status follows the requested command's own result and required transitions: an unsuccessful switch, incomplete required repair, or refusal on a transition the command actually needs is nonzero. An unrelated earlier ordinary refusal does not turn an otherwise successful explicit consumer release into failure. A startup marker refusal before a live host exists is classified from its typed error in the CLI error path and exits nonzero. Read-only status never clears or constructs a live capacity observation.

For every measured exhausted refusal, the client and operator report the complete bounded dimension set, every `capacity.owed` component as its known value or `unknown`, and that an unchanged retry cannot bypass the measured limit without an actual change in resources or obligations. A free-space change, restoration or authorized eligible cleanup is such a change, not a guarantee that a subsequent full admission will succeed. For unavailable refusal, report its dependency reason and each owed component known from independent authority or `unknown`; do not invent an exhausted dimension, a zero obligation, or a claim that unchanged retry will help. These readouts are diagnostics, never instructions to prune protected evidence or abandon automatically.

`freshness.class` and `reason` in a deliverable block come from a complete validated acquisition diagnostic, a pre-arm supervisor failure with no unresolved obligation, or the stated journal-level withholding reasons; they never turn an armed unresolved supervisor failure into provider input. Live status and the blocked-turn terminal instead report recovering/settlementPending for a validated pending check or unavailable/contextUnavailable for unreadable authority, while the bounded supervisor reason remains diagnostic evidence rather than raw stderr sent to a model. `consumer` is `notOwner` when the last acquisition ended with a 7.6 consumer reason. Journal fault codes remain exactly `foreignRecord`, `outboxConflict`, `recordRejected`, `adapterMismatch`, `repairFailed`, and `runtimeCapacityExceeded`. The last code is present only while at least one live transition slot reports complete measured exhaustion and no other journal fault takes precedence. `capacityUnavailable` is an interaction-level reason, not a seventh durable or derived journal fault. An exhausted or unavailable slot never overwrites `foreignRecord`, `outboxConflict`, `recordRejected`, `adapterMismatch`, or `repairFailed`; those faults retain their existing recomputation and clearing rules. The capacity-derived fault is recomputed after each assessment, drain, repair and retention pass from all five slots and the journal's independent evidence. A complete re-evaluation of the same transition clears its exhausted classification only if the full resource vector and reserved control workspace are admitted. An unavailable recheck replaces that slot's exhausted classification with unavailable but preserves the refusal; a different exhausted slot, if any, continues to justify the capacity fault. The other faults clear under their existing file, configuration and repair conditions. A non-capacity journal fault does not by itself block chat when no unresolved safety obligation remains and provider authority validates; its turn context reports failed freshness with class `journal` and that fault code for disclose-and-stop. Journal-class interaction reasons are the six fault codes plus `journalUnavailable`, `settlementPending`, `contextUnavailable`, and `capacityUnavailable`. A refusal discovered before send prevents provider input except the already-admitted turn's optional sent-mark failure under its separate verified fallback; a later capacity publication failure grants no acknowledgement or clean context block from the earlier send (Context block and State acceptance and context safety).

### Startup, shutdown, and recovery

Startup is a fixed sequence of phases; safety reconciliation also reads terminal operations whose safety phase remains pending, so their completion never hides an obligation, and each command runs a stated subset:

| Phase | `chat` | `consumer` | `repair` | `status` |
|---|---|---|---|---|
| A. Read configuration, resolve/validate the principal, derive safe scope keys and admit existing candidate paths; chat may combine its principal and initial admissions in one read-only helper. | Yes | Yes | Yes | Yes |
| B. Take the single-instance guard, recheck admission, and initialize or validate the immutable scope binding before other metadata. | Yes | Yes | Yes | No |
| C. After verified writer quiescence and narrow guarded cleanup of exact `runtime.json` tmp/bak siblings, admit the runtimeMarker reservation, mint runtime identities, terminate the watcher recorded by the complete target, then write `runtime.json`. Chat alone may open one source-attested read-only metadata worker after B and before these checks, use its fresh observations during C, then recheck source, scope, watcher and all-role predecessor admission before marker publication; it cannot prove its own job membership. | Yes | Yes | Yes | No |
| D. Delete remaining admitted owned temp and backup siblings under the full bounded cleanup, load context safety and its independent witness, preserve or recover every obligation, and load the journal or, when its directory is empty, create `journal.json` with `historyVerified` false and a cursor at 0. | Yes | Yes | Yes | Reads only |
| E. Resume consumer operations and effectively unfinished repair roots, validating and recovering a repair's prerequisites within that root. With none unfinished, read structural authority; take its `header`, `cursor`, `operationLost`, and `gap` causes in that order, then any historical cleanup replay. Only with structurally healthy authority, one guarded eligible-retention pass and a fresh measured ordinary-transition exhaustion may `repair` select `capacity` after complete-plan admission; `chat` runs no extra phase-E capacity pass and relies on its F/G admission and H retention, never creating a capacity root. One new repair at most starts per run. | A release or hand-over, safety reconciliation, then a repair and the evaluation | A release or hand-over, retaining safety obligations | A release or hand-over, safety reconciliation, then a repair and the evaluation | No |
| F. Drain the outbox and send pending settlements. | Yes | No | Yes | No |
| G. Run the startup acquisition and drain again, with its own 120-second post-acquisition settlement gate; if that leaves a pending check, an unfinished repair or a preparing/transferring witness, reconcile safety again in this same startup before provider admission. | Yes | No | No | No |
| H. Run the retention pass. | Yes | No | Yes | No |
| I. Start the watcher when enabled; perform final owner, state, journal, safety, instruction, capability, session identity and liveness admission; start or resume the provider normally, or bind an already initialized unbound candidate after those checks; establish namespace ownership and predecessor quiescence before enabling file tools. | Yes | No | No | No |
| J. Admit a client attach and chat. | Yes | No | No | No |

A failure in phase A, B, or C is fatal for every command, with the code `configurationInvalid`, `identityUnavailable`, `dataRootUnavailable`, or `runtimeAlreadyRunning`. A typed capacity refusal at the pre-kernel runtime-marker reservation or phase-C publication retains the outer fatal code `dataRootUnavailable`, because no live status exists yet; its operator error text adds only the bounded `unavailable` reason or complete `exhausted` dimensions from the capacity grammar, with unknown owed work stated as unknown. It exposes no raw path, child stderr or new sixth fatal code. Capacity preflight applies before consumption and cardinality-increasing writes in every phase, even though the general retention checkpoint is H. A failure to complete a capacity inventory is unavailable and a complete limit failure is exhausted; both refuse dependent work before consumption. A safe re-evaluation may run in the same single-writer startup or the next `chat` or `repair` start, but no denied player message is queued or automatically resent. A failure in phases D through H keeps a status-only client available where the existing branch permits, but unavailable context-safety authority prevents final provider binding and all provider input until recovery. Chat may have begun one guarded, unbound SDK initialization after C; on any such failure it cancels the pending start, closes any returned candidate and proves the provider job absent before status-only attachment or guard release. The failure becomes a journal fault or failed freshness in the status surface (a journal read or write failure in a phase F or G drain is `journalUnavailable`), and startup continues. `chat` stops early in exactly two cases. If a resumed release completes in phase E, or the acquisition in phase G reports a 7.6 consumer reason, the runtime does not own consumption: `chat` prints how to hand ownership over and exits with `notOwner` before phase I. If the provider cannot be started after its reconnect ladder, `chat` exits with `providerUnavailable`.

`consumer` resumes an incomplete release or hand-over but never starts, resumes, or evaluates a repair, and it never drains, so an unfinished repair or damaged journal does not require successful repair before a consumer switch. It excludes confirmed release and requires the explicit abandon decision where applicable. Both consumer transitions still require their own bounded durable intent and admitted capacity; unreadable authority or an irreducible release-plan budget can therefore refuse them safely. After phase E it performs the switch described under [Cutover and bridge retirement](#cutover-and-bridge-retirement). The operator-facing `repair` command first emits a bounded pre-action caution, before phase-E work, that if a capacity rewind is admitted it may set aside undelivered journal changes and later disclose missing history with a current-state `resync`; surviving exact core records remain replayable under their retained bindings. This notice states a possibility, not a claim that a capacity root will be selected or that a particular range is known. It is informational under the already explicit `repair` command, with no extra prompt, flag or automatic abandon. If the preliminary synchronous writer call throws, stop before phase-E repair work; a successful return means only local write acceptance, not proof of terminal display, so a later downstream transport loss is unobservable and cannot retroactively undo work. Otherwise continue under the existing command. Its final result reports bounded exact affected extent only from a durable validated plan; a failed final output does not undo a committed plan and the next start resumes it. `repair` resumes an incomplete repair, or selects a new structural, historical-cleanup or freshly assessed capacity cause under phase-E priority and complete-plan admission, and reports `notOwner` when its `-Resync` publish is refused. A prior volatile capacity slot alone never selects that cause. `status` reads the runtime's own files and reports what they hold as of the last run (the last start and whether it shut down cleanly, the journal's unacknowledged events and verified history, the faults derivable from operation records, context safety and any pending correction, and the agent-session binding), saying that consumer, freshness, operational warnings, capacity, watcher, and provider state exist only while `chat` runs; it runs no core command, consumes nothing, takes no guard, and works beside a running `chat`. Each operator command reports capacity refusals but exits nonzero only when its own result or a transition required by that command failed. An unrelated ordinary refusal never overrides a successful explicit consumer release; a refused release intent still fails even if the journal has no fault.

Shutdown stops admitting, interrupts an unfinished provider turn (which then acknowledges nothing), and waits for acknowledgement finalization when `turn.completed` was already emitted. It then closes the provider session, terminates the watcher, and waits up to 30 seconds for a running core child before terminating its tree. After provider/tool work, metadata preflights and core children are verified quiescent, it writes `cleanShutdown: true` and releases the instance and file-tool namespace guards. If completion or termination cannot be verified, report the failure, retain ownership while the process lives and leave `cleanShutdown: false`; a forced exit leaves file tools unavailable on restart until predecessor quiescence is established. It runs no final acquisition.

Recovery follows from the durable state after each write. The partially persisted transitions and their resume rules are:

| Interrupted between | Durable state | Resume |
|---|---|---|
| Scope directories and scope publication | Empty scope directories, or an unverified publication sibling | Empty directories permit create-only initialization; any content without the binding fails closed for ownership recovery, before consumption. |
| Outbox record commit and journal append | Record in the outbox; no event | The next drain appends it. |
| Event file write and high-water raise | Event one above the recorded high water | The next drain, or startup, accepts the event and raises the high water. |
| Journal append and core settlement | Event `pending`; record still in the outbox | The next drain treats the record as a duplicate and resends the settlement. |
| Core settlement and event mark | Tombstone in the core; event still `pending` | The resend returns `already-settled`; the event is marked `accepted`. |
| Acceptance publication and provider input | Positive exact-byte evidence exists; no input yet | Replay uses the same evidence and original binding; input still requires a durable current-generation binding. |
| Checked child launch and safety completion | `pendingCheck` remains non-null | Invalidate potentially affected provider history and resume one durable correction/resync; never infer acceptance from the missing reply. |
| Generation replacement and repair planning | Pending correction with null operation pointer | Locate a plan by correction identity or create it once, publish its pointer, then resume. |
| Rejection and partial session invalidation | New generation excludes every old binding, even if their files were not rewritten | No old startup, reconnect or named resume is admitted; establish a clean session. |
| Consumer intent and core switch | A pending safety obligation exists independently of the fixed safety file | Resume the switch without erasing uncertainty; provider use remains blocked until correction transfer. |
| Safety transfer and consumer-intent marking | New generation/correction published; operation still pending | Idempotently mark it transferred; completion or pruning never clears correction. |
| Abandon release and correction repair replacement | The correction may still name an abandoned repair | Retain correction, retire the abandoned pointer and plan one successor after re-hand-over. |
| Recovery acknowledgement and correction clearing | Corrected state is in the transcript; correction still pending | Repeat the correction until its final safety write succeeds. |
| The sent mark and the turn's end | `lastSentSequence` above `lastAckedSequence` | Those events ride the next turn as redeliveries. |
| A failed sent-mark write and the turn's end | The turn was sent; the cursor is unchanged | In the same process the in-memory mark labels those events as redeliveries; after a restart they ride the next turn unmarked. |
| Turn completion and cursor write | Transcript holds the events; cursor unchanged | The same: they ride the next turn as redeliveries. |
| Cursor write and the acknowledgement stamps | Cursor advanced; some events lack `acknowledgedAt` | Fill only actual acknowledgement advances from `updatedAt`; retained synthetic skipped ranges never manufacture acknowledgement. |
| Cursor write and the `agent-session.json` update | Cursor advanced; `turnsCompleted` stale | The next turn repeats the opening brief once; nothing is lost, and the resume after the restart binds `needsState` true. |
| A dropped-state turn's `needsState` write and its cursor write | `needsState` set; cursor unchanged | The event rides the next turn again and the state is wanted; nothing is lost. |
| Witness arm and repair plan | Preparation independently preserves the owed disclosure | Publish the same reserved plan, or its defined conservative contextUncertain plan, before any destructive action. |
| Witness transfer and successor publication | Predecessor remains owed; the single intended successor may be absent or durable | Reconcile that exact successor plan, then switch the witness; never allocate a competing recovery. |
| Recovery completion and disclosure acknowledgement | awaitingDisclosure remains independently recorded | Permit the accepted recovery turn, retain missing-history duty through its acknowledgement/provenance writes, then clear the witness. |
| Any two steps of a stream repair | Root record retains its active episode, attempt and prerequisite manifest | The next `chat` or `repair` start reconciles planned partial writes, handles genuine prerequisite damage in that root, then resumes the recorded phase/token. Historical completion alone never bypasses it; deferred carry release follows its dedicated crash table and remains owed after structural actions complete. |
| Any two steps of a release | Operation record present and incomplete | Every command except `status` resumes it in phase E; a `confirmed` one re-checks step 1's conditions first and ends as `refused` when they no longer hold. |
| Journal creation and its first verifying write | `historyVerified` false | Any release takes mode `abandon` until a verifying write (History verification) sets it. |
| The core hand-over and the `historyVerified` write | Marker `runtime`; flag false | A rerun reports `previousOwner: runtime` and cannot verify, so the journal's first append runs one cautionary `lostJournal` repair. |

The pattern's three process-recovery classes map directly: a core child that exits mid-operation is covered by the first four rows and the core's own reconciliation; an agent subprocess that exits mid-turn is the reconnect rule; and a client exit is a runtime exit in the MVP, recovered by the startup phases above.
Chat's bounded startup optimization does not reorder durable phase results: combined pre-guard observation and the guarded early read-only metadata worker accelerate A through C, while one unbound provider initialization may overlap D through H after C has completed. `startupCoreReply` and `startupMutation` remain post-marker roles. The early worker never proves its own membership; the unbound provider never receives input or becomes ready. Before J, close and prove all startup workers absent, await or cancel any pending provider initialization, repeat final `providerSafety`, prove exact provider liveness and reserve one asynchronous attach witness with current scope, guard, generation and bound session identity. Safety observation expires after at most three seconds, provider liveness after at most one second; a change or expiry forces fresh final checks or the existing refusal branch. The full ordering, failure and copied-root acceptance design is [integrated startup execution](runtime-startup-execution-30.md). No optimization relaxes the fixed 120-second post-acquisition settlement gate or permits a status-only attachment to count as healthy.

### Text client

`chat` runs a line-oriented terminal client in the runtime's process. It prints streamed text, renders a dialog as numbered options with their previews and a free-text choice, shows status changes and notices as single lines, and accepts `/new` (new agent session), `/status`, `/think <question>` (one question with the configured override), and `/quit`; Ctrl+C interrupts a running turn and quits when idle. It exists to verify the runtime against the live game. It is not the product interface and gains no features beyond what verification needs.

### Cutover and bridge retirement

The MVP originally shipped dark. `state\consumer.json` was absent before the user-directed hand-over, so the bridge owned consumption and companion sessions behaved as before; the bridge-parity claim in state extraction section 11 applies to that period. The real-root hand-over on 2026-10-13 set runtime ownership. The bridge remains available through explicit release.

- **Hand-over.** `consumer runtime` first writes its hand-over operation with pending safety intent, then runs `Set-CompanionConsumer.ps1 -Owner runtime`. It records the validated result and discharges or transfers the safety obligation through the common checked-operation rule before marking the core operation complete; an unreadable fixed safety file leaves the protected intent pending. A resumed hand-over repeats the same owner request, preserves prior uncertainty even on `changed: false`, and performs the remaining writes. When its result reports `previousOwner: bridge`, the command's last write sets `historyVerified` true; it skips that write when `journal.json` cannot be read, leaving the `header` repair to verify the journal it creates. From then on a Claude Code or Codex companion session that tries to acquire gets `config` / `consumer-not-owner` and follows the standing rule for it.
- **Release.** `consumer bridge` is one operation with a recorded intent, in this order:
  1. Count the unacknowledged journal events and the record files still in the outbox, without draining, and read the operation records. With no unacknowledged event, no record file, no effectively unfinished repair, and readable consistent authority proving no pending recovery witness or missing-history duty, the mode is `confirmed`. Pending context correction is retained separately and never interpreted as permission to clear it. Every other missing-history case is `abandon`, including a journal, cursor, or operation record that cannot be read and a journal whose `historyVerified` is false, because a journal created since the last verifying write cannot show what an earlier one left undelivered (see [History verification](#journal)). An incomplete repair counts because its step 2 may already have moved unacknowledged events to `quarantine\` and lowered the high water, so the independent witness preserves that duty even if the operation file disappears. `--abandon-undelivered` selects mode `abandon` whatever the counts show: with nothing undelivered the release still records mode `abandon`, the core still removes the baseline (with `abandonedCount` 0), and the bridge's next read discloses a reset. In mode `abandon` without `--abandon-undelivered` the new release is refused and names what is undelivered (an unfinished repair by its operation identifier), without writing a new release intent or performing its switch. Required startup and recovery phases may already have written state.
  2. Preflight the complete release transition and final publications under Recovery capacity admission, then write the release operation record with the mode, its pending safety intent, independent recovery witness or uncertainty, and, for `abandon`, the effectively unfinished roots and active episode indices, synthetic skipped ranges, and sequences being abandoned, which include the events named in the plan of every incomplete repair record. When `journal.json` cannot be read, the plan records that fact and the event file names found, in place of a range above the cursor.
  3. Apply the checked-operation safety protocol, establishing conservative context invalidation before opaque abandon or preserving it in the protected intent when the fixed safety record is unreadable, then run `Set-CompanionConsumer.ps1 -Owner bridge` with `-DeliveryConfirmed` or `-AbandonUndelivered` according to the recorded mode. This is the commit point: for `abandon` the core removes the baseline, so the bridge's next read discloses a baseline reset.
  4. For `abandon`, first retain the exact synthetic skipped ranges in the release plan, then write a fresh cursor at the high water whatever the old cursor's state, set `historyVerified` true, and terminate every effectively unfinished repair's active episode as `abandonedByRelease` with this release identifier. Fill root completion fields only when they were never terminal; preserve earlier historical completion. The skipped ranges are discharged by the explicit abandon, not relabeled as actually acknowledged. The release record, already durable, carries what the repair would have delivered, so this is the repair's defined end. When the plan records an unreadable `journal.json`, step 4 writes no cursor and no journal header and still ends the repair records the same way; the journal is left for the `header` repair, which the next `chat` or `repair` start evaluates once this record is complete, after reconciling the independently protected context correction, and whose `resync` publish is refused as `notOwner` until the next hand-over, which `consumer runtime` permits while a repair is incomplete.
  5. Mark the release operation record complete, then clear the readable recovery witness against that exact discharge proof. If safety authority is unreadable or its publication fails, the protected release intent carries the duty until reconciliation; no provider use or safety-dependent pruning follows. Its recorded skipped-range discharges remain the durable proof of explicit abandonment, never actual acknowledgement.

  A `confirmed` step 3 that the core refuses with `release-pending-records`, because a record was committed after step 1's count, ends the release with nothing switched: the operation record is completed with outcome `refused`, the command reports what is pending, and a later `consumer bridge` counts afresh. A resumed `abandon` release repeats step 3 with its recorded mode, never with a fresh count, and then finishes steps 4 and 5. A resumed `confirmed` release first re-checks step 1's conditions, inside phase E with no drain between the check and the switch, because a drain or acquisition after a failed earlier resume may have journaled and settled an event no turn delivered; when they still hold it repeats step 3 and finishes, and when they no longer show complete delivery it does not pass `-DeliveryConfirmed` and ends as `refused`. A re-check can only move a confirmed release toward refusal, never an abandon toward confirmed. One branch is accepted rather than resolved: a confirmed switch that ran before a crash, after which the journal, cursor, or a record became unreadable, fails its re-check and is labelled `refused` although the marker already says `bridge`, which costs at most one extra reset disclosure on a later abandon. For mode `confirmed`, once the root is no longer releasing, the core performs no marker write and reports `changed: false` after required reconciliation; earlier recovery and housekeeping remain durable. For mode `abandon` the repeat deletes `baseline.json` again whenever one exists, whatever the marker says (state extraction 7.6): a bridge read between the crash and the resume may have written one, so the repeat can report `baselineRemoved` true and costs the bridge one extra reset disclosure, which loses nothing. The resume completes whatever `changed`, `baselineRemoved`, and `abandonedCount` report. An interrupted abandon therefore can never turn into a confirmed release.

## Turn-context acquisition bridge (shipped; retained for bridge ownership)

The bridge is live production behavior, not a runtime slice. It carried consumption at dark coordinator delivery; after the user-directed real-root hand-over on 2026-10-13, the runtime owned consumption for that root. The consumer-ownership marker of state extraction section 7.6 selects exactly one owner, and an absent marker defaults to the bridge. The bridge remains available for explicit release and is retired, not wrapped, only when the user directs it. See the FEATURES.md entry, which excludes it from the slice breakdown.

Provide `core/Get-ValidatedTurnContext.ps1` as the host-facing entry point for the current CLI companion while the bridge owns consumption. The host calls it once at the start of each game-related turn and skips it for repository, backlog, and feature-design conversation. It invokes `core/Get-TurnContext.ps1` exactly once as a child, captures its complete streams, validates the selected envelope or terminal diagnostic, resolves one fresh Acquisition config, and adapter-admits the nested state before returning the original complete envelope unchanged. This gives Codex and Claude Code one identical command and removes host-authored capture and validation scripts. The transaction includes the single prescribed not-consumed in-process attempt retry when needed. Neither host-facing layer invokes or captures an individual attempt. If the final raw-byte write fails, the entry returns a consumed `[delivery]` diagnostic; any partial stdout is rejected rather than injected.

`Get-TurnContext.ps1` captures candidate envelopes and typed consumption results in private memory, validates them, selects the final result, and discards rejected or superseded full envelopes before returning. It emits only one selected envelope on exit 0 or one bounded terminal diagnostic on exit 1. A malformed or invariant-breaking candidate is fail-closed `[protocol]`; a consumed cache failure selects that attempt with `cacheDegraded: true`; and a not-consumed baseline failure permits exactly one new attempt, which may select a newer save. `Get-ValidatedTurnContext.ps1` validates the inner successful stdout once more before returning it and never infers consumption from free-form stderr. Successful stderr is empty; typed degraded-state notices travel in the envelope's validated `warnings` array. Failure records use canonical unbracketed class tokens in both their terminal prefix and JSON diagnostic. Section 7.5's structured result contract and exhaustive transaction table are authoritative.

The authoritative acquisition algorithm, source-identity order, exact envelope, failure taxonomy, consumption lock, retry behavior, and verification matrix live in section 7.5 of [State extraction](state-extraction.md#75-game-turn-acquisition-validated-host-entry-and-consuming-transaction). The bridge returns each diff with the exact digest source receipt it targets. Candidate payload values are built before baseline mutation but remain private until transaction selection, preventing a superseded retry payload from entering the host transcript.

The watcher remains a precomputation optimization. The bridge remains the correctness guard when the watcher is late, stopped, or temporarily regresses `current.json`. It follows the configured adapter's loaded timeline; it does not claim playthrough identity, which the runtime resolves from the signed-in Windows principal at startup (see the [playthrough identity](../patterns/runtime-work-projection-persistence-boundaries.md#playthrough-identity-settled)).

This is an explicit temporary exception to the runtime ownership boundary: an absent marker defaults the consumer role to `bridge`, a valid marker selects its stored owner, and invalid or unreadable metadata fails closed. Bridge consumption additionally requires successful enumeration with no legal outbox record filename, as specified in [state extraction section 7.6](state-extraction.md#76-durable-consumption-consumer-ownership-state-event-outbox-and-settlement). It creates no durable event, acknowledgement, or second persistence layer, and it retains the documented crash-loss window between successful consumption and model delivery. The runtime replaces the bridge with the durable state-event lifecycle rather than wrapping it: the two share the freshness acquisition and the locked comparison inside the core, never a consumed diff, and [Cutover and bridge retirement](#cutover-and-bridge-retirement) governs when the bridge goes.

## Settled design decisions

- The session-host seam is settled as the runtime-owned [SessionHostV1 contract](#sessionhostv1-contract-runtime-owned), which the TUI consumes without importing a provider library. It defines the conversation stream, host dialog callbacks, session control and resume, interruption, per-question model override, capability declaration and degraded behavior, identity and binding propagation, and restart or handoff failure behavior. The first provider is the Claude Agent SDK (TypeScript, streaming mode) as the same engine as Claude Code; it reuses the `claude /login` OAuth, ships the native binary as a platform dependency, and resolves session ids. The 2026-10-05 probe confirmed a working default-profile request with SDK-reported `apiKeySource: "none"`; it did not identify the non-API-key credential method. A token fallback is specified under [Claude Agent SDK provider](#claude-agent-sdk-provider). Declared alternates are Codex CLI, Claude Code via an alternate endpoint (OpenRouter), and a local llama.cpp gateway; each asserts its own capabilities, and hosts degrade visibly when a capability is absent rather than faking it. Provider-specific SDK behavior remains adapter-owned.
- The durable consumption protocol is settled: each state or domain transition commits its domain-owned state and durable outbox as one durable fact (a single store transaction for a domain such as Session focus; for a consumed diff, the outbox record as commit point with the baseline rolled forward, per state extraction section 7.6), while the runtime owns the separate journal, delivery, acknowledgement, and compaction lifecycle. See [durable state-event protocol](../patterns/runtime-work-projection-persistence-boundaries.md#durable-state-event-lifecycle).
- Playthrough identity is settled: the runtime resolves it from the signed-in Windows principal at startup, with no user-selectable profiles anywhere. The isolation key is (adapter, principal identity). See [playthrough identity](../patterns/runtime-work-projection-persistence-boundaries.md#playthrough-identity-settled).
- Process recovery is settled: core commands are crash-safe by atomic writes and lock release, bounded retry plus reaping covers transient failures, an agent session reattaches by id and replays unacknowledged events, a client detach never ends a session, and startup reconciliation compares the recorded validated `gameProcessInstanceIdentity` against the live process, remaining distinct across PID reuse, to tell "same sitting continued" from "previous sitting ended and a new one began." Ambiguous, unreadable, or failed probes fail closed. See [process recovery](../patterns/runtime-work-projection-persistence-boundaries.md#process-recovery-settled).
- The minimum host API is settled as `SessionHostV1`, owned by the runtime and consumed by the TUI: conversation stream, host dialog callbacks, session control and resume, interruption, and per-question model override, all provider-agnostic so the TUI never imports a provider library.
- The play-session start and end boundary is settled: the runtime owns validated OS-backed `gameProcessInstanceIdentity`, the singleton `active(playSessionId, processIdentity)` or `endedAwaitingNextInteraction(endedPlaySessionId, processIdentity-or-absence, sessionCloseId)` state, and the session lifecycle. It mints and persists one stable `playSessionId` per active sitting atomically with session status and process identity, and emits a durable session-end event with two causes (game process exit; explicit user sign-off). The same ID survives a restart only on an exact process-identity match; a mismatch closes the prior sitting once and starts new, while no process closes active and opens none. Sign-off never resumes the ended ID, and the next interaction or process appearance mints one fresh ID. The runtime owns opaque `sessionCloseId` binding, which is the canonical session-end identity and is consumed by Focus without a second Focus-minted close ID, plus the required-consumer reaction ledger and bounded close tombstone. The session focus dial and the psychologist persona report both consume it. See the [play-session lifecycle](../patterns/runtime-work-projection-persistence-boundaries.md#play-session-lifecycle).

Runtime ingress owns one immutable `InteractionContextV1` for each player interaction. It carries the current authoritative `playSessionId` binding, or null when no sitting is active, alongside interaction identity, receipt time, and ingress order. Before Focus sees a request, the runtime admits the context; missing or malformed context fails closed, while a context older than the admitted watermark or carrying a valid play-session ID different from the current session is mutation-free stale before malformed or identity handling, pending-reset, expiry, fingerprint, deduplication, keepalive, or selection. A chat submission and any structurally derived focus command share that admitted context and `requestReceivedAt`, so one player action cannot produce multiple keepalive extensions or competing ordering timestamps. Only admitted contexts enter the exhaustive Focus matrix. An admitted chat may perform one keepalive or expiry reset; derived malformed bytes then return `invalidCommand` with no invocation, fingerprint, deduplication, command keepalive, or second refresh. Retries, model output, and presentation redraws never mint a new interaction ID. The runtime carries these fields through the chat and command event surfaces without exposing them as player content.

Every typed adapter handoff carries the adapter identity and an opaque adapter-binding epoch through the capability declaration, ProjectionV1, commands, and events. The runtime mints a fresh epoch for each adapter switch and validates the epoch with the adapter and principal binding; traffic from a prior epoch is stale. Duplicate and malformed handoffs follow the existing typed handoff safety rules.

The runtime owns durable `handoffIdentity` and its binding and phase ledger, including principal, immutable source and target adapters, and source and target binding epochs. Focus stores it and immutable bindings as origin evidence, then mints a distinct focus-owned `adapterHandoff` reset `operationId`; their association is persisted so duplicate valid handoff references resolve to the same focus operation. Same identity and bindings replay idempotently; differing bindings conflict; malformed, foreign, or stale inputs mutate nothing. Resumable phases are ordered: old session end, active discard and reset, old-epoch work and delivery retirement, target store and binding, target session-start position, target catalog health, target Balanced and current projection admission, then command release. Restart resumes the same identity without repeating completed phases. Failures retain the safe gate and retry; invalid target capability, unhealthy catalog, or projection keeps commands blocked, and old-epoch traffic never crosses the boundary. The runtime handoff identity is never reused as the focus reset operation identity.

Capability loss is explicit runtime state. If an admitted provider capability is withdrawn, downgraded, or fails verification, the runtime enters `capability-pending`, clears command admission and the projection baseline, and presents a safe Balanced state. After a valid replacement declaration, it enters `projection-pending` and admits commands only after the first structurally valid projection for the new declaration establishes the baseline. A typed adapter handoff follows the same ordering: clear the old adapter binding, admit the target adapter capability and fresh binding epoch, then accept its first valid projection. Old-adapter commands and projections are stale at the boundary.

The runtime owns idempotent acquisition of the authoritative current ProjectionV1 on client attach or reconnect, capability replacement, and runtime or adapter handoff. Acquisition fabricates no event and advances no domain projection revision when state is unchanged. An overdue acquisition first follows the normal expiry-reset path. Commands remain blocked until a healthy catalog and structurally valid projection for the admitted identity and binding epoch are accepted; a structurally valid fallback projection does not release target commands.

When the focus catalog is absent or invalid, startup exposes only the volatile safe Balanced projection with an empty picker and its player-safe fault. It performs no seed or domain writes, creates no normal startup operation, outbox, or event, and blocks non-Balanced admission. Pending-reset recovery, journal repair, and explicit catalog repair remain distinct trusted paths. After repair, exactly one healthy startup reconciliation is performed or recognized under one operation identity before command admission.

ProjectionV1.revision is focus-domain-owned. Runtime rebinding derives the authoritative projection and preserves its domain revision; the runtime owns only event identity, journal sequence, timestamps, integrity metadata, delivery state, and acknowledgement.

The runtime owns one `runtimeSessionId` seam per process startup. It validates the ID under the shared opaque-token profile, keeps it stable across reconnect, play-session transitions, and same-process adapter switches, never restores it after restart, and fails closed on missing or colliding values. It is distinct from `runtimeInstanceId` and `playSessionId`, and is injected internally into focus commands and jobs rather than accepted as command JSON.

For adaptive activation, the runtime owns provider raw-text capability states `admitted`, `unavailableOrWithdrawn`, `denied`, and `invalidOrReplaced`, together with the binding epoch. Withdrawal blocks new work, pauses queued work, and makes old-epoch results stale or superseded. Fresh verified admission reopens only after domain revalidation; provider raw text is never accepted as caller-supplied approved text.

Reset operation mapping is exhaustive: startup uses `startupReset`, session end uses `sessionEnd`, expiry uses `expiryReset`, timer failure uses `timerReset`, explicit balance uses `explicitBalance`, adapter handoff uses `adapterHandoff`, journal repair uses `journalRepair`, and catalog repair uses `catalogRepair`. Session-end uses stable logical-close identity and ended-play-session guard across restart and rebind. Adapter handoff uses its runtime-owned source and target binding identity and lifecycle. Explicit balance uses `(adapter, principal, runtimeInstanceId, requestId)`, not bare `requestId`; every non-reset operation kind retains its named owner and separate identity namespace.

`InteractionContextV1` is internal non-wire runtime context containing immutable interaction ID, receipt timestamp, and monotonic ingress order. Chat and every structurally derived focus command share it; callers cannot supply these values as command JSON fields or affect fingerprints. The runtime admits interactions in monotonic order before Focus, or rejects a context older than the admitted watermark as mutation-free stale before malformed or identity handling, pending-reset, expiry, fingerprint, deduplication, keepalive, or selection. Missing or malformed context fails closed before Focus. Only admitted contexts enter the exhaustive Focus matrix. An admitted chat may perform one keepalive or expiry reset, then derived malformed bytes return `invalidCommand` with no invocation, fingerprint, deduplication, command keepalive, or second refresh. Retries preserve the original context and ordering, and `requestId` remains the command dedup identity rather than the interaction identity.

Adapter binding epoch is transport and session identity, not semantic evidence provenance. Evidence remains valid across an epoch change only when adapter identity, semantic adapter version, comparator, threshold and disclosure versions, store incarnation and generation, entry content and versions, and eligibility remain valid. Semantic drift is retryable stale or superseded. Adapter switching is an explicit runtime and focus-domain boundary: complete old session-end, discard the runtime-wide active selection through the typed handoff reset, retire old-epoch work and delivery, bind the target store and epoch, emit target session-start, then admit the target Balanced/current projection and release commands. Switching back never restores prior selection. Duplicate handoff is a no-op; failure retains the safe gate and retries the same identity; malformed or foreign handoff mutates nothing.

The adapter seed contract is provider-neutral: an immutable adapter-release seed resource has a strict versioned schema, validation, active release binding, and explicit release/version change semantics. Initialization copies a validated seed exactly once; missing or invalid seed data leaves Balanced with a configuration or persistence fault and requires explicit repair. The contract is interface-based and does not require a particular resource filename.

Administration uses a local same-principal maintenance channel owned by runtime or offline maintenance, bound to the active adapter and principal and inaccessible to player conversation, model output, and TUI capabilities. Focus remains the sole writer and enforces operation identity, CAS, replay, and conflict rules. Unauthorized, foreign, or unbound attempts mutate nothing. Startup, pending-reset, and adapter-handoff recovery gates administration before it is admitted; concrete wire fields remain deferred.
