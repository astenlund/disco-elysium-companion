# Coordinator startup latency

This feature follows a deferred design question from Nightshift run cffcf94d-49be-4cab-afcb-3fad1dabfd95. The user chose to track it after the dark coordinator MVP and agreed to the startup-scoped worker boundary and targets on 2026-10-13.

The next section records the original finding. Its time-dependent wording refers to its review snapshot and must be checked against current files before new design work.

## Recorded evidence and uncertainty

In a private runtime-verified-bridge-diagnostic fixture on an earlier source snapshot, the combined release, hand-over, contextUncertain resync recovery and chat startup took roughly 27 minutes before the fake provider host started. The bounded payload-free trace under .tmp/nightshift/verified-bridge-diagnostic records repeated supervised path-admission calls as the dominant measured cost. This is a private, recovery-heavy path, not a measured clean steady-state startup or an actual player session. The user explicitly said that a 27-minute startup is poor UX and should be taken care of, probably as a follow-up. The fixture's final result, gate margin, accepted turn and restart remain separate current MVP obligations.

On 2026-10-13, after the user handed real consumer ownership to the runtime and started `node runtime/src/cli.ts chat`, the CLI showed no progress output while startup ran. At that time the CLI awaited `createChatRuntime` before attaching the text client, which printed its first status and input prompt only after attachment. Silence left the player unable to distinguish slow recovery from a stalled startup. The first live run reached provider session creation roughly 14 minutes after process start. After gracefully quitting, the user restarted chat, reported its prompt in under 11 minutes, and received an answer to a brief current-state question. Those observations do not isolate clean startup from recovery or establish a steady-state latency target.

## Original investigation direction

Track a startup-latency investigation and design after the MVP acceptance work. Measure clean and recovery startup separately, locate mandatory versus duplicate admissions by phase, benchmark any batching or persistent metadata mechanism against path identity, quiescence, failure and deadline safety, then select a UX target and implementation with the user. Preserve the fixed 120-second interaction gate and never treat a faster helper as permission to reuse stale admission.

The startup progress slice is implemented separately from latency optimization. `chat` routes structured phase, UTC timestamp and monotonic elapsed-time events through an injectable callback; the current CLI sink renders them on host stderr and a later sink can write a log. The reported phases are exactly `configuration`, `scopeAdmission`, `instanceGuard`, `runtimeMarker`, `storageRecovery`, `consumerReconciliation`, `streamRecovery`, `outboxDrain`, `startupAcquisition`, `safetyReconciliation`, `retention`, `watcher`, `providerPreparation` and `providerStart`. A 15-second timer reports ongoing work once the current phase has been quiet for at least 15 seconds while the event loop runs; timer alignment can delay the next update. Failed and refused starts have terminal events; success is announced after client attachment, not before. No percentage, save content, credential or path enters the progress event. Focused tests cover formatting, heartbeat and terminal behavior, early failure, and the client attachment boundary. The private cold-recovery integration fixture reached teardown on its first attempt, where its source-integrity guard failed because files had changed during the run; a second unchanged-source attempt was stopped after about 30 minutes without a verdict. Slow-recovery integration remains unverified for this slice. This feedback does not relax any safety gate or reduce startup latency.

Startup progress reporting emits phase and heartbeat events. The optimization design below keeps consumer ownership unchanged and performs no writes under SaveGames.

## Startup-scoped metadata worker

The [2026-10-13 timing investigation](../reports/runtime-timing-verification.md#startup-helper-investigation-2026-10-13) separates the old recovery-heavy trace, the acknowledged-binding restart in that trace, a current one-shot helper benchmark, and two scratch-only warm-helper probes. In the old trace, 229 path-admission calls occupied 480.395 seconds inside a 704.007-second chat backend startup, alongside 57 file-hash calls; its later acknowledged-binding restart still needed 87 admissions occupying 187.360 seconds inside a 292.910-second backend startup. These nested helper times are not independent wall intervals or current-tree performance claims. On the current checkout, one-shot admission took a 2129.5332-millisecond median when compiling source and 1763.5593 milliseconds with a precompiled assembly. A private supervised warm PowerShell child re-admitted one synthetic file in a 0.9851-millisecond median over 20 subsequent requests, observed removal and recreation, and terminated with verified quiescence. A second supervised warm child reused `FileHashes.Read`, gave matching hash replies in a 1.9578-millisecond median over 20 subsequent requests, detected a content change and terminated with verified quiescence. Their test-only line protocols lack the correlation, bounds, deadlines and crash handling required for production; they show feasibility of reusing a supervised read-only process, not a startup saving.

The first optimization slice is a **startup-scoped metadata worker** for `chat`, not a persistent process during player turns. After phase C admits and writes the runtime marker under the single-instance guard, start one supervised read-only worker in a new scope-bound `startupMetadata` process role, distinct from the existing one-shot `metadata` role. Use it through phase D to provider start for fresh physical path admissions, file-hash observations and native Inventory/Marker observations, then drain its queue, stop it, and verify process-tree quiescence before client attachment. `consumer`, `repair`, standalone `status`, pre-marker/bootstrap admission and the final clean-shutdown marker continue using the existing one-shot helpers. The worker performs no core command, state write, publication, consumer switch or result caching; any compiler scratch must remain under the bound companion root's physically admitted ordinary `.tmp` directory. If that directory is absent, the startup keeps the existing one-shot path without creating a directory; an invalid or unreadable directory fails closed. Data requests admit only roots inside that companion root, never SaveGames; the fixed worker/native source bundle is separately admitted under the runtime installation root, which may differ in private fixtures.

- **Protocol and ownership.** The runtime process owns one request queue and one child job for the admitted runtime scope. A versioned startup handshake must correlate the child identity, scope binding and a fresh nonce before routing requests; absent, stale, duplicate or mismatched handshake values fail startup closed. The 30-second handshake bound starts before waiting for child identity and covers the hello; expiry requests termination and fails startup closed. Every bounded request carries a unique identifier, operation kind, admitted root and the caller's remaining deadline; an admission request adds its exact target batch and missing-path policy, a file-hash request adds its exact canonical input bytes, current scope hash or null, and input digest, and an inventory request adds exact bound scope and companion-root identities plus Inventory or Marker mode. Frame lengths, UTF-8 and JSON shape, response identifier, operation and complete cardinality are checked before any result is used. At most one request is in flight. The worker loads native admission, hash and resource-inventory code once, pins that code for this startup with no hot reload, and performs fresh native admission or inventory reading for every request. It retains no path identity, file bytes, hash or inventory between requests and returns no result before request-local native handles close. A later startup loads its then-current admitted code; a detected source or handshake mismatch fails closed rather than reusing the old worker.
- **Wire grammar.** Each frame is a four-byte unsigned big-endian byte count followed by that many strict UTF-8 JSON bytes; input frames are 1 to 2,097,152 bytes and output frames are 1 to 65,536 bytes, with no trailing or unsolicited output. The first output is exactly `{version:1, nonce, scopeSha256, sourceSha256}`, where `nonce` is the caller's fresh 32-lowercase-hex challenge, passed at spawn and echoed, and both hashes are 64-lowercase-hex digests. The worker independently admits `scope.json` and hashes its exact bytes; for `sourceSha256` it concatenates a four-byte big-endian length followed by the exact bytes of each of `StartupMetadataWorker.ps1`, `NativeFiles.cs`, `JsonDocuments.cs`, `FileHashes.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs`, `RuntimeCodec.cs` and `resource-lifecycle/ResourceInventory.cs`, separately admitted under the runtime installation root, in that order, then hashes the concatenation. The host compares both digests with its pre-spawn admitted values. An absent, unreadable or mismatched source or field is refusal. Each later request has exactly `{version:1, id, op, root, remainingMs}` plus operation fields: `id` is a fresh 32-lowercase-hex value never reused in this worker, `op` is `admit`, `hash` or `inventory`, `root` is a nonempty normalized absolute path inside the admitted companion repository, and `remainingMs` is an integer from 1 to 30,000 that never extends the caller's existing deadline. `admit` adds exactly `targets` (one to 64 exact absolute paths within `root`) and Boolean `allowMissing`, with no hash fields. `hash` adds exactly `inputBase64` (the existing canonical target-batch bytes, decoded to at most 1,048,576 bytes), its 64-lowercase-hex `inputSha256`, and `scopeSha256` (a 64-lowercase-hex binding or null when the current one-shot call omits it), with no admission or inventory fields. `inventory` adds exactly `mode` (`Inventory` or `Marker`), `scopeSha256` (the 64-lowercase-hex bound scope digest) and `companionRoot` (the exact bound absolute companion root), with no admission or hash fields and no input bytes. An output is exactly `{version:1,id,op,status:"ok",result}` carrying the current admission `paths` array, file-hash reply or validated native resource inventory, or `{version:1,id,op,status:"error",code}` with a fixed nonsecret `admissionUnavailable`, `hashUnavailable` or `inventoryUnavailable` code and no result. Those internal codes map to the current typed path, hash or inventory refusal, not new CLI statuses. The worker accepts at most 8,192 distinct request identifiers before refusing further work. Missing, extra, duplicate, malformed, out-of-order, late or oversized frames and any unsolicited stderr invalidate the worker; EOF is graceful only after the request queue drains.
- **Existing limits and readers.** Path admission retains the current maximum of 64 targets and 65,536 control bytes, `PathInspector`'s exact physical identity, kind and link-count validation, and its 30-second maximum metadata deadline including queue wait. File hashing retains `readFileHashes` batching, its 512-target and JSON budgets, its 65,536-byte reply bound, the request SHA-256 echo and nullable per-target hashes. `ScopeStorage`, `ResourceAuthority`, `FilePublisher`, journal, safety, operation and session readers continue consuming only those validated observations through the existing inspector, hash and inventory APIs; absent or stale worker state selects the original one-shot transport only after a verified stop, never a cached result. Standalone status and watcher orphan inspection stay on their current independent paths.
- **Changed proof boundary.** Today's one-shot helper returns only after verified process-tree termination. A warm worker would return while its process stays alive, so every success reply must prove that the exact request finished and its native file handles and request-local buffers were closed before the frame was emitted. The worker may retain loaded code and its input loop, never a target handle or prior observation. Tests must hold and replace target files between replies and during an in-flight request; if this per-request quiescence property cannot be established, the worker is not admitted as a substitute for one-shot helpers even if its timing is better.
- **Failure and shutdown.** Add the new role to `processRoles`, marker startup admission, failed-open cleanup, shutdown and role-verification fixtures; the existing core, publication, provider, watcher and one-shot metadata roles keep their present behavior. A launch failure with verified child absence may use the original one-shot path for this startup. A source or handshake mismatch is fatal rather than a fallback. A malformed or uncorrelated reply, truncated or excessive output, expired request, lost child, or termination uncertainty cannot supply admission to the dependent operation: fail that operation without automatic retry, stop and verify the worker, and allow later independent work to use one-shot checks only after verified termination. If termination cannot be verified, retain the runtime guard and fail closed. An ordinary native path, hash or inventory refusal keeps its existing typed failure and does not become a permissive fallback. An unexpected worker exit fails the in-flight observation; queued calls can use one-shot checks only after a verified stop, while completed observations still face use-time revalidation. On normal readiness, not-owner return, provider refusal or another exception, first stop new worker requests, settle or reject the queue, switch the inspector to one-shot, and stop and verify the worker; only then attach the client or run existing host/backend shutdown and release. If worker termination is unverified, do not write a clean-shutdown marker or release the guard. The runtime's final marker write uses the one-shot transport so `cleanShutdown: true` never precedes worker quiescence. A crash leaves the next start's process-role admission responsible for detecting a surviving job; uncertain predecessor ownership blocks startup.
- **Measurement and gate.** First record current-tree baselines with phase timestamps, helper counts, status and unchanged fixture inputs for three private cases: a clean runtime-owned start with valid verified journal/cursor/safety, no pending event, repair or correction and no prior provider binding; an acknowledged-binding restart with one delivered event and valid binding; and a bridge-to-runtime hand-over with conservative recovery and resync. Build their state through supported private fixture operations and validate these preconditions before timing; the last two have historical traces but need current-tree baselines. Use the production-equivalent enabled watcher against private staged saves as the primary setting and a disabled-watcher control to isolate its cost; neither setting touches real SaveGames. Then compare the worker on equivalent private fixtures with source-frozen attempts, a fake provider, and the same accepted-event and safety outcomes. The first-slice private acceptance targets were at most 60 seconds for clean startup, 90 seconds for acknowledged restart, and 180 seconds for recovery-heavy startup in those private fixtures. The first-slice player-facing target on this machine was a prompt within 60 seconds of process start on a routine clean or acknowledged restart, and within 180 seconds on recovery, including provider start and excluding any interactive credential login; only a later user-coordinated live measurement can establish that target. A missed target remains an open performance finding rather than permission to remove checks. Exercise absent, changed, reparse and multiply linked targets, worker crash and timeout before and after a reply, output overflow, wrong correlation, launch fallback, uncertain termination, not-owner and provider-start failure, restart, and the fixed 120-second interaction gate. Do not run a real-root consumer command or alter SaveGames as part of private verification.

This design keeps the worker out of ordinary turns so the separate whole-turn latency feature and its settlement budget do not become implicit scope. It leaves publication, core-reply validation, Event/Quarantine inventory modes and codec helpers one-shot. If the private targets are missed, use the measured residual phase and helper walls to choose a separately agreed follow-up rather than broadening this slice silently. The worker boundary and targets were agreed before graduation.

## Warm read-only resource inventory

The approved next slice warms only the native `Inventory` and `Marker` modes within the same startup-scoped `startupMetadata` child after its bound hello and before verified stop. `ResourceAuthority.observe` continues to consume and validate each fresh result, then separately reads operation records and applies the existing capacity decision; no inventory, admission or capacity lease is cached across requests. The pre-marker `runtimeMarker` reservation, commands without a chat worker, ordinary turns, standalone status and final shutdown keep one-shot inventory. The `Event` mode used for event-expansion admission and the mutating `Quarantine` trim also remain one-shot, including when the worker is active. `PathInspector.metadata` routes only the exact no-input resource argument vector `-Root <bound dataRoot> -ScopeSha256 <bound binding> -CompanionRoot <bound companionRoot> -Mode Inventory|Marker`; all other resource vectors use the original helper, while a direct malformed worker request refuses. The existing path and hash modes keep their prior routing.

The pre-spawn `Get-StartupMetadataSource.ps1` helper and the worker independently admit and read the nine files listed in the wire grammar under the installation root, using the existing 1,048,576-byte per-file bound, before/after physical identity and byte checks, and four-byte length-framed SHA-256 order. The worker compiles those fixed native dependencies once and independently emits its scope and source digests in the hello; the host refuses any mismatch against its pre-spawn observation before routing requests. `ResourceInventory.Read(root, scopeSha256, markerOnly, companionRoot)` uses the verified binding and fresh physical file admission on each request; the worker passes `markerOnly` true exactly for `Marker`, returns only after native enumeration and request-local handles have closed, and retains only loaded code and its input loop. The read-only mode does not create, refresh or delete durable state. A later startup loads and binds its then-current source bundle; an absent `.tmp` selects the original one-shot path and an invalid `.tmp` fails closed.

An exact `inventory` request adds `mode`, the bound non-null `scopeSha256` and exact bound `companionRoot` to the common `{version:1,id,op,root,remainingMs}` frame; `root` must equal the bound data root, `mode` is case-sensitive `Inventory` or `Marker`, no input bytes or extra fields are allowed, and the common deadline includes queue wait. Its successful result has exactly `uncompactedEvents`, `retainedHandoffs`, `retainedHandoffIdentitySha256`, `potentialHandoffs`, `fullTerminalOperations`, `unfinishedOperations`, `invalidEvents`, `invalidOperations`, `pendingOutbox`, `uncertainWorkspace` and `freeBytes`: counts are nonnegative safe integers, the digest is 64 lowercase hexadecimal characters, uncertainty is Boolean, and free bytes is an unsigned decimal string. The host validates the complete result before returning it to `ResourceAuthority`, which retains its independent semantic checks. `Marker` intentionally excludes ordinary `codec.json` residue; `Inventory` reports it. A native refusal returns only `inventoryUnavailable`, which maps to the current unavailable capacity observation without clearing obligations or treating it as zero.

Malformed, incomplete, stale, wrong-root, wrong-mode, late, oversized or uncorrelated inventory frames or replies and unexpected child output are protocol failures: no dependent reservation uses them, the worker is stopped and its process tree verified before later independent work may fall back to one-shot metadata. A malformed direct caller request rejected before any frame is sent fails that call without a worker result and leaves the worker available. A valid native inventory refusal may leave the worker running for a later fresh request, but the refused transition stays unavailable. An unverified stop retains the runtime guard and blocks clean shutdown or client attachment. Normal ready, not-owner, provider refusal and exception paths stop the worker as already specified. The common 8,192-request lifetime and 30-second per-request maximum remain shared across admission, hash and inventory operations.

Private verification must exercise exact routing of all four resource modes, source-bundle and handshake mismatch, `Inventory` and `Marker` freshness across creation and deletion of ordinary residue, reparse and multiply linked refusal, exclusive file access after each reply, timeout and worker crash before and after a reply, malformed result and correlation, launch fallback and unverified stop, unchanged capacity and owed-status decisions, and provider withholding after a refusal. Source-frozen enabled-watcher clean, acknowledged-restart and recovery-heavy fixtures then measure full fake-client readiness and helper counts, with a disabled-watcher control; the fixed current-source 120-second one-new-record interaction gate is checked separately. The 60/90/180-second targets were the first-slice private criteria; current targets are stated below, and historical misses remain open findings. Neither private nor live behavior is inferred from a warm microbenchmark. Core-reply validation and `source`/`event` codec inspection remain one-shot because they need separately agreed module-identity and side-effect boundaries; native runtime-file publication is a writer outside this read-only authority. Real-root consumer commands and SaveGames writes remain prohibited.

## Implemented worker and open acceptance

The worker protocol and chat-startup routing are implemented. The worker runs in a separate supervised process role after the runtime marker is established, reuses loaded native code while observing each requested path or hash afresh, and stops with verified quiescence before client attachment. Non-chat commands and ordinary turns retain one-shot helpers. The process role is admitted by the native job-name validator. The private normal-path test passed creation, changed content, deletion, hash change, multiply linked and reparse refusal, one-shot restoration and verified shutdown; a separate test passed an externally stopped worker after a reply followed by one refused observation and a one-shot observation after verified stop; a private bridge-owned root returned not-owner from backend.startup and verified worker stop before clean shutdown. Unit tests passed framed bounds, correlation and unsolicited-output checks, a mismatched handshake, a silent broker readiness timeout, verified launch fallback, and refusal when launch termination cannot be verified. The exact test and timing evidence is in [runtime-timing-verification.md](../reports/runtime-timing-verification.md#startup-metadata-worker-verification-2026-10-13).

## Bounded bootstrap batching

Scope discovery and existing-binding reads now each admit their two exact paths in one fresh native request, retaining root, kind and binding validation. Startup process admission checks all six fixed job roles in one read-only native query, requires complete ordered responses, compares in-process owner snapshots before clearing them, and uses the original per-role quiescence wait when a job is reported present; a missing or malformed batch fails closed. Metadata-worker startup gathers the temp-directory and source-byte evidence in one supervised read-only helper; absent `.tmp` still selects one-shot metadata, invalid evidence refuses startup, and the worker still independently rechecks and echoes its bound source digests. The healthy storage path carries one admitted release reservation through journal initialization and conditional new-scope safety initialization; a capacity refusal still runs the bounded retention pass and obtains a fresh reservation before dependent writes. None of these changes caches a path, inventory or checked state, moves consumption, or changes the fixed settlement gate.

The [sequential spike report](../reports/runtime-startup-spikes-2026-10-14.md#applied-batching-control) records a source-checked private no-save control after batching at 65.242 seconds through fake-provider binding and verified worker stop, versus 83.035 seconds in a separate earlier control. The observed difference is 17.794 seconds, concentrated in scope admission, existing-binding admission, marker and worker bootstrap, and storage recovery. It is not a complete CLI or live-game comparison; the no-save fixture still reported failed freshness, while safety was ready and the journal healthy. This control missed the 60-second private clean target by 5.242 seconds. At that batching-only snapshot, representative fresh-state and live launches, together with the previously open entry-point and recovery cases, remained unverified.

## Current startup performance objective

Routine clean starts and acknowledged-binding restarts target at most 30 seconds from process start to healthy client attachment on this machine; recovery retains an at-most-180-second target for the same healthy readiness. A successful timed start, routine or recovery, requires consumer ownership, fresh admitted state, a healthy journal, ready safety, a bound ready provider, the required enabled-watcher startup observation and verified startup-worker stop when the client attaches. The existing `chat client ready` progress line alone proves client attachment, not those healthy conditions: phase D through H failures may still attach a status-only client with provider input refused. Record that attachment's duration and fault separately. It does not count as a successful timed start, whether routine or recovery, and its existing behavior stays unchanged. Interactive credential login remains outside the timed target. A performance miss never licenses a skipped authority check, missing warning or false ready status.

The corresponding private acceptance target is at most 30 seconds through fake-client attachment for both source-checked, watcher-enabled fresh-state clean and acknowledged-binding restart fixtures with equivalent validated state and session outcomes; a source-checked, watcher-enabled recovery fixture with healthy final status stays at most 180 seconds. Record repeated attempts and misses, keep degraded recovery attachment duration and fault separate, and retain the no-save controls as diagnostic lower bounds only. Claim player-facing attainment only after user-coordinated live runs with the real provider establish healthy status at attachment and show the target is repeatable. The 54.721-second live launch above misses the new target by 24.721 seconds. The next implementation mechanism remains undecided: the private native apphost probe saved about 0.564 seconds per supervised single-file path admission, but the private control had only six such one-shot calls and other helper modes were not tested, so that substitution does not demonstrate a route to closing the live gap; a startup-scoped writer or earlier read-only host would need an independently agreed source, publication, crash and ownership design before production wiring. Presentation changes remain deferred.

The [private warm-publication feasibility result](../reports/runtime-startup-spikes-2026-10-14.md#warm-publication-full-path-feasibility) exercised actual `FilePublisher` admission and postcondition logic through a test-only writer transport. A watcher-enabled no-save startup with five post-marker publications routed warm reached fake-provider binding and verified worker stops in 38.932 seconds, compared with 48.693 seconds in a separate current-tree no-save control, an observed 9.761-second difference. It still missed the 30-second private target by 8.932 seconds before a representative fresh save or real provider was involved. The primitive and startup fixtures do not establish the source-attested writer protocol, uncertain-stop and crash behavior, capacity coverage or healthy live timing required for production. The next design study must measure whether earlier guarded read-only admission and separately justified core-reply work can close the remaining full-start gap; no part of this scratch writer is installed or active in the runtime.

A further test-only no-save startup overlapped shutdown of the independent read-only and writer workers after fake-provider binding and completion of all publication requests. It still waited for verified stop of both before readiness. The complete private startup took 37.799 seconds versus 38.932 seconds in the separate serial-stop control, an observed 1.132-second difference, with 22 matching named production source hashes.
