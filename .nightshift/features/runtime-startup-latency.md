# Coordinator startup latency

This feature follows a deferred design question from Nightshift run cffcf94d-49be-4cab-afcb-3fad1dabfd95. The user chose to track it after the dark coordinator MVP and agreed to the startup-scoped worker boundary and targets on 2026-10-13.

The evidence below is the original finding. Time-dependent wording refers to its review snapshot and must be checked against current files before design work.

## Recorded evidence and uncertainty

In a private runtime-verified-bridge-diagnostic fixture on a local pre-publication source snapshot, the combined release, hand-over, contextUncertain resync recovery and chat startup took roughly 27 minutes before the fake provider host started. The bounded payload-free trace under .tmp/nightshift/verified-bridge-diagnostic records repeated supervised path-admission calls as the dominant measured cost. This is a private, recovery-heavy path, not a measured clean steady-state startup or an actual player session. The user explicitly said that a 27-minute startup is poor UX and should be taken care of, probably as a follow-up. The fixture's final result, gate margin, accepted turn and restart remain separate current MVP obligations.

On 2026-10-13, after the user handed real consumer ownership to the runtime and started `node runtime/src/cli.ts chat`, the CLI showed no progress output while startup ran. At that time the CLI awaited `createChatRuntime` before attaching the text client, which printed its first status and input prompt only after attachment. Silence left the player unable to distinguish slow recovery from a stalled startup. The first live run reached provider session creation roughly 14 minutes after process start. After gracefully quitting, the user restarted chat, reported its prompt in under 11 minutes, and received an answer to a brief current-state question. Those observations do not isolate clean startup from recovery or establish a steady-state latency target.

## Original investigation direction

Track a startup-latency investigation and design after the MVP acceptance work. Measure clean and recovery startup separately, locate mandatory versus duplicate admissions by phase, benchmark any batching or persistent metadata mechanism against path identity, quiescence, failure and deadline safety, then select a UX target and implementation with the user. Preserve the fixed 120-second interaction gate and never treat a faster helper as permission to reuse stale admission.

The startup progress slice is implemented separately from latency optimization. `chat` routes structured phase, UTC timestamp and monotonic elapsed-time events through an injectable callback; the current CLI sink renders them on host stderr and a later sink can write a log. The reported phases are exactly `configuration`, `scopeAdmission`, `instanceGuard`, `runtimeMarker`, `storageRecovery`, `consumerReconciliation`, `streamRecovery`, `outboxDrain`, `startupAcquisition`, `safetyReconciliation`, `retention`, `watcher`, `providerPreparation` and `providerStart`. A 15-second timer reports ongoing work once the current phase has been quiet for at least 15 seconds while the event loop runs; timer alignment can delay the next update. Failed and refused starts have terminal events; success is announced after client attachment, not before. No percentage, save content, credential or path enters the progress event. Focused tests cover formatting, heartbeat and terminal behavior, early failure, and the client attachment boundary. The private cold-recovery integration fixture reached teardown on its first attempt, where its source-integrity guard failed because files had changed during the run; a second unchanged-source attempt was stopped after about 30 minutes without a verdict. Slow-recovery integration remains unverified for this slice. This feedback does not relax any safety gate or reduce startup latency.

Startup progress reporting is shipped. The optimization design below is approved for local implementation, not publication, another consumer switch, or changes under SaveGames.

## Startup-scoped metadata worker

The [2026-10-13 timing investigation](../reports/runtime-timing-verification.md#startup-helper-investigation-2026-10-13) separates the old recovery-heavy trace, the acknowledged-binding restart in that trace, a current one-shot helper benchmark, and two scratch-only warm-helper probes. In the old trace, 229 path-admission calls occupied 480.395 seconds inside a 704.007-second chat backend startup, alongside 57 file-hash calls; its later acknowledged-binding restart still needed 87 admissions occupying 187.360 seconds inside a 292.910-second backend startup. These nested helper times are not independent wall intervals or current-tree performance claims. On the current checkout, one-shot admission took a 2129.5332-millisecond median when compiling source and 1763.5593 milliseconds with a precompiled assembly. A private supervised warm PowerShell child re-admitted one synthetic file in a 0.9851-millisecond median over 20 subsequent requests, observed removal and recreation, and terminated with verified quiescence. A second supervised warm child reused `FileHashes.Read`, gave matching hash replies in a 1.9578-millisecond median over 20 subsequent requests, detected a content change and terminated with verified quiescence. Their test-only line protocols lack the correlation, bounds, deadlines and crash handling required for production; they show feasibility of reusing a supervised read-only process, not a startup saving.

The first optimization slice is a **startup-scoped metadata worker** for `chat`, not a persistent process during player turns. After phase C admits and writes the runtime marker under the single-instance guard, start one supervised read-only worker in a new scope-bound `startupMetadata` process role, distinct from the existing one-shot `metadata` role. Use it through phase D to provider start for fresh physical path admissions and file-hash observations, then drain its queue, stop it, and verify process-tree quiescence before client attachment. `consumer`, `repair`, standalone `status`, pre-marker/bootstrap admission and the final clean-shutdown marker continue using the existing one-shot helpers. The worker performs no core command, state write, publication, consumer switch or result caching; any compiler scratch must remain under the bound companion root's physically admitted ordinary `.tmp` directory. If that directory is absent, the startup keeps the existing one-shot path without creating a directory; an invalid or unreadable directory fails closed. Data requests admit only roots inside that companion root, never SaveGames; the fixed worker/native source bundle is separately admitted under the runtime installation root, which may differ in private fixtures.

- **Protocol and ownership.** The runtime process owns one request queue and one child job for the admitted runtime scope. A versioned startup handshake must correlate the child identity, scope binding and a fresh nonce before routing requests; absent, stale, duplicate or mismatched handshake values refuse the fast path. Every bounded request carries a unique identifier, operation kind, admitted root and the caller's remaining deadline; an admission request adds its exact target batch and missing-path policy, while a file-hash request adds its exact canonical input bytes, current scope hash or null, and input digest. Frame lengths, UTF-8 and JSON shape, response identifier, operation and complete cardinality are checked before any result is used. At most one request is in flight. The worker loads the existing native admission and hash code once, pins that code for this startup with no hot reload, but reopens and re-admits every requested path on every call. It retains no path identity, file bytes or hash between requests and returns no result before native handles close. A later startup loads its then-current admitted code; a detected source or handshake mismatch fails closed rather than reusing the old worker.
- **Wire grammar.** Each frame is a four-byte unsigned big-endian byte count followed by that many strict UTF-8 JSON bytes; input frames are 1 to 2,097,152 bytes and output frames are 1 to 65,536 bytes, with no trailing or unsolicited output. The first output is exactly `{version:1, nonce, scopeSha256, sourceSha256}`, where `nonce` is the caller's fresh 32-lowercase-hex challenge, passed at spawn and echoed, and both hashes are 64-lowercase-hex digests. The worker independently admits `scope.json` and hashes its exact bytes; for `sourceSha256` it concatenates a four-byte big-endian length followed by the exact bytes of each of `StartupMetadataWorker.ps1`, `NativeFiles.cs`, `JsonDocuments.cs` and `FileHashes.cs`, separately admitted under the runtime installation root, in that order, then hashes the concatenation. The host compares both digests with its pre-spawn admitted values. An absent, unreadable or mismatched source or field is refusal. Each later request has exactly `{version:1, id, op, root, remainingMs}` plus operation fields: `id` is a fresh 32-lowercase-hex value never reused in this worker, `op` is only `admit` or `hash`, `root` is a nonempty normalized absolute path inside the admitted companion repository, and `remainingMs` is an integer from 1 to 30,000 that never extends the caller's existing deadline. `admit` adds exactly `targets` (one to 64 exact absolute paths within `root`) and Boolean `allowMissing`, with no hash fields. `hash` adds exactly `inputBase64` (the existing canonical target-batch bytes, decoded to at most 1,048,576 bytes), its 64-lowercase-hex `inputSha256`, and `scopeSha256` (a 64-lowercase-hex binding or null when the current one-shot call omits it), with no admission fields. An output is exactly `{version:1,id,op,status:"ok",result}` carrying the current admission `paths` array or current file-hash reply, or `{version:1,id,op,status:"error",code}` with a fixed nonsecret `admissionUnavailable` or `hashUnavailable` code and no result. Those internal codes map to the current typed path or hash refusal, not new CLI statuses. The worker accepts at most 8,192 distinct request identifiers before refusing further work. Missing, extra, duplicate, malformed, out-of-order, late or oversized frames and any unsolicited stderr invalidate the worker; EOF is graceful only after the request queue drains.
- **Existing limits and readers.** Path admission retains the current maximum of 64 targets and 65,536 control bytes, `PathInspector`'s exact physical identity, kind and link-count validation, and its 30-second maximum metadata deadline including queue wait. File hashing retains `readFileHashes` batching, its 512-target and JSON budgets, its 65,536-byte reply bound, the request SHA-256 echo and nullable per-target hashes. `ScopeStorage`, `ResourceAuthority`, `FilePublisher`, journal, safety, operation and session readers continue consuming only those validated observations through the existing inspector and hash APIs; absent or stale worker state selects the original one-shot transport only after a verified stop, never a cached result. Standalone status and watcher orphan inspection stay on their current independent paths.
- **Changed proof boundary.** Today's one-shot helper returns only after verified process-tree termination. A warm worker would return while its process stays alive, so every success reply must prove that the exact request finished and its native file handles and request-local buffers were closed before the frame was emitted. The worker may retain loaded code and its input loop, never a target handle or prior observation. Tests must hold and replace target files between replies and during an in-flight request; if this per-request quiescence property cannot be established, the worker is not admitted as a substitute for one-shot helpers even if its timing is better.
- **Failure and shutdown.** Add the new role to `processRoles`, marker startup admission, failed-open cleanup, shutdown and role-verification fixtures; the existing core, publication, provider, watcher and one-shot metadata roles keep their present behavior. A launch failure with verified child absence may use the original one-shot path for this startup. A source or handshake mismatch is fatal rather than a fallback. A malformed or uncorrelated reply, truncated or excessive output, expired request, lost child, or termination uncertainty cannot supply admission to the dependent operation: fail that operation without automatic retry, stop and verify the worker, and allow later independent work to use one-shot checks only after verified termination. If termination cannot be verified, retain the runtime guard and fail closed. An ordinary native path or hash refusal keeps its existing typed failure and does not become a permissive fallback. An unexpected worker exit invalidates queued or in-flight observations, while any completed observation still faces its existing use-time revalidation. On normal readiness, not-owner return, provider refusal or another exception, first stop new worker requests, settle or reject the queue, switch the inspector to one-shot, and stop and verify the worker; only then attach the client or run existing host/backend shutdown and release. If worker termination is unverified, do not write a clean-shutdown marker or release the guard. The runtime's final marker write uses the one-shot transport so `cleanShutdown: true` never precedes worker quiescence. A crash leaves the next start's process-role admission responsible for detecting a surviving job; uncertain predecessor ownership blocks startup.
- **Measurement and gate.** First record current-tree baselines with phase timestamps, helper counts, status and unchanged fixture inputs for three private cases: a clean runtime-owned start with valid verified journal/cursor/safety, no pending event, repair or correction and no prior provider binding; an acknowledged-binding restart with one delivered event and valid binding; and a bridge-to-runtime hand-over with conservative recovery and resync. Build their state through supported private fixture operations and validate these preconditions before timing; the last two have historical traces but need current-tree baselines. Use the production-equivalent enabled watcher against private staged saves as the primary setting and a disabled-watcher control to isolate its cost; neither setting touches real SaveGames. Then compare the worker on equivalent private fixtures with source-frozen attempts, a fake provider, and the same accepted-event and safety outcomes. The first-slice private acceptance targets are at most 60 seconds for clean startup, 90 seconds for acknowledged restart, and 180 seconds for recovery-heavy startup in those private fixtures. The player-facing target on this machine is a prompt within 60 seconds of process start on a routine clean or acknowledged restart, and within 180 seconds on recovery, including provider start and excluding any interactive credential login; only a later user-coordinated live measurement can establish that target. A missed target remains an open performance finding rather than permission to remove checks. Exercise absent, changed, reparse and multiply linked targets, worker crash and timeout before and after a reply, output overflow, wrong correlation, launch fallback, uncertain termination, not-owner and provider-start failure, restart, and the fixed 120-second interaction gate. Do not run a real-root consumer command or alter SaveGames as part of private verification.

This design keeps the worker out of ordinary turns so the separate whole-turn latency feature and its settlement budget do not become implicit scope. It also leaves publication and core helpers one-shot. If the private targets are missed, use the measured residual phase and helper walls to choose a separately agreed follow-up rather than broadening this slice silently. The worker boundary and targets were agreed before graduation.

## Local implementation and open acceptance

The worker protocol and chat-startup routing are committed locally on `main`, following graduation of this entry. The worker runs in a separate supervised process role after the runtime marker is established, reuses loaded native code while observing each requested path or hash afresh, and stops with verified quiescence before client attachment. Non-chat commands and ordinary turns retain one-shot helpers. The process role is admitted by the native job-name validator. The private normal-path test passed creation, changed content, deletion, hash change, multiply linked and reparse refusal, one-shot restoration and verified shutdown; a separate test passed an unexpected post-reply worker exit followed by one refused observation and a one-shot observation after verified stop; a private bridge-owned root refused chat and verified worker stop before clean shutdown. Unit tests passed framed bounds, correlation and unsolicited-output checks, a mismatched handshake, verified launch fallback, and refusal when termination cannot be verified. The exact test and timing evidence is in [runtime-timing-verification.md](../reports/runtime-timing-verification.md#startup-metadata-worker-verification-2026-10-13).

In the private disabled-watcher handover fixture, chat open through fake-provider binding fell from about 849 to 214.838 seconds; acknowledged restart fell from about 412 to 80.252 seconds. The full candidate fixture passed accepted delivery, durable acknowledgement and persisted-provider resume. A second private recovery-heavy startup profile reached fake-provider binding in 153.838 seconds without running a turn, so this workload crossed the 180-second target in opposite directions on two attempts. Its worker handled 250 path admissions and 71 hash requests in 1.657 seconds of aggregate nested request wall; the residual measured work included 77.228 seconds in stream recovery and repeated one-shot resource inventory and publication calls. A watcher-enabled no-save control with verified empty journal and safety, zero pending events, no correction and no prior provider binding fell from 317.032 to 81.776 seconds through fake-provider binding. Its failed freshness makes it an authority-clean lower-bound control rather than a representative fresh game state. The acknowledged-restart target passed, but recovery-heavy startup did not consistently meet 180 seconds and the clean-control target missed 60 seconds. A representative fresh-state clean start and enabled-watcher recovery-heavy and acknowledged-restart comparisons remain unverified. The fixed 120-second settlement gate was not changed and was not timed separately in these startup comparisons. Real game behavior remains unprobed.

The worker is a local implementation, not a shipped or published feature. The missed targets and remaining private acceptance cases keep this entry active. Residual private traces found a 42-second clean backend open, a 77-second recovery stream phase, repeated one-shot path admission, resource inventory and publication calls, and 0.545 and 1.657 seconds of aggregate warm-worker metadata time in the clean and recovery profiles respectively. These nested call walls are not additive savings. Any broader latency mechanism, including extending the worker to another read-only operation, requires a separate agreed design and deciding measurement of its source admission and pre-marker costs; this slice does not relax path identity, history, safety, quiescence or gate checks to meet a timing goal.
