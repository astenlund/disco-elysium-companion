# Go native helper

Status: scope agreed with the user on 2026-10-23 and graduated from Exploring; no implementation has been authorized. The user raised the direction on 2026-10-18 as a follow-up to the compiled Go startup path and on 2026-10-23 decided that Go is the default language for native code, that one long-lived helper replaces the per-call PowerShell helpers, that the helper is built on first launch instead of being checked in, and that a local Go toolchain is an accepted host requirement. This design is governed with [companion execution runtime](companion-execution-runtime.md), [integrated startup execution](runtime-startup-execution-30.md) and [state extraction](state-extraction.md). It does not alter the 30-second startup or 180-second recovery acceptance gates of [Coordinator startup latency](runtime-startup-latency.md).

## Problem

The runtime under `runtime/src` is TypeScript, but almost every native operation runs through `pwsh -NoProfile -File runtime/scripts/<script>.ps1`, and 22 of those 27 scripts compile one or more sibling C# files with `Add-Type` at every load. A supervised one-shot call costs at least three PowerShell processes on the shipped path: the broker `Invoke-OwnedProcess.ps1`, the helper child, and the `Get-OwnedJobState.ps1` job-absence check that `verifyOwner` runs when the broker closes. Each PowerShell start also carries profile, temporary-folder and .NET first-run side effects that the runtime now has to redirect under `.tmp` (`brokerEnvironment` in `runtime/src/compiled-broker.ts`, `dotnetFirstRunOptOuts` in `runtime/src/dotnet-environment.ts`, `prepareStartupHelperScratch` in `runtime/src/startup-helper-scratch.ts`); the open bugs "Per-start helper profiles accumulate" and ".NET tools folders leak into the User PATH" and the quick win "Contained test pwsh profiles" are all consequences of that machinery. The startup-scoped PowerShell workers (`StartupMetadataWorker.ps1`, `StartupCoreReplyWorker.ps1`, `StartupMutationWorker.ps1`) reduce the per-call cost during startup but add two long-lived PowerShell processes each, prove their source bundles by hashing nine files per start, and stop before client attachment, so player turns fall back to one-shot helpers.

The compiled Go images `runtime/native/go-broker.exe` and `runtime/native/job-observer.exe` already replace the broker and the job query on the selected compiled-image path, but that selector is off (`compiledSelectorEnabled = false` in `runtime/src/cli.ts`), the binaries are committed, and the startup execution design gates the selector on proving parity with the PowerShell broker it would replace.

## Design

**One helper image, two roles.** A single Go module under `runtime/native/helper/` builds one executable, `runtime/native/companion-helper.exe`. Started with no subcommand it is the long-lived helper service: one per runtime process, started before scope admission and stopped last at shutdown, speaking the existing startup-worker frame grammar over stdio (four-byte big-endian length, strict UTF-8 JSON, one request in flight, handshake with a fresh nonce). Started as `companion-helper.exe broker` it is the per-child broker that `go-broker.exe` is today: it claims a kill-on-close job containing itself and the child, launches the child with the version-2 control frame and writes the owned-process header. The job-observer logic becomes a request of the helper service. Every supervised child, including the provider, the watcher and the core entry scripts, keeps its own broker and job, so a helper crash cannot end any child; the helper service holds no child job handle.

**Requests.** The service serves the operations the startup workers serve today (`admit`, `hash`, `inventory`, `eventBatch`, `sourceEvidence`, `jobBatch`, `publish`, `codec`, `quarantineTrim`) plus the one-shot operations that never had a warm form: `processIdentity`, `ownedProcessLive`, `principal`, `fileAction`, `contextPreparation`, `stopOrphanWatcher` and `jobAbsent`. Request and reply budgets, the admitted-root rule (only roots inside the companion root, never SaveGames), the per-request deadline, the result validation every consumer performs today and the changed proof boundary of the startup-scoped metadata worker all carry over unchanged: the service retains loaded code and its input loop, never a target handle, file bytes, hash or observation between requests, and a reply proves that the request's handles closed before the frame was written. `publish` keeps the state-extraction 7.1 discipline and the existing-target contract of the runtime design (complete old bytes for an already-open reader, complete new bytes for a new reader) through `MoveFileExW` for create-only targets and `ReplaceFileW` for existing targets; the acceptance fixture repeats the 2026-10-06 open-reader probe against the Go implementation before `Write-RuntimeFile.ps1` is removed. `codec` keeps the lossless payload contract of the runtime design, including numbers beyond JavaScript's safe range, negative zero, exponent spelling and seven-fractional-digit timestamps, through byte-preserving raw JSON handling rather than any decode-and-reencode path; the existing codec probes become Go tests.

**Lifetime and authority.** The helper service lives for the whole runtime process, which supersedes the decision in Coordinator startup latency that the warm worker is startup-scoped and that player turns use one-shot helpers: with every request leaving no retained state, a warm service during turns gives the one-shot guarantees without the one-shot cost. It is execution transport, not an authority cache: the instance guard, scope re-admission, consumer ownership, state-event settlement, journal, recovery, safety, watcher, provider binding and verified client attachment keep their gates, and the fixed 120-second interaction gate is unchanged. The service runs inside its own kill-on-close job that it claims at start, so its exit ends any descendant it may have started, and Node's exit observation of the service process is the stop proof; the final-attachment verified stop of the startup workers is replaced by a verified-live check of the service (its process identity and job membership, answered by the service and cross-checked against Node's child handle). If the service exits or a frame fails validation during a session, the in-flight request fails with the same failure the one-shot helper would report today, every later request is refused until the runtime has observed the old service's exit and started a replacement with a fresh handshake, at most once per runtime process; a second failure makes the runtime unavailable for mutations and the client shows the existing runtime-unavailable status. Standalone `status` stays a read-only reader and starts the service without any build step; when the image is absent or unverifiable, `status` reports the helper unavailable instead of building.

**Trust and first-launch build.** The binary is not committed. `runtime/native/compiled-images.json` keeps its role as the release manifest with one `helper` entry: toolchain name, version, target and flags, the ordered LF-normalized source list with digests, and the expected output size and SHA-256; `runtime/src/compiled-image-release.ts` keeps the manifest generation digest and the output digest as fixed reviewed pins. Before `openBackend`, the `chat`, `consumer` and `repair` commands run the native build step: if `runtime/native/companion-helper.exe` is present and its SHA-256 equals the pin, nothing is built; otherwise the runtime verifies every manifest source digest against the checkout, takes a build lock (`runtime/native/companion-helper.build.lock`, create-only, removed on completion, stale when its owner process is gone), reports the progress phase `nativeBuild`, and runs `go build` from the manifest's flags with the environment the runtime README prescribes for the images today (`CGO_ENABLED=0`, `GOENV=off`, `GOTOOLCHAIN=local`, empty `GOFLAGS`, `GOTELEMETRY=off`, every Go cache, temporary and profile location under the installation's `.tmp`), writing the output to a unique sibling temp and publishing it with a create-only move. The output is hashed and admitted only when it equals the pin. Refusals are one code, `nativeHelperUnavailable`, with a bounded reason: `go` not on `PATH`, `go version` not equal to the manifest version, a source digest mismatch (the sources changed without a re-pin), a build failure, an output hash mismatch (a non-reproducible environment), a lock held by a live process, or a publication failure. The refusal names the required toolchain version and the pin command below; it never falls back to a looser check, a cached binary from another location or the PowerShell path. A sharing violation on the existing image while another chat holds it open is reported as the existing close-chat remedy. The first build after a checkout or a source change takes seconds once the module cache is warm and longer when `golang.org/x/sys` must be fetched; it is reported as a one-time phase, not counted against the 30-second routine start, and the acceptance timing excludes it.

**Pinning the running image.** Before launching the service or a broker, the runtime hashes the image and compares it with the pin, as `releaseGoBrokerSpawn` does today. The service opens its own executable with `GENERIC_READ` and `FILE_SHARE_READ` for its lifetime and returns the SHA-256 of that held handle in the handshake, which the runtime compares with the pin; while the service lives, replacing the image is denied by Windows sharing, which is the same operator contract the startup execution design states for the selected path. The cross-process `DuplicateHandle` pinning of `NativeImagePins.cs` and the selected-bootstrap request grammar are retired with the selector.

**Developer workflow.** `node runtime/tools/pin-native-helper.ts` builds the image with the manifest environment, rewrites the `helper` entry's source digests, size and SHA-256, and rewrites the pins in `compiled-image-release.ts` and its test; a review verifies a pin by running the same build. The source list is every `.go` file and `go.mod` under `runtime/native/helper/` in sorted path order, so adding a file cannot escape the manifest. Go unit tests run with `go test ./...` in the module under the README's contained environment; `npm test` keeps the Node contract tests and gains a test that builds the image into a private `.tmp` location and checks reproducibility against the pin.

**Removal.** When the MVP ships, every script in the inventory except the core-reply validation trio is deleted together with every `.cs` file under `runtime/scripts`, the `.NET` compiled broker project under `runtime/native/process-broker`, the Go prototypes under `runtime/prototypes`, the committed images and their `.gitattributes` lines, `dotnet-environment.ts`, the DOTNET and NuGet members of `brokerEnvironment`, and the PowerShell-specific `.tmp/runtime-startup-*` helper scratch; the service's own scratch is the Go cache under `.tmp` named above. The compiled selector, its token module, the selected bootstrap and the private `fastCopiedStartup`, `privateGoBrokerSpawn` and `compiledBrokerSpawn` options are removed, since the helper is the only transport. `Get-FileToolAdmission.ps1` and `Get-StartupMetadataSource.ps1` have no production caller and are deleted without replacement; the file-tool adapter keeps refusing until a Go `fileToolAdmission` request is designed with the file-tool work. The runtime README's requirement line changes from PowerShell 7.5 to Go at the manifest version, with PowerShell remaining a requirement of the state core.

**Boundary with the state core.** The state core, its adapter and `core/DigestDiff.psm1` stay PowerShell under the state extraction design and are launched as today, through the Go broker instead of the PowerShell one. `Read-CoreReply.ps1`, `StartupCoreReplyWorker.ps1` and `CoreReplyValidation.ps1` import the core module and so belong to the core side of the line; the MVP keeps them as the one remaining runtime PowerShell launch, one supervised one-shot per core call, and the core-reply slice below removes them.

## Slices

- **Go helper and first-launch build (MVP).** The service and broker image, its manifest and pins, the build step and its refusals, every request in the inventory except core-reply validation, the removal list above, and the acceptance fixtures: open-reader publication, codec round-trips, job containment and exit-code relay for the broker (the cases `runtime/test/release-go-broker.test.ts` covers today), service crash and single restart, absent and mismatched image, each build refusal, and a copied-root chat fixture that completes a turn, an acknowledged restart and a graceful shutdown with no PowerShell process other than the core and core-reply launches, measured on the existing process-to-attachment timing fixtures.
- **Core-reply validation in Go.** Port `Convert-CoreReply` and the reply grammar it reads from `core/DigestDiff.psm1` into a `validateCore` request of the service, so a core call costs its own PowerShell process and nothing else; the core sources stay the grammar's authority and the port is verified against the existing core-reply fixtures. Requires the MVP.
- **State core in Go.** Replace the PowerShell state core and adapter glue (watcher, differ, mapper, acquisition entry points) under a revision of the state extraction design, keeping the digest and diff schemas, the consumer-ownership marker, the outbox and the save-directory read-only contract. This is a separate design decision; it is listed so the dependency order is explicit, and it ships only after its own spec revision. Requires the core-reply slice.

## Effects on other backlog entries

Shipping the MVP retires the compiled-selector acceptance gates of the startup execution design that concern parity with the PowerShell broker and the selected-bootstrap pin transfer; the remaining Coordinator startup latency gates (repeatable real-provider new-save, acknowledged-restart and recovery timing) are then measured on the helper path. The bug "Per-start helper profiles accumulate" and the quick win "Contained test pwsh profiles" lose their subject, and the runtime's contribution to ".NET tools folders leak into the User PATH" ends because the runtime stops redirecting `DOTNET_CLI_HOME` at all; that bug's confirmation check still applies to the untracked probe scripts it names. The bug "Selected path requires canonical launch spelling" concerns the selected bootstrap and is retired with it. Each of these is settled by its own backlog edit when the slice ships, not by this design.

## Anti-goals

No change to the digest, diff, state-event, journal or outbox schemas. No change to consumer ownership or the bridge. No fallback to PowerShell helpers when the Go image is unavailable. No automatic Go toolchain download: the runtime requires the manifest version locally and refuses otherwise. No pre-built image download. No change to the provider package or the text client beyond the progress phase and the refusal rendering.
