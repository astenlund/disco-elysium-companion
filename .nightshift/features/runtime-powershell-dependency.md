# Go native helper

Status: scope agreed with the user on 2026-10-23 and graduated from Exploring. The user raised the direction on 2026-10-18 as a follow-up to the compiled Go startup path and on 2026-10-23 decided that Go is the default language for native code, that one long-lived helper replaces the per-call PowerShell helpers, that the helper is built on first launch instead of being checked in, and that a local Go toolchain is an accepted host requirement. This design is governed with [companion execution runtime](companion-execution-runtime.md), [integrated startup execution](runtime-startup-execution-30.md) and [state extraction](state-extraction.md); [Superseded passages](#superseded-passages) names where it replaces their text. It does not alter the 30-second startup or 180-second recovery acceptance gates of [Coordinator startup latency](runtime-startup-latency.md).

## Problem

The runtime under `runtime/src` is TypeScript, but almost every native operation runs through `pwsh -NoProfile -File runtime/scripts/<script>.ps1`, and 22 of those 27 scripts compile one or more sibling C# files with `Add-Type` at every load. A supervised one-shot call costs at least three PowerShell processes on the shipped path: the broker `Invoke-OwnedProcess.ps1`, the helper child, and the `Get-OwnedJobState.ps1` job-absence check that `verifyOwner` runs when the broker closes. Each PowerShell start also carries profile, temporary-folder and .NET first-run side effects that the runtime now has to redirect under `.tmp` (`brokerEnvironment` in `runtime/src/compiled-broker.ts`, `dotnetFirstRunOptOuts` in `runtime/src/dotnet-environment.ts`, `prepareStartupHelperScratch` in `runtime/src/startup-helper-scratch.ts`); the open bugs "Per-start helper profiles accumulate" and ".NET tools folders leak into the User PATH" and the quick win "Contained test pwsh profiles" are all consequences of that machinery. The startup-scoped PowerShell workers (`StartupMetadataWorker.ps1`, `StartupCoreReplyWorker.ps1`, `StartupMutationWorker.ps1`) reduce the per-call cost during startup but add two long-lived PowerShell processes each, prove their source bundles by hashing their files at every start, and stop before client attachment, so player turns fall back to one-shot helpers.

The compiled Go images `runtime/native/go-broker.exe` and `runtime/native/job-observer.exe` already replace the broker and the job query on the selected compiled-image path, but that selector is off (`compiledSelectorEnabled = false` in `runtime/src/cli.ts`), the binaries are committed, and the startup execution design gates the selector on proving parity with the PowerShell broker it would replace.

## Design

**One helper image, two roles.** A single Go module under `runtime/native/helper/` builds one executable, `runtime/native/companion-helper.exe`. The module uses only the Go standard library and calls Windows through `syscall`, so a build needs no module download. Started as `companion-helper.exe service` it is the long-lived helper service: one per runtime process, started before scope admission and stopped at shutdown after the final marker write and before the guard is released, as Predecessor jobs and scope binding orders it. Started as `companion-helper.exe broker` it is the per-child broker that `go-broker.exe` is today: it claims a kill-on-close job containing itself and the child, launches the child with the version-2 control frame and writes the owned-process header. Any other argument list exits with code 2 and writes nothing to stdout. The job-observer logic becomes a request of the helper service. Every supervised child, including the provider, the watcher and the core entry scripts, keeps its own broker and job, so a helper service crash cannot end any child; the helper service holds no child job handle and starts no process.

**Wire protocol.** The service speaks the startup worker framing over stdio: each frame is a four-byte unsigned big-endian byte count followed by that many strict UTF-8 JSON bytes, with no trailing or unsolicited output and nothing on stderr. Request frames are 1 to 2,097,152 bytes and reply frames 1 to 2,097,152 bytes. The runtime starts the service with a fresh 32-lowercase-hex nonce argument; the first reply is exactly `{version: 1, nonce, pid, created, imageSha256, imageVolume, imageFileId}`, where `pid` and `created` are the service's own process identity in the existing creation-time grammar and the image fields describe the executable file the service holds open, as Pinning the running image states. Each request is exactly `{version: 1, seq, op, deadlineMs}` plus that operation's fields, and each reply is either `{version: 1, seq, op, status: "ok", result}` or `{version: 1, seq, op, status: "error", code}`. `deadlineMs` is the caller's remaining budget and never extends it. The runtime sends no request whose remaining budget is below 250 milliseconds: it fails that request locally with the caller's existing deadline failure and leaves the service untouched. The service enforces `deadlineMs` itself. A request that runs out before its commit point replies with the error code `deadlineExceeded`, which the reader maps to the failure the replaced script's timeout produces today; the commit point of a mutating request is its first change to a target, staging aside (the publication move or replacement, the first move or removal of a `fileAction`, the termination of `stopOrphanWatcher`, the first Quarantine deletion, the job creation of `bindScope`), and a request already past it completes and replies normally. Only a reply that has not arrived by `deadlineMs` plus a fixed five-second grace counts as a missed deadline under Lifetime and authority. Up to sixteen requests are in flight at once. The service runs each request on its own goroutine and writes each reply as one whole frame under a single writer, so replies may arrive in any order; the runtime correlates a reply to its request by `seq`, and a reply whose `seq` is neither in flight nor a missed request awaiting its late reply, or that repeats one already answered, fails frame validation. A request failed for a missed deadline stays remembered as missed until its first late reply, which the runtime validates as a frame and discards without reviving its caller or disturbing any other request, or until the service exits; at most sixteen are remembered at once, since each held a slot, and all are forgotten with the service. A slow request therefore never delays another request, and a request that misses its deadline fails alone, as Lifetime and authority states; only a fault of the whole service process (an exit, a frame that fails validation or a byte on stderr) ends every request in flight, since one process cannot isolate it. Four of the sixteen slots are reserved for proof requests (`jobStates`, `processIdentity`, `ownedProcessLive`), so other requests use at most twelve and a proof request is sent as soon as any slot is free, never waiting behind ordinary requests. The service shares no mutable state between requests except its scope binding, and the runtime sends `bindScope` only while no other request is in flight. The service client keeps its own request queue, which holds a request only while every slot it may use is taken, independent of the `PathInspector`, publication and core queues, and no service request is ever queued behind a queue its own caller holds: in particular, the stop proof of a `metadata` or `startupCoreReply` child awaited inside the `PathInspector` queue sends its job observation straight to the service queue, which never waits on another runtime queue.

**Request sequence.** The service remembers no request identifiers. `seq` is a positive integer that starts at 1 for each service process and increases by exactly 1 per request; the service fails closed on any other value, a repeated or out-of-order request included, by writing nothing further and exiting with code 125. Memory use is therefore constant over the life of the process. The runtime refuses to issue a sequence above 9,007,199,254,740,991; when the next request would exceed it, the runtime holds new requests until none is in flight, stops the service, observes its exit and starts a new one with a fresh handshake, and that renewal is not a failure and does not use the failure restart below. A bound service's renewal binds the same scope by the rule a restart replacement follows, as Predecessor jobs and scope binding states, before any mutating request reaches the new service. A renewal whose start, handshake or binding fails is a service failure and takes the single failure restart, or once that is spent, the helper-unavailable paths below. A test drives one service through more than 8,192 requests and checks the renewal branch with an injected low bound, including a mutating request that succeeds after renewal.

**Requests.** The service serves one request per native operation in the inventory except core reply validation: `admit`, `hash`, `inventory` (Inventory, Marker, Event and Quarantine modes), `eventMetadata`, `eventBatch`, `publish`, `codec`, `contextPreparation`, `fileAction`, `principal`, `processIdentity`, `jobStates`, `ownedProcessLive`, `stopOrphanWatcher` and `coreReplySource`, plus `bindScope`, defined under Predecessor jobs and scope binding. Each `ok` result carries the exact JSON value that the script it replaces printed on success, with the same field names, value grammar and bounds, so every TypeScript reader keeps its existing validation; each `error` code names the script's failure class (`admissionUnavailable`, `observationUnavailable`, `inventoryUnavailable`, `inspectionUnavailable`, `publicationFailed`, `documentInvalid`, `codecUnavailable`, `contextUnavailable`, `fileActionFailed`, `principalUnavailable`, `processIdentityUnavailable`, `jobUnavailable`, `ownedProcessLiveUnavailable`, `orphanWatcherUnavailable`, `sourceUnavailable`, `deadlineExceeded` for any request that runs out before its commit point, and `scopeUnbound` for a mutating request before binding), and the reader maps it to the same failure it takes today for that script's exit 1; a failed `principal` request fails with `identityUnavailable` for every command, chat included, since the combined bootstrap that mapped a chat principal failure to `dataRootUnavailable` is retired. Three results differ from their scripts. `eventBatch` returns the expanded documents JSON directly, bounded by the config document budget, instead of the zlib-compressed bytes the 65,536-byte capture forced. `jobStates` takes 1 to 16 distinct names, each a role job of the scope (current, `helper` or retired), and an `owner` that is null or the expected `{name, pid, created}` of one listed job; its result keeps the per-name `{name, state, processes}` entries and, only when an owner is named, adds a Boolean `owned` that is true exactly when that job's membership is that one process, replacing the script's eight-name bound and its owned-process, broker and console proof. `coreReplySource` is defined under Retained core reply validation. Request budgets, the admitted-root rule (only roots inside the companion root, never SaveGames; `coreReplySource` alone also admits its `runtime/scripts` bundle under the installation root, which may lie outside the companion root in private fixtures, exactly as `Get-StartupWorkerSource.ps1` does, and no other request accepts the installation root), the per-request deadline and the changed proof boundary of the startup-scoped metadata worker all carry over: the service retains loaded code and its input loop, never a target handle, file bytes, hash or observation between requests, and a reply proves that the request's handles closed before the frame was written. Byte-level outputs that are persisted or hashed (event documents, codec metadata and target identity digests, prepared context text, inventory identity digests, the request digests that readers echo) must be identical to what the C# implementation produces for the same input. The acceptance fixtures compare them directly against the C# implementation before it is removed, and the C#-produced outputs for synthetic inputs (never game data) are committed as reference vectors under the Go module's test data, which `go test` compares permanently, so byte parity stays checked after the C# removal; changing a vector is a format migration that needs its own decision. A `.gitattributes` rule marks `runtime/native/helper/testdata/**` as `-text`, so the vector bytes checked out are the bytes committed. File sharing matches the C# readers path by path: raw observations (`hash`, the `fileAction` preimage, raw event observation and `inventory`) open through `CreateFileW` with read and delete sharing, as `ObserveRaw` does, so they still exclude writers while they read, and bounded document reads and identity opens share read, write and delete, as `ReadBounded` and `NativeFiles.cs` do. Every open shares delete, and none goes through `os.Open` or `os.ReadFile`, whose handles withhold delete sharing and make a concurrent `ReplaceFileW` fail with a sharing violation. The service's hold on its own image, under Pinning the running image, is the only exception. `publish` keeps the state-extraction 7.1 discipline and the existing-target contract of the runtime design (complete old bytes for an already-open reader, complete new bytes for a new reader) through `MoveFileExW` with no flags for create-only or absent targets, deliberately omitting the `MOVEFILE_COPY_ALLOWED` that .NET `File.Move` passes so a publication can never become a cross-volume copy, and `ReplaceFileW` with `REPLACEFILE_IGNORE_MERGE_ERRORS` alone for existing targets, the flag .NET `File.Replace` passes when metadata errors are ignored; the acceptance fixture repeats the 2026-10-06 open-reader probe against the Go implementation before `Write-RuntimeFile.ps1` is removed. `codec` keeps the lossless payload contract of the runtime design, including numbers beyond JavaScript's safe range, negative zero, exponent spelling and seven-fractional-digit timestamps, through byte-preserving raw JSON handling rather than any decode-and-reencode path; the existing codec probes become Go tests.

**Lifetime and authority.** The helper service lives for the whole runtime process, which supersedes the decision in Coordinator startup latency that the warm worker is startup-scoped and that player turns use one-shot helpers: with every request leaving no retained state, a warm service during turns gives the one-shot guarantees without the one-shot cost. It is execution transport, not an authority cache: the instance guard, scope re-admission, consumer ownership, state-event settlement, journal, recovery, safety, watcher, provider binding and verified client attachment keep their gates, and the fixed 120-second interaction gate is unchanged. The runtime starts the service directly, not through a broker. The service exits when its stdin closes or its parent process ends and starts no process, so Node's observation of the service process exit is its stop proof; the only job it belongs to is the scope job it joins at binding. The final-attachment verified stop of the startup metadata and mutation workers is replaced by a liveness check of the service: a `processIdentity` request for the service's own pid whose created value matches the handshake. If the service exits or a frame fails validation during a session, every request then in flight fails with the same failure the one-shot helper would report today. If instead one request has no reply by its deadline plus the grace of Wire protocol, that request alone fails, and the runtime drains the service: it sends it no new request other than proof requests, which keep using the reserved slots within their own deadlines, accepts the reply of every other request already in flight within that request's own deadline plus grace, discards the missed request's own late reply as Wire protocol states, and only then stops the service and observes its exit, so a validated reply that arrives during the drain completes normally and a peer that also misses fails the same way. In both branches a proof request that failed only because its service failed, not because it observed a job or process present, is sent once more to the replacement within the restart window before its caller reports termination unverified, and a proof that cannot complete within its own budget leaves its child termination unverified, since no proof budget is extended; for every failed mutating request (`publish`, `codec`, `contextPreparation`, `fileAction`, `stopOrphanWatcher` and Quarantine trim) the runtime first observes the service's exit, stopping it when still running, before any target inspection, as it did for the startup mutation worker. A later request of any operation is not refused while the service is replaced: it waits in the service queue, within its own deadline, while the runtime observes the old service's exit and starts a replacement with a fresh handshake, which binds the same scope again once the old service's exit has closed its scope job, and the replacement then serves it. This covers every verification that follows a failed request, including publication readback, file-action postimage settlement, watcher stop proofs and the job observations of a child whose broker closes inside the window. When the failure restart is already spent, or the replacement fails to start, verify or bind, the waiting requests take the helper-unavailable paths below. This failure restart happens at most once per runtime process; renewal at the sequence bound and the rebinding of a replacement do not count against it. After a second failure chat stays attached and introduces no new status: every later native-dependent operation, supervised launches included, takes the failure path it already takes when its helper is unavailable (publication blocked or uncertain, a journal fault, failed freshness, `stateSafety` unavailable, a launch refused as Pinning the running image states), and shutdown follows the existing failed-shutdown rules, keeping the guard and leaving `cleanShutdown` false. Standalone `status` stays a read-only reader and starts the service without any build step; when the sources fail the manifest's source check, or the image is absent or fails its pin, `status` fails before scope discovery with `nativeHelperUnavailable` through the CLI's ordinary error output and exit code 1, naming the reason's own remedy (restoring a committed checkout for a source mismatch, running `chat` once to build an absent or pin-failing image), and adds no status field.

**Predecessor jobs and scope binding.** Retiring a launch role does not retire its job name from predecessor proof: a runtime from an earlier release, or one that ended mid-request, can leave a job named for a retired role (`publication`, `startupMetadata`, `startupMutation`) or for the new `helper` role. The helper service starts unbound: before binding it serves only the read-only requests (`admit`, `hash`, `inventory` in Inventory, Marker and Event modes, `eventMetadata`, `eventBatch`, `principal`, `processIdentity`, `jobStates`, `ownedProcessLive`, `coreReplySource`) and refuses `publish`, `codec`, `contextPreparation`, `fileAction`, `stopOrphanWatcher` and Quarantine trim with `scopeUnbound`. Binding happens right after the instance guard is taken and before any mutating request of the start, the creation of `scope.json` included: the runtime first observes the `helper` job and every retired name in one `jobStates` request and requires positive absence of each, then sends `bindScope` with the scope's job token, companion root and data root. The service creates the named job `Global\game-companion-process-<scope token>-helper` exclusively and assigns itself to it, failing closed with `jobUnavailable` if the job already exists or the assignment fails. A first start binds before scope initialization creates the data root, so binding admits only that root's location; from then on the service serves mutating requests only within that data root and admits every path again per request. A second `bindScope` is refused, and standalone `status` never binds, so it can never mutate. Later gates treat the `helper` name as an owned observation. Startup predecessor admission observes, in one `jobStates` request under the held guard, every current launch role (`core`, `provider`, `watcher`, `metadata`, `startupCoreReply`), the `helper` role and every retired name, and the pre-marker residue pass of the runtime design observes `helper`, `publication` and `startupMutation` before its scan and again before each deletion, in place of its prior publication-job check. Each observed name is absent, present or unavailable. A retired name passes only when positively absent. The `helper` name passes only when the job's sole member is the bound service, whose process identifier and creation time match its handshake; the `jobStates` request names that expected owner and reports whether the membership is exactly it. A present current launch role takes the existing predecessor-quiescence path. A present retired name, or a present `helper` job before binding, gets the same bounded absence poll that current roles get, up to five seconds, so a predecessor that is still ending does not fail a quick restart. A name still present after that poll, a bound helper job with any other membership, or an unavailable observation blocks the gate with the existing termination-unverified failure, since no in-process owner can stop it, and the remedy is to end the earlier runtime and retry. A later runtime's predecessor proof therefore sees a surviving service of a runtime that ended, until that service has exited. After the single restart or a renewal, the replacement binds only once the old service's exit has been observed and a fresh observation proves the helper job absent. Every guard release after binding is ordered after the service's exit: at shutdown the final marker write goes through the service, and on a start that fails after binding the existing role-quiescence checks run; in both cases the runtime then closes the service's input, observes its exit, which closes the helper job, and only then releases the guard. When that exit cannot be observed, the runtime keeps the guard while the process lives, under the existing failed-shutdown and failed-start rules, and reports the failed shutdown without rewriting a final marker already written: `cleanShutdown: true` attests the quiescence of every role except the helper service, which retains no handle or state between requests and whose survival the next start's predecessor proof blocks on.

**Retained core reply validation.** Core reply validation imports `core/DigestDiff.psm1` and stays PowerShell until the core-reply slice. Its path is kept unchanged: `Read-CoreReply.ps1`, `StartupCoreReplyWorker.ps1`, `CoreReplyValidation.ps1` and `StartupWorkerProtocol.ps1`, plus the six C# files they load (`NativeFiles.cs`, `JsonDocuments.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs`, `RuntimeCodec.cs`), the `startupCoreReply` process role, its transport (`runtime/src/startup-worker-transport.ts` and `runtime/src/startup-core-reply.ts`) and the framing helpers they use. During chat startup the warm core-reply worker opens and closes exactly as today; otherwise, and whenever it is unavailable, each core call validates through a one-shot `Read-CoreReply.ps1` under the `metadata` role. The worker's expected source digest now comes from the service's `coreReplySource` request instead of `Get-StartupWorkerSource.ps1` or the metadata worker's `sourceEvidence`. `coreReplySource` takes the companion root, data root and installation root and returns exactly `{status: "absent"}` when the companion root's `.tmp` directory is absent, the condition under which today's evidence is absent and no warm worker opens, or `{status: "present", scopeSha256, coreReplySha256}`, where `scopeSha256` is the SHA-256 of the admitted `scope.json` bytes and `coreReplySha256` is computed exactly as `Get-StartupWorkerSource.ps1` computes it today: the SHA-256 over, in order, each of `StartupCoreReplyWorker.ps1`, `StartupWorkerProtocol.ps1`, `Read-CoreReply.ps1`, `CoreReplyValidation.ps1`, `NativeFiles.cs`, `JsonDocuments.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs` and `RuntimeCodec.cs` under `runtime/scripts` and then each of the fifteen core files that script lists under `core/`, every file contributing a four-byte big-endian length followed by its bytes, read twice under one admitted identity. A missing or changed file, a non-directory `.tmp` or an unreadable scope is the `sourceUnavailable` error, and a file that changes between this observation and the worker's hello fails the worker's handshake closed, as today. The metadata and mutation digests and the combined bootstrap form with scope bytes are retired with their workers, so `StartupWorkerEvidence` keeps only `scopeSha256` and `coreReplySha256`. An acceptance fixture runs the publish, settlement and consumer core calls through both the warm worker and the one-shot path after the removal, and a check confirms that every file each retained script loads or dot-sources exists.

**Publication transport.** The publication queue, staging grammar, exact target readback, uncertain-response handling, cleanup ownership, crash states and recovery of the runtime design are unchanged. Two things change. The primitive is the Go `publish` request described above instead of the runtime-owned PowerShell helper, and the codec and prepared-context requests move with it. Verified process termination between ordinary publication requests is replaced by the per-request handle-closure proof of the service reply, with the service's process exit observed before target inspection whenever a reply is malformed, lost or late, as Lifetime and authority states; owned staging is removed after a validated reply or after that observed exit, and uncertain service termination retains ownership and blocks dependent work as uncertain helper termination did. The reconciliation that follows a failed `publish`, `codec` or `contextPreparation` reply (exact target inspection, codec verification and owned staging cleanup) follows the restart-window rule of Lifetime and authority and runs on the rebound replacement; when that rule ends in the helper-unavailable path, the reconciliation takes today's readback-unavailable path, so the publication stays uncertain and the publisher blocks. A lost or malformed reply still blocks later publication as today, because the reply's own sibling cleanup cannot be proven; a `publish`, `codec` or `contextPreparation` reply validated during the drain of Lifetime and authority is not lost, so an unrelated request's missed deadline never blocks publication by itself. The two in-process publication-writer gates that verified the `publication` role quiescent, before the redelivery fallback send and before phase-D residue cleanup, now require the publication queue to be idle with no `publish`, `codec` or `contextPreparation` request queued or in flight on the service; absence of the retired `publication` job is proven by the predecessor observations of Predecessor jobs and scope binding. The attachment and shutdown quiescence proofs drop `startupMetadata` and `startupMutation`, keep `startupCoreReply` and add the helper service's liveness or observed exit as Lifetime and authority states.

**Trust and first-launch build.** The binary is not committed. `runtime/native/compiled-images.json` keeps its role as the release manifest with one `helper` entry: toolchain name, version, target and flags, the ordered LF-normalized source list with digests, and the expected output size and SHA-256; `runtime/src/compiled-image-release.ts` keeps the manifest generation digest and the output digest as fixed reviewed pins. Before `openBackend`, the `chat`, `consumer` and `repair` commands run the native build step, which, when a build runs, reports the progress phase `nativeBuild` on the host's error stream for all three commands through a build reporter separate from chat's startup reporter: it repeats the 15-second heartbeat only while the build runs and finishes when the build step ends, with the terminal `native helper built` on success or `failed` with the refusal. `consumer` and `repair` report no other phase, and chat's startup reporter starts after the build reporter has finished, as today. The step first enumerates the source set from the checkout by the rule of Developer workflow and requires it to equal the manifest's list with every digest matching, so a cached image is never accepted for changed sources; a mismatch refuses with the source-digest reason. Only then, if `runtime/native/companion-helper.exe` is present and its SHA-256 equals the pin, nothing is built; otherwise the runtime builds. No native helper exists during this step, so it uses Node alone. It canonicalizes the installation root through its native final path (`fs.realpathSync.native`, which resolves case, junctions and substituted drives) and admits that root and `runtime/native` with an `lstat` walk that accepts only ordinary directories without reparse points. The build guard is a named pipe `game-companion-native-build-<installation token>`, where the token is the instance guard's token computed from that final-path spelling, so every spelling of one installation shares one guard; it is held like the instance guard for the life of the build and released by the operating system when its holder ends, so a guard held by another live build is the only lock state. Under the guard it admits `.tmp` and `.tmp/native-build` with the same walk. Each one that is positively absent, as `.tmp` is in a fresh clone, is created as an ordinary directory by one non-recursive create beneath its admitted parent and then admitted, and a create that loses a race to another process admits the entry that won; only a present entry that is not an ordinary directory, is a reparse point or cannot be read refuses. Once created, `.tmp` stays, so `coreReplySource` reports it present and chat opens the warm core-reply worker from then on. Then the runtime rechecks the image pin, since another start may have just finished building; removes the build directories that earlier builds provably created: each build picks a fresh `build-<32 lowercase hex>` name, first creates the empty claim file `build-<hex>.claim` create-only, then creates the directory of that name exclusively, then records the directory's volume serial and file index as `owner.json` before any other content is written there, writing the record to a unique temporary file in that directory and publishing it by a create-only move within the directory, so `owner.json` is either absent or complete and a write interrupted by a kill leaves only that temporary file. Since the guard proves no other build is live, the sweep removes a claimed directory, one whose name has that form and whose ordinary-file claim exists, when its `owner.json` is absent, as a kill before the record's move leaves it, or present and matching its identity, deleting its contents without following reparse points and then its claim; it removes a claim with no directory alone, and leaves every other entry, including an unclaimed directory or one whose record does not match, untouched and named in the build diagnostics; and removes a present image that failed its pin only after reopening it and confirming the volume serial and file index it hashed, so it never removes an image another start published meanwhile. Both `go version` and `go build` then run in an environment built from scratch rather than inherited: `SystemRoot`; `PATH` reduced to the directory of the `go` executable resolved from the inherited `PATH`; `GOOS`, `GOARCH` and `GOAMD64` from the manifest target; `CGO_ENABLED=0`, `GOENV=off`, `GOTOOLCHAIN=local`, `GOWORK=off` and an empty `GOFLAGS`; and `APPDATA`, `LOCALAPPDATA`, `USERPROFILE`, `HOME`, `TEMP`, `TMP`, `GOCACHE`, `GOMODCACHE`, `GOPATH` and `GOTMPDIR` all inside one unique build directory under `.tmp/native-build`. No other variable is passed. Go reads its telemetry mode from a file, not from the environment, so before the first `go` invocation the runtime writes `off` to `go/telemetry/mode` under the redirected `APPDATA`. `go build` writes its output into the same build directory under a ten-minute deadline. When the deadline expires, the runtime ends `go` with the system `taskkill /T /F`, which also ends every descendant still parented in its tree; a descendant it misses can write only inside the build directory. The output is published to the image path create-only, through a hard link, so a concurrent publication is never overwritten, and that link is the build's only write outside `.tmp`. The build directory is removed on every path the runtime survives, and the next build's sweep removes one a killed runtime left. The output is hashed and admitted only when it equals the pin. `runtime/native/companion-helper.exe` is git-ignored. Every native helper refusal, from the build step, `status`, the prelaunch check, the service start or the scope binding, is one code, `nativeHelperUnavailable`, with one reason from a closed list, each with its remedy. The build reasons are an installation root, `.tmp` or `runtime/native` that fails the build step's admission, whose remedy is to run from an ordinary directory; `go` not on `PATH` or `go version` not equal to the manifest version, whose remedy names the required toolchain version; a source digest mismatch, meaning the sources changed without a re-pin, whose remedy is to restore a committed checkout; an output hash mismatch under the required toolchain, whose remedy is to report it, since the reviewed pin and this build disagree, and never the developer pin command; a build failure or timeout, which also names the toolchain; a build guard held by another live build, whose remedy is to retry when that build finishes; and a publication failure or an image held by a running chat, whose remedy is to close that chat and retry. The image reasons are an absent image and an image that fails its pin, raised by `status` and by the prelaunch check, whose remedy is to run `chat` once to build it; `status` also raises the source-digest reason, with its remedy, when the checkout's sources fail the manifest's source check. The service reasons are a start or handshake failure and a held image whose hash or identity differs from the prelaunch observation, whose remedy is to rerun `chat`, which rebuilds the image when it fails its pin, and a bind failure after the predecessor observation proved the helper job absent, such as an exclusive creation lost to a concurrent start or a failed job assignment, whose remedy is to end the other runtime of this scope and retry. A predecessor helper job or retired name still present when binding starts is not a bind failure: it takes the termination-unverified path of Predecessor jobs and scope binding. A refusal never falls back to a looser check, a cached binary from another location or the PowerShell path. The first build after a checkout or a source change takes seconds; it is reported as a one-time phase, not counted against the 30-second routine start, and the acceptance timing excludes it.

**Pinning the running image.** The pins detect accidental drift: a stale or partial build, a changed toolchain or environment, or a concurrent rebuild. They are not a defense against another process running as the same user, which can already rewrite the runtime's TypeScript sources, the same boundary the startup execution design draws for its direct-main token. Within that boundary the image identity is established as follows. Before launching the service, the runtime opens the image, hashes it through that descriptor and records its volume serial and file index; the hash must equal the pin. The service's first act after start is to open its own executable path with read access and read sharing only, which denies writes, replacement and deletion for the life of the service, and to hash that held handle; the handshake reports that hash and the held file's volume serial and file index, and the runtime requires all three to equal its prelaunch observation and the pin before sending any request. A mismatch stops the service, observes its exit and refuses with `nativeHelperUnavailable`. Because the service starts and is verified inside phase A, `nativeHelperUnavailable` joins the runtime design's closed set of phase A to C fatal codes, and `phaseFatalError` passes it through with its reason instead of rewrapping it as `dataRootUnavailable`. Supervised launches are synchronous. While a verified service holds that handle, a broker process is created from the bytes the service's verified hold attests. While no verified service holds it during the restart window of Lifetime and authority, when a replacement can still serve the launched child's liveness and stop proofs, the runtime first reopens the image, hashes it and requires the hash to equal the pin and its volume serial and file index to equal the prelaunch observation, the same window and boundary the service's own prelaunch check accepts, and launches only then. An image that fails this check refuses the launch without creating a process, with the role's existing launch failure carrying `nativeHelperUnavailable` as its cause. After a second failure no service can prove a child's liveness or stop, so every supervised launch is refused the same way before any process is created: the watcher stops, the provider takes its failed or status-only path and a core call takes its helper-unavailable path. The remaining window, between the runtime's prelaunch hash and the service's own hold, cannot be closed from Node, which opens files with full sharing; a replacement in that window is either reported by the handshake mismatch or is the same-user rewriting the boundary above excludes. The cross-process `DuplicateHandle` pinning of `NativeImagePins.cs` and the selected-bootstrap request grammar are retired with the selector.

**Developer workflow.** `node runtime/tools/pin-native-helper.ts` builds the image with the manifest environment, rewrites the `helper` entry's source digests, size and SHA-256, and rewrites the pins in `compiled-image-release.ts` and its test; a review verifies a pin by running the same build. The source list is every `.go` file and `go.mod` under `runtime/native/helper/` in sorted path order, so adding a file cannot escape the manifest. Go unit tests run with `go test ./...` in the module under the README's contained environment; `npm test` keeps the Node contract tests and gains a test that builds the image into a private `.tmp` location and checks reproducibility against the pin.

**Removal.** When the MVP ships, every script in the inventory except the retained core reply validation path is deleted, together with every `.cs` file under `runtime/scripts` except the six that path loads, the `.NET` compiled broker project under `runtime/native/process-broker`, the Go prototypes under `runtime/prototypes`, the committed images and their `.gitattributes` lines, `dotnet-environment.ts`, `brokerEnvironment` with its scratch argument and the per-launch scratch admission, and the PowerShell-specific `.tmp/runtime-startup-*` helper scratch. The service starts with the runtime's environment and each broker with its child's environment, both without `HOME` as `withoutHome` provides today; neither needs a scratch directory, each child still receives its own environment through the version-2 control frame, and the Go cache exists only inside a build directory while a build runs. The startup metadata and mutation workers, their sessions in `runtime/src` and the warm job observer are removed, since the service serves those requests for the whole process; the `startupMetadata`, `startupMutation` and `publication` roles stop being launch roles, while their job names stay in predecessor proof as Predecessor jobs and scope binding states. Of the PowerShell test suites under `runtime/test`, those whose subject is deleted (`Test-ContextCodec.ps1`, `Test-ContextFingerprint.ps1`, `Test-FileToolAdmission.ps1`, `Test-NativeImagePins.ps1` with its fixtures `pin-helper.ps1` and `pin-target.ps1`, `Test-NativeJobs.ps1`, and `resource-lifecycle/Test-ResourceInventory.ps1`) are deleted with it, their cases carried into Go tests where the subject moved to the service, the inventory suite's capacity, Marker, Event-expansion and Quarantine-trim cases included with its identity digests among the reference vectors; those that exercise only retained C# files (`Test-PathAdmission.ps1`, `Test-PayloadCodec.ps1`, `Test-FilePublication.ps1`) stay while those files stay; and the orphan-job fixture `job-owner.ps1`, which loads the deleted `NativeJobs.cs`, is reworked to launch its process tree under `companion-helper.exe broker` with the watcher job name, keeping `owned-descendant.ps1`, which loads no C# file, as the descendant it starts, so the orphaned-watcher test keeps proving reconciliation through `stopOrphanWatcher`. ## Anti-goals

No change to the digest, diff, state-event, journal or outbox schemas. No change to consumer ownership or the bridge. No fallback to PowerShell helpers when the Go image is unavailable. No automatic Go toolchain download: the runtime requires the manifest version locally and refuses otherwise. No pre-built image download. No change to the provider package or the text client beyond the progress phase and the refusal rendering.
