# Integrated startup execution toward healthy 30 seconds

Status: decision-complete candidate design for the next startup execution slice; implementation and publication require their separate project decisions. This breakout belongs to [Coordinator startup latency](runtime-startup-latency.md) and is governed by [companion execution runtime](companion-execution-runtime.md) and [state extraction](state-extraction.md). It changes helper execution authority only; those documents retain their ownership, state-event, journal, safety, recovery, provider and client contracts.

## Objective and evidence boundary

The measured objective is at most 30 seconds from process start to healthy attached chat on routine clean startup with a newly detected save published, journaled and settled, and on an acknowledged-binding restart; healthy recovery remains at most 180 seconds. Enabled-watcher startup observation, fresh admitted state, runtime consumer ownership, healthy journal, ready safety, bound ready provider and verified startup-worker stop remain required at attachment. A phase-D-through-H fault may still attach a status-only client, but its elapsed time and fault are reported separately and do not satisfy either healthy target. Interactive credential login is excluded. The fixed current-source 120-second interaction gate is measured and tested separately, without changing its deadline, acceptance or result semantics. Presentation changes remain deferred.

The [copied-save timing controls](../reports/runtime-startup-copied-save-controls-2026-10-14.md) record 72.568 seconds from immediately before measured `openBackend` to in-memory fake-client attachment on the current path, and 48.338 seconds over the same broad boundary in a separate optimized scratch source snapshot with 2.406 seconds of explicit test-only job rechecks. A separate stub scheduling pair reached a 38.089-second synthetic fake-provider and verified-stop boundary without client attachment. Fixture staging and process launch are outside these clocks; none uses the real provider or client. These are distinct feasibility observations, not additive savings or proof of healthy 30. Earlier source-checked startup controls and their limits are recorded in [runtime startup spikes](../reports/runtime-startup-spikes-2026-10-14.md) and [runtime core startup feasibility](../reports/runtime-core-startup-feasibility-2026-10-14.md). A target miss never removes an admission, warning, write postcondition or worker-stop proof.

## Exact authority changes

The chat-only startup opens three independent scoped workers after the scope binding, instance guard, phase-C runtime-marker reservation, prior-marker read, watcher-orphan reconciliation and complete predecessor admission for every process role, including the new roles. `initializeRuntimeMarker` exposes a single post-admission, pre-write opening seam. A single pre-spawn source-evidence observation precedes all spawns; worker opening and the existing marker publication may then proceed concurrently. The marker publication remains on its one-shot path. No worker request is routed until the marker publication has passed its existing exact postcondition and that worker has completed its independently source-attested hello. If either side fails, wait for the in-flight marker operation to reach its existing reconciled outcome, close or stop every launched worker, verify their jobs absent, and follow the existing startup failure or verified-absence fallback rules. A valid prior marker with an orphan watcher is reconciled before opening; an absent prior marker has no orphan identity to reconcile; an invalid or unreadable marker, incomplete predecessor observation or surviving predecessor stops before opening. The new workers cannot grant marker, scope, guard, watcher or predecessor authority.

`startupMetadata` keeps its existing read-only admission, hash and exact Inventory/Marker modes, but its launch moves to that seam. Before marker completion it may load code and send hello only; requests wait for the marker gate. All pre-marker scope discovery, residue cleanup, Marker reservation and marker-publication admissions remain one-shot. After the gate, its fresh request-local observations and current failure mapping remain unchanged. Source change or mismatch invalidates the worker; an absent ordinary companion `.tmp` chooses the existing one-shot route for the startup, while invalid, unreadable or redirected `.tmp` fails closed. No worker creates `.tmp` or uses a compiler directory under runtime-data.

`startupCoreReply` is a new read-only process role. It warms exactly the current `Read-CoreReply.ps1` transformation for `Publish`, `Settlement` and `Consumer`, using the same admitted `core/DigestDiff.psm1`, its imported private scripts, and runtime native sources. It receives frozen captured core exit code, stdout and stderr after the original `Publish-StateEvent.ps1`, `Set-StateEventSettlement.ps1` or `Set-CompanionConsumer.ps1` child has terminated and its `core` job is verified absent. It returns the existing version-1 core-reply document, which `CoreClient.validate` and its current operation-specific TypeScript checks still validate; a worker success never turns an invalid core result into success. The worker does no core command, consume, settlement, cache, state write or result caching, and it closes request-local source handles before replying. The original core scripts, `CoreClient` queue, checked safety intent, journal append between Publish and Settlement, core-command process-stop proof, failure classifications and deadline accounting remain unchanged. No retained core-command host is introduced.

`startupMutation` is a new process role and the only warm mutating role. It executes the native work currently reached through `Write-RuntimeFile.ps1` and ordinary `Invoke-PayloadCodec.ps1`, including source/event inspection, create, rewrite, reconstruct, preview and codec `VerifyOnly`, after the host's existing `FilePublisher.exclusive` owner has completed guard, path, capacity, reservation, prospective-budget and staged-input checks. The host retains the one `FilePublisher` queue for file writes and codec calls, exact frozen input/control hashes, native result parser, destination admission and readback, cleanup of only owned staged files, deadline check and invalidation. The worker accepts one request at a time, performs no independent reservation or second publication attempt, retains no target handle or previous payload, and closes every request-local handle before its reply. It uses the ordinary companion `.tmp` as PowerShell compiler scratch, never a runtime-data `.tmp`; output targets remain inside the admitted identity scope. The original one-shot `publication` role remains available for pre-marker publication, final clean-shutdown marker and verified-absence fallback. `startupMutation` and `publication` are separate jobs, so an acquisition codec call cannot collide with the warm runtime writer. Non-chat commands, standalone status, bridge consumption and later turns keep their existing one-shot routes.

The three role changes do not relax `ResourceAuthority`, `ScopeStorage`, `OperationStore`, journal, safety or recovery readers. A worker is an execution transport, not an authority cache. Before each request the caller still obtains the fresh observation, binding and reservation its current site requires; after a reply it still applies the current host validation and use-time recheck. An ordinary native refusal stays its current typed refusal and never causes a permissive retry. A launch failure with verified job absence, or an absent `.tmp`, permits the unchanged one-shot route for that role. Source admission, hello or source-drift mismatch, malformed or unsolicited output, request timeout and uncertain stop fail the dependent operation closed. A failed or absent worker never supplies a stale reply.

## Batched source proof and wire contracts

The proposed `Get-StartupWorkerSource.ps1` is invoked once through the existing one-shot metadata transport with exactly `-CompanionRoot <held companion root> -DataRoot <held scope root> -SourceRoot <admitted runtime installation root>` and no stdin. Those three paths are nonempty normalized absolute paths; DataRoot must be the already bound child of CompanionRoot, while SourceRoot may be a different installation tree in a private fixture. Its stdout is one strict JSON object under the existing 65,536-byte metadata capture bound, stderr is empty on success, and a nonzero exit or malformed, partial, extra-field or oversized output is source-evidence failure. The helper has no mutation authority and emits no path or source bytes in its result.

One supervised, read-only pre-spawn evidence call checks the ordinary physically admitted companion `.tmp`, exact scope binding bytes and three independently named source bundles, replacing separate source-helper launches. Its own native admission and bounded double-read procedure follows the existing `Get-StartupMetadataSource.ps1` source-observation pattern: admit each file under its owning root, require ordinary singly linked files, read at most 1,048,576 bytes per file, re-admit and re-read, compare identity and exact bytes, and hash each bundle as the SHA-256 of ordered four-byte unsigned big-endian length plus exact bytes for each member. Missing, unreadable, changed, extra or aliased source fails the complete evidence call; an absent `.tmp` returns only `{status:"absent"}` and creates nothing. A present result has exactly `{status:"present",scopeSha256,metadataSha256,coreReplySha256,mutationSha256}` with four 64-lowercase-hex digests; scope digest is exact admitted `scope.json` bytes and must equal the held scope binding. No partial bundle may authorize a worker. Evidence is startup-local memory only, not a file or reusable cache. A changed source after evidence but before hello is rejected by the worker's independent admission and hash; a changed source after hello is rejected by a fresh same-bundle admission and hash before the next request. A completed request under pinned loaded code is not retroactively reinterpreted. Next startup takes new evidence. The evidence helper is one-shot through the current supervised metadata path, with no extra PowerShell launch per worker; if this batching cannot retain complete attestation and measured startup cost, implementation keeps the original separate proof and records the target miss rather than dropping a source check.

The metadata bundle is the current ordered ten-file bundle: `StartupMetadataWorker.ps1`, `StartupWorkerProtocol.ps1`, `NativeFiles.cs`, `JsonDocuments.cs`, `FileHashes.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs`, `RuntimeCodec.cs`, `resource-lifecycle/ResourceInventory.cs`, all under runtime scripts. The core-reply bundle is `StartupCoreReplyWorker.ps1`, `StartupWorkerProtocol.ps1`, `Read-CoreReply.ps1`, `CoreReplyValidation.ps1`, `NativeFiles.cs`, `JsonDocuments.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs`, `RuntimeCodec.cs` under runtime scripts, followed by `core/DigestDiff.psm1` and, in the module's current dot-source order, `private/CompanionJson.ps1`, `private/SourceIdentity.ps1`, `private/DocumentValidation.ps1`, `private/AdapterConfig.ps1`, `private/DiffEngine.ps1`, `private/ProcessRunner.ps1`, `private/Acquisition.ps1`, `private/StateFiles.ps1`, `private/Consumption.ps1`, `private/TurnContext.ps1`, `private/StateEvents.ps1`, `private/StateEventStorage.ps1`, `private/Watcher.ps1`, `private/WalkProtocol.ps1`, all under core. The mutation bundle is `StartupMutationWorker.ps1`, `StartupWorkerProtocol.ps1`, `Write-RuntimeFile.ps1`, `Invoke-PayloadCodec.ps1`, `NativeFiles.cs`, `JsonDocuments.cs`, `EventDocuments.cs`, `PayloadCodec.cs`, `RuntimeFilePublication.cs`, `RuntimeCodec.cs` under runtime scripts. The two runtime scripts are included even when their command body is moved into a common native entry point, so the one-shot and warm paths cannot silently diverge. Source roots are the admitted runtime installation and companion core roots, which may differ in private fixtures; no bundle member is inferred from the current working directory. An implementation edit to the module import list or native dependency list updates this complete bundle in the same change and proves it against actual imports.

All three workers use a four-byte unsigned big-endian length followed by strict UTF-8 JSON, with input length 1 through 2,097,152 bytes, output length 1 through 65,536 bytes, no duplicate/unknown fields, no unsolicited stderr or extra frame and no trailing bytes. The first output is exactly `{version:1,nonce,scopeSha256,sourceSha256}`: `nonce` is a fresh 32-lowercase-hex challenge passed at spawn, `scopeSha256` is the held 64-lowercase-hex scope digest, and `sourceSha256` is that role's 64-lowercase-hex bundle digest. The host checks the exact role, scope, source and nonce against the pre-spawn evidence before routing. The bound handshake deadline is at most 30,000 milliseconds from spawn and includes child identity and hello; it does not restart after child-ready. Request and reply identifiers are fresh 32-lowercase-hex values, never reused within a worker; each worker admits at most 8,192 requests. At most one request is in flight per role, including time in its queue. Every request has exactly `{version:1,id,op,root,remainingMs}` plus the operation fields below, where `root` is the exact bound normalized absolute companion or data root specified for that operation and `remainingMs` is an integer 1 through 30,000 capped by the caller's already running deadline. A worker may return exactly `{version:1,id,op,status:"ok",result}` or `{version:1,id,op,status:"error",code}`; result and code are mutually exclusive, and all error codes are fixed nonsecret tokens that map to current typed refusals. Timeout, late, missing, out-of-order, malformed or excessive reply invalidates that role and supplies no result. Only after its queue drains is EOF a normal close.

For `startupCoreReply`, `op` is `validateCore`; `root` is the held companion root, and the additional exact fields are `operation`, `exitCode`, `stdout`, `stderr`. `operation` is ordinal `Publish`, `Settlement` or `Consumer`; `exitCode` is integral 0 or 1; `stdout` and `stderr` are strict UTF-8 strings each bounded to 65,536 bytes and together serialize within the input frame and existing config budget. The worker executes the same `CoreReplyValidation.ps1` function used by `Read-CoreReply.ps1` and returns its existing bounded JSON object as `result`; host `CoreClient` applies the same `coreReplyVersion`, success/exit, class, reason, target hash, data and operation-specific checks as on the one-shot path. The sole error code is `coreReplyInvalid` for a native or core validator refusal; source drift invalidates the role without supplying a result, and no raw save, reply stream, exception or path enters an error frame. The validated failure envelope from a core exit 1 remains a successful validator result carrying `success:false`, never a worker transport error. The core command's original deadline is not renewed for the validator.

For `startupMutation`, `op` is `publish` or `codec` and `root` is the held data root. Both add exact `target`, `inputFile`, `inputSha256`, where paths are normalized absolute paths within that root and the hash is 64-lowercase-hex. `publish` further adds exact `profile` (`config` or `state-event`) and Boolean `createOnly`, with no codec fields; its success result is the existing exact `Write-RuntimeFile.ps1` object containing `published`, `sha256`, `cleanupComplete` and `retainedSiblings`. `codec` further adds exact `controlFile`, `controlSha256`, Boolean `verifyOnly` and Boolean `preview`, with no publication fields; its success result is the existing exact `Invoke-PayloadCodec.ps1` object containing `codecVersion`, `sha256`, `published`, `cleanupComplete` and `metadata`. The codec control file retains the current exact `{mode,metadata,compact,expectedSequence,createOnly,binding}` grammar and native validation; the worker must not infer a mode from the request. Codes are `publicationFailed`, `documentInvalid` and `codecUnavailable`, preserving the one-shot document-invalid distinction. Input and control files remain staged and fsynced by the host, and native code validates their hashes before use. Worker request parsing never grants write authority from a path string alone: exact bound root, scope, target kind, input/control kind and native publication's path checks still apply. The worker replies only after the native call returns and every request-local file handle closes.

The existing metadata worker keeps its published wire grammar, deadlines and 8,192-request limit. Shared framing and source-proof code may be extracted only while the three role-specific allowed operations, roots and error maps remain explicit. Parser and worker source lists are compared to actual loaded files in tests. No frame field carries raw payload bytes for the mutation worker; frozen payloads remain on the existing staged-file path and under the current byte budgets.

## Failure and durable-state lifecycle

The workers themselves persist no marker, checkpoint, receipt, source cache or ownership flag. Their scope is one guarded chat startup; after provider start or refusal and before client attachment, not-owner return, normal shutdown or guard release, stop new requests, settle or reject queued work, close each worker and verify every new role's job absent. The runtime's final clean-shutdown marker remains on the one-shot publication path after all startup roles are quiescent. A worker close failure retains the guard while the process lives and prevents clean marker or healthy attachment. A crash leaves the next start's full role admission responsible for any surviving job; failure to prove absence blocks startup. The existing marker, outbox, journal, safety and provider state retain their writers and readers.

Before marker publication begins, an absent ordinary `.tmp` selects one-shot transports without creating it; invalid, unreadable or redirected `.tmp`, failed pre-spawn source evidence, prior-watcher uncertainty or incomplete predecessor admission stops with the prior marker unchanged. A crash after predecessor admission but before any spawn or marker staging repeats fresh guarded admission. If a worker has spawned while marker publication has not started, a crash leaves the prior marker unchanged. On restart, a surviving `startupMutation` job requires an early writer-absence proof before residue cleanup, while every surviving read-only role remains subject to full predecessor admission before new worker opening or marker publication.

Once marker publication starts concurrently with worker opening and hello, the target may remain old, be staged with tmp or bak residue, or become a complete dirty marker with `cleanShutdown:false` before hello fails; no branch rolls it back. On marker or hello failure, await exact-target reconciliation of the in-flight publication, stop all launched workers and verify their jobs absent before any guard release. If reconciliation or stop is uncertain, retain the guard while the process lives and fail closed. On restart, guarded pre-marker residue cleanup must prove both `publication` and `startupMutation` jobs absent before its scan and again before every selected sibling deletion. An uncertain absence check stops before the next deletion, preserves remaining objects and retains the guard while the process lives. After cleanup, reserve the runtime marker, read the prior marker, reconcile any watcher orphan, and complete all-role predecessor admission before opening a new worker or writing a new marker. A valid dirty marker follows existing recovery, while incomplete publication follows the existing unavailable path. No request routes on a merely started worker or an unknown marker postcondition.

For publication, the host's staged input and optional control files, native target and temporary sibling retain the existing crash states: before staging there is no target mutation; after staging but before native completion the owned files are residue; after native target publication but before a reply, target bytes may have changed; after a validated reply, exact target readback and cleanup still decide success. A malformed, lost or timed-out mutation reply never authorizes a second mutation. First stop and verify `startupMutation` and its process tree; only then inspect exact target bytes and owned stage files through the current host postcondition path. For `Write-RuntimeFile`, reconcile exact expected target bytes and cleanup exactly as `FilePublisher.publish` does. For a mutating codec call, after verified stop run the current `VerifyOnly` path over the same frozen staged source/control, without re-publication, then do the existing target readback and cleanup; an ordinary source/event inspection can retry only under its existing nonmutating semantics. If stop is unverified, target or stage is unreadable/changed, VerifyOnly fails, cleanup is incomplete, guard is lost, or the deadline has expired for caller success, block the publisher, preserve owed authority and fail closed. An exact target found after an expired call is a recovery fact, not permission to extend a settlement or provider gate.

A codec create or rewrite can occur before a core record, between core publication and journal append, or during journal/settlement reconciliation. At each point the existing `Kernel.checked` intent, outbox record, journal transaction, safety record and settlement binding remain the only durable authority; worker success does not mark them complete. Crash before the core outbox commit repeats the core's own acquisition rules; crash after commit but before journal append drains that same record; crash after append but before settlement retries the same binding; crash after core settlement but before journal acknowledgement follows the existing settlement readback and journal rewrite. A helper reply lost at any such boundary is resolved only from its own target and then the higher-level durable records, never from elapsed time or worker memory. The 120-second safety check remains armed until its current result or recovery closes it. An unreadable, stale, duplicated, foreign or unexpected-kind durable record keeps the existing unavailable, conflict or recovery branch; no warm worker infers an empty state from an absent reply.

Not-owner and consumer hand-over still use the core command and owner marker before any provider input. A not-owner return closes all workers and keeps the existing consumer result; it does not claim healthy chat. Provider-start refusal closes all workers before shutdown and does not write a clean marker while any stop is uncertain. An ordinary native document refusal is reported without a second write; a source or protocol mismatch invalidates that role. If a role has verified absence after a launch failure or later stop, subsequent independent work may use its one-shot transport with fresh admission; no in-flight dependent operation is silently retried. Worker state is invalidated at close, scope loss, guard loss, source drift, provider refusal and startup failure. The post-close worker reference is never reused by a later turn or restart.

## Implementation boundary and reader-writer sweep

First establish a source-checked private baseline and instrumentation through process start, `openBackend`, marker, worker hello, acquisition, journal append, settlement, provider bind, verified stops and client attachment; record status at attachment and helper counts. Then add the two process roles to `processRoles`, native job-name validation, all-role predecessor admission, failed-open cleanup and shutdown fixtures. Move the metadata opening seam only after watcher-orphan reconciliation and all-role admission, retain one-shot marker publication, and prove marker/hello concurrency and guarded failure before adding another worker. Next implement the one-call source evidence and source lists, then the read-only core-reply worker and its parity. Add the single mutation worker last, routing both publication and ordinary codec under `FilePublisher.exclusive` while keeping host staging, reservations, exact readback, VerifyOnly recovery and one-shot final marker. Each boundary remains independently runnable with an off switch for a private control; no partial slice is described as meeting healthy 30.

The affected reader/writer sweep is explicit. `backend/marker-bootstrap.ts` owns marker ordering and watcher reconciliation; `backend/index.ts` owns open, failed-open, not-owner and shutdown sequencing; `runtime.ts` owns provider/startup-worker closure before attachment; `process.ts` and native `NativeJobs.cs` own every role's job name and predecessor admission; `StartupWorkerProtocol.ps1` owns shared framing and field parsing; `startup-metadata.ts`, its scripts and `PathInspector` own read-only metadata routing; `core-client.ts`, `Read-CoreReply.ps1`, `CoreReplyValidation.ps1`, `DigestDiff.psm1` and every dot-sourced private module own core-reply interpretation; `files.ts`, `codec.ts`, `Write-RuntimeFile.ps1`, `Invoke-PayloadCodec.ps1` and their native source set own the single publication queue, staging, mutation, readback and cleanup. `ScopeStorage`, `ResourceAuthority`, `OperationStore`, journal, outbox, safety and `Kernel.checked` remain consumers of those validated results and must be traced for changed timing or failure propagation. Search each process-role enumeration, helper source list, cleanup path, capacity inventory, source-reference comment and test fixture after changes; update all siblings the changed pattern covers. Standalone status, consumer and repair are negative routing controls.

## Acceptance matrix and decision gate

Private tests cover role admission and ordering with prior marker absent, valid clean, valid dirty, invalid and unreadable; watcher orphan absent, matching, mismatched and unverifiable; every old and new role absent, present, starting and unknown; and guard loss before spawn, during marker write and during stop. For each, assert whether the marker is unchanged, dirty or valid, whether any worker request ran, which jobs remain, and whether guard release is allowed. Inject termination after source evidence, each individual spawn, each hello, marker staging, marker completion and marker reply loss; restart from every durable state. Source tests cover absent/invalid `.tmp`, each bundle member missing/unreadable/changed during double read, changed between evidence and hello, changed after hello, wrong installation versus companion root, redirected or multiply linked file, altered module import and source-list mismatch. No mismatch may route a request or fall back permissively.

Protocol tests cover exact fields, duplicate/extra/missing members, UTF-8 and BOM handling, both frame bounds, wrong nonce/role/scope/hash, wrong operation/root/id, malformed result, status/code mismatch, unsolicited output, EOF, late and second replies, queue saturation, 8,192-request bound and expired caller deadline. Core-reply parity covers Publish, Settlement and Consumer successes, complete validated exit-1 diagnostics, malformed stream, shape, target-hash and operation-specific refusal, with original core children still verified stopped and the fixed 120-second gate separately exercised. Metadata tests retain fresh path, hash, Inventory/Marker, one-shot excluded modes and request-local handle replacement checks. Mutation tests cover create-only collision, replace under a held reader, native refusal, staged input and control changes, target change between reply and readback, tmp/bak residue, absent reply before and after target replacement, VerifyOnly success/failure, timeout, lost job and unverified stop. Cross a publication with a codec request to prove the one shared queue and no `publication` role collision; test worker close against queued and in-flight requests.

Whole-start private fixtures use copied saves and private companion/data roots only, with enabled watcher, fake provider and fake client. Run repeated source-frozen current-path and candidate controls for routine newly detected save with one actual core record, journal append and accepted settlement; acknowledged-binding restart with persisted provider-session resume; no-save diagnostic; healthy recovery; degraded status-only; not-owner; and provider-start refusal. Capture non-overlapping phase intervals, source hashes, original versus warm helper counts, core record and settlement identities, safety/journal/ownership/capacity/watcher state at attachment, verified worker-stop timing, test-only overhead and every target miss. Exercise the real current-source 120-second interaction gate separately with a complete accepted turn and a failure branch. Do not normalize away differences between source snapshots, and do not label the fake provider boundary as live ready.

Only after these private checks pass is a user-coordinated live measurement appropriate. Measure repeated real-provider, real-client starts from process start to healthy attachment on a newly detected save, an acknowledged restart and a recovery case, plus a status-only control if encountered. Keep the real SaveGames tree read-only and never run a real-root consumer command or mutate saves for this study. Completion is gated on repeated user-coordinated real-provider and real-client measurements: both routine fresh-save and acknowledged-binding starts must attach healthy within 30 seconds from process start, and healthy recovery must attach within 180 seconds. Any missed or unmeasured case keeps this candidate and the 30-second goal open; record its limiting phases and pursue the next agreed design without weakening provider readiness, startup settlement, watcher observation, safety or the objective. Local commits may retain validated partial improvements, but they do not count as goal completion. Earlier provider initialization and a retained core-command host remain separate design questions requiring their own source, authority, process-stop and whole-start evidence.
