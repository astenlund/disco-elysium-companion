# Session focus

A runtime-scoped declaration of what kind of progress the player wants now. Exactly one focus is active at a time. Balanced means no declared override: ordinary guidance ordering, including any learned interest profile, remains in charge.

The feature is useful without a TUI. Its MVP exposes preset selection through explicit conversation and runtime commands. A later paired TUI slice presents the same domain projection, and the adaptive-vocabulary slices learn new canonical focuses from repeated ad hoc requests.

## Delivery slices

While Adaptive Guidance and the TUI remain Exploring, only the Preset focus domain (MVP) is an active Session focus slice. Guidance integration, ad hoc activation, semantic comparison, promotion, Promotion delivery and restart rebind, TUI integration, and focus management remain deferred directional slices and are not parser-visible work units; their dependency order is preserved below until the exploratory upstream contracts graduate. ComparatorV1 and adapter-handoff contracts are inert compatibility groundwork in the MVP, not active MVP behavior.

### Preset focus domain (MVP)

Create the focus aggregate, initialize the adapter's canonical seed catalog, accept balanced and canonical selection commands, expose the provider-neutral focus projection, and apply runtime-start, play-session-end, and inactivity resets. Explicit conversation may select a canonical preset through the runtime command surface only after the runtime admits a current stable play-session ID. A missing play-session ID cannot mutate selection, activation, or audit state; when the request is at or after expiry, normal expiry-first processing still applies before the typed configuration rejection. Canonical-ID requests that do not name an available entry preserve focus identity, label, catalog, and activation history; conversational ambiguity is resolved before the domain command and is not a domain result. While a focus is active, the separate expiry-only keepalive may still change expiry and revision.

This slice requires the [Companion execution runtime: Single-session state coordinator (MVP)](companion-execution-runtime.md). It does not depend on the TUI or on the broader adaptive-guidance feature family.

### Guidance integration

Connect the focus projection to recommendation ordering and hidden-enrichment priority through the adaptive-guidance disclosure producer, Adaptive interest profile, and research scheduler. This continuation requires the preset-focus MVP, [Adaptive guidance knowledge: Evidence core and safe query](adaptive-guidance-knowledge.md#evidence-core-and-safe-query), [Adaptive guidance knowledge: Hidden enrichment policy](adaptive-guidance-knowledge.md#hidden-enrichment-policy), and the runtime's [Background work broker](companion-execution-runtime.md#background-work-broker). Keeping this integration separate preserves an independently usable headless focus domain while making the producer, scheduler, interest-profile, and broker dependencies explicit.

### Ad hoc activation and bounded history

Add conversational ad hoc focuses, provisional state, bounded comparison history, and durable low-priority comparison-job creation. This slice requires the preset-focus MVP, [Adaptive guidance knowledge: Evidence core and safe query](adaptive-guidance-knowledge.md#evidence-core-and-safe-query) specifically for activation-time safe-label production, and the runtime's [Background work broker](companion-execution-runtime.md). The conversational agent continues to own initial intent-summary approval; promotion-only classification remains gated to the later promotion slice. It owns insertion-time 256-entry cap enforcement, including victim ordering, active-entry protection, dependent-job terminalization, and late-result supersession. Age expiry belongs to the semantic-comparison slice. This slice owns the foreground canonical-resolution ComparatorV1 attempt and initial provisional-entry/job creation; it does not perform quiet-time canonical retries, pairwise semantic comparison, or promotion.

### Semantic comparison and retained evidence

Add quiet-time canonical-resolution retries and pairwise semantic comparison, age expiry, retained-evidence revalidation, comparison retry behavior, unresolved-entry retention, and adaptive-history handling across runtime restart. This slice requires [Session focus: Ad hoc activation and bounded history](session-focus.md#ad-hoc-activation-and-bounded-history) and the runtime's [Background work broker](companion-execution-runtime.md#background-work-broker) for quiet-time execution and restart rehydration. It does not depend on disclosure intent classification or promotion.

### Promotion domain and active-selection conversion

Add automatic promotion into the canonical catalog, matched-entry removal, active-selection conversion, and the domain promotion outbox and event payload. This slice requires [Session focus: Semantic comparison and retained evidence](session-focus.md#semantic-comparison-and-retained-evidence) and [Adaptive guidance knowledge: Evidence core and safe query](adaptive-guidance-knowledge.md#evidence-core-and-safe-query). Focus management depends on this slice when promoted canonical entries are required. Promotion remains unavailable until the disclosure contract and retained evidence are available.

### Promotion delivery and restart rebind

Add promotion delivery compatibility and restart rebinding through the runtime event lifecycle. This slice requires [Session focus: Promotion domain and active-selection conversion](session-focus.md#promotion-domain-and-active-selection-conversion) and the runtime's [Single-session state coordinator (MVP)](companion-execution-runtime.md#single-session-state-coordinator-mvp). Promotion delivery state is runtime-owned; the focus domain supplies the stable handoff, origin evidence, and complete post-transition projection needed for rebinding. Compatibility schemas and fixtures may land earlier, but promotion emission, application, and rendering remain inert until the promotion domain and delivery slices are available.

### TUI integration contract

Own provider-facing bindings only: capability declaration, wire schemas, projection serialization, reset and promotion event compatibility schemas, shared fixtures, and provider-side contract tests. Focus-domain slices own command semantics, projection construction, reset transitions, and event emission. The paired [TUI companion app: Session focus control](tui-companion-app.md#session-focus-control) slice owns consumer rendering and interactions.

Either paired slice may land first. A TUI implementation remains capability-gated and testable against fixtures until the provider exists; a provider implementation remains usable through conversation and runtime commands until a TUI exists. The second slice to land adds the end-to-end integration test and activates the control.

TUI integration remains separate so the headless provider contract can be validated independently and either paired slice can land first.

Maintenance invariant: any change to the shared focus command, projection, capability, or event contract must inspect and update the linked slice in the other feature in the same change.

The preferred cheaper order is to land this provider contract first, then the TUI control. The provider establishes the executable capability, command, projection, event contract, and shared fixtures, leaving end-to-end integration for the second landing. The reverse order remains supported through capability gating and fixtures when delivery constraints require it.

The provider's canonical selection options are canonical-only. ProjectionV1 `picker` contains the canonical entries and, while an ad hoc focus is active, one display-only Provisional transient row that is never a `focus.select` target. Balanced is rendered through the separate `focus.balance {}` action and is never a picker item. The linked TUI consumer follows this representation.

### Seeded focus management

Add rename and removal commands for seeded canonical entries. Removing the active focus resets the aggregate to balanced. There is no restore-defaults operation, and later adapter seed changes never reinsert removed entries. This deferred domain continuation requires the Preset focus domain (MVP) and remains non-parser-visible until graduation.

The concrete management UI belongs to each presentation client. The domain command behavior is part of this slice and remains available headlessly.

### Promoted focus management

Add the same rename and removal behavior for promoted canonical entries, preserving picker order and resetting an active removed entry to balanced. This deferred continuation requires Promotion domain and active-selection conversion plus Seeded focus management when staged sequentially. It remains non-parser-visible until those upstreams graduate.

Rename and removal wire details are outside capability version `1` and remain deferred until this slice. Before implementation, the slice must define request and result schemas, validation and error outcomes, event or no-event behavior, idempotency identity, and concrete fixtures while reusing the shared strict JSON, atomic persistence, replay, and fault rules.

## Ownership and scope

Session focus introduces a narrow focus service at the adaptive-guidance domain boundary. It owns focus meaning, catalog state, selection policy, expiry policy, and every transition of focus-domain state. The service is the only writer of focus-domain state; the runtime remains the owner of runtime journals, event delivery, and process and worker lifecycle.

The runtime supplies adapter and principal identity, runtime-start events, direct companion-interaction events, durable play-session-end events, timers, and background-job execution. It never interprets focus meaning. Presentation clients and conversational agents send commands and consume projections; they never mutate focus persistence directly.

State is isolated by `(adapter, signed-in principal)`, following [Runtime work, projection, and persistence boundaries](../patterns/runtime-work-projection-persistence-boundaries.md). The active selection is runtime-transient. The canonical catalog and, in the adaptive-vocabulary slices, unresolved comparison entries are durable domain state.

## Operating context

- **Deployment environment and operational criticality:** A local Windows companion runs for one signed-in principal beside a game. Focus is optional guidance state, not safety-critical infrastructure, and never writes game saves.
- **Audience:** The player is the sole operator and product audience; repository maintainers, adapter authors, and presentation-client implementers are trusted contributors. The audience category is `personal use` because the deployed product serves one owner rather than an organization or public user base.
- **Failure consequence and data or security sensitivity:** Incorrect ordering can waste play time, and a spoiler-projection failure can irreversibly diminish the playthrough. Persistence failures affect only companion focus state and must not reach saves. The catalog and activation phrases are local preference data, not credentials.
- **Concurrency and compatibility risk:** The domain service, runtime lifecycle, timer, conversational agent, background broker, adapters, and optional TUI may act concurrently through a versioned cross-feature contract. Compatibility and ordering risk are material.
- **Reversibility and recovery cost:** Active state is transient and resets fail closed to balanced. Catalog mutations are atomic and user-recreatable, although there is deliberately no restore-defaults operation. Recovery cost is bounded to companion preference state.
- **Expected feature lifetime:** This is a long-lived cross-adapter capability intended to survive new games, clients, and adaptive-guidance machinery.

Rigor derivation: `personal use` gives a low baseline. The failure-consequence, concurrency-and-compatibility, and expected-lifetime uplift predicates fire; deployment criticality and reversibility cost do not. Three uplifts reach the high-tier cap. Validation, recovery, compatibility, observability, and proof effort are therefore all high.

Judgment notes: trusted implementers do not change the personal-use audience category; spoiler irreversibility is enough to fire the failure-consequence uplift even though saves are read-only; the multi-writer-looking event surface fires the concurrency uplift despite the single domain writer; and the explicit cross-adapter direction fires the expected-lifetime uplift.

## State model

### Canonical catalog

On first initialization for an adapter and principal, the service atomically copies the adapter's seed catalog into durable domain state as an ordered persisted sequence using seed-table order. Later startups read that catalog and never merge, restore, or overwrite it from adapter seeds. Promotion appends each new canonical entry after existing entries in the same atomic transaction. Rename preserves position, and removal preserves the relative order of remaining entries. Capability version `1` defines a finite canonical catalog capacity and finite serialized projection and comparator candidate capacity. A promotion or repair whose committed result would exceed any applicable capacity fails closed with a typed capacity outcome and no silent truncation or hidden selectable entries; operations that remain within every capacity proceed normally. Archive, paging, or partition behavior requires a new capability contract; the v1 durable catalog is bounded. This preserves future edits and removals and makes the initial entries a starting set rather than privileged built-ins.

CapacityPolicyV1 is immutable: 64 canonical entries per adapter and principal, 65 ProjectionV1 picker items including at most one transient ad hoc row, 65,536 UTF-8 bytes for complete strict ProjectionV1 JSON without a byte-order mark, and 64 candidate objects per ComparatorV1 request or response. The unresolved adaptive-history limit remains 256. A typed `capacityExceeded` outcome carries operation context, scope, observed value, limit, unit, and retryability, exposes only player-safe text, and is present in every exhaustive carrier that can surface it. After identity, structural, safety, and expiry ordering, the complete prospective post-state is preflighted under the domain lock before model calls, deduplication writes, or mutation; load and seed preflight precede startup reset, and projection preflight includes the transient row. Failure preserves all state, generations, history, jobs, evidence, deduplication, and outboxes and never truncates or creates unprojectable active state. An over-cap persisted store exposes safe Balanced with an empty picker and `capacityExceeded` fault and requires repair. Seed and repair failures require corrected input; promotion records a terminal capacity outcome while leaving entries unresolved and resumes only after explicit state change or repair under the same operation identity. Candidate overflow makes no model call, oversized model output is retryable without evidence or recency, and projection or rebind overflow remains pending and unacknowledged. The same policy and its complementary branch govern every v1 producer and consumer, including initialization, load, commands, projection access, ad hoc activation, comparator request and response, job and result, promotion, repair, faults, outbox serialization, runtime rebind, and consumer admission.

The durable focus store carries `schemaVersion`, distinct from capability, event, comparator, entry-version, sequence, and store-incarnation values. Schema version `1` is the only supported persisted schema in the MVP. Older, unversioned, missing-schema, or otherwise unsupported stores fail closed to Balanced with `persistenceFault`, preserve their original bytes, and require explicit repair; v1 makes no unspecified migration or backfill promise. Explicit repair validates and atomically installs a complete supported v1 store without reseeding removed entries. The focus-domain repair operation uses a stable `catalogRepair` identity with `(adapter, principal, operationKind, operationId)` uniqueness, restart persistence, collision failure, same-ID replay, different-payload conflict, and stale-generation behavior. Its `operationId` is NFC UTF-8, has no C0 or C1 controls, contains 1 to 128 Unicode scalars, and is at most 512 UTF-8 bytes. Under the store lock it verifies the expected generation or explicit corruption precondition before installing a complete replacement with a fresh generation; if valid state has appeared, the repair is stale and makes no mutation. It is accepted only by the trusted maintenance path, never by player capability; a valid operation commits the complete replacement and dependency closure atomically, or preserves the prior store on validation or write failure. The active-entry removal invariant applies to repair: an accepted replacement that omits the active canonical ID produces Balanced in the same committed post-state, while a replacement retaining that ID preserves active state. Failed repair preserves the prior store and active projection. Automatic startup never synthesizes a malformed generation.

Startup ordering is load, validate, and seed binding first, followed by the normal startup reset only when a complete catalog is available. If no complete catalog is available, expose only a volatile Balanced ProjectionV1 with an empty picker and the existing configuration or persistence fault, perform no normal startup reset, operation identity, outbox, event, seed, or domain write, and block every non-Balanced command until repair. A healthy startup performs the reset and only then clears faults that reset is authorized to clear. Durable pending-reset recovery, journal repair, and explicit catalog repair are distinct trusted paths and do not become normal startup reconciliation. After a successful catalog repair, the runtime performs or recognizes exactly one healthy startup reconciliation under one governing operation identity before command admission, with its fault-clear behavior determined by the reset-source rules.

Healthy startup reset clears only selection-scoped `configurationFault`, `timerFault`, and `semanticComparisonFault` sources that its reset explicitly supersedes; it does not clear `brokerFault`, `capacityExceeded`, catalog or initialization `configurationFault`, or any persistence fault. Catalog or initialization and persistence faults survive startup until their owning repair or successful persistence transition resolves them. Malformed persisted fault-source metadata fails closed and preserves the player-safe fault, except for the separately resolved pre-store external-source branch.

Each canonical entry contains:

- A stable focus ID.
- A short, spoiler-safe display label.
- A spoiler-safe intent summary used to steer recommendation and enrichment priority.
- Creation and update timestamps.

Origin does not change selection, steering, presentation, or management behavior. Promotion may emit compact audit metadata, but a promoted entry is otherwise indistinguishable from a seeded entry.

All externally supplied and persisted text is valid UTF-8, NFC-normalized, and free of Unicode control characters. Required strings are nonempty. Kebab IDs use the exact ASCII grammar `[a-z0-9]+(?:-[a-z0-9]+)*`: lowercase letters or digits in nonempty segments separated by single hyphens, with no leading, trailing, or repeated hyphens. Canonical focus IDs use that grammar, contain 1 to 64 characters, are unique within the `(adapter, signed-in principal)` catalog, and must not begin with the reserved `ad-hoc-` namespace. Display labels contain 1 to 40 Unicode scalar values, intent summaries contain 1 to 240, and activation phrases contain 1 to 512. Generated labels and intents obey the same limits. Entry IDs use the same grammar and contain 1 to 52 characters so a derived promoted ID fits the 64-character catalog bound. Entry IDs are focus-domain-owned and durably unique across the catalog, activation history, comparison jobs, evidence, promotion handoffs, outboxes, and audit records for the adapter and principal, including late references to pruned entries. A collision or unavailable durable uniqueness proof fails closed with no partial mutation. Transient activation IDs use the same grammar, begin with `ad-hoc-`, and contain 1 to 128 characters. `runtimeInstanceId`, `runtimeSessionId`, `playSessionId`, and `incarnationId` use one opaque-token profile: valid NFC-normalized UTF-8, no C0 or C1 controls, 1 to 128 Unicode scalar values, and at most 512 UTF-8 bytes. Their owners generate collision-resistant values, and every consumer compares them exactly without parsing. Reset, journal-repair, catalog-repair, and promotion operation IDs use the same bounded profile and are focus-domain-owned durable identities except for runtime-owned journal-repair ingress, with exact comparison and preservation across restart. Each focus-domain `operationId` is unique within `(adapter, principal, operationKind)`, and its durable uniqueness key is `(adapter, principal, operationKind, operationId)`; runtime-owned journal-repair ingress retains its separate `(adapter, principal, journal identity, target sequence, operationId)` key. The internal activation source union is exactly `{ kind: "activation", runtimeSessionId, activationId }`; the internal operation source union is exactly `{ kind: "operation", operationKind, operationId }`, with operationKind exhaustively `startupReset`, `initialization`, `load`, `migration`, `catalogRepair`, `expiryReset`, `timerReset`, `sessionEnd`, `adapterHandoff`, `explicitBalance`, `comparison`, `broker`, `promotion`, or `journalRepair`. Pre-store faults whose main store cannot hold source metadata use the focus-domain-owned external source record defined in Failure behavior; there is no exemption path. A collision or malformed persisted operation ID fails closed without partial mutation and surfaces a player-safe persistence or configuration fault as appropriate. `eventId` uses the runtime-owned `EventIdV1` profile defined in the shared runtime pattern. Timestamps are RFC 3339 UTC strings with a `Z` suffix. Violating an encoding, normalization, control-character, emptiness, size, ID, timestamp, namespace, or uniqueness rule is malformed input.

Session-end is the exception to the focus-owned reset identity list: runtime owns `sessionCloseId` as the canonical identity, and Focus stores and replays that identity without minting a second session-end operation ID. Its runtime binding and retention rules remain those of the session-close ledger.

The Disco Elysium adapter seeds exactly these six records in this order:

| ID | Label | Intent summary |
|---|---|---|
| `story` | Story | Advance the main narrative and preserve critical-path momentum. |
| `side-content` | Side content | Pursue meaningful optional threads without sacrificing critical guidance. |
| `white-checks` | White checks | Prepare for and revisit available white skill checks. |
| `loot-money` | Loot and money | Find useful items and manage available money. |
| `thoughts-build` | Thoughts and build | Shape the detective's build through thoughts, skills, and equipment. |
| `exploration-lore` | Exploration and lore | Explore safely and deepen setting knowledge. |

Balanced is the absence of a selected catalog entry, not a seventh entry. No focus targets busywork. Balanced is represented as the null selection because it is control state, not a catalog entry: it is not seeded, promoted, renamed, or removed and has no catalog-entry persistence lifecycle. This preserves ordinary pre-feature ordering without adding a competing focus weight.

### Active selection

The active state is one of:

- Balanced: no focus ID, label `Balanced`, not provisional, and no expiry deadline.
- Canonical: focus ID and label from the catalog, not provisional, with the runtime's stable play-session ID plus selection and expiry timestamps.
- Ad hoc, after the Ad hoc activation and bounded history slice: a runtime-session-unique activation ID used as its ephemeral focus ID, generated label, intent summary, activation phrase, provisional status, runtime-session identity, the runtime's stable play-session ID, and selection and expiry timestamps.

The runtime supplies the current stable play-session ID when admitting any non-Balanced selection. Session-end reset work carries the ended play-session ID. It resets focus exactly once only when that ID matches the active selection's play-session ID. A mismatch between two valid, unequal play-session IDs is retired as a terminal stale no-op: it emits no reset, does not advance focus revision, and remains idempotent on duplicate delivery. A missing, malformed, or otherwise invalid identity is not stale; it follows invalid-command validation and the ordinary expiry-first ordering. This epoch guard supplements the runtime's replay-before-command barrier so delayed old-session work cannot reset a newer session's selection.

Session focus is runtime-scoped: the active selection lives only for one companion runtime lifetime. Runtime startup independently initializes it to balanced, even when startup reconciliation determines that the same play session and game process continue. A play-session-end event is a separate reset path. A TUI reconnect to the same live runtime preserves the in-memory selection. No active focus is restored after runtime restart.

### Projection and command contract

The provider-neutral `CapabilityDeclarationV1` is strict JSON shaped as `{ runtimeInstanceId, adapter, adapterBindingEpoch, sessionFocus: { version: 1, promotionMode: "compatibility" | "active" } }`. It is authoritative only for its current `runtimeInstanceId`, adapter, and binding epoch. Version `1` declares projection, canonical selection, balance, reset, and focus-event support. `compatibility` permits promotion schema compatibility only; live promotion emission, application, and rendering remain disabled. `active` is valid only after the Promotion domain and active-selection conversion and Promotion delivery and restart rebind slices are available. An absent, malformed, unsupported, or downgraded declaration fails closed: clients disable focus commands and live promotion, clear stale focus UI to a visible Balanced capability-unavailable state, and never infer or emulate support from prior UI or conversation. Management capability remains deferred to the management slice.

Capability version `1` uses strict UTF-8 JSON with case-sensitive field names, no duplicate properties, and no unknown fields. The projection contains:

- `capabilityVersion`: positive integer, with MVP value `1`. Any incompatible field, enum, or semantic change increments it.
- `runtimeInstanceId`: required nonempty opaque UTF-8 token generated once per companion process lifetime.
- `adapter`: required adapter identity.
- `adapterBindingEpoch`: required opaque epoch for the current adapter binding.
- `revision`: positive integer owned by the focus domain that increases for every committed focus transition, focus-fault transition, active-focus expiry keepalive, or current-runtime transient safety transition.
- `active`: object containing `kind`, nullable `focusId`, `label`, `provisional`, nullable `selectedAt`, and nullable `expiresAt`.
- `picker`: every canonical entry as a `{ focusId, label }` pair in persisted catalog order when the complete catalog is representable by this wire version, plus exactly one transient selected custom item with an ephemeral focus ID and label when `active.kind` is `adHoc`. If the complete catalog is not representable, the projection fails closed rather than truncating or hiding selectable entries. Balanced is a separate return-to-balanced action and never a picker item.
- `fault`: null or a player-safe `{ code, message }` object.

`active.kind` is exactly `balanced`, `canonical`, or `adHoc`. Balanced requires null `focusId`, `selectedAt`, and `expiresAt`, label `Balanced`, and `provisional: false`. Canonical requires a catalog focus ID, its label, `provisional: false`, and non-null timestamps. Ad hoc requires the activation ID as `focusId`, a player-safe label, `provisional: true`, and non-null timestamps.

ProjectionV1 `fault` is exactly the player-facing `{ code, message }` object and never carries source identity. Alongside it, the focus store atomically persists nullable internal fault-source metadata, null exactly when no current fault source exists, using the discriminated activation or operation source union defined above. Only the typed `focus.fault` event payload carries that tagged source. The player-facing fault may contain only a player-safe fault from `configurationFault`, `persistenceFault`, `timerFault`, `semanticComparisonFault`, `brokerFault`, or `capacityExceeded`; result-only codes never populate it. Consumer and runtime delivery faults (`projectionFault`, `staleProjection`, and `invalidProjection`) remain outside the projection and do not write this slot. When a producer fault change accompanies another committed focus transition, it is part of that single post-state, advances revision only through that transition, and appears in that transition event's complete projection. `focus.fault` is reserved for fault-only set, replacement, or clear transitions; an identical code and message is a no-op. A current fault is attributable to the focus-domain operation that produced it: the tagged source identifies that producer, never the clearing transition or runtime event, and is null exactly when no current fault source exists. For an accepted ad hoc activation, a comparator fault's source is `(runtimeSessionId, activationId)`, never the ingress `requestId`; the pair remains stable across comparator retries. Only same-source resolution or an explicitly source-superseding transition may clear or replace it; late or mismatched completion is a no-op. An unrelated incoming fault cannot replace an incumbent visible fault, advance revision, emit an event, or enqueue hidden replacement; its producer retains typed job and attempt evidence and retry or terminal behavior. A same-source changed fault replaces, an identical fault is a no-op, source-only resolution clears, and an empty slot sets atomically. A valid safe-fallback handoff is admitted; its activation-sourced `configurationFault` occupies the visible slot when comparator failure also exists, while comparator failure remains private retryable evidence. A successful same-activation label retry replaces fallback and clears only its configuration fault; if comparator failure remains it atomically becomes `semanticComparisonFault`, otherwise the fault clears. Comparator success clears only the same-source semantic fault. A changed accepted selection supersedes only selection-scoped `configurationFault`, `semanticComparisonFault`, or `brokerFault` when its own transition commits; a same-target selection with no aggregate change does not. A committed explicit balance supersedes only those active-selection-scoped faults, not `timerFault`, `capacityExceeded`, catalog or initialization `configurationFault`, or unrelated `persistenceFault`; a failed balance leaves the source fault unchanged. Keepalive, rejected commands, exact replay, duplicate, stale, and other no-op inputs preserve the slot. On restart, the service restores the persisted player-safe fault and its tagged internal source from focus-domain state, then derives a fresh current-runtime ProjectionV1 that never includes source identity; source is never reconstructed from projection bytes. Failed writes leave the prior slot unchanged.

After restart, source matching uses the restored tagged fault-source metadata, so only the matching source or an explicitly source-superseding transition may clear or replace a fault.

The tagged source metadata is internal and atomically persisted beside the domain state. ProjectionV1.fault is exactly the player-facing `{ code, message }` object and never contains source identity. Only the typed `focus.fault` event payload carries the discriminated source union. If the store is unavailable before source metadata can be persisted, the focus-owned external pre-store source record governs clearing and recovery; there is no exemption path and no unavailable-store identity is fabricated in player output.

A projection from another `runtimeInstanceId`, adapter, or adapter-binding epoch, or with a revision lower than the last accepted revision, is stale. A same-revision projection with different content, an unsupported capability version, or a projection with duplicate, unknown, missing, or malformed fields is invalid. Consumers map stale runtime, adapter, binding epoch, or revision to `staleProjection`, malformed, conflicting, or unsupported projection to `invalidProjection`, and missing or rejected capability, transport failure, or verification failure to `projectionFault`. These delivery faults remain outside ProjectionV1 `fault`, and exact UI copy is presentation-owned. Consumers show Balanced, surface the corresponding player-safe fault, and never infer focus from old UI state or conversation history. Loss, withdrawal, downgrade, or verification failure of a previously admitted capability moves the consumer to `capability-pending`, clears command admission and its projection baseline, and shows Balanced with the delivery fault. A newly valid declaration moves it to `projection-pending`; only the first structurally valid supported projection for that declaration's `runtimeInstanceId`, adapter, and binding epoch establishes a new baseline. After a typed runtime or adapter handoff identifies a new `runtimeInstanceId`, adapter, or binding epoch, a consumer enters `handoff-pending`, clears its prior instance, revision, adapter, and projection baseline, and accepts exactly the first structurally valid supported projection carrying the admitted identities. A same-ID duplicate handoff is a no-op. Prior-runtime and prior-epoch projections remain stale. An invalid or unsupported first projection does not establish a baseline; the consumer remains handoff-pending or projection-pending as applicable and shows Balanced with the corresponding fault.

Every command request is strict UTF-8 JSON with case-sensitive property names, no duplicate properties, a `type`, current `runtimeInstanceId`, current `adapter`, current `adapterBindingEpoch`, and caller-generated `requestId` of 1 to 128 characters using the exact kebab-ID grammar. The MVP requests are `{ type: "focus.select", runtimeInstanceId, adapter, adapterBindingEpoch, requestId, focusId }` and `{ type: "focus.balance", runtimeInstanceId, adapter, adapterBindingEpoch, requestId }`. `focus.select` is strictly canonical-ID based: it accepts only an available `focusId`, and natural-language mapping, ambiguity handling, and unsupported-language handling belong to the conversational agent before it emits this command. The deferred adaptive handoff is `{ type: "focus.selectAdHoc", runtimeInstanceId, adapter, adapterBindingEpoch, requestId, trustedActivationApproval }`, where `trustedActivationApproval` carries only runtime-bound approved label and intent, disclosure policy and version, raw-text capability evidence, and validated runtime-bound approval and snapshot data; it carries no activation identity and is not caller-supplied approved text. After structural, identity, disclosure, catalog, and expiry admission, Focus mints `activationId` under its lock and atomically binds it to the approval, runtime session, request identity, activation, entry, and job. Requests require the fields shown, reject null, unknown, duplicate, or case-mismatched properties, and apply the text grammar above. A duplicate or case mismatch returns `invalidCommand` before fingerprint derivation, deduplication, keepalive, or selection, subject only to the existing malformed-command expiry ordering. The command fingerprint is internal derived metadata and is never a wire field. A supplied `fingerprint` property is therefore an unknown field with the same result.

The service derives the fingerprint after structural and field validation. It NFC-normalizes strings, preserves array order, sorts object properties by ordinal UTF-8 property-name bytes at every level, emits JSON with no insignificant whitespace, encodes it as UTF-8 without a byte-order mark, and stores the lowercase hexadecimal SHA-256 digest with the deduplication record. Numbers use their schema-defined canonical decimal form; the request schemas contain no unconstrained numeric fields. Deduplication identity is `(adapter, signed-in principal, runtimeInstanceId, requestId)`. Exact command-request replay is same-`runtimeInstanceId` only. A request with the same identity and fingerprint returns its stored result without mutation. A same-ID different-fingerprint request returns `requestConflict`. Restart begins a new deduplication scope, so prior-runtime records never participate; an old request is stale, while a request from the current runtime is a new interaction. Requests bound to another runtime instance remain `staleRequest` and never restore transient focus or mutate expiry. Durable reset and promotion operations retain their separate focus-domain logical identities across restart.

Every received command returns exactly `{ type: "focus.result", accepted, stateChanged, code, projection }`, where `accepted` is true when a valid selection or balance request is honored, including an already-active target, `stateChanged` is true when any aggregate state changed, `code` is one of `selected`, `balanced`, `invalidCommand`, `unsupportedRequest`, `unknownFocus`, `invalidIntent`, `requestConflict`, `staleRequest`, `configurationFault`, `persistenceFault`, or `capacityExceeded`, and `projection` is ProjectionV1. Rejections preserve the selection result and every field other than the expiry metadata that the defined keepalive permits, subject to the exhaustive ordering matrix in Lifecycle. An unaccompanied direct malformed request returns `invalidCommand` and the current projection, with no invocation, derived fingerprint, deduplication record, command keepalive, or selection effect, even when overdue; an admitted chat may perform one keepalive or expiry reset before derived malformed bytes return `invalidCommand`. Structural validation always precedes deferred capability or slice gating: an adaptive command sent before its slice is available returns `unsupportedRequest` only when its shape and fields are valid, while malformed or unknown input returns `invalidCommand`. This is the only MVP domain producer of `unsupportedRequest`. Comparator failure still honors a valid ad hoc selection and therefore returns `selected`; `semanticComparisonFault` appears only in the projection fault slot.

The result-code set is exhaustive: `selected`, `balanced`, `invalidCommand`, `unsupportedRequest`, `unknownFocus`, `invalidIntent`, `requestConflict`, `staleRequest`, `configurationFault`, `persistenceFault`, and `capacityExceeded`. `ambiguousRequest` is not a domain result: the conversational agent resolves natural language before issuing an ID-only command. The focus-owned ProjectionV1 fault-slot set is exhaustive: `configurationFault`, `persistenceFault`, `timerFault`, `semanticComparisonFault`, `brokerFault`, and `capacityExceeded`. Consumer/runtime delivery faults are `projectionFault`, `staleProjection`, and `invalidProjection`; `supersededComparison` is a domain job outcome. These latter codes never appear in the focus-owned projection fault slot unless separately admitted by a future capability. Fault messages are player-safe and never expose internal exception text.

## Commands and selection

The conversational agent receives the valid catalog and may invoke the MVP commands only for an explicit request. It resolves natural-language intent to exactly one canonical ID before invoking `focus.select`; zero or multiple matches produce no domain command and require clarification. `focus.select` accepts canonical catalog IDs only; reserved `ad-hoc-` IDs and transient activation IDs are never selectable through this command. A domain rejection leaves active state, identity, label, catalog, and activation history unchanged; only the defined expiry metadata may change through keepalive. Repeated questions never silently select a focus.

`TrustedActivationApprovalV1` is the shared strict activation-time handoff from the runtime and disclosure producer to Focus. It is bound to the current runtime, adapter, adapter-binding epoch, signed-in principal, and `playSessionId`, and carries only the approved safe label and intent plus the validated disclosure snapshot and its governing policy, comparator, adapter, evidence-generation, store-incarnation, and candidate-version bindings. It has no activation ID and accepts no caller-supplied approved text. Missing, malformed, stale, foreign, or policy-rejected approval returns a typed stale or rejection outcome with no Focus mutation, no deduplication success, and no identity allocation. After the handoff is accepted, Focus mints the `activationId` and atomically binds it to the approval, activation, entry, and job.

The deferred `focus.selectAdHoc` command's `trustedActivationApproval` is exactly `TrustedActivationApprovalV1`; it carries activation-time safe-label and intent approval, not promotion-only classification. Unknown, duplicate, missing, null, or case-mismatched fields are invalid before fingerprinting or deferred-slice gating.

The conversational agent first approves one spoiler-safe intent summary for an ad hoc request, then passes a trusted internal activation handoff rather than caller-supplied approved text. The focus domain stores that summary once as the downstream comparator and guidance source; the raw activation phrase remains private and is retained while its owning entry is active, unresolved, eligible, requeueable, or otherwise referenceable. The adaptive command then resolves the approved request semantically against the canonical catalog. A confident exact-one canonical match selects that entry and records a canonical activation. A valid nonmatch or ambiguous result creates an ad hoc selection. A malformed or failed comparator response cannot select a canonical entry; it creates the requested ad hoc selection with `semanticComparisonFault`, persists one unresolved activation entry and job, and requires that job to complete canonical resolution successfully before pairwise vocabulary comparison may begin. When no valid canonical catalog exists, configuration or persistence failure takes precedence over adaptive classification: the command is rejected with unchanged Balanced safe state and no comparator or adaptive side effects. Ambiguity never forces a request into an unrelated canonical entry, and clustering never begins ahead of successful canonical classification. Direct or unbound intent is rejected before mutation. Structural validation, trusted approval and the current disclosure snapshot precede ComparatorV1; a missing, stale, unsafe, unavailable, or policy-rejected snapshot creates no activation, entry, job, comparator evidence, deduplication success, or focus mutation. Transient cases remain retryable. Comparator failure after valid admission retains the existing accepted provisional selection and its semantic fault behavior.

The raw activation phrase is private durable comparator input only. It is excluded from ProjectionV1, events, audits, logs, errors, and every presentation surface, and is deleted only in the same accepted atomic transition that makes its owning entry non-referenceable, including expiry, matched-entry removal, pruning, or repair omission or terminalization. Terminal job or attempt outcomes alone do not authorize deletion. Repair retaining an active or eligible entry carries forward its exact validated phrase; missing or changed phrase either rejects the repair with the prior store intact or terminalizes the entry and deletes the phrase atomically. Failed or stale repair preserves it. It may cross a provider boundary only when an explicit approved raw-text data-handling capability and policy admit it; otherwise comparison remains blocked or retryable with no disclosure.

Comparator version `1` uses these exact JSON shapes, with no unknown or duplicate fields:

- Canonical request: `{ "comparatorVersion": 1, "kind": "canonicalResolution", "activationPhrase": string, "intent": string, "candidates": [{ "candidateId": string, "label": string, "intent": string }] }`.
- Entry request: `{ "comparatorVersion": 1, "kind": "entryComparison", "source": { "entryId": string, "entryVersion": positiveInteger, "activationPhrase": string, "intent": string }, "candidates": [{ "candidateId": string, "candidateVersion": positiveInteger, "activationPhrase": string, "intent": string }] }`.
- Success response: `{ "comparatorVersion": 1, "status": "success", "scores": [{ "candidateId": string, "score": decimal }] }`.
- Failure response: `{ "comparatorVersion": 1, "status": "failure", "failure": { "code": "unavailable" | "timeout" | "invalidModelOutput" | "policyRejected" } }`.

ComparatorV1 also defines `guidanceResolution` with the same strictness: stable candidate identities, deterministic eligible order, one score per candidate, and explicit empty, single, invalid, and no-match branches. Its exact request is `{ "comparatorVersion": 1, "kind": "guidanceResolution", "activeIntent": string, "candidates": [{ "candidateId": string, "intent": string }] }`; its exact success response is `{ "comparatorVersion": 1, "kind": "guidanceResolution", "status": "success", "scores": [{ "candidateId": string, "score": decimal }] }`; and its exact failure response is `{ "comparatorVersion": 1, "kind": "guidanceResolution", "status": "failure", "failure": { "code": "unavailable" | "timeout" | "invalidModelOutput" | "policyRejected" } }`. Private activation text is excluded from player-facing output. Runtime owns raw-text capability and binding epochs with states `admitted`, `unavailableOrWithdrawn`, `denied`, and `invalidOrReplaced`. Withdrawal blocks new work, pauses queued work, and makes old-epoch results stale or superseded; fresh verified admission reopens only after revalidation. Canonical and entry-comparison results bind activation and attempt, entry versions, store generation, disclosure and comparator versions, and capability epoch. Guidance-resolution results instead bind the guidance pass, active-focus identity, candidate identities and order, comparator and disclosure versions, and current store or evidence generation. A non-current activation may update only still-valid private job or evidence state, never active projection or fault; expired, removed, or superseded results are deterministic no-ops.

Candidate arrays preserve request order and contain unique IDs. A successful response contains exactly one score for each requested candidate in the same order and no failure field. A failure response contains no scores. Each score is one finite JSON decimal in `[0,1]` with at most six fractional digits. Strings obey the shared field grammar and required fields are never null. Zero candidates returns a successful empty score array, has no runner-up, and cannot match; one candidate has no runner-up and needs only the `0.85` floor. Duplicate, missing, reordered, non-finite, out-of-range, over-precision, malformed, or version-mismatched responses are treated as `invalidModelOutput`. Canonical resolution accepts the best match only when its score is at least `0.85` and it leads the runner-up by at least `0.05`. A tie or insufficient lead is ambiguous and never selects a canonical entry. Completed comparison evidence records comparator version, candidate IDs, relevant scores, decision, and decision timestamp. A canonical-resolution attempt also captures the source store incarnation and generation plus the exact ordered candidate identities and comparison-relevant content and eligibility identity. The result applies under the store lock only after those bindings are revalidated. Same-incarnation recency-only drift may be revalidated; any substantive catalog change produces retryable stale with no selection.

| Adaptive classification branch | Result and projection | Active state and history | Hidden work and evidence |
|---|---|---|---|
| Valid confident canonical match | `selected`, accepted canonical projection | Select canonical; record canonical activation; create no ad hoc entry | No comparison job; persist successful classification evidence |
| Valid nonmatch or ambiguity | `selected`, accepted provisional projection | Select ad hoc; atomically record activation and unresolved entry | Create one durable job; persist successful nonmatch or ambiguity evidence |
| Comparator failure or malformed response | `selected`, accepted provisional projection carrying `semanticComparisonFault` | Select ad hoc; atomically record activation and unresolved entry | Create one durable retryable job; persist typed failure evidence; require successful canonical classification before entry comparison |
| Invalid adaptive command input | `invalidIntent` or `invalidCommand`, rejected current projection | Leave selection and history unchanged, except the validly framed `invalidIntent` branch may apply active-focus keepalive | Create no job or comparison evidence |

A later successful canonical-resolution result, including a nonmatch or ambiguity, clears the still-current `semanticComparisonFault`; a newer replacement fault is preserved. A confident canonical match settles the existing unresolved activation and job, records canonical attribution exactly once, suppresses pairwise work, and converts active state only when that same activation remains active, preserving its selection and expiry timestamps; otherwise current active state remains unchanged. A clear accompanying active conversion shares that transition and event projection. A successful nonmatch or ambiguity retains the ad hoc entry and proceeds to pairwise comparison. Another comparator failure leaves it unresolved and retryable. If clearing the fault is the only focus-domain transition, it advances revision once and emits `focus.fault` with `currentFault: null`; when no current semantic fault exists, no fault transition is emitted.

ComparatorV1 includes immutable threshold-policy semantics. These version 1 thresholds favor precision because an incorrect canonical selection or vocabulary promotion is costlier than falling back to ad hoc or unresolved state. Lower thresholds were rejected as too permissive, while higher thresholds were rejected as too conservative. The `0.85` floor governs canonical resolution, vocabulary-pair matching, and ad hoc guidance resolution. The `0.05` margin governs canonical and ad hoc guidance runner-up separation, while vocabulary-pair matching remains floor-only. Any threshold or calibration change requires a comparator-version change and invalidates retained decisions under the existing stale-evidence rules. They are version 1 calibration assumptions subject to outcome-based review.

Every newly accepted selection operation is serialized through the domain service and writes one structured focus activation audit record. When projection state is unchanged, that audit-only side effect does not set `stateChanged`, advance revision, or emit an event. Exact request replay writes no additional activation record. The service resolves expiry, selection, and lifecycle races in command order; presentation and runtime processes never become competing writers.

## Lifecycle

`InteractionContextV1.requestReceivedAt` is authoritative for selection timing. A changed selection sets `selectedAt` to that timestamp and `expiresAt` to eight hours later. Selecting the same target preserves `selectedAt` and extends only to a strictly later deadline. Expiry-reset-then-selection uses the same interaction timestamp. Canonical-resolution conversion, promotion conversion, and repair preserve persisted `selectedAt` and `expiresAt`; an uncommitted retry reuses the original interaction context, while committed replay returns persisted values without recomputation.

Deduplication projection bytes are historical, not replay authority. If the stored projection is current-safe, exact replay returns it byte-for-byte. If it is stale and no safety transition is required now, replay preserves the historical `accepted` and `code`, derives the authoritative current projection, returns `stateChanged: false`, and performs no mutation. If safety transitions now, replay returns those same historical fields with the current projection and `stateChanged: true`.

A canonical or ad hoc focus expires eight hours after the most recent player-originated chat submission or structurally valid explicit focus invocation received by the runtime. The eight-hour window preserves a deliberate focus through a long play period while bounding how long it can steer after the player's context may have gone stale. A structurally valid rejected request can record fresh player intent and active companion use, but only the rejection matrix below may commit a strictly later expiry. Malformed command bytes do not establish an invocation, but any player-originated chat submission that caused them already refreshes through the chat path. A runtime or model retry replays existing work rather than adding player intent; allowing retries to refresh expiry could keep a stale focus alive without further player action. Runtime or model retries, game activity, save changes, TUI launches or reconnects, passive viewing, and background work do not refresh expiry.

A rejected request while a canonical or ad hoc focus is active changes only `expiresAt` when `requestReceivedAt + eight hours` is strictly later than the current deadline. That keepalive sets `stateChanged: true`, increments `revision` once, writes a typed `focus.keepalive` outbox record with the complete post-keepalive projection, and follows the normal journal path. An equal or earlier candidate deadline is a no-op with `stateChanged: false`, unchanged revision and projection, and no event. Focus kind, identity, label, `selectedAt`, catalog, and activation history remain unchanged. A rejected request while Balanced is active is always a true no-op. This defines `stateChanged` as whether any aggregate state changed. Ordinary chat uses the same keepalive transition: the runtime assigns one interaction ID and receipt time to the chat bytes and any derived command bytes, and the domain emits the same typed event when that interaction strictly extends the deadline.

The runtime admits `InteractionContextV1` before Focus sees a request. It carries the immutable current authoritative `playSessionId` binding (or null when no sitting is active) alongside interaction ID, receipt time, and ingress order. Missing or malformed context fails closed at runtime. A context older than the admitted watermark, or carrying a valid play-session ID different from the current session, is mutation-free stale before malformed or identity handling, pending-reset, expiry, fingerprinting, deduplication, keepalive, or selection. Only admitted contexts enter this exhaustive Focus matrix. Commands and expiry then linearize under the domain lock against the admitted context's `requestReceivedAt`. Safety reconciliation of a pending reset and overdue expiry always precedes exact replay: replay is byte-identical only when no safety transition is required and the stored projection remains current-safe. After a committed safety transition or recovery, the historical acceptance and code may be preserved, but the result returns the current safe projection and `stateChanged: true`; selection is not reapplied and no activation or outbox side effect is created. A failed pending-reset recovery returns the safe `persistenceFault` path.

The no-side-effect rule applies to the replayed or later selection request; the safety transition's own reset outbox and completion records remain the sole durable recovery effects.

| Input branch | Expiry processing | Result and mutation |
|---|---|---|
| Runtime identity is valid and unequal to the current identity | Rejected before expiry processing | `staleRequest`, actual current ProjectionV1, no fingerprint, deduplication record, keepalive, selection, revision, event, or durable write |
| Unaccompanied direct command input is structurally malformed, including a missing or malformed runtime, adapter, or binding-epoch identity or a supplied `fingerprint` field | Rejected before pending-reset and expiry, even when overdue | `invalidCommand`; no invocation, request-derived fingerprint, deduplication record, command keepalive, selection, revision, event, or durable write |
| Same request ID with the same derived fingerprint, with no pending reset or overdue expiry and a current-safe stored projection | No lifecycle mutation | Return the stored result byte-for-byte with no refresh or event |
| Same request ID with a different derived fingerprint | Process overdue expiry before producing the conflict | `requestConflict`, actual current ProjectionV1, no keepalive; if expiry commits, return its reset projection and event |
| Current-runtime valid request received strictly before expiry | Continue against the active focus | Accepted selections and balance follow the transition table; valid rejections may keep alive only when the candidate deadline is strictly later |
| Current-runtime valid request at or after expiry | Commit expiry reset first, then process the request against Balanced | A successful reset followed by a rejection keeps its rejection code and `accepted: false` but returns `stateChanged: true` with the incremented Balanced projection; balance returns `accepted: true`, `code: balanced`, and `stateChanged: true` with that same projection. Both emit exactly the expiry `focus.reset`, with no keepalive or second `explicitBalance` reset. An accepted selection commits two transitions, expiry reset then selection, emits `focus.reset` followed by `focus.selected`, and returns the selected result at the prior revision plus two. If the reset cannot commit, return `persistenceFault` with the safe Balanced projection and do not process the later request. No-op describes only the later request's additional mutation |
| Current-runtime configuration or persistence fault | No keepalive | Return the typed fault with the safe projection; do not extend expiry |
| Current-runtime valid request while Balanced | No expiry mutation | Valid rejections and repeated balance are unchanged no-ops; a valid selection may transition to canonical or ad hoc |

A valid non-Balanced selection also requires a present, well-formed current `playSessionId`. Before expiry, its absence is an unchanged `configurationFault` with no selection, activation, audit, revision, event, or durable write. At or after expiry, expiry processing remains first; a successful reset is reflected in the rejection projection, and a failed reset returns `persistenceFault` without attempting selection.

When a command is strictly before expiry, the active focus remains current. A timer racing the same boundary observes the serialized result and becomes a no-op if the reset already committed. Projection reads also apply an overdue reset before returning state. If expiry reset commits and any later request-processing step fails, the response preserves Balanced, the reset event, and `persistenceFault` with `stateChanged: true` and the reset-revision projection; no follow-on selection, balance, keepalive, rejection-result persistence, or deduplication side effect occurs, and the same request retries fresh against Balanced without repeating expiry. If the expiry reset itself cannot commit, its pending-reset or timer-failure branch is authoritative and the later request is not evaluated. A post-commit response failure uses stable-request replay: exact replay is byte-identical only when the stored projection remains current-safe and no safety transition is required; otherwise historical acceptance and code are returned with the authoritative current projection and the applicable `stateChanged` value. Fixtures cover one tick before, exactly at, and one tick after the deadline for accepted selection, rejected request, balance, timer, and projection access, including malformed and stale-request branches.

For one admitted player chat action at time `t` that also yields malformed command bytes, the admitted-chat lane may perform at most one chat keepalive when `t < expiresAt`, or expiry reset at or after the deadline, before derived malformed bytes return `invalidCommand`. The malformed bytes create no invocation, fingerprint, deduplication record, command keepalive, or second refresh. Chat cannot revive the expired focus.

Fresh semantic repeats have these outcomes:

| Request | Result | Projection and revision | Expiry and event | Durable effect |
|---|---|---|---|---|
| Exact `requestId` and fingerprint replay with current-safe stored projection and no safety transition | Return the stored result byte-for-byte | Unchanged from stored result | No refresh or event | Read the deduplication record only |
| Exact `requestId` and fingerprint replay with stale stored projection and no current safety transition | Preserve stored `accepted` and `code`, derive the authoritative current projection, and return `stateChanged: false` | Current projection only; no domain mutation | No refresh or event | Read the deduplication record only |
| Select the already-active canonical focus with a new request | `selected`, `accepted: true` | Same identity; `stateChanged: true` and revision advances when expiry changes | Refresh expiry and write a `focus.selected` outbox record; if received at the same timestamp and nothing changes, `stateChanged: false` and no event | Store one activation audit and the result; store the changed projection and outbox only when expiry changes |
| Select a different canonical focus | `selected`, `accepted: true`, `stateChanged: true` | New canonical projection and one revision advance | Set a new deadline and write a `focus.selected` outbox record | Store activation, result, projection, and outbox record atomically |
| Balance while a focus is active | `balanced`, `accepted: true`, `stateChanged: true` | Balanced projection and one revision advance | Clear expiry and write a `focus.reset` outbox record with reason `explicitBalance` | Store result, projection, and outbox record atomically |
| Balance while already Balanced | `balanced`, `accepted: true`, `stateChanged: false` | Unchanged Balanced projection and revision | No expiry or event | Store only the deduplication result |

The runtime schedules the deadline supplied by the domain. If device sleep or runtime suspension crosses it, the first resumed timer or domain access applies the overdue reset before exposing state. If the timer cannot be scheduled, renewed, or verified, the service performs a distinct `timerFailure` reset with `timerFault`, a stable timer-reset operation identity, and the normal reset event path rather than leaving a sticky override. A timer-failure retry reuses that operation identity; a failure to persist the reset is a separate `persistenceFault` pending-reset path and never changes the reset reason to `timerFailure` after the fact.

Reset operation mapping is exhaustive: startup uses `startupReset`, session-end uses `sessionEnd`, expiry uses `expiryReset`, timer failure uses `timerReset`, explicit balance uses `explicitBalance`, adapter handoff uses `adapterHandoff`, journal repair uses `journalRepair`, and catalog repair uses `catalogRepair`. Session-end uses runtime-owned `sessionCloseId` as its canonical identity and the ended-play-session guard across restart and rebind; Focus does not mint a second close identity. Adapter handoff uses its runtime-owned source and target binding identity and lifecycle. Explicit balance uses the full request scope `(adapter, principal, runtimeInstanceId, requestId)`, never bare `requestId`. Every non-reset operation kind retains its named owner and separate identity namespace.

If an expiry or timer reset cannot commit durably, the service immediately suppresses only the runtime-transient active focus, advances the current domain revision once, and publishes a non-replayable current-runtime Balanced projection update with a player-safe `persistenceFault`; it never exposes the expired focus as the prior safe projection. This transient safety transition creates no domain outbox or journal event. It creates a `pendingReset` record when durable marker creation succeeds, containing a stable reset operation ID, immutable positive `projectionRevisionFloor` equal to the transient safety projection revision, compact immutable origin identity (reset reason, source selection kind and focus or activation ID, play-session ID when present, and source state generation), attempt state, and timestamps. The floor is distinct from source state generation and adaptive store generation. It contains no player text, activation phrase, label, intent summary, or projection data, and does not preserve a replayable event envelope or projection bytes. Later focus commands are serialized behind the reset or rejected with `persistenceFault` until it commits. Timer and domain access retry the same operation ID. A same-runtime or restart recovery commits revision `max(durableRevision, projectionRevisionFloor) + 1`, clears only that reset fault, and emits one durable `focus.reset`. Marker-write failure leaves the defined volatile-only lifecycle; a persisted marker before commit is retried by the same operation, ambiguous commit is resolved by operation completion, and a post-commit drain crash rebinds the same outbox. On restart, the runtime mints its new `runtimeInstanceId` before reconciliation and admits no commands until recovery finishes. Under the domain lock, recovery treats the marker as that runtime's sole startup reset, atomically commits the next Balanced ProjectionV1 revision, one `focus.reset` outbox record keyed by the stable reset operation ID, one operation-completion record, and marker removal. The runtime then drains that outbox before command admission, assigns a fresh current-journal event ID and sequence, and records the binding in its delivery ledger. Origin evidence remains compact audit data, old event or projection bytes are never replayed, and duplicate retries use the operation completion and outbox identity as no-ops.

While `pendingReset` exists, every focus-domain mutation and result-application path is blocked except the pending reset operation itself, including admin repair, pruning and expiry reconciliation, comparison evidence, promotion, and catalog management. No new queued work is admitted. In-flight computation may finish, but its result is deferred or retryable and nonterminal; it is not superseded merely because the gate was active. A restart gates command, administration, and broker admission until pending-reset recovery completes.

If marker persistence itself fails, equivalent volatile pending state preserves the Balanced safety projection and stable operation ID only for the remaining life of that runtime process. Timer and domain-access retries may reuse it while the process remains alive. Process exit discards the volatile safety revision and loses the volatile record and its operation identity. A restart with no durable marker initializes Balanced and performs exactly one fresh startup reset under the new runtime and operation identities; it never infers or replays the lost operation, restores the suppressed focus, or emits an event for the old operation. A restart with a durable marker performs the rebound pending reset as its sole startup reset, emits `focus.reset` with its immutable original reason, and never rewrites that reason or also emits a fresh startup reset.

With a complete validated catalog, focus resets on every runtime startup without a pending durable reset and every matching durable play-session-end event, whether caused by game-process exit or explicit sign-off; the no-catalog exception creates no startup reset. A recovered durable reset is the sole startup reset. All reset paths use the same transition. Session-end replay preserves runtime-owned `sessionCloseId` as its canonical logical close identity plus the ended `playSessionId`, not the old runtime event ID; Focus consumes that identity and mints no second close identity. Rebinding under a new runtime mints a fresh event ID, journal sequence, runtime identity, projection binding, and integrity metadata; old event bytes retire, and deduplication uses the logical close identity. Process exit, sign-off, and startup synthesis for an already-closed session are duplicate no-ops; replay of an acknowledged event is a no-op. Replay is gated only against commands for the ended `playSessionId`. Once a newer play session is established, its commands may proceed; delayed replay of the older end is retired by the play-session guard with no reset, revision, event, or focus mutation. A rebound end for an older play session reaches current delivery, then the domain guard retires it. Reset creates no chat notice, toast, or inbox item.

When a complete validated catalog admits startup reconciliation, startup reset has a stable focus-domain operation and outbox identity persisted atomically with its completion. A crash before commit retries that same startup operation; a commit before drain rebinds the same operation and suppresses a second fresh reset. Once delivered and completed, the next runtime creates and owns its own new startup operation.

Focus events use strict version 1 JSON envelopes with exactly `eventVersion`, `eventId`, monotonic journal `sequence`, `runtimeInstanceId`, `adapter`, `adapterBindingEpoch`, `occurredAt`, `logicalOutboxId`, `type`, `projectionRevision`, complete `projection` ProjectionV1, and typed `payload`. `logicalOutboxId` is internal event identity outside ProjectionV1 and player output, persists once per transition, and remains stable across rebind while runtime event metadata is fresh. The common strict UTF-8 JSON rules apply recursively. The envelope's projection runtime identity, adapter, and binding epoch equal its envelope fields, and `projection.revision` equals `projectionRevision`; any mismatch is invalid and cannot enter the journal. Version 1 payloads are exact:

- `focus.selected`: `{ selectionKind, focusId, playSessionId }`, where `selectionKind` is `canonical` or `adHoc`, `focusId` matches `ProjectionV1.active.focusId`, and `playSessionId` matches the authoritative play-session ID stored with the post-transition internal active selection. `ProjectionV1` remains player-facing and does not add `playSessionId`.
- `focus.reset`: `{ reason }` except that `sessionEnd` requires `{ reason, endedPlaySessionId, sessionCloseId }`. `reason` is `startup`, `sessionEnd`, `expiry`, `timerFailure`, `explicitBalance`, `adapterHandoff`, `journalRepair`, or `catalogRepair`; `endedPlaySessionId` and `sessionCloseId` are forbidden for every other reason. `sessionCloseId` is the runtime-owned canonical close identity and is not minted by Focus. The post-transition projection is Balanced.
- `focus.keepalive`: `{ source, rejectionCode, expiresAt }`, where `source` is `chat` or `rejectedCommand`, `rejectionCode` is null for `chat` and is `unsupportedRequest`, `unknownFocus`, or `invalidIntent` for `rejectedCommand`, and `expiresAt` equals the active projection deadline. The source and nullability combinations are exhaustive; a chat keepalive is not represented as a command rejection.
- `focus.promoted`: `{ operationId, focusId, label, activeSelectionConverted }`, where the catalog and picker contain the canonical focus and label. When conversion is true, the active projection is that canonical focus; otherwise active selection is unchanged.
- `focus.catalogRepaired`: `{}`, where the complete projection carries the repaired catalog and retains any still-valid active selection. This event is forbidden when repair resets to Balanced or leaves ProjectionV1 unchanged.
- `focus.fault`: `{ priorFault, currentFault, source }`, where each field is required, the fault values use the ProjectionV1 fault shape, prior and current differ, they are not both null, and current equals `projection.fault`. `source` is the exact discriminated activation or operation source persisted with the current internal fault-source metadata; it is null exactly when that metadata is null. Source identity is never part of ProjectionV1 or player output.

The domain writes the typed payload plus complete post-transition projection to an outbox record atomically with its transition; the runtime journal owner drains it idempotently and mints `EventIdV1` event ID, current-journal sequence, occurrence timestamp, and integrity metadata. The focus domain owns `projectionRevision` and `ProjectionV1.revision`; runtime delivery does not mint or advance projection revision. Events replay oldest-first, and replay never overwrites newer projection state or reuses stale projection bytes. These events are UI transition signals only and never chat notices, toasts, or inbox items.

The runtime owns event acknowledgement, replay, cursor state, delivery recovery, quarantine, retirement, and journal-repair ingress under [Runtime work, projection, and persistence boundaries](../patterns/runtime-work-projection-persistence-boundaries.md#durable-state-event-lifecycle). Runtime journal repair owns quarantine and the idempotency identity `(adapter, principal, journal identity, target sequence, operationId)`, and supplies validated immutable target evidence to focus. Focus CAS-validates current state and commits one Balanced `journalRepair` reset/outbox or an authorized no-state-change outcome when already Balanced; runtime appends only that domain-authorized or rebound event. Same-identity replay returns the stored outcome, target conflict is rejected, stale, foreign, or retired targets are no-ops, and repair failure leaves the original journal and cursor unchanged for retry. Restart partial states are resumed by the same identity, and command admission remains blocked until terminal completion. A valid matching session-end or journal-repair input resets to Balanced. A duplicate, stale, foreign, quarantined, or retired input does not mutate focus. Runtime delivery or acknowledgement failure leaves focus unchanged. A new runtime starts authoritative Balanced state; a TUI reconnect preserves the live selection because the same runtime identity remains active. The execution runtime owns a typed `runtime.handoff` signal carrying the new `runtimeInstanceId`, adapter, and adapter-binding epoch before that instance's first projection. Consumers enter handoff-pending on that signal, clear the prior instance, adapter, revision, and projection baseline, and same-ID duplicate handoffs are no-ops. Runtime acquisition is idempotent on attach or reconnect, capability replacement, and runtime or adapter handoff, fabricates no event or revision when state is unchanged, follows the normal expiry-reset path first when overdue, and blocks target commands until a healthy catalog and a structurally valid projection for the admitted identities are accepted. A structurally valid fallback projection does not release target commands. An adapter switch clears the old adapter's focus baseline and rebinds the focus service to the target adapter before admitting the target adapter's first projection; no old-adapter or prior-epoch command, projection, or event may cross that boundary.

Startup resets fail closed because a runtime restart provides no durable proof that the prior declaration remains current; a TUI reconnect preserves it because the same live runtime retains the in-memory declaration. The direct-interaction keepalive boundary above remains authoritative across both paths.

Adapter switching is an explicit focus-domain/runtime boundary. The runtime completes the old session-end, discards the runtime-wide active selection through the typed `adapterHandoff` reset, retires old-epoch work and delivery, binds the target store and binding epoch, then emits the target session-start before admitting the target Balanced/current projection and releasing commands. Switching back never restores the prior active selection. A duplicate switch is an idempotent no-op; a failed handoff preserves the safe Balanced gate and retries the same handoff identity, while a malformed or foreign handoff mutates nothing.

Valid unequal values in any member of the current `(runtimeInstanceId, adapter, adapterBindingEpoch)` identity triple are `staleRequest` before expiry, deduplication, keepalive, or selection and are mutation-free. Malformed identity is `invalidCommand`. Only the current identity triple reaches expiry, deduplication, keepalive, or selection; the canonical repository adapter identity is `disco_elysium` and hyphenated aliases are invalid.

Every focus-domain mutation, including initialization, migration, selection, balance, keepalive, reset, repair, ad hoc activation, pruning, comparison evidence, promotion, and later catalog management, follows one atomic persistence rule. Before commit, validation or write failure leaves the prior durable aggregate, projection, revision, catalog, history, and deduplication records unchanged and returns `persistenceFault` with the prior safe projection, except for the runtime-transient safety suppression defined for a failed expiry or timer reset. Every focus outbox carries a stable logical operation or outbox identity and immutable origin evidence. Command transitions retain validated `requestId` where applicable; reset and fault transitions retain their governing domain operation identity. Runtime event identity, sequence, timestamp, and integrity metadata are delivery bindings only; ProjectionV1 revision remains focus-domain-owned. The runtime journal is a separate store: its owner drains each outbox record idempotently under the journal lock and records the outbox identity, so a crash before drain leaves the outbox pending and a crash after journal append but before acknowledgement is recovered as a duplicate no-op. After domain commit, response or projection failure never rolls back or repeats the domain mutation; replay uses the stable request or operation ID, rebinds pending delivery to current-runtime identity, and never reuses old projection bytes. Runtime-owned event delivery and acknowledgement follow the linked lifecycle. ## Guidance behavior

Adapter handoff uses the runtime-owned durable `handoffIdentity` binding principal, immutable source and target adapters, and source and target binding epochs. Focus stores that identity and immutable bindings as origin evidence, then mints a distinct focus-owned `adapterHandoff` reset `operationId`; their association is persisted so duplicate valid handoff references resolve to the same focus operation. Same identity and bindings replay idempotently; differing bindings conflict; malformed, foreign, or stale inputs mutate nothing. Resumable phases are ordered: end the old session, discard and reset active state, retire old-epoch work and delivery, bind the target store, establish target session-start position, admit target Balanced and current projection, then release commands. Restart resumes the same identity without repeating completed phases. Failures retain the safe gate and retry; invalid target capability or projection keeps commands blocked, and old-epoch traffic never crosses the boundary. The runtime handoff identity is never reused as the focus reset operation identity.

Focus is a priority nudge, never a filter. Filtering was rejected because it would hide otherwise eligible guidance, including context the player still needs. A busywork focus was rejected because busywork is a classification boundary, not a desirable progress target; focus may reorder classifications but never redefine them. Guidance order is:

1. Mandatory response notices and safety or evidence constraints.
2. The player's direct question.
3. Critical time-sensitive guidance.
4. Focus-adjusted ordering of the remaining recommendations.
5. Learned-interest ordering when no declared focus decides the order.

After items 1 through 3, guidance forms the complete eligible recommendation set without changing eligibility. The adaptive-guidance disclosure service is the sole producer and validator of focus guidance metadata; runtime and presentation clients consume projected recommendations without authoring or repairing it. The exact internal shape is `{ focusIds: string[], intent: string }`. `focusIds` is required, ordered, contains unique known canonical IDs using exact ID equality, and uses `[]` as its only empty form. `intent` is required, spoiler-safe, valid UTF-8, NFC-normalized, free of Unicode control characters, nonempty, and 1 to 240 Unicode scalar values. Unknown, duplicate, null, non-string, missing, malformed, or unsafe values produce internal `invalidFocusMetadata` evidence. The item remains otherwise eligible but is focus-neutral and nonmatching; invalid metadata never reaches a comparator or presentation client. With a canonical focus, a stable partition puts valid items containing the active focus ID before nonmatching items while preserving the pre-focus order within both groups.

With an ad hoc focus, a named runtime-only resolver evaluates the valid item intents once in deterministic candidate order against the active ad hoc intent and admits at most one match. It uses the `0.85` floor and requires the best candidate to lead the runner-up by at least `0.05`; zero candidates produce no match, and one candidate uses only the floor. Only the one confident match adds the ephemeral activation ID to the runtime match set. Producers never persist or invent ephemeral IDs. Missing or invalid metadata, an unavailable comparator, or no qualifying candidate is nonmatching. Balanced ignores focus metadata. Every eligible item appears exactly once.

Hidden enrichment uses canonical `focusIds` membership for canonical focus and the runtime ad hoc resolver result for ad hoc focus. Matching eligible work precedes nonmatching work with stable within-group order. No ephemeral activation ID is persisted in `focusIds`; Balanced preserves the existing scheduler order; and all eligible work remains included. Focus never weakens spoiler projection, evidence standards, required-tool or loadout rules, or the critical path / meaningful side content / busywork classification.

Landing and situation briefs remain focus-independent so reorientation after time away never hides critical-path state. Focus never hides otherwise eligible content.

Session-phase-aware learning remains part of the adaptive interest profile in [Adaptive guidance knowledge](adaptive-guidance-knowledge.md). Session focus supplies explicit source and intent metadata but does not implement learned-interest recall.

## Adaptive vocabulary lifecycle

`storeGeneration` is exactly `{ incarnationId, sequence }`, where `incarnationId` is a required opaque token and `sequence` is a positive integer. First adaptive-store initialization creates a fresh incarnation ID with sequence `1`. Reads, rejections, no-ops, and failed transactions do not change it. Restart reloads the pair unchanged. Missing or malformed generation in the current schema fails closed and is never synthesized by startup. Explicit repair uses the explicit corruption precondition for absent or malformed generation, verifies that same observed corrupt state under the store lock, and atomically installs a complete store with a fresh incarnation ID and sequence `1`; if valid state has appeared, it returns stale without mutation.

Each comparison captures `storeGeneration` and every candidate entry version after expiry and pruning and carries them in its result. `storeGeneration` is the compare-result apply compare-and-swap token. Failed application makes no durable or active-state change and does not advance sequence.

## Failure behavior

After the runtime admits `InteractionContextV1`, direct command input undergoes strict structural, field, identity, and NFC validation. Unknown, duplicate, case-mismatched, missing, malformed, non-NFC, and unsupported fields in an unaccompanied direct command return `invalidCommand` before pending-reset or expiry, even when overdue, and create no invocation, fingerprint, deduplication, command keepalive, selection, revision, event, or write. A structurally valid unequal runtime, adapter, or binding triple is mutation-free `staleRequest` before all Focus processing.
