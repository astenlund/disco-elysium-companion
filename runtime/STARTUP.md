# Chat startup progress

`node runtime/src/cli.ts chat` writes UTC timestamps and elapsed time to stderr. Each line marks the start of a phase, not its completion. The time until the next line gives a rough phase duration; recovery can revisit a phase, and a failed start can stop before later phases appear. The table capitalizes each message; the runtime prints it in lower case.

|                   Message                    |                                                                     What the runtime is doing                                                                     |
|----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Building the native helper (first launch)    | Only when the image is absent or fails its pin: builds the helper from its pinned sources before chat starts. It ends with `native helper built` or `failed`.     |
| Loading configuration                        | Reads and validates the runtime and adapter settings.                                                                                                             |
| Validating the companion scope               | Starts and verifies the native helper service, then checks the companion root, Windows principal and physical paths used to select the runtime data scope.        |
| Claiming the runtime instance                | Takes the single-instance guard, proves no earlier helper or retired worker still runs, binds the helper service to the scope and prepares the bound runtime scope so another writer cannot start there. |
| Initializing runtime metadata                | Checks the prior runtime marker, admitted residue, old watcher and supervised process jobs; writes this start's marker and, for chat, may open the warm core reply worker alongside it. |
| Preparing provider tools and instructions    | Private opt-in only: builds initial instructions and an inactive tool boundary before storage reconciliation.                                                     |
| Checking guarded unbound provider startup    | Private opt-in startup reads binding and safety, then may initialize an unbound provider while storage work continues. It sends no player input or tools.         |
| Checking durable storage                     | Reconciles owned publication residue and reads or initializes the journal, safety record and required directories.                                                |
| Reconciling consumer ownership               | Resumes an unfinished handover or release. Chat stops if a completed release returned consumption to the bridge.                                                  |
| Reconciling recovery                         | Resumes interrupted repair, handover or journal work while retaining unresolved obligations.                                                                      |
| Draining pending state records               | Moves accepted core outbox records into the runtime journal and settles them as required.                                                                         |
| Acquiring current state                      | Reads the current save through the core, publishing and settling a new state event when needed. No player message is sent here.                                   |
| Checking state safety                        | Checks pending safety obligations and resumes required recovery before provider admission.                                                                        |
| Finishing storage maintenance                | Applies eligible retention and refreshes capacity and operational observations.                                                                                   |
| Starting the save watcher                    | Starts or checks the watcher that notices later saves; its status appears in the client.                                                                          |
| Preparing provider tools and instructions    | Final instruction admission before provider binding, and the tool boundary unless private opt-in startup already built it. Private opt-in startup rereads and compares the initial source bytes. |
| Checking provider safety and session binding | Checks current safety and the stored session binding before deciding whether to resume or start fresh.                                                            |
| Starting the provider session                | Starts or resumes the provider process and waits for its initialization. No player message is sent here.                                                          |
| Binding the provider session durably         | Writes and verifies the current session binding before the provider can serve the client.                                                                         |
| Switching to a fresh provider session        | After a failed resume, closes that attempt and immediately tries a fresh session.                                                                                 |
| Waiting to retry provider startup            | Waits before another provider start attempt after a fresh start fails.                                                                                            |
| Checking final attachment safety             | Runs full provider safety while the warm core reply worker is still open. If the provider exited, waits for its reconnect, which can retry a resume after pauses of 1, 5 and 30 seconds, and repeats the check up to three times in all. Attachment later rechecks the bound session, guard, provider job, worker jobs and the helper service. |
| Closing startup workers                      | Drains, stops and verifies the warm core reply worker before attachment, refusal, or failed-start cleanup continues.                                              |

`still working` means the current phase has been quiet for at least 15 seconds while the event loop could report progress. It is not a percentage or a deadline. `chat client ready` means the text client attached; a start can instead end with `stopped: runtime is not the consumer`, `stopped: provider unavailable` or `failed`. A status-only client can also attach after some authority failures or a failed provider reconnect, so read the following consumer, state, journal, safety and provider status before treating the session as usable. The current performance target counts only a healthy attached session.

When the native helper cannot be built, started or bound, the command exits with a `nativeHelperUnavailable (<reason>)` line whose message names the remedy. `chat`, `consumer` and `repair` build a missing image first; `status` never builds and refuses instead.
